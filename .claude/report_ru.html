Как вы используете Claude Code

Вы работаете в стиле пакетной делегации: часто указываете Claude на файл PROMPT.md с набором задач и просите выполнить всё от начала до конца. Вместо управления отдельными шагами вы объединяете работу — «исправь баги, добавь тесты, добейся прохождения всех тестов, затем проанализируй архитектуру enum Extend» — и позволяете Claude работать автономно по сотням вызовов инструментов (352 Bash, 323 Read на 43 сообщения). Высокое соотношение инструментов к сообщениям показывает, что вы доверяете Claude длинные автономные циклы, не прерывая их. Вы работаете над серьёзным Rust-проектом (393 Rust-файла) с LSP/Zed-интеграцией и доверяете Claude многофайловые рефакторинги, работу с кодогенерацией и архитектурный анализ.

Ваш стиль взаимодействия ориентирован на результат и терпим к итерационному трению. Когда тесты падают из-за неверных assertions, ошибок lifetime или кросс-платформенных проблем путей, вы позволяете Claude проходить несколько раундов отладки самостоятельно. У вас также заметен паттерн локализации и полировки документации — перевод комментариев в кириллицу, добавление русской документации, локализация HTML-отчётов — что говорит о том, что вы воспринимаете Claude как компетентного многоязычного коллаборатора. 6 из 11 сессий нацелены на исправление багов, и 9 случаев трения «buggy_code» подтверждают комфортность модели работы «сгенерировать — исправить».

Самая заметная болевая точка — лимиты API: две сессии не сделали ровно ничего, а ещё одна частично завершилась неудачей в середине задачи. Несмотря на это, уровень удовлетворённости высокий (17 «вероятно доволен», 9/11 сессий выполнены полностью или в основном).

Ключевой паттерн: Вы делегируете пакеты задач из PROMPT.md-файлов и даёте Claude работать в длинных автономных циклах с минимальными прерываниями, принимая итеративные циклы исправления багов как часть рабочего процесса.

Где всё ломается

В ваших сессиях прослеживается повторяющееся трение: лимиты API, итеративное исправление тестов и неполные начальные реализации, требующие нескольких раундов отладки.

Срабатывание лимита API
Вы часто сталкиваетесь с лимитами API в середине задачи или прямо в начале сессии, оставляя работу незавершённой. Рассмотрите разбивку списков задач PROMPT.md на меньшие пакеты и проверку бюджета использования перед запуском длинных сессий.
  • Две полные сессии не сделали ровно ничего: лимиты срабатывали сразу при старте
  • Выполнение многопунктового PROMPT.md исчерпало лимит API в середине исправления бага, оставив ошибку hover в LSP нерешённой
Неверные assertions в тестах с первой попытки
Новые тесты часто содержали неверные assertions или неразрешённые зависимости, требуя нескольких раундов исправлений. Просьба к Claude верифицировать ожидаемые значения по реальному выводу перед написанием assertions сократила бы эти циклы.
  • Новые тесты содержали неверное имя модели и неверный адрес, потребовав двух раундов исправлений
  • Начальные тесты падали, потому что условия переходов не разрешались конвейером — потребовалось полное переписывание тестов
Неполные исправления, вызывающие регрессии
Первые попытки исправлений часто ломали соседний функционал или пропускали шаги конфигурации. Просьба к Claude перечислить все затронутые места вызова и запустить полный тест-сьют перед объявлением исправления завершённым выявила бы проблемы раньше.
  • Начальное исправление разрешения переменных сломало вложенный доступ к модели в функциях tick/init, потребовав контекстно-зависимого второго исправления
  • Настройка расширения Zed пропустила language-биндинг в extension.toml, и LSP всё равно не распознавался после первой попытки

Кастомные скиллы (Custom Skills)
Переиспользуемые промпты, запускаемые командами /.
Зачем вам: Вы раз за разом повторяете один воркфлоу: «выполни задачи PROMPT.md → исправь баги → добавь тесты → обнови README → сгенерируй патч». Скилл /prompt-tasks стандартизирует это и гарантирует запуск тестов между шагами.
mkdir -p .claude/skills/prompt-tasks && cat > .claude/skills/prompt-tasks/SKILL.md <<'EOF' # Выполнение задач PROMPT.md 1. Прочитай PROMPT.md и перечисли все задачи 2. Для каждой задачи по порядку: a. Реализуй изменение b. Запусти `cargo test` и исправь сбои c. Обнови документацию (README.md) 3. После всех задач: `git diff > changes.patch` 4. Отчитайся по каждой задаче EOF
Хуки (Hooks)
Автоматический запуск shell-команд при событиях жизненного цикла Claude.
Зачем вам: 9 случаев трения «buggy_code» и повторяющиеся циклы отладки. Хук PostToolUse с `cargo check` после правок ловил бы ошибки компиляции/borrow немедленно, а не в конце работы.
// .claude/settings.json { "hooks": { "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{"type": "command", "command": "cargo check --quiet 2>&1 | tail -20"}] }] } }

Запуск сфокусированных субагентов для параллельного исследования.

Спросите: «Используй параллельных агентов для анализа: (1) как работает разрешение переменных в парсере, (2) как оно используется в кодогенерации tick/init, (3) тестовое покрытие вложенного доступа к модели. Затем предложи единое исправление.»

Новые способы использования Claude Code

Скопируйте в Claude Code, и он проведёт вас через это.

Верифицировать перед написанием assertions
Claude иногда угадывает ожидаемые значения (имена моделей, адреса), что ведёт к нескольким раундам исправлений.
В ваших сессиях новые тесты падали из-за неверных assertions об именах моделей и адресах, требуя 2+ раундов. Перед написанием assertion Claude должен запустить небольшой зонд (println, dbg!, или cargo run-сниппет), чтобы захватить реальное значение. Это превращает метод проб и ошибок в однопроходное написание теста.
Вставьте в Claude Code:
При написании новых тестов сначала запускай небольшой зонд для захвата реальных выходных значений, затем пиши assertions против этих захваченных значений. Не угадывай ожидаемые строки/адреса.
Предварительная проверка перед длинными списками задач
Запускайте полный тест-сьют перед началом многозадачной PROMPT.md-сессии, чтобы выявить предсуществующие сбои.
Одна сессия потеряла оставшийся контекст на отладку предсуществующего сбоя теста hover_model, всплывшего в середине пути. Предварительный cargo test выявил бы его до начала выполнения, позволив вам решить — исправить или отложить. Это особенно важно при многократном столкновении с лимитами.
Вставьте в Claude Code:
Перед началом работы с PROMPT.md запусти `cargo test` и сообщи о предсуществующих сбоях. Мы решим — исправить их сначала или отложить — до начала выполнения списка задач.
Управление риском лимитов через контрольные точки
2 из 11 сессий не сделали ничего из-за немедленного срабатывания лимитов; другие исчерпали ресурс в середине задачи.
Почти 20% ваших сессий потеряны из-за лимитов. Попросите Claude сохранять прогресс в STATUS.md после каждой задачи и читать его в начале сессий. Так возобновление сможет продолжиться с того места, где остановилось, без повторного исследования.
Вставьте в Claude Code:
После завершения каждой задачи из PROMPT.md добавляй однострочную запись в STATUS.md (название задачи, изменённые файлы, тесты проходят). В начале сессии сначала читай STATUS.md, чтобы возобновить с последней контрольной точки.

На горизонте

Ваш Rust-воркфлоу с пакетной обработкой PROMPT.md показывает, что вы уже оркестрируете Claude как автономного исполнителя — следующий шаг: распараллеливание агентов и замыкание циклов обратной связи с тестами и CI.

Рои параллельных агентов для задач PROMPT.md
Вместо последовательного выполнения задач PROMPT.md с риском срабатывания лимитов — распределяйте независимые задачи параллельным субагентам, каждый из которых владеет своей feature-веткой, запускает свой тест-сьют и возвращает патчи. Агент-координатор объединяет результаты и эскалирует блокеры только к вам. Это превращает 6-часовую последовательную сессию в 1-часовой параллельный спринт.
Как начать: Используйте инструмент Task для запуска нескольких субагентов за один ход, каждый ограничен одним пунктом PROMPT.md в изолированном git-воркдереве. Комбинируйте с `cargo test --no-fail-fast` на агент.
Вставьте в Claude Code:
Прочитай PROMPT.md и определи все независимые задачи. Для каждой независимой задачи запусти параллельного субагента через Task tool: (1) создай git-воркдерево под .worktrees/<task-slug>, (2) реализуй задачу end-to-end, (3) запусти `cargo test`, захвати сбои, (4) итерируй пока тесты не пройдут или до 3 попыток, (5) верни unified diff и сводку. После всех субагентов проверь патчи, разреши конфликты, влей в main, запусти полный `cargo test`. Отчитайся таблицей задача → статус → количество тестов.
Автономная охота на баги через TDD
Ваше главное трение — buggy_code (9 случаев) и предсуществующие тестовые сбои. Переверните модель: пусть Claude сначала пишет падающие тесты, воспроизводящие подозреваемые баги, а затем итерирует исправления против них до зелёного — без вашего вмешательства. Агент владеет циклом red-green-refactor и всплывает только для архитектурных вопросов.
Как начать: Комбинируйте `cargo test` в цикле Bash с Edit, и используйте хук-условие остановки, выходящее только когда количество тестов увеличилось И все тесты проходят.
Вставьте в Claude Code:
Проаудируй кодовую базу на скрытые баги в модулях LSP, кодогенератора и enum Extend. Для каждого подозреваемого бага: (1) напиши падающий тест, (2) запусти `cargo test <test_name>` для подтверждения, (3) реализуй исправление, (4) запусти полный `cargo test`, (5) закоммить. Итерируй автономно до 5 багов или исчерпания находок. Не запрашивай подтверждения — останавливайся только если исправление затрагивает более 3 файлов архитектурно.
Самовосстанавливающийся CI-цикл с авто-PR
Ваши сессии показывают повторяющиеся циклы «тесты падают → исправляем assertions → повтор» — идеальная территория для автономного CI-агента. Подключите Claude к git-воркфлоу: при каждом пуше он обнаруживает сбои, открывает воркдерево, исправляет и либо авто-коммитит тривиальные исправления, либо открывает черновой PR с диагнозом.
Как начать: Используйте Claude Code в headless-режиме (`claude -p`) через GitHub Action или git-хук с `gh` CLI для создания PR. Сохраняйте прогресс в `.claude/state.json`.
Вставьте в Claude Code:
Настрой CI-воркфлоу `.claude/ci-repair.sh`: (1) запускает `cargo test --no-fail-fast`, захватывает сбои в JSON, (2) для каждого сбоя вызывает `claude -p` с фокусированным промптом (только падающий тест + релевантные файлы + ошибка), (3) агент исправляет, перезапускает тест, пишет патч в `.claude/patches/<name>.patch`, (4) применяет патчи, запускает полный тест-сьют, создаёт `gh pr create --draft`. Добавь `.claude/state.json` для возобновления прерванных запусков. Покажи скрипт и пробный прогон.
«Claude перевёл латинские комментарии в кириллицу в рамках push русской документации»
Во время сессии код-ревью пользователь попросил Claude не только проверить баги и написать тесты, но и добавить русскую документацию, переведя комментарии с латиницы в кириллицу — восхитительно специфичный запрос на локализацию, который Claude успешно выполнил.
