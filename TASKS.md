### 1. `cond` — отсутствует обязательный `;`

**Проблема.** Объявление `ConditionDefine` в грамматике не включает завершающий `";"`:

```lalrpop
ConditionDefine: ConditionDefine = {
    "cond" <name> "=" <c:Condition> => ...   // нет ";"
}
```

Символ `;` после `cond` парсится как отдельный `ModelElement::StraySemicolon` и
молча игнорируется. Все остальные объявления уровня модели (`var`, `const`, `type`,
`fn`, `in`, `out`) требуют `;` явно.

**Рекомендация.** Добавить `";"` в правило `ConditionDefine`:

```lalrpop
ConditionDefine: ConditionDefine = {
    "cond" <name> "=" <c:Condition> ";" => ...
}
```

### 3. Индекс массива принимает только литерал

**Проблема.** В грамматике `ArraySubscript` принимает только `number` (целочисленный
литерал), не переменную:

```lalrpop
<i:Identifier> "[" <n:number> "]"  // только литерал
```

Конструкция `arr[i]` (переменная как индекс) **не поддерживается** ни в выражениях,
ни в условиях. Это резко ограничивает применимость массивов.

**Рекомендация.** Заменить `<n:number>` на `<n:Expression>` (или отдельное
подмножество, исключающее присваивание), добавить семантический проход для разрешения
типа индекса.

## Ограничения системы типов

### 4. Нет встроенных целочисленных типов

Единственный примитивный тип — `bit`. Пользователь вынужден писать:

```lam
type u8  = [bit;8];
type u16 = [bit;16];
type i8  = [bit;8];   // неотличимо от u8 семантически
```

**Рекомендация.** Добавить встроенные типы `u8`, `u16`, `u32`, `u64`, `i8`, `i16`,
`i32`, `i64` в лексер и семантику. Сохранить `[bit;N]` как низкоуровневый псевдоним.

---

### 5. Нет знакового/беззнакового разграничения

Тип `[bit;8]` одновременно используется и как знаковое, и как беззнаковое число.
Деление и сравнение в C ведут себя по-разному для `int8_t` и `uint8_t`.

**Рекомендация.** Ввести ключевые слова `signed`/`unsigned` для массивов или явные
встроенные типы (см. п.4).

---

### 6. `struct` — частичная поддержка

`struct` объявляется в грамматике, но:

- в C-генераторе не видно генерации структур-typedef
- в семантическом индексе нет `SemanticNodeKind::Struct`
- в LSP hover нет ветки для `struct`

**Рекомендация.** Завершить реализацию: семантический проход, C-генерация `typedef
struct { ... } Name;`, поддержка в LSP.

---

### 8. Нет `while` (читаемый вариант `loop`)

`loop cond { body }` — нестандартный синтаксис. Большинство разработчиков привыкли
к `while (cond) { body }`.

**Рекомендация.** Добавить `while` как синоним `loop`: `while <expr> <block>`. Можно
разделить `loop` (бесконечный цикл) и `while` (цикл с условием).

---

### 10. Нет `match`/`switch`

Для работы с `enum` и числовыми состояниями требуется разветвлённый `if-else if`,
тогда как `match` был бы более выразительным и безопасным (полнота покрытия).

**Рекомендация.** Ввести `match expr { pattern => block, ... }` с проверкой полноты
вариантов для `enum`-типов.

---

## Система портов

### 11. Адрес порта жёстко встроен в объявление

```lam
in sensor: u8 = 0x200:0;   // адрес аппаратного регистра
```

Аппаратный адрес не должен быть частью языкового объявления — это деталь
конфигурации платформы.

**Рекомендация.** Разделить объявление порта и его привязку к адресу:

```lam
in sensor: u8;                    // объявление без адреса
#[address = 0x200:0] sensor;      // атрибут или отдельный раздел platform map
```

---

### 12. Нет двунаправленного (`inout`) порта

Только `in` и `out`. Для шин с тремя состояниями или двунаправленных линий нет
нативного типа.

**Рекомендация.** Добавить `inout <name>: <type>` с семантикой чтения и записи.

---

## Система импорта

### 13. `from` — контекстный идентификатор, не ключевое слово

```lam
import { A, B } from "file.lam";   // 'from' проверяется в run-time
import * as M from "file.lam";
```

`from` не зарезервировано — при опечатке парсер принимает неверный идентификатор и
генерирует ошибку только в семантике.

**Рекомендация.** Добавить `"from"` в список токенов лексера как зарезервированное
слово.

---

## Именованные блоки

### 14. Любой идентификатор — корректное имя именованного блока

```lam
start S {
    enteer { ... }   // опечатка: нет ошибки, парсируется как валидный блок
    alwways { ... }  // опечатка: то же самое
}
```

Только `enter`, `exit`, `always` имеют семантику. Остальные молча игнорируются.

**Рекомендация.** Либо ограничить допустимые имена именованных блоков ключевыми
словами (`enter`, `exit`, `always`), либо генерировать предупреждение при
неизвестном имени блока.

---

## Условный подъязык

### 15. Дублирование грамматики Condition/Expression

Язык содержит два независимых выражения-грамматики: `Condition` (для условий
переходов и `cond`) и `Expression` (для блоков кода). Каждый изменён отдельно, что
затрудняет поддержку.

Например, `LoopCond` — третий вариант той же грамматики (без `{` для разрешения
LR-конфликта). Итого 3 похожие грамматики выражений.

**Рекомендация.** Рассмотреть унификацию в один `Expression` с разной семантической
валидацией (например, запрет присваивания в позиции `cond`).

## Диагностика

### 16. `StraySemicolon` не генерирует предупреждение

Стражный `;` (лишняя точка с запятой) принимается молча как `ModelElement`. Это
маскирует опечатки вроде `;;`.

**Рекомендация.** Генерировать предупреждение `SE-0XX: лишняя точка с запятой`.

---

### 17. Нет диагностики недостижимых состояний

Если состояние не является стартовым и ни одно другое состояние не ссылается на него
через `ref` или `next`, оно недостижимо.

**Рекомендация.** Добавить проход валидации `check_unreachable_states` с
предупреждением.

---

### 18. Нет диагностики условий, которые никогда не выполнятся

Например, `ref S: x = 5 & x = 6;` — тавтологически ложно. Простая статическая
проверка может обнаружить очевидные константно-ложные условия.

**Рекомендация.** Добавить базовый анализ константных условий (constant folding) при
семантическом проходе.
