# Тестбенчи цели SystemVerilog

Тестбенчи для порождённых `lamc -t sv` модулей из `examples/generated/sv/`.
Написаны **руками**: тестбенч — принадлежность проверки, а не продукта, поэтому
`lamc` его не порождает (решение открытого вопроса задачи 0045-07).

| Тестбенч | Модуль под тестом | Сценарий |
|---|---|---|
| `stacker_tb.sv` | `../stacker.sv` | Заявка на забор груза; замкнутая среда ведёт автомат через весь цикл (забор → ячейка → завершение). Проверяет `cmd_ack`, `cmd_fork`, `cmd_done`. |
| `elevator_mini_tb.sv` | `../elevator_mini.sv` | Нажата кнопка кабины «этаж 5»; «физика лифта» довозит кабину. Проверяет `ElevatorMotor_Up`, `DoorOpen`, приезд на этаж. |

Каждый тестбенч делает две вещи:

1. **Проверяет функционирование** — прогоняет модуль на осмысленном сценарии и
   сверяет наблюдаемое поведение `assert`-ами. Провал → `$fatal` → ненулевой код
   выхода → красный предкоммит.
2. **Снимает осциллограмму** `<module>.vcd` (`$dumpvars`) для просмотра в
   [GTKWave](https://gtkwave.sourceforge.net/).

> Потактовую *эквивалентность* RTL и симулятора Lam проверяет отдельная сверка
> (`simulation/tests/conformance_sv_tests.rs`) — она строже: сравнивает значение
> на каждом такте. Тестбенчи здесь проверяют «событие когда-нибудь произошло»
> (устойчиво к сдвигу такта) и служат прежде всего источником осциллограмм.

## Прогон вручную

Из каталога `examples/generated/sv/`:

```sh
verilator --binary --timing --trace --top-module tb \
    tb/stacker_tb.sv stacker.sv -o simtb
(cd tb && ../obj_dir/simtb)     # пишет tb/stacker.vcd
gtkwave tb/stacker.vcd
```

## Автоматический прогон

`scripts/precheck.sh` (гейт тестбенчей цели sv) собирает и запускает оба
тестбенча Verilator-ом; провал `assert` валит предкоммит. При отсутствии
`verilator` шаг мягко пропускается локально и обязателен в CI
(`SV_GATE_REQUIRED=1`) — как и соседние гейты линта/синтеза.

Осциллограммы (`*.vcd`), каталог сборки (`obj_dir/`) и бинарь (`simtb`) — под
`.gitignore`: это артефакты прогона, а не исходники.
