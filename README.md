# Lam — Язык описания автоматных моделей

**Lam** (Language of Automata Models) — предметно-ориентированный язык (DSL) для моделирования
конечных автоматов (FSM) и компонентных систем. Компилятор реализован на Rust.

## 1. Введение

### Целевая аудитория

Этот документ предназначен для:

- **Разработчиков встраиваемых систем**, которые проектируют управляющую логику на основе
  конечных автоматов и нуждаются в формальном и читаемом способе её описания.
- **Исследователей и инженеров** в области верификации, желающих описывать поведение систем
  на высоком уровне абстракции.
- **Опытных разработчиков** (C/C++/Rust), знакомых с понятиями FSM, которые хотят изучить
  синтаксис и семантику Lam.

### Соглашения по нотации

| Обозначение      | Смысл                              |
|------------------|------------------------------------|
| `ключевое_слово` | Литерал: пишется дословно          |
| `идентификатор`  | Любое имя, выбранное пользователем |
| `[ ... ]`        | Необязательный элемент             |
| `{ ... }`        | Повторение (0 и более раз)         |
| `a \| b`         | Альтернатива                       |

Полная грамматика в формате ISO EBNF — в файле [`Lam.ebnf`](Lam.ebnf).

### Привет, мир!

Минимальная программа — модель со стартовым состоянием:

```lam
model Hello {
    start World;
}

start Main = Hello;
```

Запустить компилятор:

```sh
cargo build --release --bin lamc
./target/release/lamc compile --target c hello.lam -o out/
```

В `out/` появятся `hello.h` и `hello.c`.

## 2. Назначение DSL

### Проблема

Традиционный подход — писать конечные автоматы вручную на C — приводит к рутинному коду,
который сложно верифицировать и сопровождать. Типичная реализация FSM на C требует:
`switch-case` по состояниям, ручного управления флагами входа/выхода, указателей MMIO вместо
типизированных портов.

### Решение

Lam предлагает:

- **Декларативный синтаксис** для FSM вместо `switch-case` на C.
- **Компиляцию в C**: сгенерированный код оптимален и пригоден для встраиваемых систем.
- **Формальную семантику**: типизация, детерминированность переходов, диагностика.
- **Никакого рантайма**: ни сборщика мусора, ни кучи — только стек и порты.

### Парадигма

Lam — **декларативный, ориентированный на состояния** язык:

- **Модели** (`model`) — основные строительные блоки; каждая модель — один FSM.
- **Состояния** (`start`, `state`) — узлы автомата; логика выполняется в их блоках.
- **Переходы** (`ref`, `next`) — рёбра автомата с условиями или безусловные.
- **Параллельная и последовательная композиция** (`|`, `+`) — сборка систем из компонентов.

### «Дзен» языка

| Принцип            | Смысл                                                   |
|--------------------|---------------------------------------------------------|
| **Явность**        | Переходы описаны явно — нет скрытой передачи управления |
| **Локальность**    | Каждая модель инкапсулирует состояния и данные          |
| **Минимализм**     | Язык содержит только необходимые конструкции            |
| **Встраиваемость** | Нет GC, рантайма или кучи — только стек и порты         |

### Сравнение с C

| Концепция          | C (switch-case)        | Lam                      |
|--------------------|------------------------|--------------------------|
| Состояние          | `enum` + переменная    | `state`/`start`          |
| Переход            | `case` с `goto`        | `ref Цель: условие;`     |
| Вход в состояние   | ручная флаг-переменная | `enter { ... }`          |
| Параллелизм        | потоки / ручная логика | `M1 \| M2`               |
| Последовательность | вложенный switch       | `M1 + M2`                |
| Порты              | указатели MMIO         | `in`/`out` внутри модели |
| Типизация          | слабая                 | строгая статическая      |

## 3. Термины и сущности домена

### Глоссарий

| Термин                  | Определение                                                         |
|-------------------------|---------------------------------------------------------------------|
| FSM                     | Конечный автомат (Finite State Machine)                             |
| Модель                  | Объявление конечного автомата (`model M { ... }`)                   |
| Состояние               | Узел автомата (`start` или `state`)                                 |
| Переход                 | Смена активного состояния (`ref` или `next`)                        |
| Условие                 | Булево выражение для `ref`-перехода                                 |
| `cond`                  | Именованное условие — псевдоним для переиспользования               |
| Порт                    | Переменная, отображённая на аппаратный адрес или интерфейс модели   |
| Композиция              | Объединение моделей: последовательная (`+`) или параллельная (`\|`) |
| `enter`/`exit`/`always` | Именованные блоки кода с семантикой жизненного цикла                |
| `next`                  | Безусловный переход в следующее состояние                           |
| DSL                     | Domain-Specific Language — предметно-ориентированный язык           |

### Структура программы

Программа Lam — это последовательность **элементов верхнего уровня**:

| Конструкция          | Описание                                     |
|----------------------|----------------------------------------------|
| `import "file.lam";` | Импорт другого файла                         |
| `type T = ...;`      | Псевдоним типа                               |
| `var x: T := v;`     | Глобальная переменная                        |
| `const C: T := v;`   | Константа                                    |
| `fn f(...) {...}`    | Функция                                      |
| `extern fn f(...);`  | Прототип внешней функции                     |
| `enum E {...}`       | Перечисление                                 |
| `struct S {...}`     | Структура                                    |
| `model M {...}`      | Конечный автомат                             |
| `cond C = ...;`      | Именованное условие                          |
| `start Main = ...;`  | Точка входа (составная модель или псевдоним) |

### Система типов

Lam использует **статическую строгую типизацию** с **выводом типов** из инициализаторов.

| Тип     | Размер     | Описание                                    |
|---------|------------|---------------------------------------------|
| `bit`   | 1 бит      | Одиночный бит                               |
| `bool`  | 1 бит      | Булев тип                                   |
| `float` | переменный | Число с плавающей точкой                    |
| `unit`  | 0          | Пустой тип (возвращаемое значение процедур) |

Массив фиксированной длины: `[ТипЭлемента; Длина]`:

```lam
type u8  = [bit;8];
type u16 = [bit;16];
type u32 = [bit;32];
type u64 = [bit;64];
type Word = [u8;4];
```

Вывод типов из инициализатора:

| Инициализатор     | Выводимый тип |
|-------------------|---------------|
| `0` … `255`       | `[bit;8]`     |
| `256` … `65535`   | `[bit;16]`    |
| `65536` … `2³²−1` | `[bit;32]`    |
| `2³²` … `2⁶⁴−1`   | `[bit;64]`    |
| `true` / `false`  | `bool`        |
| `3.14`, `1e10`    | `float`       |

### Объявление переменных

```lam
var x;               // без типа и значения
var x: u8;           // с явным типом
var x := 100;        // тип выводится
var x: u8 := 50;     // явный тип и значение
const MAX: u8 := 255; // константа
```

### Функции

```lam
fn add(a: u8, b: u8) -> u8 { return a + b; }

fn reset();                    // прототип без тела

extern fn hal_uart_send(data: u8);   // внешняя функция
```

**Композиция функций** (фича 0031). Тело функции видит **другие функции своей
модели** (и родительских), независимо от порядка объявления — `f` может вызывать
`g`, объявленную ниже:

```lam
fn f(x: u8) -> u8 { return g(x) + 10; }   // g объявлена ниже — это допустимо
fn g(x: u8) -> u8 { return x + 1; }
```

**Рекурсия запрещена** — осознанное свойство языка синтеза управляющих автоматов:
встраиваемая цель требует ограниченного стека и вычислимого WCET, а отраслевые
стандарты её прямо запрещают (MISRA C:2012 Rule 17.2, IEC 61131-3). Цикл в графе
вызовов — прямой (`f → f`) или взаимный (`f → g → f`, любой длины) — отвергается
диагностикой **`SE-053`** с указанием цепочки вызовов:

```lam
fn f(x: u8) -> u8 { return f(x); }   // SE-053: Рекурсия функций запрещена: f → f
```

Рекурсивные алгоритмы (обход деревьев и т. п.) выражаются **циклами** `while`/
`loop`, которые в языке есть.

> **Контрпример (что отвергается).** Дубликат имени функции в одной модели —
> ошибка `SE-009` (прежде принимался молча, побеждала последняя): смысл программы
> обязан быть определён.

### Импорт

```lam
import "shared.lam";
import "engine.lam" as Motor;
import * as Utils from "lib.lam";
import { TrafficLight, u8 } from "common.lam";
import { OldName as NewName } from "types.lam";
```

### Краткая грамматика EBNF

```ebnf
source_unit   = { model_element } ;

model_element = import_define | type_define | variable_define
              | function_define | enum_define | struct_define
              | model | state_define | condition_define
              | named_block | ";" ;

variable_define
    = "var"   identifier [ ":" type ] [ ":=" expression ] ";"
    | "const" identifier [ ":" type ] ":=" expression ";"
    | "in"    identifier [ ":" type ] [ ":=" expression ] ";"
    | "out"   identifier [ ":" type ] [ ":=" expression ] ";" ;

model        = "model" identifier [ "=" expression ]
               "{" { model_element } "}" ;

state_define = state_kind identifier [ "=" expression ]
               ( "{" { state_element } "}" | ";" ) ;
state_kind   = "start" | "state" ;

state_element
    = named_block
    | "ref"  identifier [ ":" condition ] ";"
    | "next" identifier ";"
    | ";" ;
```

## 5. Семантика

### Присваивание `:=` и сравнение `=`

В Lam присваивание и сравнение разведены по разным знакам (стиль ST/IEC 61131-3,
привычный инженерам АСУ ТП):

| Знак  | Смысл                                   | Где                                        |
|-------|-----------------------------------------|--------------------------------------------|
| `:=`  | Присваивание / инициализация значения   | выражения, тела, инициализаторы `var`/`const`/портов |
| `=`   | Сравнение на равенство                  | выражения **и** условия (`cond`, `ref`)    |
| `<=`  | «Меньше или равно» (реляционный)        | выражения и условия                        |

Оператор `==` из языка **выведен** — равенство всегда пишется `=`. Знак `=`
дополнительно служит связкой в **определениях имён**: `type T = …`,
`enum E { A = 0 }`, `model M = …`, `start Main = …`, `cond C = …` — здесь `=`
вводит определение, а не присваивает значение переменной.

```lam
always { x := 0; }      // := — присваивание значения
if x = 0 { ... }        // = в выражении — сравнение на равенство
cond IsZero = x = 0;    // первое = — связка cond, второе = — сравнение
ref Green: timer = 255; // = в условии перехода — сравнение
var y: u8 := 5;         // := — инициализация переменной
```

### Управляющие конструкции

```lam
// if — без скобок вокруг условия
if x > 0 { x := x - 1; }
else if x = 0 { x := 10; }
else { x := 0; }

// loop — бесконечный или с условием
loop { x := x + 1; if x >= 10 { break; } }
loop x > 0 { x := x - 1; }

// for
for var i := 0; i < 10; i := i + 1 {
    // тело
}
```

> Условие `loop` не может начинаться с `{`. Используйте скобки: `loop ({1,2,3}) { }`.

### Жизненный цикл автомата

Каждое состояние может содержать именованные блоки:

| Блок     | Когда выполняется                          |
|----------|--------------------------------------------|
| `enter`  | Один раз при входе в состояние             |
| `exit`   | Один раз при выходе из состояния           |
| `always` | Каждый такт, пока автомат в этом состоянии |

Порядок выполнения за один такт:

1. **Инициализация**: устанавливается начальное `start`-состояние.
2. **Вход**: выполняются блоки `enter`.
3. **Такт**: выполняются блоки `always`.
4. **Проверка переходов**: вычисляются условия `ref`; при истинности — переход.
5. **Выход**: выполняются блоки `exit` текущего состояния.
6. **Переход**: активируется следующее состояние → шаг 2.

#### Семантика первого такта (моментность)

Такт — это один **цикл сканирования** (scan cycle) промышленного контроллера. На
**такте 1** модель **уже находится** в стартовом состоянии: вход в состояние
(шаги 1–2) **не расходует отдельного такта**, поэтому блоки `enter`, затем
`always`, затем проверка переходов стартового состояния отрабатывают **в том же
первом такте**. Это верно на **любом** уровне иерархии.

Ключевое следствие — **моментность не зависит от глубины вложенности**: чисто
структурное обёртывание модели (`model Mid { start S = Inner; }`) **не сдвигает**
потактовую трассу. Потактовые свойства модели (время до первого воздействия на
выход, проверки `--sim-file`, LTL-верификация) поэтому **композируемы**.

> **Единый эталон моментности — модель**, и симулятор, и порождённый C исполняют
> тело стартового состояния на такте 1 (фича 0033, версия языка 0.3.0). Прежде
> генератор C тратил по такту на каждый уровень иерархии на служебные
> `INIT`-переходы — это была бухгалтерия бэкенда, а не семантика языка; поведение
> **изменено** (ломающее для потактовой трассы, см. `CHANGES.md`).

**Пример (потактовая трасса совпадает у симулятора и порождённого C).** Модель
глубины 2, переменная `n` меняется по мере переходов:

```lam
model Counter {
    var n: u8 := 0;
    start S0 { always { n := 1; } ref S1; }
    state S1 { always { n := 2; } ref S2; }
    state S2 { always { n := 3; } }
}
start Entry = Counter;
```

| Такт | Симулятор `n` | Порождённый C `n` |
|------|---------------|-------------------|
| 1    | 1             | 1                 |
| 2    | 2             | 2                 |
| 3    | 3 (терминал)  | 3 (терминал)      |

**Контрпример (что было до 0033).** Тот же вход давал в C `n = 0, 0, …, 1, 2, 3` —
тело исполнялось лишь с `depth`-го такта, а трасса симулятора была `1, 2, 3` с
такта 1. Сдвиг рос с глубиной вложенности; теперь он нулевой.

### Переходы

```lam
ref NextState: условие;   // условный переход
next NextState;           // безусловный переход
```

Операторы в условии `ref`:

- `=` — проверка равенства; `&` — И; `|` — ИЛИ; `!` — НЕ
- Сравнения: `<`, `>`, `<=`, `>=`, `!=`

### Именованные условия

```lam
cond IsActive  = x = 1;
cond InRange   = x > 0 & x < 100;
cond Either    = IsActive | InRange;
cond NotActive = !IsActive;
```

### Инварианты и assert

Язык различает **определение условия** (`cond`) и **обязательство** — условие,
которое обязано быть истинным.

**`assert` языка Lam** — форма `: условие;` (краткая) и `: [Guard] условие;`
(явная). Проверяется в точке записи: симулятор останавливает прогон при
нарушении (`SIM-025`), а порождённый C эмитит `assert(...)` (флаг
`--guard-disable` убирает проверки из прошивки). Допустима как элемент модели, как
элемент состояния и как оператор в блоке кода:

```lam
always { x := step(x); : x <= 100; }   // assert после присваивания
```

**`invariant Имя = <Условие>;`** (фича 0044) — **именованное** обязательство,
проверяемое автоматически: на уровне модели — каждый такт, на уровне состояния —
пока автомат в этом состоянии.

```lam
var temp: u8 := 0;
invariant Safe = temp <= 100;   // на уровне модели: держится всегда
: [LTL] G(Safe);                // имя инварианта — атом LTL
```

Инвариант — сахар над `cond Имя = C;` + `: [Guard] Имя;`: имя становится **атомом
LTL** (`G(Safe)` — реляционное свойство, прежде невыразимое) и переиспользуемым
условием (`ref Next: Safe;`). Нарушение инварианта в симуляторе даёт
`SIM-025` **с именем** («нарушен инвариант 'Safe'»).

**Рекурсия невозможна, ассерты дороги — почему без имени нельзя?** Диагностика
«нарушено условие в строке 42» нечитаема; имя же указывает **что именно** нарушено
и делает обязательство переиспользуемым и проверяемым LTL-верификатором.

> **Контрпример.** Имя инварианта, совпадающее с уже объявленным `cond` или
> переменной, — ошибка `SE-054` (не молчаливая перезапись): смысл программы
> обязан быть определён. Слово `assert` ключевым **не** является — `var assert:
> u8;` остаётся валидным.

### Области видимости

- Переменные модели видны во всех вложенных состояниях.
- Переменные состояния видны только в нём.
- Разрешение: локальная область → состояние → модель → глобальный уровень.
- Затенение: локальное объявление скрывает одноимённое родительское.

### Минимальный конечный автомат

```lam
type u8 = [bit;8];

model TrafficLight {

    }

        always { timer := timer + 1; }
        ref Yellow: timer = 100;
    }

    state Yellow {
        enter  { timer := 0; }
        always { timer := timer + 1; }
        ref Red: timer = 50;
    }
}

start Entry = TrafficLight;
```

### Кнопка и светодиод (направленные порты, внешние функции)

```lam
type u8 = [bit;8];

extern fn debug(msg: u8);

fn toggle(val: u8) -> u8 { return ~val; }

model ButtonLED {
    var state: u8 := 0;

    in  BTN: bit;   // входной порт — кнопка
    out LED: u8;    // выходной порт — светодиод

    start Idle {
        ref Active: BTN = 1;
    }

    state Active {
        enter {
            state := toggle(state);
            LED   := state;
            debug(state);
        }
        next Idle;
    }
}

start M = ButtonLED;
```

### Управление лифтом (параллельная композиция)

```lam
type u8 = [bit;8];

enum Command { Up, Down, Stop }

var command: Command := Stop;

model Motor {
    start Idle {
        ref Up:   command = Up;
        ref Down: command = Down;
        enter { ElevatorMotor_Stop := true; }
    }
    state Up {
        ref Stop: command = Stop | ElevatorMotor_SensorU;

        always   { ElevatorMotor_Down := true; }

    out ElevatorMotor_Up:    bit;
    out ElevatorMotor_Down:  bit;
    out ElevatorMotor_Stop:  bit;
    in  ElevatorMotor_SensorU: bit;
    in  ElevatorMotor_SensorD: bit;
}

start Main = Cabin | Motor;   // параллельный запуск
```

```lam

```

### Симуляция: вычисления в теле блока

Симулятор (`simulation`) исполняет тела `enter`/`exit`/`always` и вычисляет
условия переходов. Значения приводятся к **объявленному типу** переменной при
записи — как в C.

```lam
var temperature: u8 := 0;

start Idle {
    always {
        var delta: u8 := 1;          // локальная переменная блока
        temperature := temperature + delta;
    }
    ref Heating: temperature > 10;   // переход по вычисленному значению
}

state Heating {
    enter { temperature := temperature + 5; }
}
```

Прогон: `temperature` растёт на 1 за такт; на 11-м такте условие `> 10`
выполняется, происходит переход в `Heating`, и его `enter` добавляет ещё 5.

**Усечение по типу** совпадает с поведением C (проверяется автоматической
сверкой с кодом, порождённым `lamc -t c`):

```lam
var x: u8 := 0;

start Idle {
    always {
        x := 255;
        x := x + 1;   // → 0   (обёртка mod 2⁸, как uint8_t в C)
        x := 300;     // → 44  (300 mod 256)
        x := 1 << 8;  // → 0   (продвижение до int, затем усечение при записи)
    }
}
```

### Симуляция: вызов функции и сравнение с вариантом `enum`

```lam
enum Mode { Auto = 0, Manual = 1 }

var mode: Mode := Manual;
var eta:  u8   := 0;

fn chebyshev(a: u8, b: u8, c: u8) -> u8 {
    var t: u8 := 0;
    t := a;
    if b > t { t := b; }
    if c > t { t := c; }
    return t;
}

start Idle {
    always { eta := chebyshev(5, 3, 7); }   // → 7 (метрика Чебышёва)
    ref Active: mode = Manual;              // сравнение с вариантом enum
}

state Active {
}
```

Примеры выше соответствуют фикстурам `simulation/tests/data/eval/` и покрыты
интеграционными тестами (`simulation/tests/eval_tests.rs`), поэтому не могут
разойтись с реальным поведением.

| Код    | Описание                                         |
|--------|--------------------------------------------------|

| CC-002 | Неразрешённая функция в условии перехода         |
| CC-008 | Начальное состояние модели не определено         |
| CC-010 | Ошибка записи выходного файла (`.h` или `.c`)    |
| CC-014 | Бит-вектор непредставимой ширины (`[bit;128]`; допустимо 8/16/32/64) |
| CC-015 | Тип не представим в C (в т.ч. тип элемента массива) |
| CC-016 | Ширина доступа к регистру порта неизвестна для его типа C (`c-hal`) |
| CC-017 | Инициализатор массива не выразим в C (скалярный либо иной длины) |
| CC-018 | Условие перехода не переводится в C (причина — заметкой) |

**`CC-018`: непереводимое условие — ошибка, а не мёртвый автомат.** Если условие
`ref`-перехода не транслируется в C, компиляция **прекращается** с указанием
целевого состояния, позиции `ref` в исходнике и исходной причины:

```text
Ошибка компиляции [CC-018]: условный переход в состояние 'Work' не переводится
в C: BitAccess на float-порт не поддерживается в условии
  примечание: причина [CC-001]: BitAccess на float-порт не поддерживается в условии
```

Прежде такой переход **молча** заменялся комментарием: `lamc` печатал
«Скомпилировано» и завершался с кодом `0`, а порождённый C собирался без
замечаний — но автомат терял ребро. Ошибка ломает ровно те сборки, которые были
сломаны и раньше, просто незаметно.

#### Условие по состоянию другой модели: `S(Модель) = Состояние`

`S(Модель)` — встроенная функция: **текущее состояние** модели. В C переводится
сравнением поля состояния в порождённой структуре:

```lam
model Pong {
    start Go {
        ref Stop: S(Ping) = Done;   // ждём, пока Ping не окажется в Done
    }
    state Stop;
}
```

```c
if (main->entry.ping0.state == SREF_PING_DONE) { … }
```

База пути зависит от родства: своя под-модель адресуется через свою структуру
(`model->…`), а модель-сестра — от корня (`main->…`), потому что корневая
структура владеет всеми под-моделями по значению. Работает и `!=`.

Имя состояния ищется **в модели-аргументе**, а не в той, где записано условие:
`S(Ping) = Done` — это `Done` **модели `Ping`**. Несуществующее состояние даёт
`SE-033` на стадии семантики.

⚠️ **Скобочная форма не поддерживается:** `(S(Ping)) = Done` и `S((Ping)) = Done`
отвергаются с `SE-025`.

### Ошибки симуляции (SIM)

Ошибки времени выполнения симулятора. **Симулятор не подставляет значения по
умолчанию и не «пропускает» невычислимое молча**: любая из этих ошибок
останавливает прогон и даёт **ненулевой код возврата**.

| Код     | Описание                                                            |
|---------|---------------------------------------------------------------------|
| SIM-001 | Деление или остаток на ноль                                         |
| SIM-002 | Сдвиг на отрицательное число или ≥ 64 бит                           |
| SIM-003 | Значение не помещается в знаковый тип назначения                    |
| SIM-004 | Переполнение внутреннего 64-битного представления                   |
| SIM-005 | Операция не определена для операндов таких типов                    |
| SIM-006 | Значение нельзя привести к типу назначения                          |
| SIM-007 | Тип не поддерживается симулятором (например, структуры)             |
| SIM-008 | Не удалось разобрать вещественный литерал                           |
| SIM-009 | Переменная не найдена                                               |
| SIM-010 | Ошибка доступа к массиву (не массив, нецелый индекс, выход за границы) |
| SIM-011 | Ошибка доступа к биту (не целое, номер бита вне 0..64)              |
| SIM-013 | Сравнение с состоянием или моделью пока не поддерживается           |
| SIM-014 | Конструкция не поддерживается симулятором (строки и др.)            |
| SIM-015 | Пустое выражение/условие не может быть вычислено                    |
| SIM-016 | Неразрешённый узел не может быть вычислен                           |
| SIM-017 | Оператор пока не поддерживается симулятором                         |
| SIM-018 | Превышен предел итераций цикла (100 000)                            |
| SIM-019 | Внешняя функция без тела: симуляция значения невозможна             |
| SIM-020 | Встроенная функция пока не поддерживается симулятором               |
| SIM-021 | Неверное число аргументов при вызове функции                        |
| SIM-022 | Превышена глубина рекурсии (256)                                    |
| SIM-023 | Функция не вернула значение                                         |
| SIM-024 | `break`/`continue` вне цикла                                        |
| SIM-025 | Нарушен инвариант / Guard-формула (assert языка Lam)                |

**Контрпример — деление на ноль:**

```lam
var d: u8 := 0;
var x: u8 := 1;

start Idle {
    always { x := 10 / d; }
}
```

```
ОШИБКА вычисления на шаге 1: деление на ноль (SIM-001)
Симуляция остановлена: результат недостоверен.
```

**Контрпример — внешняя функция со значением:** у `extern fn` нет тела, поэтому
вычислить результат нельзя; симулятор отказывает, а не подставляет ноль.

```lam
extern fn calc() -> u8;

var x: u8 := 0;

start Idle {
    always { x := calc(); }
}
```

```
ОШИБКА вычисления на шаге 1: внешняя функция 'calc' не имеет тела:
симуляция значения невозможна (SIM-019)
```

> `extern fn` **без** возвращаемого значения (процедура) — не ошибка: вызов
> считается no-op, поскольку в симуляции нет платформенного слоя.

### Известные ограничения симулятора

- Структуры (`struct`) не представимы — `SIM-007`.
- Строки в выражениях не поддерживаются — `SIM-014`.
- Сравнение с состоянием (`S(Ping) = End`) и моделью — `SIM-013`.
- Порождённый C заводит служебные такты инициализации, поэтому потактовые трассы
  симулятора и синтезированного кода **смещены**; совпадают установившиеся
  значения.
- `--save-state`/`--load-state` не сохраняют переменные модели.

### Структура сообщения об ошибке

```
Уровень:  Debug | Info | Warning | Error
Тип:      ParserError | SyntaxError | DeclarationError |
          TypeError | CastError | SemanticError | Warning
Позиция:  файл, строка, столбец (начало и конец)
Заметки:  дополнительный контекст
```

### Типичные ошибки пользователей

- Забытое `start` в модели → SE-011.
- Использование `:=` вместо `=` в условии (`if`, `cond`, `ref`) → присваивание
  вместо сравнения (в большинстве позиций условия — ошибка разбора).
- Запись в `in`-порт или чтение из `out`-порта → ошибка направления.
- Перекрывающиеся условия в `ref` → SE-042, недетерминированный переход.

## 8. Интеграция и реализация

### Конвейер компиляции

```
Исходный файл (.lam)
        │
        ▼
┌─────────────────┐
│   Лексер        │  lexer.rs — токены с позиционной информацией
└────────┬────────┘
         ▼
┌─────────────────┐
│   Парсер        │  LALRPOP (LR(1)) — Абстрактное синтаксическое дерево
└────────┬────────┘
         ▼
┌─────────────────┐
│   Семантический │  7 проходов → семантическое дерево + диагностика
│   анализатор    │
└────────┬────────┘
         ▼
┌─────────────────┐
│   Генератор C   │  c_header.rs (.h) + c_source.rs (.c)
└─────────────────┘
```

**Детерминированная генерация.** Один и тот же `.lam` компилируется в
**байт-в-байт одинаковый** код от прогона к прогону — для всех целей (`c`,
`c-hal`, `plantuml`, `st`). Порядок эмиссии задаётся **типом контейнера**
(`BTreeMap`, алфавитный порядок), а не привычкой отдельного бэкенда, поэтому
воспроизводимость получают все цели разом. Это делает возможными
codegen-снапшоты и осмысленный дифф порождённых файлов, а главное —
стабильный **ABI** прошивки: числовые значения `enum` портов и состояний
одинаковы при любой пересборке. Гарантируется гейтом `precheck.sh` (два прогона
на пример × цель → `diff -r`).

### Семантические проходы

| № | Проход            | Описание                                               |
|---|-------------------|--------------------------------------------------------|
| 0 | Скелет            | Извлечение имён моделей/состояний, загрузка импортов   |
| 1 | Композиция        | Разрешение составных состояний (`+ M1 M2`, `M1 \| M2`) |
| 2 | Выражения         | Разрешение переменных, вывод типов, порты              |
| 3 | Условия (`cond`)  | Разрешение именованных условий                         |
| 4 | Именованные блоки | Разрешение `enter`/`exit`/`always`                     |
| 5 | Функции           | Разрешение тел функций                                 |
| 6 | Переходы (`ref`)  | Замена `Condition::Unresolved` на разрешённые условия  |

### Запуск компилятора

```sh
# Компиляция в C
lamc compile --target c input.lam -o output/

# Результат:
# output/input.h  — заголовочный файл
# output/input.c  — реализация
```

#### Отображение типов Lam в типы C

| Тип Lam | Тип C | Пример объявления |
|---------|-------|-------------------|
| `bit` | `uint8_t` | `var fl: bit;` → `uint8_t fl;` |
| `bool` | `bool` | `var b: bool;` → `bool b;` |
| `u8`/`u16`/`u32`/`u64` (`[bit;N]`) | `uint{N}_t` | `var b: u8;` → `uint8_t b;` |
| `i8`/`i16`/`i32`/`i64` | `int{N}_t` | `var n: i16;` → `int16_t n;` |
| `float` | `double` (по умолчанию) | `var r: float;` → `double r;` |
| `float` при `--float-width=32` | `float` | `var r: float;` → `float r;` |
| `[T;N]`, где `T` ≠ `bit` | `T name[N]` | `var data: [u8;4];` → `uint8_t data[4];` |
| перечисление | `uint{N}_t` по максимуму варианта | `enum Mode {…}` → `uint8_t mode;` |
| структура | одноимённая `struct` | `var p: Point;` → `Point p;` |
| `unit` | `void` | тип возврата процедуры |

**Бит-вектор — не массив.** `[bit;8]` — это способ записать `u8`: в C он
**скаляр** `uint8_t`, а не массив из восьми элементов. Настоящий массив —
`[T;N]` с любым другим элементом, и в C он объявляется `T name[N]`. Ширина
бит-вектора ограничена {8, 16, 32, 64}: типа `uint128_t` в C нет, поэтому
`[bit;128]` отвергается диагностикой `CC-014` — а не порождает невалидный код.

**`float` — 8 байт по умолчанию.** `double` совпадает по точности с симулятором
(f64), поэтому проверка модели до синтеза сходится с прошивкой. Для платформ,
где 8-байтное чтение недопустимо, — `--float-width=32`; в цели `c-hal` это
меняет и ширину доступа к регистру порта (8 → 4 байта).

**Инициализация массива — только агрегатом.** Массив в C не присваивается,
поэтому `_init` заполняет его поэлементно:

```lam
var arr: [u8;4] := {0, 0, 0, 0};   // → model->arr[0] = 0; … model->arr[3] = 0;
```

Скалярный инициализатор массива (`var arr: [u8;4] := 0;`) цель `c` **отвергает**
(`CC-017`): язык не определяет, значит ли это «обнулить весь массив» или
«записать в первый элемент».

### Генерация Structured Text (IEC 61131-3)

Третья цель наряду с `c` и `plantuml` — **ST**, стандартный язык ПЛК. Модель Lam
ложится на него естественно: модель → `FUNCTION_BLOCK`, состояния → `CASE state OF`.

```sh
# Библиотека блоков: порты — входы/выходы FUNCTION_BLOCK, адреса не эмитятся
lamc compile -t st examples/stacker.lam -o out/

# Программа для ПЛК целиком: порты размещены по адресам
lamc compile -t st-at --address-map examples/elevator.plc.map examples/elevator.lam -o out/
```

**Цели `st` и `st-at` асимметричны — и это не косметика:**

| | `st` | `st-at` |
|---|---|---|
| Что порождает | **библиотеку блоков** | **программу для ПЛК целиком** |
| Порты | `VAR_INPUT` / `VAR_OUTPUT` блока | `VAR_GLOBAL … AT %IX256.0`; блоки видят их через `VAR_EXTERNAL` |
| Обёртка | не нужна | **обязательна**: `CONFIGURATION`/`RESOURCE`/`TASK`/`PROGRAM` |
| `--address-map` | игнорируется | потребляется |

Асимметрия навязана стандартом: `VAR_GLOBAL` **вне** `CONFIGURATION` недопустим,
тогда как отдельный `FUNCTION_BLOCK` принимается сам по себе.

#### Отображение

| Lam | ST |
|---|---|
| `model M` | `FUNCTION_BLOCK M` |
| состояния | `CASE state OF`; `INIT` — ветвь `0` (холодный старт ПЛК обнуляет `VAR`) |
| `ref T: cond;` (несколько) | `IF … ELSIF …` — порядок объявления сохраняется |
| `always` / `enter` / `exit` | тело ветви / инлайн в переход / перед `enter` цели |
| `M1 \| M2` | экземпляры под-блоков, последовательные вызовы, завершение по конъюнкции `is_done` |
| `M1 + M2` | вложенный `CASE` по счётчику шагов |
| `bit`/`bool` → `BOOL`, `u8`→`USINT`, `i16`→`INT`, `float`→**`LREAL`** | ⚠ `INT` в IEC — **16-битный** |
| `[u8; 4]` | `ARRAY [0..3] OF USINT` |
| `enum` | целое + именованные константы `<Enum>_<Вариант>` |
| `fn` | `FUNCTION`; возврат — присваивание **имени функции** |

#### Чего ожидать: ограничения IEC 61131-3

Модель Lam опирается на общий доступ к состоянию, которого в IEC нет ни у
функций, ни между POU. Всё разделяемое выражается **явной передачей**, поэтому
порождённый ST многословнее исходника:

- **Перечисления** не становятся перечислимым типом: явные значения вариантов —
  фича 3-й редакции, широко не поддержанная. Вместо этого целое + константы.
- **Битового доступа `x.0` нет**: разворачивается в маску
  `(USINT_TO_BYTE(x) AND 16#01) <> 16#00`.
- **Побитовые операции** определены на битовых строках, а не на числах:
  `n & m` → `BYTE_TO_USINT(USINT_TO_BYTE(n) AND USINT_TO_BYTE(m))`.
- **`extern fn` невыразим**: `FUNCTION` обязана иметь тело, не может быть без
  параметров и не может возвращать `VOID`. Эмитится заглушка + предупреждение
  **`ST-009`** — в ПЛК она **ничего не сделает**, тело надо написать вручную.
- **LTL-формулы** не транслируются → предупреждение **`ST-010`**.

#### Внешняя карта адресов

`elevator.lam` написан под МК-адресацию (`0x10000000`) — для ПЛК это абсурдные
локации. Модель при этом **корректна** (для целей `c`/`c-hal`), поэтому её не
правят: ПЛК-локации держат отдельно, во внешней карте
([`examples/elevator.plc.map`](examples/elevator.plc.map)):

```
// Входы → %IX
sensors_1 = 0x0;      // → %IB0 вместо %IB268435456
```

Приоритет источников: inline `:=` < оператор `address` < внешняя карта. Оверлей
поверх inline даёт предупреждение `SE-050` на каждый порт — по замыслу.

#### Проверка порождённого

Валидность ST доказывает внешний транспилятор **MatIEC `iec2c`** — юнит-тесты
проверяют лишь, что генератор напечатал задуманное. `precheck.sh` прогоняет гейт
по всему корпусу; установка — `scripts/ensure-iec2c.sh` (см. «Необязательные
зависимости»).

> ⚠ Гейт доказывает, что ST **валиден и компилируется**, но **не** что он ведёт
> себя как модель. Поведенческую эквивалентность даёт только сверка трасс.

### Канонический форматтер (`lamc fmt`)

Приводит `.lam` к единому детерминированному стилю: воспроизводимые диффы,
отсутствие споров о форматировании, проверяемость в CI.

```sh
lamc fmt examples/            # отформатировать каталог на месте (рекурсивно, *.lam)
lamc fmt --check examples/    # проверить: код возврата ≠ 0, если нужен формат (CI)
cat a.lam | lamc fmt --stdin  # из stdin в stdout (редакторы, конвейеры)
```

Гарантии:

- **Идемпотентность:** `fmt(fmt(x)) == fmt(x)`.
- **Семантика не меняется:** `parse(fmt(x))` структурно равен `parse(x)`.
  Скобки, написанные автором, сохраняются; операторы `:=`/`=` не подменяются.
- **Комментарии сохраняются** — все три вида (`//`, `///`, `/* */`), в ведущей и
  хвостовой позиции. Пустые строки восстанавливаются, но не более одной подряд.
- **Выбор автора между синонимами сохраняется:** `while` не переписывается в
  `loop`, `: [Guard] x;` — в `: x;`.
- **Отказ вместо порчи:** если конструкция не поддержана печатью, `lamc fmt`
  сообщает об этом и возвращает ненулевой код — файл не трогается.

То же ядро используют `lamc fmt`, LSP (`textDocument/formatting`) и будущая
интеграция с IDE, поэтому стили инструментов не расходятся.

### Порты ввода-вывода

```lam
model Motor {
    out Enable: bit;   // запись
    out Speed:  u8;
    in  Sensor: bit;   // чтение
    in  Limit:  bit;
}
```

- **`out`-порт**: модель пишет в него; чтение — ошибка.
- **`in`-порт**: модель читает из него; запись — ошибка.

При кодогенерации создаются отдельные enum-типы и типизированные функции для in/out.

### Адресные литералы (MMIO)

```lam
var LED : u8  := 0x00100000;      // привязка к адресу
var BTN : bit := 0x00200000:0;    // адрес:номер_бита
```

### Внешние функции (FFI)

```lam
extern fn hal_uart_send(data: u8);
extern fn hal_gpio_set(pin: u8, val: bit);
```

В сгенерированном C-коде они превращаются в прямые вызовы без обёрток.

## 9. Тестирование

### Запуск тестов

```sh
cargo test                   # все тесты
cargo test --features lsp    # включая LSP-тесты
```

### Стратегия тестирования

- `.lam`-файлы в `tests/data/valid/` — должны компилироваться без ошибок.
- `.lam`-файлы в `tests/data/invalid/` — должны производить ожидаемую диагностику.

### Виды тестов

| Вид               | Что проверяется                       |
|-------------------|---------------------------------------|
| Лексические       | Корректное разбиение на токены        |
| Синтаксические    | Построение AST из допустимых программ |
| Семантические     | Разрешение имён, типы, ошибки         |
| Кодогенерация     | Валидный C-код на выходе              |
| Эталонные примеры | Полный прогон из `examples/`          |

### Сборка из исходников

**Требования:** Rust 1.75+, LALRPOP (генерируется автоматически через `build.rs`).

```sh
git clone https://github.com/Pastor/BuT.git
cd BuT
cargo build --release --bin lamc
cargo install --path grammar --bin lamc
```

#### Необязательные зависимости (проверка порождённого кода)

Нужны только для проверки того, что компилятор породил **валидный** код целевого
языка. Сборка и тесты `lamc` без них проходят полностью.

| Инструмент | Зачем | Что проверяет |
|---|---|---|
| `cmake` + `ninja` + C-компилятор | гейт цели `c` (`scripts/precheck.sh`) | порождённый C компилируется |
| **MatIEC `iec2c`** | гейт цели `st` (фича 0041) | порождённый Structured Text компилируется |

**MatIEC** — открытый транспилятор ST → ANSI C; пакетом дистрибутивов **не
поставляется**. Ставить руками не нужно: `precheck.sh` сам проверяет наличие и
при отсутствии собирает из исходников. Тем же скриптом можно вызвать отдельно:

```sh
scripts/ensure-iec2c.sh          # → ~/.local/bin/iec2c (≈15 с; повторный вызов мгновенный)
IEC2C_SKIP=1 scripts/ensure-iec2c.sh   # отключить (оффлайн/CI)
```

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `IEC2C_PREFIX` | `~/.local` | Куда ставить (`$PREFIX/bin/iec2c`) |
| `IEC2C_SRC` | `~/.cache/matiec` | Куда клонировать исходники |
| `IEC2C_SKIP` | — | `1` — пропустить проверку целиком |

Ручной прогон (`-I` обязателен — без библиотеки `ieclib.txt` инструмент падает
на любом входе):

```sh
~/.local/bin/iec2c -I ~/.local/share/matiec/lib -T /tmp/out файл.st   # код 0 = ST валиден
```

⚠ **macOS:** системный `bison` — версии 2.3, а `configure` требует ≥ 2.4
(`Wrong bison version: 2.3 < 2.4`). Нужен `brew install bison`; скрипт сам
подхватывает `/opt/homebrew/opt/bison/bin`, а при слишком старом bison мягко
пропускает сборку, не роняя предкоммит. На `ubuntu-latest` bison 3.x —
препятствия нет.

⚠ `make install` MatIEC ставит **только бинарники**: библиотеку стандартных
функций (`lib/`) скрипт копирует сам в `$PREFIX/share/matiec/lib`.

Гейт ST пока **не** подключён к `precheck.sh`: цель `st` дописывается (фича 0041,
задачи 03–05), и до появления тела `FUNCTION_BLOCK` он валил бы предкоммит.
Подробности — [`docs/features/0041-st-backend.md`](docs/features/0041-st-backend.md).

## 10. Расширение и версии

### Версия

**Версия языка: 0.3.0** (крейт `grammar`). Документ актуален для ветки `v2`.
Список изменений — в файле [`CHANGES.md`](CHANGES.md).

> **0.2.0 → 0.3.0 (фича 0029, решение заказчика):** отображение типов Lam в типы
> C приведено к явному и проверяемому виду. Меняется **наблюдаемая семантика
> порождаемого кода**, а не синтаксис языка: `float` → `double` (8 байт, было
> 4 — совпадение с точностью симулятора f64), `bit` → `uint8_t` (было `int` —
> 32 бита со знаком), `[T;N]` при `T` ≠ `bit` → настоящий массив `T name[N]`
> (было `uint{N}_t` — несуществующий тип). Правки `.lam`-исходников **не
> требуется** — изменение выражается в перегенерации C; автомиграция не нужна.
>
> Ужесточения: `[bit;128]` → `CC-014` (типа `uint128_t` в C нет), скалярный
> инициализатор массива → `CC-017`. Оба прежде давали **невалидный C**, то есть
> ни одна работавшая программа не сломана.
>
> **Версия 0.3.0 накапливает изменения** (правило 22): фичи 0031, 0033, 0042,
> 0044 вносят свои изменения в **уже поднятую** версию, не поднимая её снова.
> **Фича 0031** (реализована): вызов функции из тела функции — композиция `f→g`
> внутри модели (аддитивно: ранее отвергавшиеся программы компилируются, смысл
> валидных не меняется); рекурсия запрещена диагностикой `SE-053`. См.
> «Функции».
> **Фича 0044** (реализована): именованный инвариант `invariant Имя = <Условие>;`
> (аддитивно: одно жёсткое ключевое слово, `assert` не вводится) + оживление
> Guard-формул в симуляторе (`SIM-025` вместо тихого пропуска). См. «Инварианты
> и assert».
> **Фича 0033** (реализована): вход в стартовое состояние больше не расходует
> такт — тело исполняется на такте 1 на любой глубине, как в симуляторе. Ломающее
> изменение **наблюдаемой семантики такта** (не синтаксиса): порождённый C
> меняется, прошивки при пересборке стартуют на `depth` тактов раньше; `.lam` не
> правятся. См. «Семантика первого такта».

> **Аддитивное расширение 0.1.0 → 0.2.0 (фича 0020):** оператор задания адреса
> порта `address Имя = <адрес>;` (жёсткое ключевое слово `address`), внешняя
> `.ld`-подобная карта адресов (`--address-map`) и цель генерации `-t c-hal`
> (таблица адресов + дефолтный HAL). Совместимость полная — инлайн-адрес
> `in P: T := <addr>;` работает как прежде.

> **Слом совместимости 0.0.x → 0.1.0 (фича 0021):** присваивание записывается
> `:=` (было `=`), сравнение на равенство — `=` (было `==`); оператор `==`
> выведен. Реляционный `<=` без изменений. Старые `.lam` переводятся
> AST-мигратором (см. `docs/development/0021-03-tool/`).

### Композиция моделей

Lam поддерживает два вида сборки систем:

```lam
// Последовательная: Init → Startup (после завершения Init запускается Startup)
start Sequential = Init + Startup;

// Параллельная: Run и Halt работают одновременно
start Parallel = Run | Halt;

// Комбинированная
start System = (Init + Startup) + (Run | Halt);
```

### Формулы и ассемблерные вставки

Для встраивания платформо-зависимого кода или формальных спецификаций:

```lam
assembly "arm" {
    // платформо-зависимый код
}

formula "ltl" {
    always(active())
    eventually(done())
}
```

**LTL-аннотации** (`: [LTL] φ;`) — свойства линейной темпоральной логики прямо в
модели, состоянии или блоке кода. Операторы: `X` (next), `F` (eventually),
`G` (always), `U` (until), `R` (release), `!`, `&`, `|`, `->`. **Атом — голое
имя** (переменной, состояния или `cond`); вызовы функций в атоме не допускаются:

```lam
var a: u8 := 0;
var b: u8 := 0;
start c { : [LTL] G (a -> F b), X c; }   // атомы a, b — переменные; c — состояние
```

> **Статус (фича 0035).** LTL-формула **разбирается** на всех трёх уровнях
> (модель/состояние/блок) — прежде в блоке она молча терялась. **Верификация LTL
> ещё не реализована**: ни одна цель генерации формулу не проверяет, о чём
> сообщает предупреждение `SE-055`. Неизвестный атом (опечатка) даёт `SE-056`.
> Полноценная проверка (`lamc verify`, автоматы Бюхи) — предмет будущего
> расширения.

### Архитектура компилятора

```

│   │   ├── tree.rs           — семантические проходы
│   │   ├── validate.rs       — валидация

│   │   └── builtin.rs        — встроенные функции
│   ├── generator/c/
│   │   ├── c_header.rs       — генерация .h

│   │   ├── c_model.rs        — генерация кода модели
│   │   ├── c_expr.rs         — генерация выражений
│   │   └── c_map.rs          — маппинг модели

│       ├── lamc.rs           — CLI-компилятор
│       └── lam_lsp.rs        — LSP-сервер
```

### Расширение языка

Добавить новую конструкцию в Lam:

1. Расширить грамматику в `grammar/src/grammar.lalrpop` и `lexer.rs`.
2. Добавить узел AST в `ast.rs`.
3. Реализовать семантический проход в `semantic/tree.rs`.
4. При необходимости — расширить кодогенератор в `generator/c/`.
5. Добавить тесты в `tests/data/valid/` и `tests/data/invalid/`.

Полная грамматика находится в файле [`Lam.ebnf`](Lam.ebnf).
