# Lam — Язык описания автоматных моделей

**Lam** (Language of Automata Models) — предметно-ориентированный язык (DSL) для моделирования
конечных автоматов (FSM) и компонентных систем. Компилятор реализован на Rust.

## 1. Введение

### Целевая аудитория

Этот документ предназначен для:

- **Разработчиков встраиваемых систем**, которые проектируют управляющую логику на основе
  конечных автоматов и нуждаются в формальном и читаемом способе её описания.
- **Исследователей и инженеров** в области верификации, желающих описывать поведение систем
  на высоком уровне абстракции.
- **Опытных разработчиков** (C/C++/Rust), знакомых с понятиями FSM, которые хотят изучить
  синтаксис и семантику Lam.

### Соглашения по нотации

| Обозначение      | Смысл                              |
|------------------|------------------------------------|
| `ключевое_слово` | Литерал: пишется дословно          |
| `идентификатор`  | Любое имя, выбранное пользователем |
| `[ ... ]`        | Необязательный элемент             |
| `{ ... }`        | Повторение (0 и более раз)         |
| `a \| b`         | Альтернатива                       |

Полная грамматика в формате ISO EBNF — в файле [`Lam.ebnf`](Lam.ebnf).

### Привет, мир!

Минимальная программа — модель со стартовым состоянием:

```lam
model Hello {
    start World;
}

start Main = Hello;
```

Запустить компилятор:

```sh
cargo build --release --bin lamc
./target/release/lamc compile --target c hello.lam -o out/
```

В `out/` появятся `hello.h` и `hello.c`.

## 2. Назначение DSL

### Проблема

Традиционный подход — писать конечные автоматы вручную на C — приводит к рутинному коду,
который сложно верифицировать и сопровождать. Типичная реализация FSM на C требует:
`switch-case` по состояниям, ручного управления флагами входа/выхода, указателей MMIO вместо
типизированных портов.

### Решение

Lam предлагает:

- **Декларативный синтаксис** для FSM вместо `switch-case` на C.
- **Компиляцию в C**: сгенерированный код оптимален и пригоден для встраиваемых систем.
- **Формальную семантику**: типизация, детерминированность переходов, диагностика.
- **Никакого рантайма**: ни сборщика мусора, ни кучи — только стек и порты.

### Парадигма

Lam — **декларативный, ориентированный на состояния** язык:

- **Модели** (`model`) — основные строительные блоки; каждая модель — один FSM.
- **Состояния** (`start`, `state`) — узлы автомата; логика выполняется в их блоках.
- **Переходы** (`ref`, `next`) — рёбра автомата с условиями или безусловные.
- **Параллельная и последовательная композиция** (`|`, `+`) — сборка систем из компонентов.

### «Дзен» языка

| Принцип            | Смысл                                                   |
|--------------------|---------------------------------------------------------|
| **Явность**        | Переходы описаны явно — нет скрытой передачи управления |
| **Локальность**    | Каждая модель инкапсулирует состояния и данные          |
| **Минимализм**     | Язык содержит только необходимые конструкции            |
| **Встраиваемость** | Нет GC, рантайма или кучи — только стек и порты         |

### Сравнение с C

| Концепция          | C (switch-case)        | Lam                      |
|--------------------|------------------------|--------------------------|
| Состояние          | `enum` + переменная    | `state`/`start`          |
| Переход            | `case` с `goto`        | `ref Цель: условие;`     |
| Вход в состояние   | ручная флаг-переменная | `enter { ... }`          |
| Параллелизм        | потоки / ручная логика | `M1 \| M2`               |
| Последовательность | вложенный switch       | `M1 + M2`                |
| Порты              | указатели MMIO         | `in`/`out` внутри модели |
| Типизация          | слабая                 | строгая статическая      |

### Глоссарий

| Термин                  | Определение                                                         |
|-------------------------|---------------------------------------------------------------------|
| FSM                     | Конечный автомат (Finite State Machine)                             |

| Переход                 | Смена активного состояния (`ref` или `next`)                        |
| Условие                 | Булево выражение для `ref`-перехода                                 |
| `cond`                  | Именованное условие — псевдоним для переиспользования               |

| Композиция              | Объединение моделей: последовательная (`+`) или параллельная (`\|`) |
| `enter`/`exit`/`always` | Именованные блоки кода с семантикой жизненного цикла                |
| `next`                  | Безусловный переход в следующее состояние                           |
| DSL                     | Domain-Specific Language — предметно-ориентированный язык           |

### Система типов

Lam использует **статическую строгую типизацию** с **выводом типов** из инициализаторов.

| Тип        | Размер      | Описание                                    |
|------------|-------------|---------------------------------------------|
| `bit`      | 1 бит       | Одиночный бит                               |
| `bool`     | 1 бит       | Булев тип                                   |
| `float`    | переменный  | Число с плавающей точкой                    |
| `q(m, n)`  | `m + n` бит | Fixed-point (дробное фиксированной точки)   |
| `unit`     | 0           | Пустой тип (возвращаемое значение процедур) |

### Fixed-point `q(m, n)`

`q(m, n)` — **знаковый** тип с фиксированной точкой (дополнительный код): `m`
целых бит **включая знак**, `n` дробных, полная ширина `W = m + n` (границы
`m ≥ 1`, `n ≥ 1`, `W ≤ 64`). Значение — `v · 2⁻ⁿ`, где `v` — знаковое `W`-битное
представление. В отличие от `float`, fixed-point **синтезируем в аппаратуру**
(цель `sv`), где плавающей точки нет.

```lam
var t: q(8, 8) := 1.5;   // 8.8: диапазон [−128, 127.996], шаг 2⁻⁸ ≈ 0.0039
type Temp = q(8, 8);     // псевдонимы работают штатно
```

**Нормативная арифметика** (одинакова у симулятора и всех целей — **побитово**):

| Операция | Правило |
|---|---|
| `+`, `−` | сложение представлений; переполнение — **перенос** (wraparound), как у целых |
| `*` | точное произведение шириной `2W`, затем сдвиг на `n` вправо; округление **floor к −∞** |
| `/` | делимое расширяется до `2W` и сдвигается влево на `n`, затем целочисленное деление (усечение к нулю) |
| приведения | `q ↔ int` и `q ↔ float` — **только явные** (`x as q(8, 8)`, `y as float`); неявное смешение → `SE-059` |

Литерал, присваиваемый `q`, переводится в представление **на этапе компиляции и
точно**: `q(8, 8) := 1.5` → `384`. Непредставимый в формате литерал
(`q(8, 8) := 0.001`) → **ошибка `SE-058`**, а не тихое округление.

```lam
// Пропорциональный регулятор (examples/regulator.lam):
var setpoint: q(8, 8) := 10.0;
var value: q(8, 8) := 0.0;
var half: q(8, 8) := 0.5;
start Adjust {
    always { value := value + (setpoint - value) * half; } // q +, −, *
    ref Settled: value >= near;                            // сравнение q
}
```

**Контрпримеры:** `q(0, 8)`/`q(8, 0)`/`q(40, 40)` → ошибка границ; `a + b` при
`a : q(8, 8)`, `b : u8` → `SE-059` (нужно `a + (b as q(8, 8))`).

Пропорциональный вариант на **явном `q(8, 8)`** — `examples/regulator.lam` (выше).
Полный **ПИД-регулятор** (`examples/pid_regulator.lam`) — позиционная дискретная
форма с anti-windup и объектом 1-го порядка; сходится к уставке и завершается —
написан на **прозрачном `float`** (см. ниже): тип в исходнике `float`, а
представление `q(8, 8)` для sv/встраиваемых выбирают флаги сборки. Anti-windup
осмыслен именно в `q`-представлении (арифметика переносит, а не насыщает); для
нативного `float` безвреден.

### Прозрачный `float`: представление выбирают флаги генерации

Тип `q(m, n)` задаёт формат в самом тексте. Иногда удобнее писать привычный
`float`, а **представление выбрать при компиляции** — под цель и профиль
исполнения. Два флага генерации делают `float` «прозрачным»:

| Флаг | Действие |
|---|---|
| `--float-as-q=<m>.<n>` | Глобальная Q-точность: везде, где нужен `float`, подставляется `q(m, n)`. Границы — как у `q` (`m ≥ 1`, `n ≥ 1`, `m + n ≤ 64`). |
| `--float-embedded` | Для целей `c`/`rust`/`st`: реализовать `float` целочисленным `q(m, n)` (embedded без FPU) вместо нативного. Действует только вместе с `--float-as-q`. |

Поведение по цели:

| Цель | без флагов | `--float-as-q=m.n` | `+ --float-embedded` |
|---|---|---|---|
| `c` | `double` | `double` (native) | `q(m, n)` → `int{W}_t` |
| `rust` | `f64` | `f64` (native) | `q(m, n)` → `i{W}` |
| `st` | `LREAL` | `LREAL` (native) | `q(m, n)` → `INT`/`LINT` |
| `sv` | **`SV-003`** (в RTL float нет) | `q(m, n)` → синтезируемо | `q(m, n)` (то же) |

То есть один и тот же исходник на `float` даёт: нативную плавающую точку на
FPU-целях по умолчанию; целочисленный Q для embedded без FPU (второй флаг);
синтезируемый RTL для FPGA/ASIC (цель `sv`, где нативного `float` **нет** — флаг
снимает `SV-003`). Примеры — `examples/float_regulator.lam` (тот же регулятор, что
`regulator.lam`, но на `float`) и `examples/pid_regulator.lam` (ПИД на `float`:
sv через `--float-as-q=8.8`, встраиваемые c-hal/st-at через
`--float-embedded --float-as-q=8.8`).

```sh
lamc compile examples/float_regulator.lam -t c                          # double
lamc compile examples/float_regulator.lam -t c   --float-as-q=8.8 --float-embedded  # int16_t
lamc compile examples/float_regulator.lam -t sv  --float-as-q=8.8       # q(8,8), синтезируемо
```

> ⚠️ **native-`float` и Q-`float` — разные численные семантики.** Нативная
> плавающая точка не floor'ит умножение к −∞ и не переполняется переносом, а Q —
> да (правила `q` выше). Это **две модели** одного текста; трассы совпадают внутри
> режима, но не между ними. Флаг меняет **представление и модель**, а не только
> вывод. Без `--float-as-q` цель `sv` для `float` по-прежнему `SV-003`: угадывать
> точность генератор не вправе — флаг и есть выбор формата автором.
>
> Литералы `float` в **инициализаторах** переводятся в представление точно (как у
> `q`); в **телах** (арифметика) — как у `q`, пишутся через переменные.

Массив фиксированной длины: `[ТипЭлемента; Длина]`:

```lam
type u8  = [bit;8];
type u16 = [bit;16];
type u32 = [bit;32];
type u64 = [bit;64];
type Word = [u8;4];
```

Вывод типов из инициализатора:

| Инициализатор     | Выводимый тип |
|-------------------|---------------|
| `0` … `255`       | `[bit;8]`     |
| `256` … `65535`   | `[bit;16]`    |
| `65536` … `2³²−1` | `[bit;32]`    |
| `2³²` … `2⁶⁴−1`   | `[bit;64]`    |
| `true` / `false`  | `bool`        |
| `3.14`, `1e10`    | `float`       |

### Объявление переменных

```lam
var x;               // без типа и значения
var x: u8;           // с явным типом
var x := 100;        // тип выводится
var x: u8 := 50;     // явный тип и значение
const MAX: u8 := 255; // константа
```

### Функции

```lam
fn add(a: u8, b: u8) -> u8 { return a + b; }

fn reset();                    // прототип без тела

extern fn hal_uart_send(data: u8);   // внешняя функция
```

**Композиция функций** (фича 0031). Тело функции видит **другие функции своей
модели** (и родительских), независимо от порядка объявления — `f` может вызывать
`g`, объявленную ниже:

```lam
fn f(x: u8) -> u8 { return g(x) + 10; }   // g объявлена ниже — это допустимо
fn g(x: u8) -> u8 { return x + 1; }
```

**Рекурсия запрещена** — осознанное свойство языка синтеза управляющих автоматов:
встраиваемая цель требует ограниченного стека и вычислимого WCET, а отраслевые
стандарты её прямо запрещают (MISRA C:2012 Rule 17.2, IEC 61131-3). Цикл в графе
вызовов — прямой (`f → f`) или взаимный (`f → g → f`, любой длины) — отвергается
диагностикой **`SE-053`** с указанием цепочки вызовов:

```lam
fn f(x: u8) -> u8 { return f(x); }   // SE-053: Рекурсия функций запрещена: f → f
```

Рекурсивные алгоритмы (обход деревьев и т. п.) выражаются **циклами** `while`/
`loop`, которые в языке есть.

> **Контрпример (что отвергается).** Дубликат имени функции в одной модели —
> ошибка `SE-009` (прежде принимался молча, побеждала последняя): смысл программы
> обязан быть определён.

### Импорт

```lam
import "shared.lam";
import "engine.lam" as Motor;
import * as Utils from "lib.lam";
import { TrafficLight, u8 } from "common.lam";
import { OldName as NewName } from "types.lam";
```

**Где ищется файл.** Сначала — каталоги из `-I` (в порядке объявления), затем —
**каталог импортирующего файла**. Поэтому `import "shared.lam";` находит файл,
лежащий рядом, без всякой настройки; `-I` нужен только для файлов из других
каталогов (общих библиотек):

```sh
lamc compile -t c main.lam            # shared.lam рядом с main.lam — найдётся
lamc compile -t c -I lib main.lam     # плюс общая библиотека в lib/
```

Порядок значим: одноимённый файл из `-I` **перекрывает** локальный. Так сделано
намеренно — чтобы сборки, уже настроенные через `-I`, не сменили молча найденный файл.

Если файл не найден, диагностика перечисляет пути, где его искали. Ошибка
**внутри** импортированного файла показывается с его именем и цепочкой импорта:

```text
deep.lam:2:18: Ошибка компиляции [SE-002]: Ссылка 'Missing' не найдена
  примечание: 'deep.lam' импортирован в 'mid.lam'
  примечание: 'mid.lam' импортирован в 'top.lam'
```

### Краткая грамматика EBNF

```ebnf
source_unit   = { model_element } ;

model_element = import_define | type_define | variable_define
              | function_define | enum_define | struct_define
              | model | state_define | condition_define
              | named_block | ";" ;

variable_define
    = "var"   identifier [ ":" type ] [ ":=" expression ] ";"
    | "const" identifier [ ":" type ] ":=" expression ";"
    | "in"    identifier [ ":" type ] [ ":=" expression ] ";"
    | "out"   identifier [ ":" type ] [ ":=" expression ] ";" ;

model        = "model" identifier [ "=" expression ]
               "{" { model_element } "}" ;

state_define = state_kind identifier [ "=" expression ]
               ( "{" { state_element } "}" | ";" ) ;
state_kind   = "start" | "state" ;

state_element
    = named_block
    | "ref"  identifier [ ":" condition ] ";"
    | "next" identifier ";"
    | ";" ;
```

## 5. Семантика

### Присваивание `:=` и сравнение `=`

В Lam присваивание и сравнение разведены по разным знакам (стиль ST/IEC 61131-3,
привычный инженерам АСУ ТП):

| Знак  | Смысл                                   | Где                                        |
|-------|-----------------------------------------|--------------------------------------------|
| `:=`  | Присваивание / инициализация значения   | выражения, тела, инициализаторы `var`/`const`/портов |
| `=`   | Сравнение на равенство                  | выражения **и** условия (`cond`, `ref`)    |
| `<=`  | «Меньше или равно» (реляционный)        | выражения и условия                        |

Оператор `==` из языка **выведен** — равенство всегда пишется `=`. Знак `=`
дополнительно служит связкой в **определениях имён**: `type T = …`,
`enum E { A = 0 }`, `model M = …`, `start Main = …`, `cond C = …` — здесь `=`
вводит определение, а не присваивает значение переменной.

```lam
always { x := 0; }      // := — присваивание значения
if x = 0 { ... }        // = в выражении — сравнение на равенство
cond IsZero = x = 0;    // первое = — связка cond, второе = — сравнение
ref Green: timer = 255; // = в условии перехода — сравнение
var y: u8 := 5;         // := — инициализация переменной
```

### Управляющие конструкции

```lam
// if — без скобок вокруг условия
if x > 0 { x := x - 1; }
else if x = 0 { x := 10; }
else { x := 0; }

// loop — бесконечный или с условием
loop { x := x + 1; if x >= 10 { break; } }
loop x > 0 { x := x - 1; }

// for
for var i := 0; i < 10; i := i + 1 {
    // тело
}
```

> Условие `loop` не может начинаться с `{`. Используйте скобки: `loop ({1,2,3}) { }`.

### Жизненный цикл автомата

Каждое состояние может содержать именованные блоки:

| Блок     | Когда выполняется                          |
|----------|--------------------------------------------|
| `enter`  | Один раз при входе в состояние             |
| `exit`   | Один раз при выходе из состояния           |
| `always` | Каждый такт, пока автомат в этом состоянии |

Блок `always` можно объявить и **на уровне модели** — вне какого-либо состояния.
Такой блок исполняется **каждый такт, безусловно по текущему состоянию**, до
диспетчеризации состояния (то есть до `always` активного состояния и до
переходов) — удобно для фонового действия на каждом такте (счётчик, watchdog):

```lam
model Counter {
    var n: u8 := 0;
    always { n := n + 1; }   // model-level: каждый такт, в любом состоянии
    start Run { ref Done: n > 2; }
    state Done;
}
```

Порядок выполнения за один такт:

1. **Инициализация**: устанавливается начальное `start`-состояние.
2. **Model-level `always`**: выполняются блоки `always` уровня модели.
3. **Вход**: выполняются блоки `enter`.
4. **Такт**: выполняются блоки `always` активного состояния.
5. **Проверка переходов**: вычисляются условия `ref`; при истинности — переход.
6. **Выход**: выполняются блоки `exit` текущего состояния.
7. **Переход**: активируется следующее состояние → шаг 3.

#### Семантика первого такта (моментность)

Такт — это один **цикл сканирования** (scan cycle) промышленного контроллера. На
**такте 1** модель **уже находится** в стартовом состоянии: вход в состояние
(шаги 1–2) **не расходует отдельного такта**, поэтому блоки `enter`, затем
`always`, затем проверка переходов стартового состояния отрабатывают **в том же
первом такте**. Это верно на **любом** уровне иерархии.

Ключевое следствие — **моментность не зависит от глубины вложенности**: чисто
структурное обёртывание модели (`model Mid { start S = Inner; }`) **не сдвигает**
потактовую трассу. Потактовые свойства модели (время до первого воздействия на
выход, проверки `--sim-file`, LTL-верификация) поэтому **композируемы**.

> **Единый эталон моментности — модель**, и симулятор, и порождённый C исполняют
> тело стартового состояния на такте 1 (фича 0033, версия языка 0.3.0). Прежде
> генератор C тратил по такту на каждый уровень иерархии на служебные
> `INIT`-переходы — это была бухгалтерия бэкенда, а не семантика языка; поведение
> **изменено** (ломающее для потактовой трассы, см. `CHANGES.md`).

**Пример (потактовая трасса совпадает у симулятора и порождённого C).** Модель
глубины 2, переменная `n` меняется по мере переходов:

```lam
model Counter {
    var n: u8 := 0;
    start S0 { always { n := 1; } ref S1; }
    state S1 { always { n := 2; } ref S2; }
    state S2 { always { n := 3; } }
}
start Entry = Counter;
```

| Такт | Симулятор `n` | Порождённый C `n` |
|------|---------------|-------------------|
| 1    | 1             | 1                 |
| 2    | 2             | 2                 |
| 3    | 3 (терминал)  | 3 (терминал)      |

**Контрпример (что было до 0033).** Тот же вход давал в C `n = 0, 0, …, 1, 2, 3` —
тело исполнялось лишь с `depth`-го такта, а трасса симулятора была `1, 2, 3` с
такта 1. Сдвиг рос с глубиной вложенности; теперь он нулевой.

### Переходы

```lam
ref NextState: условие;   // условный переход
next NextState;           // безусловный переход
```

Операторы в условии `ref`:

- `=` — проверка равенства; `&` — И; `|` — ИЛИ; `!` — НЕ
- Сравнения: `<`, `>`, `<=`, `>=`, `!=`

### Именованные условия

```lam
cond IsActive  = x = 1;
cond InRange   = x > 0 & x < 100;
cond Either    = IsActive | InRange;
cond NotActive = !IsActive;
```

### Инварианты и assert

Язык различает **определение условия** (`cond`) и **обязательство** — условие,
которое обязано быть истинным.

**`assert` языка Lam** — форма `: условие;` (краткая) и `: [Guard] условие;`
(явная). Проверяется в точке записи: симулятор останавливает прогон при
нарушении (`SIM-025`), а порождённый C эмитит `assert(...)` (флаг
`--guard-disable` убирает проверки из прошивки). Допустима как элемент модели, как
элемент состояния и как оператор в блоке кода:

```lam
always { x := step(x); : x <= 100; }   // assert после присваивания
```

**`invariant Имя = <Условие>;`** (фича 0044) — **именованное** обязательство,
проверяемое автоматически: на уровне модели — каждый такт, на уровне состояния —
пока автомат в этом состоянии.

```lam
var temp: u8 := 0;
invariant Safe = temp <= 100;   // на уровне модели: держится всегда
: [LTL] G(Safe);                // имя инварианта — атом LTL
```

Инвариант — сахар над `cond Имя = C;` + `: [Guard] Имя;`: имя становится **атомом
LTL** (`G(Safe)` — реляционное свойство, прежде невыразимое) и переиспользуемым
условием (`ref Next: Safe;`). Нарушение инварианта в симуляторе даёт
`SIM-025` **с именем** («нарушен инвариант 'Safe'»).

**Рекурсия невозможна, ассерты дороги — почему без имени нельзя?** Диагностика
«нарушено условие в строке 42» нечитаема; имя же указывает **что именно** нарушено
и делает обязательство переиспользуемым и проверяемым LTL-верификатором.

> **Контрпример.** Имя инварианта, совпадающее с уже объявленным `cond` или
> переменной, — ошибка `SE-054` (не молчаливая перезапись): смысл программы
> обязан быть определён. Слово `assert` ключевым **не** является — `var assert:
> u8;` остаётся валидным.

### Области видимости

- Переменные модели видны во всех вложенных состояниях.
- Переменные состояния видны только в нём.
- Разрешение: локальная область → состояние → модель → глобальный уровень.
- Затенение: локальное объявление скрывает одноимённое родительское.

### Кнопка и светодиод (направленные порты, внешние функции)

```lam
type u8 = [bit;8];

extern fn debug(msg: u8);

fn toggle(val: u8) -> u8 { return ~val; }

model ButtonLED {
    var state: u8 := 0;
```

### Симуляция: вычисления в теле блока

Симулятор (`simulation`) исполняет тела `enter`/`exit`/`always` и вычисляет
условия переходов. Значения приводятся к **объявленному типу** переменной при
записи — как в C.

```lam
var temperature: u8 := 0;

start Idle {
    always {
        var delta: u8 := 1;          // локальная переменная блока
        temperature := temperature + delta;
    }
    ref Heating: temperature > 10;   // переход по вычисленному значению
}

state Heating {
    enter { temperature := temperature + 5; }
}
```

Прогон: `temperature` растёт на 1 за такт; на 11-м такте условие `> 10`
выполняется, происходит переход в `Heating`, и его `enter` добавляет ещё 5.

### Проектирование состояний: состояние обязано удерживать управление

Частая ошибка проектирования — написать «шаг работы» там, где нужно «состояние
работы». Условия рёбер проверяются **каждый такт**, поэтому ребро, истинное сразу
после входа, выпускает управление раньше, чем состояние сделало работу.

**Контрпример** — охлаждение снимает 3 градуса за такт, а выйти можно при любой
положительной температуре:

```lam
start Cooling {
    always {
        for var i: u8 := 0; i < 3; i := i + 1 {
            if temperature > 0 { temperature := temperature - 1; }
        }
    }
    ref Done: temperature <= 0;   // мертво: сюда не попасть никогда
    ref Idle: temperature > 0;    // сработает на ПЕРВОМ такте: 101 → 98 > 0
}
```

Войдя со 101, модель уходит на первом же такте — охладив на 3 градуса из 101.
`Done` недостижим **при любом нагреве**: попасть в него можно, лишь войдя в
`Cooling` уже охлаждённым.

**Пример** — выход только по завершении работы; куда идти дальше, решает
отдельное условие:

```lam
cond Cooled = temperature = 0;
cond CyclesDone = count >= MAX_COUNT;

start Cooling {
    always {
        for var i: u8 := 0; i < 3; i := i + 1 {
            if temperature > 0 { temperature := temperature - 1; }
        }
    }
    ref Done: Cooled & CyclesDone;
    ref Idle: Cooled & !CyclesDone;
}
```

Приём: условия выхода — **непересекающиеся и покрывающие**, и оба требуют
`Cooled`. Состояние удерживает управление, пока не выполнит работу.

Оба фрагмента проверены прогоном (`simulation/tests/data/scenario/`), а
`examples/comprehensive.lam` построен на этом приёме: его сценарий
`Idle → Heating → Cooling → … → Done` **исполняется** и проверяется гейтом
достижимости — каждый пример каталога обязан иметь либо контракт сценария, либо
объявленное исключение с причиной.

**Усечение по типу** совпадает с поведением C (проверяется автоматической
сверкой с кодом, порождённым `lamc -t c`):

```lam
var x: u8 := 0;

start Idle {
    always {
        x := 255;
        x := x + 1;   // → 0   (обёртка mod 2⁸, как uint8_t в C)
        x := 300;     // → 44  (300 mod 256)
        x := 1 << 8;  // → 0   (продвижение до int, затем усечение при записи)
    }
}
```

### Симуляция: вызов функции и сравнение с вариантом `enum`

```lam
enum Mode { Auto = 0, Manual = 1 }

var mode: Mode := Manual;
var eta:  u8   := 0;

fn chebyshev(a: u8, b: u8, c: u8) -> u8 {
    var t: u8 := 0;
    t := a;
    if b > t { t := b; }
    if c > t { t := c; }
    return t;
}

start Idle {
    always { eta := chebyshev(5, 3, 7); }   // → 7 (метрика Чебышёва)
    ref Active: mode = Manual;              // сравнение с вариантом enum
}

state Active {
}
```

Примеры выше соответствуют фикстурам `simulation/tests/data/eval/` и покрыты
интеграционными тестами (`simulation/tests/eval_tests.rs`), поэтому не могут
разойтись с реальным поведением.

| CC-017 | Инициализатор массива не выразим в C (скалярный либо иной длины) |
| CC-018 | Условие перехода не переводится в C (причина — заметкой) |

### Где ошибка: `файл:строка:колонка`

Диагностика с позицией в исходнике печатается в формате `rustc`/`gcc` — он
машиночитаем и кликабелен в редакторах:

```text
$ lamc compile -t c -I lib main.lam
lib/badsem.lam:4:18: Ошибка компиляции [SE-002]: Ссылка 'Nowhere' не найдена
```

Назван **тот файл, где ошибка**, а не тот, что компилировали: ошибку внутри
импортированной библиотеки чинить нужно в библиотеке. При вложенном импорте
(`main → lib → deep`) назван самый внутренний файл — настоящий виновник.

Нумерация строк и колонок — с единицы; колонка считается в символах. Диагностика
без позиции в исходнике (например, ошибка кодогенерации) печатается **без**
префикса: выдуманные координаты отправили бы искать ошибку не туда.

Симулятор печатает позицию в том же формате — и это **одна и та же** функция, а
не договорённость: формат позиции задан один раз для всех инструментов.

```text
$ simulation -I lib main.lam --steps 3
Ошибка: lib/badsem.lam:4:18: [SE-002] Ссылка 'Nowhere' не найдена
```

Ошибки разбора симулятор показывает **все** сразу (`lamc` — первую): каждая со
своей позицией.

**`CC-018`: непереводимое условие — ошибка, а не мёртвый автомат.** Если условие
`ref`-перехода не транслируется в C, компиляция **прекращается** с указанием
целевого состояния, позиции `ref` в исходнике и исходной причины:

```text
Ошибка компиляции [CC-018]: условный переход в состояние 'Work' не переводится
в C: BitAccess на float-порт не поддерживается в условии
  примечание: причина [CC-001]: BitAccess на float-порт не поддерживается в условии
```

Прежде такой переход **молча** заменялся комментарием: `lamc` печатал
«Скомпилировано» и завершался с кодом `0`, а порождённый C собирался без
замечаний — но автомат терял ребро. Ошибка ломает ровно те сборки, которые были
сломаны и раньше, просто незаметно.

#### Условие по состоянию другой модели: `S(Модель) = Состояние`

`S(Модель)` — встроенная функция: **текущее состояние** модели. В C переводится
сравнением поля состояния в порождённой структуре:

```lam
model Pong {
    start Go {
        ref Stop: S(Ping) = Done;   // ждём, пока Ping не окажется в Done
    }
    state Stop;
}
```

```c
if (main->entry.ping0.state == SREF_PING_DONE) { … }
```

База пути зависит от родства: своя под-модель адресуется через свою структуру
(`model->…`), а модель-сестра — от корня (`main->…`), потому что корневая
структура владеет всеми под-моделями по значению. Работает и `!=`.

Имя состояния ищется **в модели-аргументе**, а не в той, где записано условие:
`S(Ping) = Done` — это `Done` **модели `Ping`**. Несуществующее состояние даёт
`SE-033` на стадии семантики.

**Скобки прозрачны** (фича 0074): `(S(Ping)) = Done`, `S((Ping)) = Done` и
`S(Ping) = (Done)` (любая вложенность) дают тот же результат, что бесскобочная
форма, — семантика канонизирует их в единой воронке разбора условий. Прежде они
отвергались с `SE-025`.

### Ошибки симуляции (SIM)

Ошибки времени выполнения симулятора. **Симулятор не подставляет значения по
умолчанию и не «пропускает» невычислимое молча**: любая из этих ошибок
останавливает прогон и даёт **ненулевой код возврата**.

| Код     | Описание                                                            |
|---------|---------------------------------------------------------------------|
| SIM-001 | Деление или остаток на ноль                                         |
| SIM-002 | Сдвиг на отрицательное число или ≥ 64 бит                           |
| SIM-003 | Значение не помещается в знаковый тип назначения                    |
| SIM-004 | Переполнение внутреннего 64-битного представления                   |
| SIM-005 | Операция не определена для операндов таких типов                    |
| SIM-006 | Значение нельзя привести к типу назначения                          |
| SIM-007 | Тип не поддерживается симулятором (например, структуры)             |
| SIM-008 | Не удалось разобрать вещественный литерал                           |
| SIM-009 | Переменная не найдена                                               |
| SIM-010 | Ошибка доступа к массиву (не массив, нецелый индекс, выход за границы) |
| SIM-011 | Ошибка доступа к биту (не целое, номер бита вне 0..64)              |
| SIM-013 | Сравнение с состоянием или моделью пока не поддерживается           |
| SIM-014 | Конструкция не поддерживается симулятором (строки и др.)            |
| SIM-015 | Пустое выражение/условие не может быть вычислено                    |
| SIM-016 | Неразрешённый узел не может быть вычислен                           |
| SIM-017 | Оператор пока не поддерживается симулятором                         |
| SIM-018 | Превышен предел итераций цикла (100 000)                            |
| SIM-019 | Внешняя функция без тела: симуляция значения невозможна             |
| SIM-020 | Встроенная функция пока не поддерживается симулятором               |
| SIM-021 | Неверное число аргументов при вызове функции                        |
| SIM-022 | Превышена глубина рекурсии (256)                                    |
| SIM-023 | Функция не вернула значение                                         |
| SIM-024 | `break`/`continue` вне цикла                                        |
| SIM-025 | Нарушен инвариант / Guard-формула (assert языка Lam)                |

**Контрпример — деление на ноль:**

```lam
var d: u8 := 0;
var x: u8 := 1;

start Idle {
    always { x := 10 / d; }
}
```

```
ОШИБКА вычисления на шаге 1: деление на ноль (SIM-001)
Симуляция остановлена: результат недостоверен.
```

**Контрпример — внешняя функция со значением:** у `extern fn` нет тела, поэтому
вычислить результат нельзя; симулятор отказывает, а не подставляет ноль.

```lam
extern fn calc() -> u8;

var x: u8 := 0;

start Idle {
    always { x := calc(); }
}
```

```
ОШИБКА вычисления на шаге 1: внешняя функция 'calc' не имеет тела:
симуляция значения невозможна (SIM-019)
```

> `extern fn` **без** возвращаемого значения (процедура) — не ошибка: вызов
> считается no-op, поскольку в симуляции нет платформенного слоя.

### Структуры в симуляторе (фича 0034)

Структуры **представимы и исполняются**: `var p: Point := {1, 2}` наблюдается как
структура (`Value::Struct`, объявленный порядок полей), `p.x` читается, `p.x := 7`
пишется точечно (не трогая `p.y`), `p.y := 300` при `y: u8` усекается до `44` —
как в порождённом C (сверено `cc`). Копия `q := p` разрешена; **сравнение
структур `p = q` не определено** (ошибка `SIM-005`) — согласование с C, который
запрещает `==` на структурах. Диагностики вместо тихой порчи: неизвестное поле
(`SIM-027`), `p.0` у структуры (`SIM-029`), поле у не-структуры (`SIM-012`),
арность `{…}` (`SIM-026`), несовпадение типа при `q := p` (`SIM-028`).

Ограничения: структура **без** инициализатора (`var p: Point;`) получает нулевые
поля; загрузка структур через `--load-state` не реализована (сохранение — да).

### Известные ограничения симулятора

- Строки в выражениях не поддерживаются — `SIM-014`.
- Сравнение с состоянием (`S(Ping) = End`) и моделью — `SIM-013`.
- Порождённый C заводит служебные такты инициализации, поэтому потактовые трассы
  симулятора и синтезированного кода **смещены**; совпадают установившиеся
  значения.
- `--save-state`/`--load-state` не сохраняют переменные модели.

### Структура сообщения об ошибке

```
Уровень:  Debug | Info | Warning | Error
Тип:      ParserError | SyntaxError | DeclarationError |
          TypeError | CastError | SemanticError | Warning
Позиция:  файл, строка, столбец (начало и конец)
Заметки:  дополнительный контекст
```

### Типичные ошибки пользователей

- Забытое `start` в модели → SE-011.
- Использование `:=` вместо `=` в условии (`if`, `cond`, `ref`) → присваивание
  вместо сравнения (в большинстве позиций условия — ошибка разбора).
- Запись в `in`-порт или чтение из `out`-порта → ошибка направления.
- Перекрывающиеся условия в `ref` → SE-042, недетерминированный переход.

## 8. Интеграция и реализация

### Конвейер компиляции

```
Исходный файл (.lam)
        │
        ▼
┌─────────────────┐
│   Лексер        │  lexer.rs — токены с позиционной информацией
└────────┬────────┘
         ▼
┌─────────────────┐
│   Парсер        │  LALRPOP (LR(1)) — Абстрактное синтаксическое дерево
└────────┬────────┘
         ▼
┌─────────────────┐
│   Семантический │  7 проходов → семантическое дерево + диагностика
│   анализатор    │
└────────┬────────┘
         ▼
┌─────────────────┐
│   Генератор C   │  c_header.rs (.h) + c_source.rs (.c)
└─────────────────┘
```

**Детерминированная генерация.** Один и тот же `.lam` компилируется в
**байт-в-байт одинаковый** код от прогона к прогону — для всех целей (`c`,
`c-hal`, `plantuml`, `st`, `st-at`, `rust`, `sv`). Порядок эмиссии задаётся **типом контейнера**
(`BTreeMap`, алфавитный порядок), а не привычкой отдельного бэкенда, поэтому
воспроизводимость получают все цели разом. Это делает возможными
codegen-снапшоты и осмысленный дифф порождённых файлов, а главное —
стабильный **ABI** прошивки: числовые значения `enum` портов и состояний
одинаковы при любой пересборке. Гарантируется гейтом `precheck.sh` (два прогона
на пример × цель → `diff -r`).

### Семантические проходы

| № | Проход            | Описание                                               |
|---|-------------------|--------------------------------------------------------|
| 0 | Скелет            | Извлечение имён моделей/состояний, загрузка импортов   |
| 1 | Композиция        | Разрешение составных состояний (`+ M1 M2`, `M1 \| M2`) |
| 2 | Выражения         | Разрешение переменных, вывод типов, порты              |
| 3 | Условия (`cond`)  | Разрешение именованных условий                         |
| 4 | Именованные блоки | Разрешение `enter`/`exit`/`always`                     |
| 5 | Функции           | Разрешение тел функций                                 |
| 6 | Переходы (`ref`)  | Замена `Condition::Unresolved` на разрешённые условия  |

### Запуск компилятора

```sh
# Компиляция в C
lamc compile --target c input.lam -o output/

# Результат:
# output/input.h  — заголовочный файл
# output/input.c  — реализация
```

#### Отображение типов Lam в типы C

| Тип Lam | Тип C | Пример объявления |
|---------|-------|-------------------|
| `bit` | `uint8_t` | `var fl: bit;` → `uint8_t fl;` |
| `bool` | `bool` | `var b: bool;` → `bool b;` |
| `u8`/`u16`/`u32`/`u64` (`[bit;N]`) | `uint{N}_t` | `var b: u8;` → `uint8_t b;` |
| `i8`/`i16`/`i32`/`i64` | `int{N}_t` | `var n: i16;` → `int16_t n;` |
| `float` | `double` (по умолчанию) | `var r: float;` → `double r;` |
| `float` при `--float-width=32` | `float` | `var r: float;` → `float r;` |
| `[T;N]`, где `T` ≠ `bit` | `T name[N]` | `var data: [u8;4];` → `uint8_t data[4];` |
| перечисление | `uint{N}_t` по максимуму варианта | `enum Mode {…}` → `uint8_t mode;` |
| структура | одноимённая `struct` | `var p: Point;` → `Point p;` |
| `unit` | `void` | тип возврата процедуры |

**Бит-вектор — не массив.** `[bit;8]` — это способ записать `u8`: в C он
**скаляр** `uint8_t`, а не массив из восьми элементов. Настоящий массив —
`[T;N]` с любым другим элементом, и в C он объявляется `T name[N]`. Ширина
бит-вектора ограничена {8, 16, 32, 64}: типа `uint128_t` в C нет, поэтому
`[bit;128]` отвергается диагностикой `CC-014` — а не порождает невалидный код.

**`float` — 8 байт по умолчанию.** `double` совпадает по точности с симулятором
(f64), поэтому проверка модели до синтеза сходится с прошивкой. Для платформ,
где 8-байтное чтение недопустимо, — `--float-width=32`; в цели `c-hal` это
меняет и ширину доступа к регистру порта (8 → 4 байта).

**Инициализация массива — только агрегатом.** Массив в C не присваивается,
поэтому `_init` заполняет его поэлементно:

```lam
var arr: [u8;4] := {0, 0, 0, 0};   // → model->arr[0] = 0; … model->arr[3] = 0;
```

Скалярный инициализатор массива (`var arr: [u8;4] := 0;`) цель `c` **отвергает**
(`CC-017`): язык не определяет, значит ли это «обнулить весь массив» или
«записать в первый элемент».

### Генерация Structured Text (IEC 61131-3)

Третья цель наряду с `c` и `plantuml` — **ST**, стандартный язык ПЛК. Модель Lam
ложится на него естественно: модель → `FUNCTION_BLOCK`, состояния → `CASE state OF`.

```sh
# Библиотека блоков: порты — входы/выходы FUNCTION_BLOCK, адреса не эмитятся
lamc compile -t st examples/stacker.lam -o out/

# Программа для ПЛК целиком: порты размещены по адресам
lamc compile -t st-at --address-map examples/elevator.plc.map examples/elevator.lam -o out/
```

**Цели `st` и `st-at` асимметричны — и это не косметика:**

| | `st` | `st-at` |
|---|---|---|
| Что порождает | **библиотеку блоков** | **программу для ПЛК целиком** |
| Порты | `VAR_INPUT` / `VAR_OUTPUT` блока | `VAR_GLOBAL … AT %IX256.0`; блоки видят их через `VAR_EXTERNAL` |
| Обёртка | не нужна | **обязательна**: `CONFIGURATION`/`RESOURCE`/`TASK`/`PROGRAM` |
| `--address-map` | игнорируется | потребляется |

Асимметрия навязана стандартом: `VAR_GLOBAL` **вне** `CONFIGURATION` недопустим,
тогда как отдельный `FUNCTION_BLOCK` принимается сам по себе.

#### Отображение

| Lam | ST |
|---|---|
| `model M` | `FUNCTION_BLOCK M` |
| состояния | `CASE state OF`; `INIT` — ветвь `0` (холодный старт ПЛК обнуляет `VAR`) |
| `ref T: cond;` (несколько) | `IF … ELSIF …` — порядок объявления сохраняется |
| `always` / `enter` / `exit` | тело ветви / инлайн в переход / перед `enter` цели |
| `M1 \| M2` | экземпляры под-блоков, последовательные вызовы, завершение по конъюнкции `is_done` |
| `M1 + M2` | вложенный `CASE` по счётчику шагов |
| `bit`/`bool` → `BOOL`, `u8`→`USINT`, `i16`→`INT`, `float`→**`LREAL`** | ⚠ `INT` в IEC — **16-битный** |
| `[u8; 4]` | `ARRAY [0..3] OF USINT` |
| `enum` | целое + именованные константы `<Enum>_<Вариант>` |
| `fn` | `FUNCTION`; возврат — присваивание **имени функции** |

#### Чего ожидать: ограничения IEC 61131-3

Модель Lam опирается на общий доступ к состоянию, которого в IEC нет ни у
функций, ни между POU. Всё разделяемое выражается **явной передачей**, поэтому
порождённый ST многословнее исходника:

- **Перечисления** не становятся перечислимым типом: явные значения вариантов —
  фича 3-й редакции, широко не поддержанная. Вместо этого целое + константы.
  В **телах** литерал печатается **по целевому типу** (как в `rust`/`sv`):
  `command := Stop` даёт `command := Command_Stop` (а не `:= 2`), а `flag := 0`
  при `flag : BOOL` — `flag := FALSE`. Так вывод согласован с объявлениями;
  значение без соответствующего варианта печатается числом (не догадываться).
- **Битового доступа `x.0` нет**: разворачивается в маску
  `(USINT_TO_BYTE(x) AND 16#01) <> 16#00`.
- **Побитовые операции** определены на битовых строках, а не на числах:
  `n & m` → `BYTE_TO_USINT(USINT_TO_BYTE(n) AND USINT_TO_BYTE(m))`.
- **`extern fn` невыразим**: `FUNCTION` обязана иметь тело, не может быть без
  параметров и не может возвращать `VOID`. Эмитится заглушка + предупреждение
  **`ST-009`** — в ПЛК она **ничего не сделает**, тело надо написать вручную.
- **LTL-формулы** не транслируются → предупреждение **`ST-010`**.

#### Внешняя карта адресов

`elevator.lam` написан под МК-адресацию (`0x10000000`) — для ПЛК это абсурдные
локации. Модель при этом **корректна** (для целей `c`/`c-hal`), поэтому её не
правят: ПЛК-локации держат отдельно, во внешней карте
([`examples/elevator.plc.map`](examples/elevator.plc.map)):

```
// Входы → %IX
sensors_1 = 0x0;      // → %IB0 вместо %IB268435456
```

Приоритет источников: inline `:=` < оператор `address` < внешняя карта. Оверлей
поверх inline даёт предупреждение `SE-050` на каждый порт — по замыслу.

#### Символьные адреса и `--define` (платформенные символы)

Выражение адреса — и у оператора `address`, и у inline-инициализатора — не
обязано быть литералом: оно **вычисляется** при сборке. В нём допустимы имена и
целочисленная арифметика (`+ - * / % << >> & | ^ ~`, унарные `+`/`-`, скобки):

```lam
const BTN_ADDR: u32 := 0x00200000;   // дефолт платформы, задокументирован в модели

in  BTN: bit;
out LED: bit;

address BTN = BTN_ADDR;              // символ
address LED = BTN_ADDR + 4;          // арифметика: модель описывает раскладку
```

Имя берётся **сначала** из `--define`, затем из `const` модели. Так один `.lam`
живёт на всех ревизиях: базу даёт платформа, раскладку — модель.

```sh
lamc compile -t c-hal -D BTN_ADDR=0x00300000 model.lam -o build/
lamc compile -t c-hal -DBASE=0x00200000 --address-map stm32.map model.lam -o build/
```

Три формы флага равнозначны и повторяемы: `--define N=V`, `-D N=V`, `-DN=V`.
Значение — литерал в **той же** грамматике, что запись внешней карты:
`0x…`/десятичное с необязательным `:бит` (`-D PIN=0x00200000:3`). Арифметика
остаётся **в модели**, где её видит ревьюер и форматтер, а не в командной строке.

**Границы (важно).**

- **Define виден только выражениям адреса.** Логика автомата от флагов сборки не
  зависит: `-D LIMIT=99` **не** изменит `ref Stop: cnt = LIMIT;` — там `const`
  сохраняет своё значение. Иначе флаг сборки мог бы молча переписать
  верифицированную модель.
- **Define — не источник адреса.** Приоритет остаётся прежним: inline `:=` <
  `address` < внешняя карта. `-D BTN=0x…` при отсутствии inline/`address`/карты
  адреса **не создаст** (даст `SE-052` и `DF-004`).
- **Адрес потребляет только `-t c-hal`** (и `st-at`). Вывод цели `c` от `-D` не
  зависит вовсе.

**Контрпримеры.**

```lam
const BTN_ADDR: u32 := 0x00200000;
address BTN = BTN_ADDR;      // + `-D BTN_ADDR=0x00300000`
// → адрес 0x00300000 (define главнее), предупреждение SE-053: перекрытие заметно

address LED = NOWHERE;       // → SE-054: символ не определён — назван по имени
address LED = x;             // x — var  → SE-055: адрес обязан быть известен при сборке
const A: u32 := B;
const B: u32 := A;
address LED = A;             // → SE-055: циклическая ссылка (не зависание)
```

| Код | Уровень | Условие |
|---|---|---|
| `SE-053` | предупреждение | define перекрыл одноимённую `const` в выражении адреса |
| `SE-054` | ошибка в `c-hal`/`st-at`, иначе предупреждение | неопределённый символ в выражении адреса |
| `SE-055` | ошибка в `c-hal`/`st-at`, иначе предупреждение | выражение не сворачивается в константу (`var`/порт/цикл) |
| `DF-001` | ошибка | негодный формат `--define` (нет `=`, негодное имя) |
| `DF-002` | ошибка | негодный литерал значения define |
| `DF-003` | ошибка | повторный `--define` для одного имени |
| `DF-004` | предупреждение | define не использован ни одним выражением адреса |

> До фичи [0042](docs/features/0042-address-defines.md) выражение адреса
> принимало **только литералы**: `address BTN = BTN_ADDR;` и
> `address BTN = 0x100000 + 4;` **молча теряли адрес**, а пользователь получал
> `SE-052` «порт не имеет адреса» — сообщение о следствии вместо причины.

#### Экспорт карты наружу — `lamc address-map` (фича [0043](docs/features/0043-address-map-export.md))

Разрешённую карту адресов можно **выгрузить** для сторонних инструментов
(генераторы HAL, отладчики, платформенные скрипты) — подкомандой
`lamc address-map`. Экспортируется **фактически разрешённая** карта: та же, что
потребляет `-t c-hal`, с учётом приоритета источников.

```sh
lamc address-map model.lam                                  # формат map в stdout
lamc address-map --emit json --address-map plat.map model.lam -o ports.json
```

Два формата:

| `--emit` | Назначение |
|---|---|
| `map` (умолчание) | `.ld`-подобный формат — **тот же**, что читает `--address-map`. Даёт **круговой рейс** `export → import → export` байт-в-байт: выгрузку можно подать обратно как `--address-map`. |
| `json` | Машиночитаемая выгрузка: на порт — имя, тип, направление, адрес (hex-строка), бит, источник; плюс `format`/`format_version`. Перечень источников **открыт** (потребитель обязан терпеть незнакомое значение). |

Выгрузка `map` для модели с тремя источниками адреса (inline / `address` /
внешняя карта):

```text
BTN = 0x40000000;
LED = 0x00200004;
SW = 0x00300000:3;
```

Правила выгрузки:

- **Порт без адреса опускается** в `map` (а `0x0` **не** подставляется — в
  выгрузке он неотличим от настоящего адреса); в `json` — явная пометка
  `"address": null`.
- **`SE-052`** (достижимый порт без адреса) **обрывает** экспорт (ненулевой код)
  — неполную карту наружу не отдаём, как и при сборке `c-hal`.
- Предупреждения (`SE-050` оверлей, `SE-051` висячая запись) идут в **stderr**;
  **stdout** — чистая выгрузка (её целиком разбирает `--address-map`).
- **CMSIS-SVD не поставляется**: `--emit svd` → ошибка. У Lam нет данных, которых
  требует его схема (peripherals, reset-значения, достоверная разрядность), а
  правдоподобный-но-неверный SVD для отладчика хуже его отсутствия (см. ADR 0043).

⚠️ Одноимённые порты разных под-моделей делят **плоский** ключ карты — в выгрузке
побеждает последний (унаследованное ограничение ядра 0020, задокументировано).

#### Проверка порождённого

Валидность ST доказывает внешний транспилятор **MatIEC `iec2c`** — юнит-тесты
проверяют лишь, что генератор напечатал задуманное. `precheck.sh` прогоняет гейт
по всему корпусу; установка — `scripts/ensure-iec2c.sh` (см. «Необязательные
зависимости»).

> ⚠ Гейт доказывает, что ST **валиден и компилируется**, но **не** что он ведёт
> себя как модель. Поведенческую эквивалентность даёт только сверка трасс.

### Генерация Rust (профиль `no_std`)

Пятая цель — **`no_std` Rust**: прошивка микроконтроллера. Ниша та же, что у
цели `c` (МК, HAL, жёсткое реальное время), поэтому цель обязана отвечать, что
она даёт **сверх** `c`. Ответ не «Rust лучше», а конкретные, зафиксированные в
репозитории дефекты цели `c`, которые здесь не воспроизводятся **by
construction**:

| Дефект цели `c` | В цели `rust` |
|---|---|
| [0026](docs/features/0026-c-root-typedef.md): у модели без под-моделей не эмитится typedef корня → порождённый C **не компилируется** | тип корня — обычная `struct`, отдельного объявления не требует |
| [0029](docs/features/0029-c-type-mapping.md): `[u8;4]` → `uint4_t` (типа не существует), `bit` → `int`, `Rational` → `float` ≠ f64 симулятора | `[u8; 4]` → `[u8; 4]`, `bit` → `bool`, `Rational` → `f64` — **точно** |
| `void *userdata` + указатели на функции: типобезопасности нет | `H: Hal` — параметр типа, проверяет компилятор |
| класс дефектов памяти | `#![forbid(unsafe_code)]` в шапке модуля |

```sh
lamc compile -t rust examples/elevator_mini.lam -o out/
# out/elevator_mini.rs
```

**Как подключить.** Порождается **один `.rs`-файл** — `Cargo.toml` генератор не
порождает и им не владеет (имя пакета, версия, edition, зависимости — ваши).
Файл подключается как модуль:

```rust
#![no_std]

#[path = "elevator_mini.rs"]
pub mod elevator_mini;

use elevator_mini::{ElevatorMini, Hal, InBitPort, OutBitPort};

/// Аппаратный слой поверх регистров вашей платы.
pub struct Board {
    inputs: u64,
}

impl Hal for Board {
    fn read_bit(&mut self, port: InBitPort) -> bool {
        (self.inputs >> (port as u8 as u32)) & 1 != 0
    }
    fn write_bit(&mut self, port: OutBitPort, value: bool) {
        let _ = (port, value); // здесь — запись в GPIO
    }
}

pub fn run() {
    let mut model = ElevatorMini::new(Board { inputs: 0 });
    model.init();
    loop {
        model.tick();
        if model.is_done() {
            break;
        }
    }
}
```

> Пример прогнан дословно (`rustc --edition 2021 --crate-type=lib -D warnings`)
> на выводе `examples/generated/rust/elevator_mini.rs`.

**`userdata` исчезает как понятие.** Состояние аппаратного слоя живёт в самом
типе-реализации, поэтому привести его не к тому типу невозможно, а «забыть
проставить колбэк» невозможно **by construction**: без `hal` модель не
конструируется.

**Атрибута `#![no_std]` в порождённом файле НЕТ — и это намеренно.** Он допустим
только в корне крейта; в файле, подключённом через `mod`, он даёт
предупреждение «the `#![no_std]` attribute can only be used at the crate root» —
то есть ломал бы **вашу** сборку под `-D warnings`. `no_std` — свойство крейта, а
не модуля: модуль просто не обращается к `std`, поэтому подключается и в
`no_std`-крейт, и в обычный (проверено). Совместимость доказывает гейт
`precheck.sh`: он кладёт вывод в корень с `#![no_std]` и компилирует.

**Проверочный крейт: `examples/generated/rust/`.** Порождённые примеры собраны в
Cargo-пакет — аналог `CMakeLists.txt` цели `c`. Он **не входит в workspace**
репозитория (своя таблица `[workspace]`): его содержимое перезаписывает `lamc`,
и под `cargo check`/`clippy` корня попадать не должно. Раскладка ровно в два
уровня — в корне порождённое (`elevator.rs`, …), в `src/` рукописное, — потому
что гейт заворачивает **каждый** `.rs` из корня в `#![no_std]`-крейт, а каркас и
`main`-ы печатают, то есть требуют std.

```sh
cargo run --manifest-path examples/generated/rust/Cargo.toml --bin stacker
```

На модель приходится один `main` (`src/bin/<модель>.rs`): он прогоняет автомат на
подставном железе и проверяет наблюдаемое поведение через `assert!` — у
`stacker`, например, приёмку груза и разряд батареи посреди дороги. Это второй
гейт цели, и проверяет он не то же, что первый: `rustc` + `clippy` доказывают,
что вывод **компилируется**, а молча неверная трансляция (перепутанный
приоритет, потерянный переход) компилируется тоже. `precheck.sh` гоняет оба.

**Границы цели** (каждая — диагностика, а не тихий пропуск):

| Код | Когда |
|---|---|
| `RS-004` | имя даёт `Self`/`self` — непредставимо ни как идентификатор, ни как `r#Self` (отдельное правило языка). Прочие ключевые слова спасает регистр (`type` → `Type`) или `r#type` |
| `RS-005` | два имени слипаются после приведения регистра (`floor_sensor` и `FloorSensor`) |
| `RS-011` | конструкция не транслируется (срез массива, `**`, строка вне `debug`) |
| `RS-014` | тип не представим; `RS-015` — `--float-width=32` (цель всегда даёт `f64`) |
| `RS-016` | тип порта не ложится на метод HAL (составной) |
| `RS-018` | чтение выходного порта либо запись во входной |
| `RS-021` | последовательная композиция (`+`) вложена в шаг другой `+` |
| `RS-022` | нужен HAL, но он в этой области недоступен |

**Функции получают состояние модели параметрами.** `fn`, читающая порт или
переменную модели, порождается свободной и получает нужное **параметром**: порт,
`extern fn` и `debug` требуют `hal: &mut H` (он идёт **последним** — иначе
`f(&mut hal, hal.read_u8(…))` заимствовал бы `hal` дважды), переменная модели —
параметр по значению. Нужда считается транзитивно по графу вызовов. В цели `c`
этого нет: там функция берёт `const Model *model` и читает через него всё сразу.

**Под-модель получает общие переменные корня структурой `Shared`.** Такт
под-модели не может взять указатель на корень (`self.cabin.tick(&mut self)` —
двойное заимствование), поэтому общие переменные свёрнуты в `<Root>Shared` и идут
**одним** параметром `&mut Shared` (фича 0059; `hal` — последним). Так арность
такта не зависит от числа общих переменных, и заглушки `#[allow]` в выводе нет.
Модель без разделяемых переменных `Shared` не получает.

Ловушки стандартной библиотеки, как у цели `st` (модель `Concat` ломает вывод),
здесь **нет**: `Box`/`Option`/`String` как имена моделей принимаются — Rust
различает пространство пользователя и прелюдию.

**Карта адресов ([0020](docs/features/0020-port-address-decl.md)) не
потребляется**: порты идут через HAL — это аналог режима `c`, а не `c-hal`.
`--address-map` с `-t rust` ничего не разместит. MMIO-режим (`rust-hal`) —
кандидат в расширения. `alloc` не используется: динамических структур в Lam нет.

**Идиоматичный возврат.** Lam всегда пишет `return` явно, а в Rust идиома —
хвостовое выражение (clippy: `return x;` последним оператором это
`needless_return`). Генератор сворачивает завершающий `return x;` в `x`, **включая
завершающий `if/else`** (фича 0058): `if c { return a; } else { return b; }` →
`if c { a } else { b }` (рекурсивно, цепочка `else if` — так же). Сворачивается
только когда сворачиваемы **обе** ветки; `if` без `else` и ранние выходы
сохраняют `return`.

**Гейт.** Порождённый `.rs` обязан приниматься `rustc` **и** `clippy` под
`-D warnings` (`precheck.sh`). Гейт **бесплатен**: инструменты уже являются
зависимостями проекта — в отличие от арбитра ST (`iec2c` собирается из
исходников). Политика `-D warnings` — не поза: она вынудила генератор не эмитить
недостижимые варианты состояний и лишний `hal`, то есть сделала вывод честнее.

> ⚠ Как и у ST, гейт доказывает, что Rust **компилируется**, но не что он ведёт
> себя как модель. Поведенческую эквивалентность даёт только сверка трасс.

### Генерация SystemVerilog (FPGA/ASIC)

Шестая цель и **первая аппаратная**. У `c`, `st` и `rust` такт модели — итерация
цикла: кто-то зовёт `_tick`. Здесь **такт Lam ≡ фронт тактового сигнала**
`posedge clk`, и это первое, что нужно понять автору модели: код не исполняется —
он **становится схемой**.

```sh
lamc compile -t sv examples/stacker.lam -o out/
# out/stacker.sv — один module на корневую модель
```

#### Служебные порты `clk` и `rst_n`

Модулю нужны два сигнала, которых в языке Lam нет. Их добавляет генератор:

```systemverilog
module stacker (
    input  logic clk,                 // служебный порт цели sv: в .lam его нет
    input  logic rst_n,               // служебный порт цели sv: сброс, активный низкий
    // … далее порты модели: сперва входы, затем выходы
    input  logic [7:0] task_stack_no, // in  task_stack_no: u8
    input  logic task_valid,          // in  task_valid: bit
    output logic cmd_fork,            // out cmd_fork: bit
    output logic is_done              // терминальность модели
);
```

> Показана выборка портов: полный заголовок `stacker.sv` несёт **11 входных
> портов модели и 6 выходных** плюс служебные `clk`/`rst_n` и `is_done`.
> Порядок — служебные, входы, выходы; внутри группы алфавитный (детерминизм,
> фича [0048](docs/features/0048-deterministic-codegen.md)).

Заводить `clock`/`reset` в самом языке было бы **ложью для четырёх целей из
пяти**: у прошивки и ПЛК такта как сигнала не существует. Поэтому `clk`/`rst_n` —
имена **цели**, а не ключевые слова языка. Порт модели с таким именем даёт
`SV-007`, и та же модель по-прежнему компилируется в `c`/`st`/`rust`.

#### Сброс несёт стартовое состояние — синтетического `INIT` нет

```systemverilog
always_ff @(posedge clk) begin
    if (!rst_n) begin
        state <= STACKER_STACKER;                       // стартовое состояние
        stacker_lift_controller_state <= STACKER_LIFT_CONTROLLER_LIFT_IDLE;
        cmd_fork <= 0;                                  // enter стартового состояния
    end else begin
        state <= state_next;
        stacker_lift_controller_state <= stacker_lift_controller_state_next;
    end
end
```

**Сдвиг такта равен нулю на любой глубине вложенности — и достаётся даром.** У
цели `c` синтетическое состояние `INIT` стоило по такту на уровень, и его
потребовалось *убирать* правкой ([0033](docs/features/0033-init-tick-alignment.md)).
Здесь его нет вовсе: регистр состояния физически не может «побыть в `INIT`», а
ветвь сброса кладёт стартовые состояния **всех** уровней одним фронтом. Проверено
автоматически против настоящего RTL на глубинах 1, 2 и 3
(`simulation/tests/conformance_sv_tests.rs`).

Отсюда единственное требование: **`enter` стартового состояния обязан быть
константным** (`SV-008`) — ветвь сброса синтезируется в цепь сброса триггеров и
выражений не вычисляет. Обход: перенести вычисление в `always` того же состояния
(вход такта не стоит, поведение не изменится). Именованная константа `const`
годится — она становится `localparam`.

#### Автомат: two-process

`always_comb` считает следующее состояние (**блокирующие** присваивания),
`always_ff` защёлкивает (**неблокирующие**). Это решение про семантику, а не про
стиль: тело состояния Lam императивно, и `v := 1; w := v;` обязано дать `w = 1` —
как в симуляторе и в `c`.

Фрагмент порождённого `stacker.sv` (под-модель `LiftController`, приведён
дословно):

```systemverilog
unique case (stacker_lift_controller_state)
    STACKER_LIFT_CONTROLLER_LIFT_IDLE: begin
        if (stacker_lift_request_next) begin
            cmd_fork_next = 1;                    // enter LiftOperating — инлайн
            stacker_lift_controller_state_next = STACKER_LIFT_CONTROLLER_LIFT_OPERATING;
        end
    end
    STACKER_LIFT_CONTROLLER_LIFT_OPERATING: begin
        if (((stacker_lift_request_next && (!stacker_lift_op_next)) && sense_loaded)) begin
            cmd_fork_next  = 0;
            stacker_lift_done_next = 1;
            stacker_lift_controller_state_next = STACKER_LIFT_CONTROLLER_LIFT_DONE;
        end
        else if ((!stacker_lift_request_next)) begin
            cmd_fork_next = 0;
            stacker_lift_controller_state_next = STACKER_LIFT_CONTROLLER_LIFT_IDLE;
        end
    end
endcase
```

Переходы — цепочка `if / else if`: **первый сработавший выигрывает**, как `break`
в C. Порядок рёбер значим.

#### Композиция `M1 | M2`: такт один на всю схему

Здесь преимущество RTL видно прямо. В `c` под-модели тикают **последовательно**,
и такт стоит суммы их работ; в RTL они работают **параллельно**, за один фронт.

Плата — **уплощение**: один `module` на корневую модель, логика под-моделей
инлайнится в общий `always_comb`. Иерархия модулей SV дерево моделей не
повторяет, и это не небрежность. `M1 | M2` в Lam означает «последовательно внутри
такта, в порядке объявления»: модель, идущая позже, видит записи предыдущей **в
том же такте**. Модуль-на-под-модель дал бы **комбинационную петлю** — проверено:
`verilator` отвечает `UNOPTFLAT`. Уплощение разрывает цикл там же, где его
разрывает такт в C. Регистры состояний при этом независимы.

#### Отображение типов

| Lam | C (дефект [0029](docs/features/0029-c-type-mapping.md)) | **SystemVerilog** |
|---|---|---|
| `bit` | `int` — 32 бита на один провод | **`logic`** — один триггер |
| `bool` | `bool` | `logic` |
| `u8` / `i16` | `uint8_t` / `int16_t` | `logic [7:0]` / `logic signed [15:0]` |
| `[u8; 4]` | `uint4_t` — типа не существует | `logic [7:0] data [0:3]` |
| `enum` | целое | `typedef enum logic [W-1:0] { … }` — имена видны в осциллограмме |
| `float` | `float` (f32) | **ошибка `SV-003`** |

Разрядность **буквальна**: в RTL машинного слова нет, округлять до 8/16/32/64 не
требуется. Ширина перечисления считается **по диапазону значений** (не по числу
вариантов): `enum Action { Idle = 670 }` требует десяти бит.

#### Сравнение целей

| | `c` | `c-hal` | `st` | `rust` | **`sv`** |
|---|---|---|---|---|---|
| Платформа | МК | МК | ПЛК | МК | **FPGA/ASIC** |
| Такт | вызов `_tick` | вызов `_tick` | скан-цикл | вызов `tick()` | **фронт `clk`** |
| `out cmd_fork: bit` | колбэк `write_bit` | `*(volatile*)0x500` | `VAR_OUTPUT` | метод трейта | **`output logic`** |
| `bit` | `int` (32 бита) | `int` | `BOOL` | `bool` | **`logic`** (1 провод) |
| `float` | `float` | `float` | `LREAL` | `f64` | **запрещён `SV-003`** |
| `extern fn` | прототип | прототип | заглушка | метод трейта | **запрещён `SV-005`** |
| Адрес порта | не эмитит | **потребляет** | `st-at` потребляет | не эмитит | **не потребляет** |
| Вход в старт | бесплатен (после 0033) | бесплатен | стоит такта | бесплатен | **бесплатен конструктивно** |
| `M1 \| M2` | последовательно, такт = сумма | то же | то же | то же | **параллельно, такт один** |

Карта адресов (`--address-map`) целью `sv` **не потребляется**: MMIO-адрес для
RTL бессмыслен — сигнал приходит на вывод кристалла, а не по адресу. Парной цели
`sv-at` нет.

#### Границы цели — и почему это границы, а не недоделки

Каждый запрет — не «пока не сделано», а свойство синтезируемого RTL. Диагностика
называет цели, где модель по-прежнему валидна.

| Код | Что | Почему |
|---|---|---|
| `SV-003` | `float` в типе **без** `--float-as-q` | В синтезируемом RTL плавающей точки **не существует**. `real` языка SV пригоден только для симуляции — синтезатор его отвергает. Снимается флагом `--float-as-q=m.n` (фича 0096): `float → q(m, n)`, синтезируемо. Без флага угадывать точность генератор не вправе — отсюда ошибка, а не умолчание |
| `SV-005` | `extern fn` | Вызова внешнего кода в RTL нет. DPI-C — механизм симуляции; аппаратный аналог «внешней функции» — отдельный модуль со своим интерфейсом, а `extern fn` не описывает ни портов, ни тактов, ни латентности |
| `SV-006` | `inout` | Двунаправленный порт — трёхстабильная шина, требующая сигнала `oe` (`assign pad = oe ? val : 1'bz;`). Lam его не выражает, и вывести нельзя: модель не сообщает, когда порт ведёт линию, а когда слушает |
| `SV-007` | порт с именем `clk`, `rst_n`, `is_done`, `state`, `state_next` | Эти имена генератор объявляет сам |
| `SV-008` | неконстантный `enter` стартового состояния | Ветвь сброса — цепь сброса триггеров, она не вычисляет |
| `SV-012` | имя = ключевое слово SystemVerilog (`fork`, `wire`, `time`, …) | Их около 250, и многие — обиходные имена автоматики. Аналог ловушки `Concat` у цели `st` |
| `SV-002` | цикл в теле, досрочный возврат из функции, `match`, срез массива | Цикл в RTL обязан разворачиваться в схему, то есть иметь границы, известные на этапе синтеза. Возврат печатается присваиванием имени функции (`return` не принимает yosys) и исполнение не прерывает |

**Композиция** — и параллельная `|`, и **последовательная `+`** (фича 0057).
Цепочке `A + B + (C | D) + E` даётся регистр шага (`<state>_step`): в
`always_comb` активен ровно один шаг, продвижение по завершении предыдущего
(«такт после», как `break` в C), последний шаг переводит родительское состояние.
`A + (B + C)` уплощается в плоскую цепочку; прямая вложенная `+` внутри
параллельного шага (`(A + B) | C`) даёт явную `SV-002` — не молча стоящий автомат.

Из корпуса цель транслирует `stacker.lam` и `elevator_mini.lam`. Отвергаются:
`elevator.lam` — `SV-005` (8 `extern fn`); `comprehensive.lam` — `SV-002` (цикл
`for`); `extend_complex.lam` — `SV-005` (`extern fn has_flag`; композиция `+`
тут поддержана, препятствие — не она).

Вне объёма: один тактовый домен и один сброс; CDC, множественные домены,
SDC/XDC, потолок частоты. Уплощение даёт длинную комбинационную цепь — это плата
за точную семантику `|`.

#### Как проверить вывод: нужны ОБА инструмента

```sh
verilator --lint-only -Wall out/stacker.sv
yosys -p "read_verilog -sv out/stacker.sv; synth -top stacker"
```

**Одного мало, и это проверено, а не предположено.** Инструменты ловят
**непересекающиеся** классы дефектов:

| Проба | `verilator --lint-only -Wall` | `yosys … synth` |
|---|---|---|
| `real` в `always_ff` | **принял молча**, код 0 | `ERROR: TOK_REAL`, код 1 |
| комбинационная петля | `UNOPTFLAT`, код 1 | **синтезировал молча**, код 0 |
| `return` в функции | **принял молча**, код 0 | `syntax error`, код 1 |
| ширина перечисления мала | `ENUMITEMWIDTH`, код 1 | **синтезировал молча**, код 0 |

То есть расхожее «`--lint-only` даёт проверку синтеза» **неверно**: Verilator —
линтер и симулятор, для него `real` легален. Оба гейта стоят в `precheck.sh` и в
CI.

> ⚠ Оба гейта доказывают, что RTL **валиден и синтезируем**, но не что он ведёт
> себя как модель: молча неверная трансляция синтезируется тоже. Поведенческую
> эквивалентность даёт только потактовая сверка трасс с симулятором
> (`conformance_sv_tests.rs`) — и она у цели `sv` строже, чем у `c`: сверяется
> значение на **каждом** такте.

#### Тестбенчи и осциллограммы для GTKWave

Для каждого транслируемого примера (`stacker`, `elevator_mini`) заведён
рукописный тестбенч в `examples/generated/sv/tb/` (фича
[0095](docs/features/0095-sv-testbenches.md)). Тестбенч делает две вещи:
прогоняет порождённый модуль на осмысленном сценарии, проверяя наблюдаемое
поведение `assert`-ами, и снимает осциллограмму `<module>.vcd` для
[GTKWave](https://gtkwave.sourceforge.net/):

```sh
# из examples/generated/sv/
verilator --binary --timing --trace --top-module tb tb/stacker_tb.sv stacker.sv -o simtb
(cd tb && ../obj_dir/simtb)     # пишет tb/stacker.vcd (и печатает OK/ошибку assert)
gtkwave tb/stacker.vcd
```

Сценарий — **замкнутая среда**: положение и датчики подаются обратной связью с
выходов модуля (тележка «телепортируется» к скомандованной цели, кабина ползёт к
целевому этажу), поэтому автомат проходит весь рабочий цикл без ручной подгонки
тактов. Обратная связь идёт только через регистры — комбинационной петли нет.

Тестбенч — **принадлежность проверки, а не продукта**: `lamc` его не порождает
(решение 0045-07). Он проверяет «событие когда-нибудь произошло» (устойчиво к
сдвигу такта); потактовую *эквивалентность* по-прежнему доказывает строгая
сверка `conformance_sv_tests.rs`. Сборку и прогон тестбенчей `precheck.sh`
выполняет отдельным гейтом — провал `assert` валит предкоммит; при отсутствии
`verilator` шаг мягко пропускается локально (в CI обязателен).

### Канонический форматтер (`lamc fmt`)

Приводит `.lam` к единому детерминированному стилю: воспроизводимые диффы,
отсутствие споров о форматировании, проверяемость в CI.

```sh
lamc fmt examples/            # отформатировать каталог на месте (рекурсивно, *.lam)
lamc fmt --check examples/    # проверить: код возврата ≠ 0, если нужен формат (CI)
cat a.lam | lamc fmt --stdin  # из stdin в stdout (редакторы, конвейеры)
```

Гарантии:

- **Идемпотентность:** `fmt(fmt(x)) == fmt(x)`.
- **Семантика не меняется:** `parse(fmt(x))` структурно равен `parse(x)`.
  Скобки, написанные автором, сохраняются; операторы `:=`/`=` не подменяются.
- **Комментарии сохраняются** — все три вида (`//`, `///`, `/* */`), в ведущей и
  хвостовой позиции. Пустые строки восстанавливаются, но не более одной подряд.
- **Выбор автора между синонимами сохраняется:** `while` не переписывается в
  `loop`, `: [Guard] x;` — в `: x;`.
- **Отказ вместо порчи:** если конструкция не поддержана печатью, `lamc fmt`
  сообщает об этом и возвращает ненулевой код — файл не трогается.

То же ядро используют `lamc fmt`, LSP (`textDocument/formatting`) и будущая
интеграция с IDE, поэтому стили инструментов не расходятся.

### Верификация модели (`lamc verify`)

Проверяет LTL-свойства модели методом **model checking** — исчерпывающим
перебором прогонов автомата, а не тестами. Ответ «свойство держится» —
доказательство, а не отсутствие найденных нарушений (фича 0049).

```sh
lamc verify model.lam                            # проверить все `: [LTL] φ;` файла
lamc verify --property "F Done" model.lam        # проверить одно свойство
lamc verify -p "G (Fault -> F Idle)" model.lam   # короткая форма
lamc verify --scope all model.lam                # + модели из import (по умолчанию: свой файл)
lamc verify --trace model.lam                    # + дамп конвейера (отладка)
```

Код возврата: `0` — все свойства держатся; `1` — есть нарушение, непроверяемое
свойство или ошибка разбора (пригодно для CI).

#### Что означает атом: абстракция управления

**Атом LTL — имя состояния.** `Fault` истинно ровно в те такты, когда автомат
находится в состоянии `Fault`. Проверяются свойства **управления**:

| Свойство | Формула | Смысл |
|---|---|---|
| Достижимость | `F Done` | автомат рано или поздно окажется в `Done` |
| Живость (отклик) | `G (Fault -> F Idle)` | после сбоя система обязана вернуться в `Idle` |
| Инвариант порядка | `G (Open -> X Closing)` | сразу за `Open` идёт только `Closing` |
| Отсутствие залипания | `G F Idle` | автомат бесконечно часто возвращается в `Idle` |

Модель абстрагируется до **графа переходов**: вершины — состояния, рёбра —
`ref`-переходы. **Условия переходов игнорируются** (любой `ref` считается
возможным), данные (`var`, порты, `cond`) в разметку не входят.

Важное следствие: если **все** выходы из состояния под условием, автомат вправе
задержаться в нём — такт, в котором ни один guard не сработал, состояния не
меняет (так же работает порождённый C). Поэтому у такого состояния есть переход
«в себя», и `F Done` на модели ниже **не держится** — прогон, вечно стоящий в
`Work`, реален:

```lam
var ready: bit := false;
start Work { ref Done: ready = 1; }   // ready может не стать 1 никогда
state Done;
```

Безусловный `ref` такой петли не даёт: он срабатывает на каждом такте.

Отсюда два следствия, которые нужно понимать при чтении вердикта:

- **«Держится» — надёжно.** Прогонов у абстракции не меньше, чем у реальной
  модели, поэтому свойство, истинное на всех прогонах абстракции, истинно и на
  всех реальных.
- **«Нарушено» — контрпример **в абстракции**.** Он может оказаться недостижим
  по данным (например, guard `error = 1` в реальности выполняется всегда, а
  абстракция считает, что он может и не сработать). Вывод помечает это явно.

#### Пример: свойство держится

```lam
// holds.lam — из Fault выход только через Recovery в Idle
: [LTL] G (Fault -> F Idle);

var error: bit := false;

start Idle {
    ref Fault: error = 1;
    ref Idle: error = 0;
}
state Fault { ref Recovery; }
state Recovery { ref Idle; }
```

```text
$ lamc verify holds.lam
СВОЙСТВО ДЕРЖИТСЯ: G (Fault -> F Idle)

Проверено свойств: 1; все держатся
```

#### Контрпример: свойство нарушено

Отличие от примера выше **ровно одно** — у `Fault` появилась самопетля, и
автомат научился залипать в сбое навсегда:

```lam
// fails.lam
: [LTL] G (Fault -> F Idle);

var error: bit := false;

start Idle { ref Fault: error = 1; }
state Fault {
    ref Fault: error = 1;   // ← залипание: сбой может длиться вечно
    ref Idle: error = 0;
}
```

```text
$ lamc verify fails.lam
СВОЙСТВО НАРУШЕНО: G (Fault -> F Idle)
  контрпример: Idle -> [ Fault ]*
  (абстракция управления: условия переходов не учитываются — контрпример может быть недостижим по данным)

Проверено свойств: 1; не держится/не проверено: 1
```

Контрпример — **лассо**: конечный префикс плюс цикл в скобках, повторяемый
бесконечно (`[ … ]*`). Читается как прогон автомата: `Idle`, затем `Fault`
навсегда. Это **какой-то** нарушающий прогон, не обязательно кратчайший:
префикс может оказаться длиннее необходимого — для доказательства нарушения
достаточно одного примера.

#### Контрпример: атом — не состояние

Свойства над данными в абстракции управления невыразимы. Верификатор не считает
их молча ложными, а **отказывается** проверять:

```lam
: [LTL] G temp;      // temp — переменная, а не состояние
var temp: u8 := 0;
start Heating { ref Cooling; }
state Cooling { ref Heating; }
```

```text
$ lamc verify atom_not_state.lam
СВОЙСТВО НЕ ПРОВЕРЕНО: G temp
  атом(ы) temp — не имена состояний проверяемой модели.
  Атом обязан быть именем состояния: проверяются свойства управления (достижимость, порядок, живость).
  Вне охвата: свойства над данными (`G (temp <= 100)`) и состояния вложенных моделей — их формулы объявляйте внутри самой модели.
```

Та же диагностика — на опечатку в имени состояния (`F Dane` вместо `F Done`) и
на состояние **вложенной** модели: у вложенной модели свой граф, поэтому её
свойства объявляются внутри неё:

```lam
model Engine {
    : [LTL] F Stop;        // проверяется по состояниям Engine
    start Run { ref Stop; }
    state Stop;
}
start Main = Engine;
```

```text
$ lamc verify nested.lam
СВОЙСТВО ДЕРЖИТСЯ [модель Engine]: F Stop
```

#### Область формулы: где объявлена, о том и говорит

Формула, объявленная **в теле состояния**, — сокращение для
`G (Состояние -> φ)`: «всякий раз, когда автомат попадает в это состояние,
дальше держится φ». Формула уровня модели областью не связана и проверяется от
стартового состояния.

```lam
var error: bit := false;

start Idle {
    ref Fault: error = 1;
}

state Fault {
    : [LTL] F Idle;        // читается как G (Fault -> F Idle)

    ref Fault: error = 1;  // ← самопетля: залипание в сбое
    ref Idle:  error = 0;
}
```

```text
$ lamc verify state_scope_fails.lam
СВОЙСТВО НАРУШЕНО: G (Fault -> F Idle)
  контрпример: Idle -> [ Fault ]*
  (абстракция управления: условия переходов не учитываются — контрпример может быть недостижим по данным)
```

Печатается **проверенная** формула (`G (Fault -> F Idle)`), а не авторская
запись: вердикт обязан говорить о том вопросе, на который отвечал.

Убрав самопетлю `ref Fault` (пример `state_scope_holds.lam` — из `Fault`
единственный путь ведёт через `Recovery` обратно в `Idle`), получаем:

```text
$ lamc verify state_scope_holds.lam
СВОЙСТВО ДЕРЖИТСЯ: G (Fault -> F Idle)
```

Область — свойство **состояния**, а не текста: формула в именованном блоке
состояния (`enter`/`exit`/`always`) связывается тем же состоянием — блок
исполняется, лишь когда автомат в нём. Формула в теле функции области не
получает (функцию вправе позвать любое состояние) и проверяется от старта.

#### Область проверки: свой файл, а не чужая библиотека

Дерево модели содержит и **импортированные** модели. Проверять их заодно нельзя:
нарушенное свойство чужой библиотеки роняло бы сборку тому, кто её лишь
импортировал, — а чинить чужой `: [LTL]` он не вправе.

Поэтому `lamc verify` проверяет **модели своего файла**; пропущенное
перечисляется — молча сузить область значило бы выдать «все держатся» за
«проверено всё»:

```text
$ lamc verify main.lam
СВОЙСТВО ДЕРЖИТСЯ: F Done

Не проверено (вне области): 1 — модели из импортов: Badlib
  --scope all — проверить их тоже.

Проверено свойств: 1; все держатся
```

```sh
lamc verify main.lam               # по умолчанию: --scope file
lamc verify --scope all main.lam   # проверить и импортированные модели
```

Область считается **по происхождению**, а не по вложенности: `model`, объявленная
в самом файле, проверяется всегда — включая её вложенные модели. Отсекается лишь
то, что пришло через `import` (любой из трёх форм), причём **поддеревом целиком**:
вложенные модели чужого файла — тоже не ваши.

#### Как это работает и как отлаживать

Конвейер — стандартный автоматный подход: по **отрицанию** свойства строится
автомат Бюхи `A_¬φ` (его язык — нарушающие прогоны), берётся произведение
`K × A_¬φ`, и проверяется пустота языка (поиск достижимого принимающего цикла
вложенным DFS). Пусто ⟹ нарушить свойство нечем ⟹ оно держится. Непусто ⟹
найденный цикл и есть контрпример-лассо.

Флаг `--trace` печатает все три звена — это основной инструмент отладки, когда
вердикт кажется неожиданным:

```text
$ lamc verify --trace --property "F Done" unreachable.lam
=== Структура Крипке (абстракция управления) ===
  Done -> Done
  Wait -> Work
  Work (start) -> Wait
=== Формула F Done ; автомат строится по отрицанию !(F Done) — его язык суть нарушающие прогоны ===
=== Автомат Бюхи (GPVW) ===
Начальные состояния: {0}
Принимающие состояния: {0}
s0 : { !Done }
  переходы -> s0
=== Произведение K x A_!phi (2 состояний, 2 принимающих) ===
  (Work,q0) (нач., принимающее) -> (Wait,q0)
  (Wait,q0) (принимающее) -> (Work,q0)
СВОЙСТВО НАРУШЕНО: F Done
  контрпример: Work -> [ Wait -> Work ]*
```

Трасса сразу показывает причину: в структуре Крипке в `Done` не ведёт ни одно
ребро, поэтому цикл `Work → Wait → Work` живёт вечно, ни разу не попав в `Done`.

Проверка **всегда завершается**: структура Крипке конечна по построению (число
вершин = число состояний FSM). Вердикт детерминирован — тот же вход даёт тот же
ответ.

#### Ограничения (текущий срез)

- Свойства над данными (`G (temp <= 100)`) не проверяются — атом обязан быть
  именем состояния. Расширение (explicit-state или символьный MC) строится
  поверх готового конвейера.
- Условия переходов абстрагированы, поэтому возможны ложные срабатывания
  (контрпример недостижим по данным). Обратной ошибки — пропуска нарушения —
  абстракция не даёт.
- `--property` проверяется против **корневой** модели файла; свойства вложенных
  моделей объявляйте внутри них (`lamc verify` без флага проверит все).
- **Импортированные модели по умолчанию не проверяются** — см. «Область
  проверки» ниже; `--scope all` возвращает проверку всего дерева.
- **Очень большие модели** (тысячи состояний) могут исчерпать стек: обходы
  рекурсивны. Для типичных моделей (десятки состояний) запаса достаточно.

### Порты ввода-вывода

```lam
model Motor {
    out Enable: bit;   // запись
    out Speed:  u8;
    in  Sensor: bit;   // чтение
    in  Limit:  bit;
}
```

- **`out`-порт**: модель пишет в него; чтение — ошибка.
- **`in`-порт**: модель читает из него; запись — ошибка.

При кодогенерации создаются отдельные enum-типы и типизированные функции для in/out.

### Адресные литералы (MMIO)

Инициализатор **порта** — это его **адрес** (а не начальное значение): порт
отображается на аппаратный регистр. Форма `адрес:бит` задаёт позицию бита в
слове; голый адрес позицию бита не задаёт.

```lam
out LED : u8  := 0x00100000;      // порт LED по адресу 0x00100000
in  BTN : bit := 0x00200000:0;    // бит 0 слова по адресу 0x00200000
in  FLAG: bit := 0x00200000;      // адрес без указания бита (фича 0070)
```

Проверка «значение типа `bit` — только 0 или 1» (`SE-035`) к инициализатору
**порта не применяется** — это адрес, а не значение (фича 0070); для обычных
`var`/`const` типа `bit` она сохраняется — контрпример `var f: bit := 5;` даёт
`SE-035`. Прежде голый адрес на `bit`-порту ошибочно отвергался этой проверкой
(тогда как `u8`-порт его принимал).

**Переход к декларации в `lam-lsp`** (фича
[0056](docs/features/0056-lsp-goto-exact-file.md)). Курсор на имени модели —


модель, чьи импорты лежат в общей библиотеке вне её каталога, `lam-lsp` не
найдёт, хотя `lamc -I lib` её собирает.

плюс страницу настройки цветов, комментирование (Ctrl+/) и подсветку парных
скобок. С фичи 0023 — **переход к декларации** (`Ctrl/⌘+Click`, `Ctrl/⌘+B`) для

также **переход по строке-пути `import`** к файлу `.lam`. Сборка/установка — см.

| Лексические       | Корректное разбиение на токены        |
| Синтаксические    | Построение AST из допустимых программ |

| Эталонные примеры | Полный прогон из `examples/`          |

### Сборка из исходников

**Требования:** Rust 1.75+, LALRPOP (генерируется автоматически через `build.rs`).

```sh
git clone https://github.com/Pastor/BuT.git
cd BuT
cargo build --release --bin lamc
cargo install --path grammar --bin lamc
```

#### Необязательные зависимости (проверка порождённого кода)

Нужны только для проверки того, что компилятор породил **валидный** код целевого
языка. Сборка и тесты `lamc` без них проходят полностью.

| Инструмент | Зачем | Что проверяет |
|---|---|---|
| `cmake` + `ninja` + C-компилятор | гейт цели `c` (`scripts/precheck.sh`) | порождённый C компилируется |
| **MatIEC `iec2c`** | гейт цели `st` (фича 0041) | порождённый Structured Text компилируется |

**MatIEC** — открытый транспилятор ST → ANSI C; пакетом дистрибутивов **не
поставляется**. Ставить руками не нужно: `precheck.sh` сам проверяет наличие и
при отсутствии собирает из исходников. Тем же скриптом можно вызвать отдельно:

```sh
scripts/ensure-iec2c.sh          # → ~/.local/bin/iec2c (≈15 с; повторный вызов мгновенный)
IEC2C_SKIP=1 scripts/ensure-iec2c.sh   # отключить (оффлайн/CI)
```

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `IEC2C_PREFIX` | `~/.local` | Куда ставить (`$PREFIX/bin/iec2c`) |
| `IEC2C_SRC` | `~/.cache/matiec` | Куда клонировать исходники |
| `IEC2C_SKIP` | — | `1` — пропустить проверку целиком |

Ручной прогон (`-I` обязателен — без библиотеки `ieclib.txt` инструмент падает
на любом входе):

```sh
~/.local/bin/iec2c -I ~/.local/share/matiec/lib -T /tmp/out файл.st   # код 0 = ST валиден
```

⚠ **macOS:** системный `bison` — версии 2.3, а `configure` требует ≥ 2.4
(`Wrong bison version: 2.3 < 2.4`). Нужен `brew install bison`; скрипт сам
подхватывает `/opt/homebrew/opt/bison/bin`, а при слишком старом bison мягко
пропускает сборку, не роняя предкоммит. На `ubuntu-latest` bison 3.x —
препятствия нет.

⚠ `make install` MatIEC ставит **только бинарники**: библиотеку стандартных
функций (`lib/`) скрипт копирует сам в `$PREFIX/share/matiec/lib`.

Гейт ST **подключён и зелён**: цель `st` дозрела (тела `FUNCTION_BLOCK`
эмитятся), и `iec2c` принимает **весь** корпус `examples/` (8/8 валидны).
Подробности — [`docs/features/0041-st-backend.md`](docs/features/0041-st-backend.md).

### Непрерывная интеграция (фича 0090)

CI (`.github/workflows/ci.yml`) прогоняет **весь** `scripts/precheck.sh` под
строгим режимом (`PRECHECK_STRICT=1`) — **единый источник истины гейтов**: логики
проверок в самом workflow нет, он лишь ставит инструменты (cmake/ninja/verilator/
yosys/bison/flex + сборка `iec2c`) и делает один вызов скрипта. Под строгим
режимом отсутствие любого инструмента — **ошибка** (а не мягкий пропуск: иначе
пропущенный гейт зелёный и неотличим от пройденного), а формат **проверяется**
(`cargo +nightly fmt --check`). Локально без флага поведение прежнее: мягкие
пропуски, `fmt` применяется. Так `main` защищён тем же барьером, что и коммит
разработчика — все семь целей и инфраструктурные гейты (воспроизводимость,
float→q, канон формата, ссылки) проверяются вживую.

## 10. Расширение и версии

### Версия

**Версия языка: 0.3.0** (крейт `grammar`). Документ актуален для ветки `v2`.
Список изменений — в файле [`CHANGES.md`](CHANGES.md).

> **0.2.0 → 0.3.0 (фича 0029, решение заказчика):** отображение типов Lam в типы
> C приведено к явному и проверяемому виду. Меняется **наблюдаемая семантика
> порождаемого кода**, а не синтаксис языка: `float` → `double` (8 байт, было
> 4 — совпадение с точностью симулятора f64), `bit` → `uint8_t` (было `int` —
> 32 бита со знаком), `[T;N]` при `T` ≠ `bit` → настоящий массив `T name[N]`
> (было `uint{N}_t` — несуществующий тип). Правки `.lam`-исходников **не
> требуется** — изменение выражается в перегенерации C; автомиграция не нужна.
>
> Ужесточения: `[bit;128]` → `CC-014` (типа `uint128_t` в C нет), скалярный
> инициализатор массива → `CC-017`. Оба прежде давали **невалидный C**, то есть
> ни одна работавшая программа не сломана.
>
> **Версия 0.3.0 накапливает изменения** (правило 22): фичи 0031, 0033, 0042,
> 0044 вносят свои изменения в **уже поднятую** версию, не поднимая её снова.
> **Фича 0031** (реализована): вызов функции из тела функции — композиция `f→g`
> внутри модели (аддитивно: ранее отвергавшиеся программы компилируются, смысл
> валидных не меняется); рекурсия запрещена диагностикой `SE-053`. См.
> «Функции».
> **Фича 0044** (реализована): именованный инвариант `invariant Имя = <Условие>;`
> (аддитивно: одно жёсткое ключевое слово, `assert` не вводится) + оживление
> Guard-формул в симуляторе (`SIM-025` вместо тихого пропуска). См. «Инварианты
> и assert».
> **Фича 0033** (реализована): вход в стартовое состояние больше не расходует
> такт — тело исполняется на такте 1 на любой глубине, как в симуляторе. Ломающее
> изменение **наблюдаемой семантики такта** (не синтаксиса): порождённый C
> меняется, прошивки при пересборке стартуют на `depth` тактов раньше; `.lam` не
> правятся. См. «Семантика первого такта».

> **Аддитивное расширение в 0.3.0 (фича 0042):** выражение адреса
> **вычисляется** — допустимы имена (`--define`, затем `const` модели) и
> целочисленная арифметика. Прежде принимались только литералы, а символьная и
> арифметическая формы **молча теряли адрес**. Совместимость полная: ни одна
> валидная программа не меняет смысла — валидными становятся те, что прежде
> отвергались. См. «Символьные адреса и `--define`».

> **Аддитивное расширение 0.1.0 → 0.2.0 (фича 0020):** оператор задания адреса
> порта `address Имя = <адрес>;` (жёсткое ключевое слово `address`), внешняя
> `.ld`-подобная карта адресов (`--address-map`) и цель генерации `-t c-hal`
> (таблица адресов + дефолтный HAL). Совместимость полная — инлайн-адрес
> `in P: T := <addr>;` работает как прежде.

> **Слом совместимости 0.0.x → 0.1.0 (фича 0021):** присваивание записывается
> `:=` (было `=`), сравнение на равенство — `=` (было `==`); оператор `==`
> выведен. Реляционный `<=` без изменений. Старые `.lam` переводятся
> AST-мигратором (см. `docs/development/0021-03-tool/`).

### Композиция моделей

Lam поддерживает два вида сборки систем:

```lam
// Последовательная: Init → Startup (после завершения Init запускается Startup)
start Sequential = Init + Startup;

// Параллельная: Run и Halt работают одновременно
start Parallel = Run | Halt;

// Комбинированная
start System = (Init + Startup) + (Run | Halt);
```

### Формулы и ассемблерные вставки

Для встраивания платформо-зависимого кода или формальных спецификаций:

```lam
assembly "arm" {
    // платформо-зависимый код
}

formula "ltl" {
    always(active())
    eventually(done())
}
```

**LTL-аннотации** (`: [LTL] φ;`) — свойства линейной темпоральной логики прямо в
модели, состоянии или блоке кода. Операторы: `X` (next), `F` (eventually),
`G` (always), `U` (until), `R` (release), `!`, `&`, `|`, `->`. **Атом — голое
имя** (переменной, состояния или `cond`); вызовы функций в атоме не допускаются:

```lam
var a: u8 := 0;
var b: u8 := 0;
start c { : [LTL] G (a -> F b), X c; }   // атомы a, b — переменные; c — состояние
```

> **Статус (фичи 0035, 0049).** LTL-формула **разбирается** на всех трёх уровнях
> (модель/состояние/блок) — прежде в блоке она молча терялась (0035).
> **Управляющие свойства проверяются** подкомандой
> [`lamc verify`](#верификация-модели-lamc-verify) (0049): атом = имя состояния.
> Свойства **над данными** (атом-переменная, как `a`/`b` в примере выше) пока не
> проверяются ничем — о чём сообщает предупреждение `SE-055` на каждую формулу
> при компиляции. Неизвестный атом (опечатка) даёт `SE-056`.

### Расширение языка

Добавить новую конструкцию в Lam:

1. Расширить грамматику в `grammar/src/grammar.lalrpop` и `lexer.rs`.
2. Добавить узел AST в `ast.rs`.
3. Реализовать семантический проход в `semantic/tree.rs`.
4. При необходимости — расширить кодогенератор в `generator/c/`.
5. Добавить тесты в `tests/data/valid/` и `tests/data/invalid/`.

Полная грамматика находится в файле [`Lam.ebnf`](Lam.ebnf).
