# Задача 0037-03: Windows в матрице CI

> Фича: [../features/0037-windows-test-failures.md](../features/0037-windows-test-failures.md) · ADR: [../adr/0037-windows-test-failures.md](../adr/0037-windows-test-failures.md) · анализ: [../analyze/0037-windows-test-failures.md](../analyze/0037-windows-test-failures.md) · тест-план: [../tests/0037-windows-test-failures.md](../tests/0037-windows-test-failures.md)

## Что было

**Реальное состояние на 2026-07-15** (ветка `v2`, коммит `6984471`; установлено
чтением `.github/workflows/ci.yml` — файл целиком, 29 строк).

### Windows в CI отсутствует. Матрицы нет вообще

```yaml
on: [ push ]

name: build

jobs:
  ubuntu:
    name: Ubuntu
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Install latest nightly
        uses: actions-rs/toolchain@v1
        with:
          toolchain: nightly
          override: true
          components: rustfmt, clippy

      - name: Сборка
        uses: actions-rs/cargo@v1
        with:
          command: build
          args: --all-features --all-targets --examples
      - name: Проверка
        uses: actions-rs/cargo@v1
        with:
          command: check
      - name: Тестики
        uses: actions-rs/cargo@v1
        with:
          command: test
```

**Единственный job — `ubuntu`.** Ни `strategy.matrix`, ни `windows-latest`, ни
`macos-latest`. Триггер — только `push` (нет `pull_request`).

### Это и есть корневая причина фичи 0037

Оба класса дефектов (5 тестов `lamc`, 1 тест `viewport`) пролежали в репозитории
до тех пор, пока разработчик **случайно** не собрал проект на Windows при работе
над фичей [0021](../features/0021-swap-assign-compare.md). Показательно, что
дисциплина `cfg` в `lamc.rs` **уже существовала** (тесты `split_*`, строки
713–780), но не доехала до соседней секции тестов — и это никем не было
замечено. **Правка шести тестов без CI лечит симптом:** следующий зашитый `:`
или `/tmp` приедет тем же путём.

Дополнительно: продукт содержит `#[cfg(windows)]`-ветки
(`split_include_dirs`, `lamc.rs:108–111`), которые **не собирает и не исполняет
никто** — по факту это мёртвый код.

### Наблюдения по тому же файлу (в объём 0037-03 НЕ входят)

Установлено чтением; вынесено в бэклог решением ADR (правило 7 — не смешивать
с предметом фичи, правило 2 — декомпозиция):

1. **`cargo test` без `--test-threads=1`.** `CLAUDE.md` и
   `scripts/precheck.sh:22` требуют однопоточного прогона «иначе гонки за общие
   файлы», а CI гоняет параллельно. На Windows с его блокировками файлов цена
   гонки выше. Правка однострочная, но меняет **контракт прогона для всех
   платформ** → отдельный кандидат.
2. **`actions-rs/*` не поддерживаются** (архивированы автором), `actions/checkout@v2`
   устарел. Модернизация (`dtolnay/rust-toolchain`, `checkout@v4`) задевает
   **весь** CI, а не Windows-часть → отдельный кандидат.
3. **macOS не в матрице**, хотя разработка ведётся именно на darwin. Отвергнуто
   в рамках 0037 (ADR, Option J): к шести падениям отношения не имеет, утраивает
   площадь стабилизации → отдельный кандидат.
4. **Нет триггера `pull_request`** — прогон только на `push`.

**Ни одно из наблюдений 1–4 в 0037-03 не правится.** Задача добавляет job
`windows` **по образцу существующего `ubuntu`**, ничего в нём не меняя: иначе
первый Windows-прогон окажется неотличим от регресса, вызванного модернизацией
CI.

### Что нельзя установить чтением

**Ни один прогон на Windows недоступен.** Всё, что известно о поведении там, —
из чтения кода и [отчёта 0021](../reports/0021-swap-assign-compare.md) (Windows 11,
nightly **gnu + MinGW**: `simulation` 149/150, 5 тестов `lamc`). Соберётся ли
проект на `windows-latest` (**MSVC**) — **не проверено**. Кандидаты риска (не
проверено, гадать не следует): сборка LALRPOP из git, системные шрифты
`fontdb`/`resvg` (`simulation/src/gif.rs:40` — `load_system_fonts()`), длинные
пути, блокировки файлов при параллельном прогоне.

## Что сделано

> **Планируется (разработка не начата).** Ниже — план по решению **Option H**
> ADR 0037; ни строки YAML ещё не изменено.

**Суть:** добавить job `windows` на `windows-latest` с теми же шагами, что
`ubuntu`, временно неблокирующим; прогнать; снять `continue-on-error`.

**Порядок обязателен: подзадача выполняется ПОСЛЕ**
[0037-01](0037-01-windows-test-failures.md) **и**
[0037-02](0037-02-viewport-tmp-write.md) — она проверяет их результат. Обратный
порядок даёт заведомо красный первый прогон и лишает job диагностической
ценности.

**План правки** (`.github/workflows/ci.yml`, аддитивно — job `ubuntu` не
трогается):

1. Добавить job `windows` — копия `ubuntu` с `runs-on: windows-latest`,
   `name: Windows`, тем же nightly и теми же тремя шагами (`build --all-features
   --all-targets --examples`, `check`, `test`). ABI — **умолчание платформы
   (MSVC)** (ADR, Decision, условие 4); расхождение с MinGW отчёта 0021 принято
   осознанно.
2. Проставить job **`continue-on-error: true`** (R8): фича не должна блокироваться
   чужими, ещё не разобранными дефектами Windows (ADR, Decision, условие 1).
3. **Прогнать** и разобрать лог:
   - **шесть известных тестов** обязаны быть `passed` — это критерии A8/A9 и
     единственное настоящее доказательство работы 0037-01 и 0037-02. В отчёте их
     имена перечисляются **явно**, а не «всё зелено»;
   - **любые новые падения** (сверх шести) — **не чинить** здесь (R9): завести
     кандидатами в `FEATURES.md` (правило 7) со ссылкой из отчёта. 0037 отвечает
     ровно за шесть перечисленных;
   - если проект **не соберётся** на MSVC — откат на `-gnu` (`toolchain:
     nightly-x86_64-pc-windows-gnu`) решается внутри этой подзадачи, тогда
     окружение совпадёт с отчётом 0021.
4. **Снять `continue-on-error`** отдельным коммитом после первого зелёного
   прогона (R8, A11, критерий T12). **До снятия фича 0037 не переводится в
   `ГОТОВО`** — иначе получится нескончаемо жёлтый job, который никто не читает
   (ADR, Decision, условие 2).

**Статус по функциональности (правило 11):**

| Функциональность | Работа | Обоснование |
|---|---|---|
| Контракт прогона CI | **да, аддитивно** | Добавляется job; `ubuntu` не меняется; `--test-threads=1` здесь **не** вводится (кандидат бэклога) |
| CLI `lamc` | **н/п** | Не затрагивается |
| Публичный API `grammar` / `simulation` | **н/п** | Не затрагивается |
| Язык Lam | **н/п** | Не затрагивается; версия языка **0.2.0** без изменений (правило 22) |
| Генераторы C / PlantUML | **н/п** | Не затрагиваются; на Windows впервые **проверяются** — новое покрытие, не новое поведение |
| Тесты `lamc` / `simulation` | **н/п** | Подзадачи [0037-01](0037-01-windows-test-failures.md), [0037-02](0037-02-viewport-tmp-write.md); здесь они только **прогоняются** |

**Роль подзадачи и честная оговорка.** Эта подзадача — **единственный
поставщик доказательств** по всей фиче: критерии A8/A9 непроверяемы локально
(на darwin все шесть тестов зелены и до, и после правок — эталон 44/44 и 1/1),
а `cargo check --target x86_64-pc-windows-msvc` проверяет лишь
**компилируемость** `cfg(windows)`-веток, не исполняя их. До первого прогона job
`windows` статус починки по фиче — **гипотеза, основанная на чтении кода**;
отчёт о тестировании (правило 20) обязан сказать это прямо, а не сгладить.

**Критерий A11 (снятый `continue-on-error` при зелёном прогоне) — условие
перехода фичи 0037 в `ГОТОВО`.**
