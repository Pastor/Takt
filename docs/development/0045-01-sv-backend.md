# Задача 0045-01: Каркас бэкенда — `Language::SV`, `generator/sv/`, `SvMap`, цель `-t sv`

> Требования: **R1**, **R2**, **R3**, **R10**. Критерии: **A1**, **A2**, **A12**.
> Порядок: **первая**; за ней — [0045-02](0045-02-validation.md) (гейт).

## Что было

Состояние кода на 2026-07-15 (проверено чтением, номера строк актуальны).

### `grammar/src/generator/mod.rs` — 96 строк, весь слой диспетчеризации

- **Строка 14 — `enum Language`.** Ровно два варианта: `C`, `PlantUML`.
  Помечен **`#[non_exhaustive]`** (строка 13) с комментарием: «список целевых
  языков будет расширяться, и добавление вариантов не должно ломать обратную
  совместимость (правило 11)». **Точка расширения спроектирована заранее — эта
  задача ею и пользуется**, ничего не рефакторя.
- **Строка 67 — `trait Generator`.** Единственный метод:
  ```rust
  fn generate(&self, model: &ModelNode, output_path: &str,
              options: &GenerateOptions) -> Result<(), Diagnostic>;
  ```
  Менять не требуется: цель `sv` пишет файл в каталог по семантическому дереву —
  ровно то, что трейт выражает.
- **Строка 30 — `GenerateOptions`**, тоже `#[non_exhaustive]`: `guard_enable`,
  `hal: bool`, `address_map: HashMap<String, ResolvedAddress>`. Поля
  `hal`/`address_map` заведены задачей 0020-05. **Цель `sv` не использует ни
  одного из них** (адрес не потребляется, ADR вопрос 5) → новых полей не нужно.
- **Строка 80 — свободная `generate(l, model, path, options)`**; строка 86 —
  `match l { Language::C => …, Language::PlantUML => … }`. `match` **внутри**
  крейта, где `#[non_exhaustive]` не действует → добавление `SV` **завалит
  сборку**, пока ветка не написана. Ровно нужное поведение.

### `grammar/src/generator/plantuml/` — образец «второго бэкенда» (324 строки)

Ближайший структурный образец для нового бэкенда:

- `mod.rs` (258 строк): `pub struct Generator {}` + `impl AsGenerator for Generator`;

  Ошибка записи → `Diagnostic::warning(Location::Codegen, …).with_code("PU-001")`

- `puml_map.rs` (66 строк): `PumlMap` — **тонкая обёртка** над общей

- Юнит-тесты живут **в модуле** и проверяют **подстроки** результата

### `grammar/src/generator/c/` — тяжёлый образец (6248 строк)

`CMap` (`c_map.rs`) добавляет к снимку `usage: UsageSet` (фильтрация
неиспользуемых) и `guard_enable`. Разделён на `c_decl`/`c_expr`/`c_header`/

первого коммита, а не потом (ср. `validate.rs` 3648 строк — кандидат 0027).

### `grammar/src/bin/lamc.rs` — 1149 строк

- **Строка 551** — `match options.target.as_str()`. Целей фактически **три**:
  `"c-hal"` (551), `"c"`, `"plantuml"` (622).

- **Строка 532** — `if !external_entries.is_empty() && options.target != "c-hal"`

  `sv` попадает под эту проверку без единой правки** (ADR, вопрос 5).
- Строка 163 — умолчание `let mut target = "c".to_string();`.
- Справка: строки 423, 436–437, 442.

- `semantic::minimap::Map` — снимок дерева (общий для `CMap`/`PumlMap`);
- `Printer` (`generator/indent.rs:29`) — печать с отступами;
- `semantic::naming::normalize_lowercase_snakecase` — нормализация имён.

### Вывод по каркасу (важно для этой задачи)

**Рефакторинг общего каркаса не требуется и не делается.** Разбор — в
[анализе](../analyze/0045-sv-backend.md), раздел «0041 — нужен ли общий каркас
бэкендов?». Кратко: точка расширения (`#[non_exhaustive] Language`), трейт,
опции и снимок дерева уже спроектированы под расширение; третий (0041) и
четвёртый (0045) бэкенды **пользуются** этим каркасом, а не обнажают его дефицит.
Пересечение с 0041 — три строки диспетчеризации, строка справки и номер версии
крейта.

### Отличия от плана

1. **Открытый вопрос «нужен ли `UsageSet`» (пункт 3 плана) — решён пробой:
   нужен.** `verilator --lint-only -Wall` даёт `UNUSEDSIGNAL` на объявленный, но
   никем не читаемый сигнал. То есть для цели `sv` фильтр — не оптимизация
   размера вывода, как в C, а **условие прохождения гейта** (A3): без него
   линтер краснел бы на легальных моделях. `SvMap` заведён по образцу `RustMap`
   (снимок + `UsageSet`), а не `PumlMap` (тонкая обёртка). Окончательно
   подтвердится задачей 0045-04, когда появятся настоящие порты.
2. **Попутный фикс строки 651 (пункт 5 плана) уже был сделан** фичами 0041/0050:
   перечисление целей в сообщении об ошибке актуально. Правка свелась к
   дописыванию `sv` в готовый список.
3. **Каркас-заглушка (пункт 6) шире, чем «пустой `always_ff`»**: минимальный
   модуль с пустым `always_ff` не прошёл бы гейт — `clk`/`rst_n` остались бы
   неподключёнными, а `verilator -Wall` даёт на это `UNUSEDSIGNAL`. Поэтому
   каркас эмитит **вырожденный случай целевой формы**: регистр состояния,
   `always_comb` с умолчанием, `always_ff` с ветвью сброса и `assign is_done`.
   Он проходит оба гейта — их можно ставить сразу (0045-02), а не после
   накопления кода.
4. **Коды `SV-010`/`SV-011`** (модель/состояние не найдены в снимке карты) —
   заведены по образцу `RS-012`/`RS-013`; реестр `SV-0xx`
   [анализа 0045-03](../analyze/0045-03-type-mapping.md) их не предусматривал,
   т.к. описывал только диагностики отображения. Конфликта с `SV-002`…`SV-008`
   нет.
