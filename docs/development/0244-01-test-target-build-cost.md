# Задача 0244-01: Отладочная информация тестовых целей — `line-tables-only`

> Фича: [../features/0244-test-target-build-cost.md](../features/0244-test-target-build-cost.md) · ADR: [../adr/0244-test-target-build-cost.md](../adr/0244-test-target-build-cost.md) · анализ: [../analyze/0244-test-target-build-cost.md](../analyze/0244-test-target-build-cost.md)

## Что было

Тестовые цели собирались с полной отладочной информацией (`debug = true` по
умолчанию профиля `dev`). Замер ADR показал, что дороже всего в стадии
`cargo test` обходится **первый запуск** свежесобранного бинарника — 0.60 с при
загрузке ЦП 2 % (проверка кода ядром, чтение с диска, работа динамического
загрузчика), а таких бинарников **147**. Полные отладочные таблицы раздувают
файл и оплачиваются этим временем на каждом прогоне гейта, где каждый бинарник
запускается впервые.

## Что сделано

**Корневой `Cargo.toml`:** добавлен профиль

```toml
[profile.test]
debug = "line-tables-only"
```

с обоснованием и замерами прямо у места (правило «цифра рядом с решением»).

⚠️ **Профиль `test`, а не `dev`** — выбор сделан замером, а не вкусом: `dev` даёт
тот же результат (27.0 с компиляции / 8.10 с первого запуска против 26.7 / 8.13
у `test`), но управляет отладкой бинарников `taktc`/`takt-sim`/`takt-lsp`, и
урезать их отладочную информацию незачем.

**`docs/CODE.md`:** заведён раздел «Отладка тестов» — что именно теряется (только
значения локальных переменных под отладчиком; номера строк и обратные трассы на
месте), как разово вернуть полную информацию
(`CARGO_PROFILE_TEST_DEBUG=true cargo test --test <цель>`) и почему нельзя
переносить урезание в `[profile.dev]`.

**`takt-sim`, семантика, цели, гейты — не затронуты** (н/п): меняется только
объём отладочной информации в тестовых бинарниках.

## Проверки

**Изолированный замер (пустой каталог сборки, устоявшаяся ФС):**

| Метрика | До | После | Δ |
|---|---|---|---|
| Компиляция всех тестовых целей (`cargo test --no-run`) | 29.3 с | **25.9 с** | −12 % |
| Холодный первый запуск 20 целей | 12.07 с | **8.39 с** | −30 % |
| Размер тестового бинарника (в среднем) | 10.6 МиБ | 10.2 МиБ | −4 % |

**Полный предкоммит на ПОЛНОСТЬЮ холодном каталоге** (те же условия, в которых
снималось «до» — методика «устоявшаяся ФС + второй прогон»):

| Метрика | До (0242) | После | Δ |
|---|---|---|---|
| Стадия `cargo test` | 152.9 с | **127.8 с** | **−25.1 с (−16 %)** |
| Полный прогон | 233.2 с | **214.9 с** | **−18.3 с (−7.8 %)** |
| Тестов пройдено | 3082 (+6 ignored) | **3082 (+6 ignored)** | без изменений |

Расчёт ADR обещал ≈ −30 с со стадии тестов; факт — −25.1 с. Разница объяснима
тем, что расчёт экстраполировал выигрыш 20 целей на 147 линейно, тогда как часть
запусков попадает в дисковый кэш.

```sh
./scripts/precheck.sh          # зелёный, 214.9 с на холодном каталоге
```

⚠️ **Промежуточный прогон на частично горячем каталоге (204.3 с) в сравнение не
годится** и в отчёт не берётся: там пересобирались только тестовые цели, то есть
условия «до» и «после» были разными. Ровно этот класс ошибки — сравнение
несравнимого — стоил проекту отменённой фичи 0242.
