# Задача 0166-01: Пример batch_cycle и его обвязка (SV_TRANSLATABLE, тестбенч, контракт, харнесс C)

> Фича: [../features/0166-sv-example-sequential-composition.md](../features/0166-sv-example-sequential-composition.md) · ADR: [../adr/0166-sv-example-sequential-composition.md](../adr/0166-sv-example-sequential-composition.md) · анализ: [../analyze/0166-sv-example-sequential-composition.md](../analyze/0166-sv-example-sequential-composition.md)

## Что было

`SV_TRANSLATABLE` состоял из моделей на `|`; последовательная композиция `+` на
гейт цели `sv` **не подавалась**. Единственный пример корпуса с `+`
(`extend_complex.takt`) целью `sv` не транслируется.

## Что сделано

### Пример

`examples/batch_cycle.takt` — технологический цикл из трёх фаз:
`start Cycle = Dose + Mix + Drain { next Done; }`. Каждая фаза — своя модель со
счётчиком тактов и терминальным состоянием; общая `stage` (1 → 2 → 3) делает
активную фазу наблюдаемой снаружи.

Форма продиктована гейтами, а не вкусом (ограничения О1–О8 анализа). Две из них
вскрыты **пробой**, а не чтением:

- ⚠️ **порт и состояние не могут называться одинаково**: первая редакция несла
  `out ready: bit` и `state Ready`, и цель `c` дала **некомпилируемый** код —
  `BATCH_CYCLE_READY` объявляется и в перечислении битовых портов, и в
  перечислении состояний, а enumerator'ы в C делят область видимости
  (`redefinition of enumerator`). Состояние переименовано в `Done`; сам дефект
  цели `c` шире фичи и записан находкой в `FEATURES.md`;
- ⚠️ **счётчики фаз названы по-разному** (`dosed`/`stirred`/`drained`):
  одинаковое имя в трёх моделях даёт предупреждение симулятора о неоднозначности
  голого имени.

### Обвязка

| Файл | Что |
|---|---|
| `scripts/precheck.sh` | `batch_cycle` в `SV_TRANSLATABLE` + **прогон** харнесса C |
| `examples/generated/sv/tb/batch_cycle_tb.sv` | тестбенч руками: наблюдает `stage` иерархической ссылкой и требует порядка 1 → 2 → 3 |
| `examples/generated/sv/tb/README.md` | строка в таблицу; заодно дописаны отсутствовавшие `regulator`/`pid_regulator` (таблица отставала — в ней было 2 из 4) |
| `takt-sim/tests/examples_scenario_tests.rs` | **контракт** сценария: цепочка из семи состояний, `must_terminate: true` |
| `examples/generated/c/batch_cycle_main.c` | харнесс руками: `assert`-ами проверяет, что номер фазы растёт **ровно на единицу** |
| `examples/generated/c/CMakeLists.txt` | `add_executable` |

⚠️ **Харнесс мало собрать — его надо запустить.** Прочие харнессы каталога
печатают лог, а этот **утверждает**; в незапущенном коде `assert` не срабатывает
никогда, и гейт остался бы зелёным при сломанной композиции. Поэтому в
`precheck.sh` добавлен явный прогон с проверкой кода возврата.

Обратная функциональность (правило 11): изменения **аддитивны** — существующие
примеры, их артефакты и контракты не тронуты.

## Проверки

Все — через `./scripts/precheck.sh` (EXIT=0):

| Гейт | Результат |
|---|---|
| `verilator --lint-only -Wall` | принял |
| `yosys synth -top batch_cycle` | синтезировал |
| тестбенч (`verilator --binary --timing`) | `OK (три фазы по порядку, затем ready и is_done)` |
| контракт сценария | цепочка из семи состояний пройдена, прогон завершился |
| `cmake`+`ninja` под `-Wall -Werror` | собран; прогон харнесса: `три фазы по порядку, завершено за 11 шагов` |
| `iec2c` | валиден |
| `rustc` + `clippy -D warnings` | приняты |
| гейт воспроизводимости | воспроизводим по всем восьми целям |
| `taktc fmt --check examples/` | канон |

**Взведённость обоих новых сторожей доказана мутацией:**

- тестбенч с укороченным прогоном (4 такта вместо 40) → `Assertion failed: фаза
  перемешивания не наблюдалась`, код выхода 1;
- харнесс с `assert(phases == 4)` → `Assertion failed`, код выхода 134.

Симулятор и цель `c` завершают цикл за **11 тактов** оба — то есть свидетели
согласуются не только по факту, но и по длине трассы.
