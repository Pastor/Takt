# Задача 0019-01: устранение дубликата LoopCond параметризацией Expression

> Фича: [../features/0019-condition-expression-unification.md](../features/0019-condition-expression-unification.md) · ADR: [../adr/0019-condition-expression-unification.md](../adr/0019-condition-expression-unification.md) · анализ: [../analyze/0019-condition-expression-unification.md](../analyze/0019-condition-expression-unification.md)

> **Статус:** ВЫПОЛНЕНО.

## Что было

`grammar/src/grammar.lalrpop` содержал цепочку `LoopCondP14…LoopCondP1` —
**96 строк**, почти дословную копию `Precedence14…Precedence1` (`Expression`).
Обе давали один AST (`ast::Expression`); отличие — ровно одно: атом
loop-условия не может начинаться с `{`, иначе LR(1)-неоднозначность между
`loop { body }` (бесконечный цикл) и `loop {init} { body }` (инициализатор
массива как условие).

Проверено механически (нормализация имён + `diff`): цепочки **структурно
идентичны**; различие сводится к тому, что правый операнд `LoopCondP*`
ссылается на полную цепочку `PrecedenceN` — это намеренно, поскольку
ограничение касается только **первого** токена.

## Что сделано (Option B из ADR)

Цепочка приоритетов вынесена в **параметризованное правило** `Chain<Atom>` и
написана **один раз**:

```lalrpop
Expression: Expression = { Chain14<Precedence1Full>    }   // атом с `{…}`
LoopCond:   Expression = { Chain14<Precedence1NoBrace> }   // атом без `{…}`
```

`Precedence1` разделён на два атома: `Precedence1Full` (с инициализатором
массива) и `Precedence1NoBrace` (без него). Правый операнд любого бинарного
оператора внутри макроса — **всегда** `Chain*<Precedence1Full>`, что в точности
повторяет прежнее поведение `LoopCondP*`.

`LoopCondP14…LoopCondP1` **удалены**.

| Метрика | Было | Стало |
|---|---|---|
| Строк в `grammar.lalrpop` | 981 | **915** (−66) |
| Упоминаний `LoopCondP` | 55 | **3** (только пояснительные комментарии) |

Разделение `Condition`/`Expression` **не** унифицировано — оно намеренное
(`=` в условии = равенство, в выражении = присваивание). Зафиксировано
комментарием в грамматике и в `CLAUDE.md` (action item ADR).

## Spike (шаг 1 плана): результат

PoC **удался** — LALRPOP принял параметризованную цепочку **без новых
LR(1)-конфликтов** (`cargo build -p grammar` → 0). Запасной вариант (Option C /
статус-кво) не понадобился.

**Первая попытка PoC упала** с `Ambiguous grammar detected: Precedence0 "<<"
Chain5<Precedence1Full> can be reduced in two ways`. Причина оказалась **не** в
LALRPOP, а в моём механическом преобразовании: у оператора `as` **левый**
операнд помечен меткой `e` (`<e:Precedence7> "as" <ty:Type>`), и шаблон принял
его за правый, подставив полную цепочку вместо `Atom`. Из-за этого в
loop-контексте `Precedence0` мог свестись и к `Precedence1Full`, и к
`Precedence1NoBrace`. После исправления (`<e:Chain7<Atom>> "as"`) грамматика
собралась. Урок: сообщение об ambiguity указывало на симптом, а не на причину —
списывать его на «LALRPOP не умеет» было бы ошибкой.

## Проверки

### Регресс = 0 (критерий A2, R4)

- `cargo test --all-features -- --test-threads=1` → **1586 passed**, 0 провалов —
  ровно столько же, сколько до задачи.
- `./scripts/run_simulations.sh` → 5 из 5; `cargo clippy` → 0.
- `syntax_simple` (инвариант `ref`-условий) — зелёный.

### Дизамбигуация `{` сохранена (критерий A1, R3)

Проверено **сравнением с исходной грамматикой**: обе версии дают **идентичный**
результат на одних и тех же пробах.

| Проба | Поведение (исходная = макро-версия) |
|---|---|
| `loop { n := 2; }` | **бесконечный** цикл: `{` — тело. Упирается в предохранитель: `превышен предел итераций цикла (100000) (SIM-018)` |
| `loop ({1, 2}) { n := 5; }` | инициализатор массива — **условие**: `операция 'логическое условие' не определена для операнда массив (SIM-005)` |
| `loop i < 3 { i := i + 1; }` | обычное условие — компилируется |

> Диагностики фичи 0025 сделали эту проверку точной: вместо «работает / не
> работает» видно, **как именно** разобрана конструкция.

### Нет новых LR(1)-конфликтов (критерий A3, R5)

`cargo build -p grammar` → 0. LALRPOP отвергает неоднозначные грамматики на
этапе сборки, поэтому успешная сборка **и есть** доказательство.

## Заметка

Инвариант `=`/`==` (R1) не затронут: `Condition` не менялся вовсе — задача
касалась только цепочки `Expression`.
