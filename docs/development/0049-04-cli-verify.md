# Задача 0049-04: Подкоманда lamc verify

> Фича: [../features/0049-model-checking-ltl.md](../features/0049-model-checking-ltl.md) · ADR: [../adr/0049-model-checking-ltl.md](../adr/0049-model-checking-ltl.md) · анализ: [../analyze/0049-model-checking-ltl.md](../analyze/0049-model-checking-ltl.md)

## Что было

CLI `grammar/src/bin/lamc.rs`: подкоманды **`compile`** и **`fmt`**,
диспетчеризация вручную в `main()` (`lamc.rs:532`; `if args[1] == "fmt"`
`:540`, иначе `compile` `:552`). `parse_compile_args` (`:171`), `print_usage`
(`:489`). Подкоманды `verify` **нет**.

## Что сделано

> **Готово.** Реализовано по ADR 0049 (R8).

1. Ветка `verify` в `main()` (по образцу `fmt`):
   `lamc verify [--property "φ"] [--trace] [-I <dirs>] <file>`.
2. `parse_verify_args(args) -> VerifyOptions { input_file, include_dirs,
   property: Option<String>, trace: bool }`. Формы флагов — как у `compile`:
   `-p`/`--property`/`--property=`, `-I /a`/`-I/a`/`-I /a:/b`.
3. Разбор свойства — публичная `grammar::parse_ltl_property` (реализована в
   0049-03): строка оборачивается в `: [LTL] φ;` и разбирается **грамматикой
   языка**, затем `ltl_ast_to_semantic`. Синтаксис свойства в CLI и в `.lam`
   совпадает буква в букву; атомы — любой длины. `parse_ltl` (тестовый,
   паникующий) не используется — A6 ADR соблюдён. Ошибка разбора — `Err`, а не
   паника; список формул через запятую отвергается (какую проверять — непонятно).
4. Без `--property` — `grammar::verify_all_traced`: все формулы файла, включая
   **вложенные модели** (каждая — против своего графа; вердикт помечается
   `[модель Engine]`).
5. Печать вердикта: `Holds` → «СВОЙСТВО ДЕРЖИТСЯ»; `Violated` → «СВОЙСТВО
   НАРУШЕНО» + трасса-лассо + пометка «абстракция управления»; `Unsupported` /
   `NoStartState` → «СВОЙСТВО НЕ ПРОВЕРЕНО» + причина.
6. `--trace` печатает конвейер (Крипке, автомат `¬φ`, произведение) —
   инструмент отладки неожиданного вердикта. Трасса едет в `PropertyResult::trace`,
   поэтому считается **за один прогон** вместе с вердиктом, а не отдельно.
7. Код возврата: `0` — все держатся; `1` — нарушение/не проверено/ошибка.
8. Справка `print_usage` дополнена подкомандой, флагами и примерами; вывод
   вердиктов и итога — оба в stdout (разведи их по потокам — итог всплывёт выше
   вердиктов из-за буферизации).

**Формулировка отказа переписана после пробы.** Первая редакция говорила «в
абстракции управления свойства над данными не поддержаны». Проба на
`examples/elevator_mini.lam` (`--property "F Idle"`) показала: `Idle` — **не**
данные, это состояние **вложенной** модели `Engine`, и сообщение вводило в
заблуждение. Причин у неизвестного атома три (переменная, состояние вложенной
модели, опечатка), поэтому текст перечисляет их и подсказывает, что делать.

## Проверки

- **Проба CLI** на фикстурах (T33): `holds.lam` → «ДЕРЖИТСЯ», код `0`;
  `fails.lam` → «НАРУШЕНО» + `Idle -> [ Fault ]*`, код `1`; `unreachable.lam` →
  «НАРУШЕНО» + `Work -> [ Wait -> Work ]*`; `atom_not_state.lam` → «НЕ
  ПРОВЕРЕНО»; вложенная модель → «ДЕРЖИТСЯ [модель Engine]».
- **Тесты аргументов** `lamc.rs::tests` (9, зелёные): файл; `--property` и его
  формы; `--trace`; `-I`. Контрпримеры: без файла; два файла; `--property` без
  значения; неизвестный флаг — везде отказ, а не молчаливый прогон.
- **Завершаемость на корпусе** (A5): `lamc verify --property "F <состояние>"` по
  всем `examples/*.lam` — вердикт возвращается, зависаний нет; то же
  автоматизировано тестом `verification_terminates_on_examples_corpus`
  (`verify_tests.rs`, проверяет все 5 примеров корпуса).
- Соответствие анализу: R8; критерии A1, A5; тест-план T26–T34.
