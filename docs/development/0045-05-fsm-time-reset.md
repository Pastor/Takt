> Фича: [../features/0045-sv-backend.md](../features/0045-sv-backend.md) · ADR: [../adr/0045-sv-backend.md](../adr/0045-sv-backend.md) (вопросы 2, 3) · анализ: [../analyze/0045-05-fsm-time-reset.md](../analyze/0045-05-fsm-time-reset.md) · тест-план: [../tests/0045-sv-backend.md](../tests/0045-sv-backend.md)

> Требования: **R6**, **R7**, **R8**. Критерии: **A8**, **A9**, **A10**.
> **Ядро фичи:** здесь модель исполнения Lam встречается с моделью исполнения RTL.

## Что было

### Как C укладывает автомат (зонд снят фактически)

`cargo build --bin lamc; lamc compile -t c examples/stacker.lam -o <tmp>` →
`stacker.c:277-326`, модель `LiftController`:

```c
void StackerLiftController_tick(StackerLiftController *model, Stacker *main) {
    switch (model->state) {
        case STACKER_LIFT_CONTROLLER_INIT: {
            (*main->write_bit)(STACKER_CMD_FORK, 0, main->userdata);
            model->state = STACKER_LIFT_CONTROLLER_LIFT_IDLE;
            break;                                   /* такт израсходован */
        }
        case STACKER_LIFT_CONTROLLER_LIFT_OPERATING: {
            if (main->lift_request && !(main->lift_op)
                && (*main->read_bit)(STACKER_SENSE_LOADED, main->userdata)) {
                (*main->write_bit)(STACKER_CMD_FORK, 0, main->userdata);
                main->lift_done = 1;                 /* enter LiftDone — инлайн */
                model->state = STACKER_LIFT_CONTROLLER_LIFT_DONE;
                break;
            }
            /* ещё два if в порядке ref-рёбер stacker.lam:365-372 */
        }
        /* … */
    }
}
```

Состав `enum` (`stacker.h:46-50`): `INIT`, `LIFT_OPERATING`, `LIFT_DONE`,
`LIFT_IDLE`, `END`. Терминальность — `state == …_END` (`stacker.c:334`).

**Параллельная композиция** (`stacker.c:415-435`): три `_tick` **последовательно
в одном такте** родителя, завершение по конъюнкции `_is_done`:

```c
case STACKER_STACKER: {
    StackerCommandReceiver_tick(&model->stacker.command_receiver0, model);
    StackerMovementController_tick(&model->stacker.movement_controller1, model);
    StackerLiftController_tick(&model->stacker.lift_controller2, model);
    if (…_is_done(…) && …_is_done(…) && …_is_done(…)) { model->state = STACKER_END; break; }
    break;
}
```

**Отсюда — ключевой факт о языке:** модели `|` вызываются **по порядку**, и модель,
идущая позже, **видит записи, сделанные ранее в этом же такте**
(`MovementController` пишет `lift_request` → `LiftController` читает его **в том же
такте**). То есть `|` в Lam — **не** «одновременно и независимо», а
«последовательно внутри такта, в порядке объявления». Это установлено зондом, а не
предположено.

### Дефект C, который SV не наследует (фича 0033)

Генератор C заводит синтетическое состояние `{PREFIX}_INIT` **на каждый уровень**
(`c_header.rs:49,102,153,181`), и `case INIT` завершается `break`
(`c_model.rs:649`) → **вход в стартовое состояние стоит такта**; сдвиг от
симулятора = **глубине** (пробы 0033: 1/2/3 уровня → сдвиг 1/2/3 такта).

ADR 0033 принял **Option B**: вход **не должен** стоить такта; эталон — **модель**;
сдвиг = 0 на любой глубине. Следствия 0033 адресованы прямо нам: «Будущие бэкенды
получают **контракт** “вход в стартовое состояние не стоит такта”, а не прецедент
чужой бухгалтерии».

Симулятор уже верен: `Unit::tick` зовёт `enter_initial_state()` и **в том же
такте** исполняет тело (задача 0025-04).

### Что уже проверено фактически (проба целевого модуля)

Рукописный `stacker_lift_controller.sv` в целевом стиле:
`verilator --lint-only -Wall` — **чисто**; `yosys synth` — **22 ячейки**; тестбенч:

```
после сброса (до 1-го такта): state=0 cmd_fork=0
такт 1: state=0 cmd_fork=0 lift_done=0     <- тело LiftIdle исполняется УЖЕ здесь
```

**Сдвиг = 0** (C на глубине 1 даёт такт 2, на глубине 3 — такт 4).

Проверена и обратная сторона: комбинационная петля (риск композиции)
**отлавливается Verilator** (`UNOPTFLAT`, код 1) и **пропускается yosys** (код 0).

## Что сделано

> **Планируется (разработка не начата).**

План — `generator/sv/sv_fsm.rs`.

### 1. Форма автомата: two-process (ADR вопрос 3, Option A)

```systemverilog
always_comb begin                 // тело состояния: БЛОКИРУЮЩИЕ присваивания
    state_next = state;           // умолчания (иначе защёлка -> verilator LATCH)
    cmd_fork_next = cmd_fork;
    unique case (state)
        LIFT_IDLE: begin
            if (lift_request) begin
                cmd_fork_next = 1'b1;      // enter цели — инлайн, как в C
                state_next    = LIFT_OPERATING;
            end
        end
        // …
    endcase
end

always_ff @(posedge clk) begin    // латч: НЕБЛОКИРУЮЩИЕ
    if (!rst_n) begin
        state    <= LIFT_IDLE;    // стартовое состояние; INIT-состояния НЕТ
        cmd_fork <= 1'b0;         // enter стартового состояния
    end else begin
        state    <= state_next;
        cmd_fork <= cmd_fork_next;
    end
end
```

**Почему блокирующие в `always_comb` — критично.** Тело состояния Lam —
императивная последовательность: `v := 1; w := v;` даёт `w = 1` (так в C, так в
симуляторе). Неблокирующие (`<=`) дали бы `w` = **старое** `v` — другая модель.
Инлайн `enter` цели в переход требует видимости записи **внутри такта** — в
неблокирующей семантике невозможно в принципе.

**Умолчания в начале `always_comb` обязательны** — иначе неполное присваивание →
защёлка; `verilator -Wall` поймает (`LATCH`).

### 2. Сброс и контракт 0033 (ADR вопрос 2, Option A)

- Синхронный, активный низкий `rst_n`.
- Ветвь сброса = **стартовое состояние** + **`enter` стартового состояния**.
- **Синтетического `INIT` нет вообще** — его роль исполняет цепь сброса.
- **Сдвиг = 0 на любой глубине бесплатно:** у каждого уровня свой `always_ff` со
  своей ветвью сброса; все сбрасываются **одним фронтом параллельно** (в C уровни
  входят последовательно — отсюда сдвиг = глубине).
- **`SV-008`:** `enter` стартового состояния обязан быть **константным** — ветвь
  сброса синтезируется в цепь сброса триггеров и выражений не вычисляет. Если он
  вычисляет значение от входов/функций → **ошибка**, а не несинтезируемый вывод.
  Цена для корпуса нулевая (проверено зондом: `enter` стартовых состояний
  `stacker.lam` — константы). Обход для автора: перенести в `always` (сдвиг всё
  равно 0) — **написать это в тексте диагностики**.

### 3. Состояния и переходы

| Lam | C (зонд) | **SV** |
|---|---|---|
| `state S` | `case …_S:` | ветвь `case` в `always_comb` |
| стартовое | `case …_INIT` (**стоит такта**) | **ветвь `if (!rst_n)`**; `INIT` отсутствует |
| `enter` цели | инлайн в переход | инлайн в ветвь `case` |
| `always` | тело `case` | тело ветви `case` |
| `exit` | перед сменой `state` | перед присваиванием `state_next` |
| `ref S: cond;` | `if (cond) { …; state = S; break; }` | `if (cond) begin …; state_next = S; end` — **порядок рёбер сохраняется** |
| терминальность | `_is_done()` | `assign is_done = (state == ST_END);` |

`typedef enum logic [W-1:0]` — задача 0045-03.

### 4. Композиция `M1 | M2` (ADR вопрос 3, Option A′) — уплощение с сохранением порядка

Один SV-модуль на **корневую** модель:

- регистры состояний под-моделей — **независимы** (свои `always_ff`);
- вся комбинационная логика — в **одном** `always_comb`, где блоки под-моделей
  идут **в том же порядке, в каком C зовёт `_tick`** (`stacker.c:425-433`:
  CommandReceiver → MovementController → LiftController), и общаются через
  **блокирующие** присваивания.

**Почему не «модуль на под-модель»** (проверено, а не по вкусу):

| Наивный вариант | Что происходит |
|---|---|
| Отдельные модули + комбинационные связи | **комбинационная петля** `lift_request → lift_done → lift_request` в `stacker.lam` → несинтезируемо (Verilator: `UNOPTFLAT`, код 1) |
| Отдельные модули, общие переменные | **несколько драйверов** одной переменной → ошибка компиляции SV |
| Отдельные модули + регистрация связей | **сдвиг на такт** → другая модель, чем C и симулятор. Ровно то, что ADR 0033 осудил |

Уплощение разрывает цикл **там же, где его разрывает такт в C**, сохраняя при этом
главный выигрыш RTL: регистры состояний остаются независимыми триггерами, такт —
один на всю композицию (C сериализует: такт стоит суммы работ под-моделей).

**Плата (документируется в 0045-08):** иерархия SV не отражает дерево моделей;
длинная комбинационная цепь → потолок частоты.

### 5. Композиция `M1 + M2`

Шаги `case` родителя: пока `!m1_is_done` — логика `M1`, затем `M2`. Изоморфно C.

**Статус по обратной функциональности (правило 11):**

| Функциональность | Работа |
|---|---|
| Цель `c` и её `INIT`-такты | **н/п** — не трогаются; их чинит фича 0033 |
| Фича 0033 | **н/п** — не зависимость; контракт исполняется конструктивно |
| Симулятор | **н/п** — только эталон сверки |
| Язык `.lam` | **н/п** |
| `generator/sv/sv_fsm.rs` | **новый** |

## Проверки

> **Планируется (разработка не начата).**

- **T20/T21/T22 (R7/A8) — сдвиг = 0 на глубине 1, 2, 3.** Тестбенчи на тех же
  формах, что пробы ADR 0033: `start Idle { always { v := 7; } }` (C: такт 2);
  `model Conf {…} start Entry = Conf;` (C: такт 3); трёхуровневая (C: такт 4).
  Ожидание: **такт 1 во всех трёх**. **Проба на глубине 1 уже пройдена вручную.**
  **Не требует закрытия 0033.**
- **T23 (R6/A8):** после сброса `state` = стартовое, `enter` исполнен, **`INIT` в
  `enum` отсутствует**.
- **T24 (R8/A9) — изоморфизм с C:** переходы `LiftController` — та же
  последовательность условий и тот же инлайн `enter`, что в зонде
  `stacker.c:277-326` (зафиксирован в ADR).
- **T25 (R8/A10):** модель с `v := 1; w := v;` → `w` = 1 (**не** старое `v`).
  Проверяет выбор two-process против one-process.
- **T26 (R8/A3):** `stacker.lam` → `verilator --lint-only` код **0**, петли нет;
  один драйвер на переменную.
- **T27 (R8/A9):** блоки под-моделей в `always_comb` — в порядке вызова `_tick` C.
- **T28/T29:** `M1 + M2` — шаги `case` по `is_done`; `assign is_done = (state ==
  ST_END);`.
- **Контрпример:** неконстантный `enter` стартового состояния → **`SV-008`**.
- **Негативный тест гейта:** рукописная петля валит `verilator --lint-only`
  (**проверено**, код 1) — гейт живой.
- **T7/T8:** оба гейта зелёные; в частности **нет `LATCH`** (умолчания в
  `always_comb` расставлены).
- Сперва **зонд**, затем assertions (`CLAUDE.md`).
- `cargo test -- --test-threads=1` — зелёный.
