# Задача 0037-02: Отладочная запись в `/tmp` в тесте `viewport`

> Фича: [../features/0037-windows-test-failures.md](../features/0037-windows-test-failures.md) · ADR: [../adr/0037-windows-test-failures.md](../adr/0037-windows-test-failures.md) · анализ: [../analyze/0037-windows-test-failures.md](../analyze/0037-windows-test-failures.md) · тест-план: [../tests/0037-windows-test-failures.md](../tests/0037-windows-test-failures.md)

## Что было

**Реальное состояние кода на 2026-07-15** (ветка `v2`, коммит `6984471`;
установлено чтением `simulation/src/unit/viewport.rs`, 1460 строк).

### Падающий тест

`mod test_highlight` (строки 1411–1460), тест
`test_highlight_frame_contains_orange_bg` (1429–1459). Тело: строит `Unit::Node`
с переходом `Off → On`, считает раскладку (`compute_layout`), рендерит кадр с
подсветкой ребра (`render_from_layout(..., is_svg: false)`) и проверяет наличие
оранжевых цветов в SVG. Проблемные строки — **1452–1453**:

```rust
let Viewport::SVG(doc) = vp;
let svg_str = doc.to_string();
std::fs::write("/tmp/highlight_test.svg", &svg_str).unwrap();   // ← 1452
println!("SVG saved to /tmp/highlight_test.svg");               // ← 1453
assert!(
    svg_str.contains("FFF3DC") || svg_str.contains("FF8C00"),
    "SVG should contain orange colors: {}",
    &svg_str[..500]                                             // ← 1457
);
```

### Механизм сбоя на Windows

Каталога `/tmp` на Windows нет (путь трактуется как `\tmp` на текущем диске),
`fs::write` → `Err(NotFound)`, `unwrap()` → **паника до собственного `assert!`
теста**. Это единственное падение крейта `simulation` — сходится с отчётом 0021
(`simulation` **149/150**).

### Три установленных факта

1. **Запись — отладочный артефакт, а не часть проверки.** `assert!` работает с
   `svg_str` **в памяти**; от файла не зависит ничто. `grep` по репозиторию
   подтверждает: `/tmp/highlight_test.svg` не читается ни одним тестом, скриптом
   или инструментом — файл пишется и забывается.
2. **Кандидат в `FEATURES.md` описывает сбой неверно.** Там сказано «путь к
   ресурсу не найден (ошибка ФС)». **Не подтвердилось:** ресурс **не читается**,
   тест **пишет**. Класс ошибки (ФС из-за POSIX-пути) тот же, но починка иная —
   удалить строку, а не искать ресурс.
3. **Нарушен подводный камень `CLAUDE.md`** («пути — через `std::path::Path`, не
   разбивка строк»), причём **тот же крейт в других местах делает правильно**:
   - `simulation/src/state_io.rs:258` — `tempfile::tempdir()`;
   - `simulation/tests/conformance_c_tests.rs:179` — `std::env::temp_dir()`;
   - `simulation/src/gif.rs:170`, `json_input.rs:132` — `tempfile::NamedTempFile`.

   Это **единственное** обращение к ФС по жёстко зашитому POSIX-пути в тестах
   `simulation` (проверено `grep` по `/tmp`, `fs::write`, `save_to_file`).
   Контрпример: `state_io.rs:274` использует `/no/such/dir/state.json`, но там
   тест **ожидает** `Err` — на Windows он ошибается так же и проходит.

### Латентный дефект в том же тесте (не связан с Windows)

Строка **1457**: `&svg_str[..500]` в сообщении `assert!` паникует, если SVG
короче 500 байт **или** если граница 500 попадает внутрь UTF-8-символа
(строковое срезание в Rust — по байтам, с проверкой границ символов).
Срабатывает только когда `assert!` уже провалился, то есть **маскирует
диагностику** ровно в момент, когда она нужна. К Windows отношения не имеет,
но живёт в той же конструкции → правится здесь, чтобы не оставлять тест
полуисправленным (требование R6).

### Побочный эффект на macOS/Linux

Тест **создаёт** `/tmp/highlight_test.svg` при каждом прогоне (проверено:
прогон на darwin зелёный, файл появляется). Фиксированное имя в общем каталоге —
источник гонки при параллельных прогонах; проект и так вынужден гонять тесты
`--test-threads=1` «иначе гонки за общие файлы» (`CLAUDE.md`).

### Прогон на darwin (эталон «до»)

```sh
cargo test -p simulation test_highlight -- --test-threads=1   # → 1 passed
```

**Зелёный** — на macOS `/tmp` существует и доступен для записи. Утверждение о
падении на Windows основано на **чтении кода** и отчёте 0021, **не на прогоне**.

## Что сделано

> **ВЫПОЛНЕНО** (2026-07-20). Реализовано по **Option E** ADR 0037: строки
> `fs::write("/tmp/…")` + `println!` удалены, `&svg_str[..500]` заменён на
> `svg_str.chars().take(500).collect()`, сообщение `assert!` — по-русски.
> Результаты — в [отчёте](../reports/0037-windows-test-failures.md).

**Суть:** удалить отладочную запись и `println!` (строки 1452–1453); заменить
`&svg_str[..500]` на безопасное усечение. Дифф — в пределах `mod test_highlight`.

**План правки:**

1. **Удалить** строки 1452–1453 (`fs::write(...)` + `println!`). Обоснование
   выбора «удалить», а не «перенести в `temp_dir()`/`tempfile`» (ADR, Options F
   и G): запись не нужна тесту — F сохраняет ненужное обращение к ФС и
   `unwrap()` на нём (новые причины падения: права, полный диск, антивирус на
   Windows), а G удаляет дамп сразу после записи, обнуляя единственный мотив его
   существования. Отладочная ценность не теряется: сообщение `assert!` печатает
   фрагмент SVG, а при нужде дамп воспроизводится одной строкой локально.
2. **Заменить** `&svg_str[..500]` на усечение по границам символов, например:

   ```rust
   let head: String = svg_str.chars().take(500).collect();
   assert!(
       svg_str.contains("FFF3DC") || svg_str.contains("FF8C00"),
       "в SVG нет оранжевых цветов подсветки: {head}"
   );
   ```

   `chars().take(n)` безопасен и для коротких строк, и для многобайтовых
   символов. Сообщение — на русском (правило 1); текущее `"SVG should contain
   orange colors"` — англоязычное, что правилу противоречит.
3. **Не трогать** продуктовый код `viewport.rs` (`create_viewport`,
   `compute_layout`, `render_from_layout`, `Viewport::save_to_file`) — правка
   целиком внутри `#[cfg(test)]`. В частности, `Viewport::save_to_file`
   (строка 33, помечен `#[allow(dead_code)]`) принимает `path: &str`, что тоже
   расходится с подводным камнем `CLAUDE.md`, — но это **продуктовый API**, и
   его типизация (`&Path`) в объём 0037 не входит (кандидат бэклога; вероятная
   пересборка при фиче [0036](../features/0036-sim-visibility.md)).

## Проверки

> **ВЫПОЛНЕНО** (локальная часть). T4 (нет `fs::write`/`/tmp`), T7 (безопасное
> усечение), T13 (darwin) — зелёные; T9 (Windows) — блокер биллинга. См.
> [отчёт](../reports/0037-windows-test-failures.md).

**Ожидаемые результаты** (правило 5; сверка с тест-планом T4, T7, T9, T13):

| Проверка | Команда / способ | Ожидание | R/A |
|---|---|---|---|
| Нет обращений к ФС в тестах файла | `grep -n 'fs::write\|"/tmp' simulation/src/unit/viewport.rs` | **пусто** | T4 / R5 / A5 |
| Тест зелен на darwin | `cargo test -p simulation test_highlight -- --test-threads=1` | **1 passed** | T13 / R10 |
| Побочный эффект устранён | `rm -f /tmp/highlight_test.svg`, прогон, проверка отсутствия файла | Файл **не создан** | T4 / R5 |
| Сообщение `assert!` не паникует | Ревью усечения + проверка на строке < 500 байт и на многобайтовой | Паники нет, сообщение печатается | T7 / R6 / A6 |
| Регресс `simulation` отсутствует | `cargo test -p simulation -- --test-threads=1` | Зелено | T13 / R10 / A10 |
| Линт/формат | `./scripts/precheck.sh` | Зелено | правило 5 |

**Честная оговорка о пределах проверки.** Локальный прогон на darwin **не
доказывает** починку: тест здесь зелёный и до, и после правки (эталон: 1
passed). Отличие от подзадачи 0037-01 в том, что здесь доступна одна **прямая**
локальная проверка — отсутствие `fs::write` в тестовом коде (T4): раз обращения
к ФС нет, то и `NotFound` на Windows возникнуть неоткуда. Это сильный, но всё
же **структурный** довод, а не прогон. Настоящее доказательство — критерий
**A9**: лог job `windows` (подзадача [0037-03](0037-03-ci-windows-matrix.md)) с
`test_highlight_frame_contains_orange_bg` в списке `passed` и итогом
`simulation` **150/150** (было 149/150). До этого закрывать A9 локальным
прогоном **запрещено**.
