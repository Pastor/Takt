# ADR 0144: Экспонента числового литерала вычисляется

- **Status:** Accepted
- **Date:** 2026-07-29
- **Authors:** Архитектор + системный аналитик
- **Related issues:** [Фича 0144](../features/0144-int-literal-exponent.md); связь с [ADR 0128](0128-lexer-literal-overflow.md) (представление литерала и `LE-009`)

## Context

Лексер **принимает** экспоненту и **молча отбрасывает** её. Замер 2026-07-29
(зонд лексера + сквозной прогон):

| Исходник | Токен | Ожидание автора |
|---|---|---|
| `1e3` | `Number(1)` | 1000 |
| `1E3` | `Number(1)` | 1000 |
| `1e-3` | `Number(1)` | 0.001 |
| `2.5e3` | `RationalNumber("2.5")` | 2500.0 |

Ни ошибки, ни предупреждения — **`errors: 0`** во всех случаях. Диапазон токена
при этом покрывает весь текст (`1e3` → `0..3`), то есть подсветка и позиции
верны, а значение — нет.

**Сквозное доказательство.** `var n: u32 := 1e3;` рядом с `var plain: u32 := 1000;`
даёт в порождённом C `model->n = 1;` против `model->plain = 1000;`.
`var f: float := 2.5e3;` в симуляторе показывает `f=2.5000` против
`g=2500.0000` — модель, ждущая их равенства, **не выходит из состояния**.

⚠️ **Объём вдвое больше, чем считала карточка.** Карточка называла только целый
литерал; проба показала, что рациональный теряет экспоненту **тем же образом** —
срез `input[start..=rational_end]` обрывается перед ней. Формулировка карточки
(«у рационального экспонента вычисляется не здесь») **опровергнута**: она не
вычисляется нигде.

**Причина в коде** (`parser/lexer.rs::parse_number`): показатель читается,
границы `exp_start..=end` вычисляются — и присваиваются `let _exp`, то есть
сознательно выбрасываются. У целого значение берётся по `old_end` (до
экспоненты), у рационального срез обрывается на `rational_end`.

**Три обстоятельства, снятые пробами при проработке:**

1. **Форматтер уже канонизирует целые литералы.** `taktc fmt` превращает
   `0xFF` → `255` и `1_000` → `1000`, а `2.5` оставляет как есть. Значит
   «вычислить `1e3` в `1000`» **не вводит нового принципа** — форма целого
   литерала уже не сохраняется, форма рационального сохраняется.
2. **MatIEC принимает строчную `e`.** Проба `iec2c`: `LREAL := 2.5e3;` и
   `:= 2.5E3;` — обе `rc=0`. Значит рациональный текст можно печатать в ST как
   есть, приводить к верхнему регистру не нужно.
3. **Понижение `float → q` разбирает текст вручную и на экспоненте сломается.**
   `semantic/type_node.rs` делает `s.split_once('.')` и парсит цифры как целое:
   для `"2.5e3"` получится `"25e3"` → `parse::<i128>()` не пройдёт → `SE-058`
   «не число». То есть простое «включить экспоненту в срез» ломает q-путь.

## Decision Drivers

1. **Молчание — суть дефекта.** Любое решение обязано его снять; спор идёт лишь
   о том, что считать правильным ответом.
2. **Форма записи уже не священна для целых.** Драйвер, снимающий главное
   возражение против вычисления: канонизация целых — действующее поведение
   форматтера, а не новшество этой фичи.
3. **Читаемость констант — требование свода.** Правило 27(е) учит выносить
   величины в именованные константы, чтобы их было видно; `1e6` читается лучше,
   чем `1000000`, и отказ от экспоненты работает против этого правила.
4. **Представление литерала ограничено `i64`** (ADR 0128). Вычисление обязано
   быть проверяемым: `1e19` не влезает, и ответ должен быть тот же `LE-009`, а
   не тихое переполнение.

## Considered Options

### Option A. Вычислять экспоненту; знак минус делает литерал рациональным

`1e3` → `Number(1000)`; `1e-3` → `RationalNumber("1e-3")` → 0.001;
`2.5e3` → `RationalNumber("2.5e3")` → 2500.0.

**Pros:**
- Совпадает с ожиданием автора и с поведением всех распространённых языков.
- Не вводит нового принципа для форматтера (драйвер 2).
- Служит правилу 27(е): `1e6` остаётся записуемым.

**Cons:**
- Тип литерала зависит от **знака** показателя — `1e3` целый, `1e-3`
  рациональный. Требует явного описания в документе.
- Нужна проверка переполнения при вычислении (иначе тихая обёртка вместо
  `LE-009`).

### Option B. Отвергать экспоненту у целого, вычислять у рационального

`1e3` → лексическая ошибка «напишите 1000 либо 1.0e3»; `2.5e3` → 2500.0.

**Pros:**
- Тип литерала не зависит от показателя — правило проще.
- Переполнения при вычислении целого не возникает вовсе.

**Cons:**
- Отвергает форму, которую автор пишет естественно, и заставляет писать
  `1.0e3` там, где нужно целое, — то есть менять тип ради записи.
- Работает против драйвера 3.

### Option C. Отвергать экспоненту везде

**Pros:**
- Самое простое правило; лексер упрощается.

**Cons:**
- Сужает язык: `2.5e3` — законная форма записи вещественного числа, и её
  изъятие не имеет обоснования, кроме простоты реализации.
- Не отвечает на вопрос «а как записать 10⁶», кроме «цифрами».

## Decision

Принимается **Option A**.

Спор A против B решает драйвер 2: главное возражение против вычисления —
«мы меняем то, что написал автор» — не действует, потому что для целых литералов
форматтер это уже делает (`0xFF` → `255`). Option C отвергнут как сужение языка
без выгоды.

**Нормативные правила решения:**

1. **Экспонента вычисляется, а не отбрасывается.** `1e3` = 1000, `2.5e3` = 2500,
   `1E3` = `1e3` (регистр `e` незначим).
2. **Знак показателя выбирает вид литерала.** Показатель без минуса у целого
   литерала оставляет его **целым**; минус делает литерал **рациональным**
   (`1e-3` ≡ `0.001`). У литерала с точкой вид не меняется — он рационален
   всегда.
3. **Переполнение — та же ошибка, что у длинного литерала.** Если вычисленное
   значение не влезает в `i64`, выдаётся **`LE-009`** (`NumberOutOfRange`) —
   тот же код, что ввела 0128 для `0xFFFFFFFFFFFFFFFF`. Вычисление ведётся
   проверяемой арифметикой; тихая обёртка недопустима.
4. **Текст рационального литерала хранится как написан** (включая экспоненту) —
   так же, как хранится `2.5` и длительность `1m30s` (0134). Канонизации
   рационального нет: форматтер печатает авторскую форму.
5. **Потребители текста приводятся в соответствие.** Понижение `float → q`
   (`semantic/type_node.rs`) обязано понимать экспоненту; печать в цели — без
   изменений (C, Rust, SV и ST принимают форму как есть, ST проверен пробой
   `iec2c`).

## Consequences

### Положительные

- `1e3`, `2.5e3` и `1e-3` означают то, что означают везде.
- Записи вида `1e6` пригодны для констант — правило 27(е) перестаёт спорить с
  языком.
- Переполнение экспоненты диагностируется тем же кодом, что и переполнение
  литерала: одно понятие — один код.

### Отрицательные / Action items

- **A-1. Правило 22: версия языка растёт.** Меняется семантика лексики —
  программа `var n: u32 := 1e3;` начинает означать другое. Подъём согласовать с
  README (гейт `check-language-version.sh`).
- **A-2. Тихая смена поведения существующих исходников.** Файл, где автор писал
  `1e3` и полагался на `1`, начнёт считать иначе. ⚠️ Корпус проверен грепом:
  литералов с экспонентой в `examples/`, `book/` и фикстурах **нет**, поэтому
  вывод генераторов обязан остаться байт-в-байт прежним — это критерий приёмки.
- **A-3. Правило 29: редакторский слой.** Новых токенов не вводится
  (`Number`/`RationalNumber` уже разбираются), классификация подсветки не
  меняется, список автодополнения не затрагивается — **правки LSP и плагинов не
  требуются**. Ответ зафиксирован явно, как требует правило.
- **A-4. Правило 24: документ.** Раздел `book/src/02-lexical/` описывает
  числовые литералы и обязан описать экспоненту и правило 2 (знак показателя).

### Acceptance criteria

1. `1e3` → 1000, `1E3` → 1000, `2.5e3` → 2500.0, `1e-3` → 0.001 — проверяется
   на **значениях**, а не на форме токена.
2. Сквозная проверка: порождённый C для `var n: u32 := 1e3;` содержит `1000`.
3. `1e19` (и любой выход за `i64`) даёт **`LE-009`**, а не тихую обёртку.
4. `float → q` понимает экспоненту: `--float-as-q` на литерале `2.5e3` даёт
   верное представление, а не `SE-058`.
5. Вывод генераторов на корпусе байт-в-байт неизменен (A-2).
6. Версия языка поднята, README согласован (A-1).
