# ADR 0020: Адрес порта отдельно от объявления

- **Status:** Accepted
- **Date:** 2026-07-10
- **Authors:** Архитектор + дизайнер языков
- **Related issues:** [Фича 0020](../features/0020-port-address-decl.md)

## Context

Сейчас адрес порта задаётся **инициализатором** в самом объявлении:

```lam
in  BTN: u8 = 0x200000;      // 0x200000 — аппаратный адрес порта
out LED: bit = 0x200004;
```

Грамматика (`grammar.lalrpop`): `"in"|"out"|"inout" name (":" Type)? ("=" Expression)? ";"`.
Выражение после `=` попадает в `VariableDefine::Port { initializer }` и
используется C-генератором как адрес (`ROOT_BTN` и т.п.).

**Проблема.** Объявление порта (имя, тип, направление) и его аппаратный **адрес**
— разные сущности (адрес зависит от платформы/ревизии). Их слияние в одной строке
мешает: (а) держать карту адресов отдельно от логики модели; (б) переопределять
адреса под разные платформы без правки объявлений.

```ebnf
@startebnf
(* Текущее состояние *)
PortDecl = ("in" | "out" | "inout"), name, [":" , Type], ["=", address], ";";
@endebnf
```

## Decision Drivers

1. **Разделение ответственностей** — объявление порта ≠ его адрес.
2. **Обратная совместимость (правило 11)** — существующие `.lam` с инлайн-адресом
   должны продолжать работать.
3. **Простота грамматики/LR(1)** — минимум конфликтов, минимум новых ключевых слов.
4. **Однозначность** — исключить двойное/противоречивое задание адреса.

## Considered Options

### Option A. Отдельный оператор `address NAME = <expr>;` (аддитивно)

Порт объявляется без адреса (`in BTN: u8;`), адрес задаётся отдельно:
`address BTN = 0x200000;`. Инлайн-форма `= <addr>` **сохраняется** как
сокращение (совместимость).

**Pros:** явное разделение; аддитивно → совместимость полная; карту адресов можно
держать в отдельном файле/секции.
**Cons:** новое ключевое слово `address` (риск столкновения с идентификаторами);
нужна семантическая проверка «адрес задан ровно один раз».

### Option B. Блок адресов `address { BTN = 0x200000; LED = 0x200004; }`

Группировка всех адресов в одном месте модели.

**Pros:** вся карта адресов в одном блоке; удобно для платформенных оверлеев.
**Cons:** то же новое ключевое слово; чуть сложнее грамматика; порядок/область
видимости имён требует правил.

### Option C. Атрибут-постфикс `in BTN: u8 @ 0x200000;`

Адрес отделён от инициализатора символом `@`, но остаётся в объявлении.

**Pros:** без нового ключевого слова; локально.
**Cons:** **не** решает задачу «адрес отдельно от объявления» — остаётся в той же
строке; новый токен `@`.

### Option D. Статус-кво

**Pros:** нулевой риск. **Cons:** проблема не решается.

## Decision

Принимается **Option A** (с возможным расширением до блока Option B позже).

Отдельный оператор `address NAME = <expr>;` прямо реализует «адрес отдельной
конструкцией». Ключевой момент — **аддитивность**: инлайн-форма
`in BTN: u8 = 0x200000;` остаётся валидной как сокращение. Это **снимает** риск
слома совместимости, отмеченный в исходной задаче (STATUS п. 11): break не
требуется.

```ebnf
@startebnf
(* Целевое состояние *)
PortDecl    = ("in" | "out" | "inout"), name, [":" , Type], ["=", address (* сокращение *)], ";";
AddressDecl = "address", name, "=", Expression, ";";   (* новый оператор, аддитивно *)
@endebnf
```

**Правило разрешения адреса (семантика):** для каждого порта адрес берётся из
`AddressDecl`, если он есть, иначе из инлайн-инициализатора. Оба сразу для одного
порта — **ошибка** (SE-код); ни одного — существующая диагностика «порт без
адреса» (если применимо к целевой платформе).

## Consequences

### Положительные

- Объявление порта и его адрес разделяемы; карту адресов можно вынести.
- Обратная совместимость полная (инлайн-форма работает как раньше).

### Отрицательные / Action items

- Новое ключевое слово `address` — правка `lexer.rs` (KEYWORDS) и риск для
  моделей с идентификатором `address`. → проверить examples/фикстуры; при
  необходимости рассмотреть контекстное ключевое слово или символ.
- Семантика: новый проход/шаг разрешения адреса порта + диагностика конфликта
  (двойное задание) и ссылки на несуществующий порт.
- C-генератор: адрес берётся из разрешённого значения (без изменения формата).
- Язык расширен → **повышение версии языка** (правило 22).

### Acceptance criteria

1. `address NAME = <expr>;` парсится, привязывается к порту `NAME`, C-код
   идентичен инлайн-варианту.
2. Инлайн-форма `= <addr>` работает без изменений (регресс = 0).
3. Двойное задание адреса (инлайн + `address`) → диагностика ошибки.
4. `address` для несуществующего порта → диагностика ошибки.
5. Нет новых LR(1)-конфликтов.
