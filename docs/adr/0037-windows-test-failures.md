# ADR 0037: Кросс-платформенность тестов и Windows в матрице CI

- **Status:** Accepted
- **Date:** 2026-07-15
- **Authors:** Архитектор + Системный аналитик + Лид разработки
- **Related issues:** [Фича 0037](../features/0037-windows-test-failures.md);
  источник наблюдения — [отчёт 0021](../reports/0021-swap-assign-compare.md)

## Context

При тестировании фичи [0021](../features/0021-swap-assign-compare.md) на
Windows 11 (nightly gnu + MinGW) зафиксированы **шесть падений**, признанные в
отчёте предсуществующими и не связанными с 0021. ADR разбирает три отдельных
решения: (1) как тестировать разбиение путей `-I` кросс-платформенно, (2) как
чинить POSIX-путь в тесте `viewport`, (3) ставить ли Windows в матрицу CI.

### Факт 1. Продуктовый код разбиения путей платформо-корректен

`grammar/src/bin/lamc.rs:105–118`, `split_include_dirs` уже выбирает разделитель
через `cfg`:

```rust
#[cfg(windows)]
let sep = ';';
#[cfg(not(windows))]
let sep = ':';
```

Это ровно тот механизм, который **снимает** конфликт с буквами дисков: на
Windows строка `C:\lib;C:\usr` режется по `;`, а двоеточие после буквы диска
разделителем не является. Конвенция совпадает с `%PATH%`/`PATH` ОС и
задокументирована в модульной документации (`lamc.rs:11–26, 81–104`) и в
`print_usage()` (`lamc.rs:425–426`).

**Вывод: продуктового бага здесь нет.** Это существенно — кандидат в
`FEATURES.md` формулирует причину как «разбиение по `:` конфликтует с
Windows-путями», что описывает мотив `cfg`, а не механизм падения.

### Факт 2. Падают тесты, зашившие `:` в вход и ожидания

Секция `mod tests` того же файла разделена на две части по дисциплине:

- Тесты **самой** `split_include_dirs` (`lamc.rs:713–780`) `cfg`-разделены
  аккуратно: `split_colon_unix`, `split_empty_segments_skipped`,
  `split_trims_whitespace`, `split_semicolon_is_not_unix_separator` помечены
  `#[cfg(not(windows))]`, а `split_semicolon_windows`,
  `split_trims_whitespace_windows` — `#[cfg(windows)]`. На Windows они
  корректно не собираются/проходят.
- Тесты **`parse_compile_args`** (`lamc.rs:782+`) той же дисциплины **не
  получили**: пять из них зашивают `:` в аргумент, оставаясь при этом
  безусловными `#[test]`. На Windows `sep = ';'`, поэтому строка не режется,
  и `assert_eq!` падает:

| Тест | Строка | Вход | Ожидание | Факт на Windows |
|---|---|---|---|---|
| `parse_include_dirs_colon` | 811 | `-I /lib/lam:/usr/lam` | `["/lib/lam", "/usr/lam"]` | `["/lib/lam:/usr/lam"]` |
| `parse_include_dirs_long_flag` | 837 | `--include-dirs /lib:/usr` | `["/lib", "/usr"]` | `["/lib:/usr"]` |
| `parse_include_dir_glued_colon` | 857 | `-I/a:/b` | `["/a", "/b"]` | `["/a:/b"]` |
| `parse_full_args` | 865 | `-I /lib/lam:/usr/lam -I /local/but` | 3 элемента | 2 элемента |
| `parse_include_filters_empty_segments` | 990 | `-I /a::/b` | `["/a", "/b"]` | `["/a::/b"]` |

Ровно пять — совпадает с отчётом 0021. Дефект — **в тестах**: платформо-нейтральный
`#[test]` проверяет платформо-зависимое поведение.

### Факт 3. Тест `viewport` пишет отладочный дамп в `/tmp`

`simulation/src/unit/viewport.rs:1452` в `mod test_highlight`, тест
`test_highlight_frame_contains_orange_bg`:

```rust
std::fs::write("/tmp/highlight_test.svg", &svg_str).unwrap();
println!("SVG saved to /tmp/highlight_test.svg");
```

На Windows каталога `/tmp` нет (путь трактуется как `\tmp` на текущем диске),
`fs::write` возвращает `Err(NotFound)`, `unwrap()` паникует — тест падает **до**
своего же `assert!`. Это единственное падение в `simulation` (отчёт 0021:
149/150).

Три уточнения по существу:

1. Запись — **отладочный артефакт**, а не часть проверки: `assert!` ниже смотрит
   только на `svg_str` в памяти. Значение дампа для теста — нулевое.
2. Это **противоречит подводному камню `CLAUDE.md`** («пути — через
   `std::path::Path`, не строковые литералы»), причём тот же файл `simulation`
   в других местах делает правильно: `state_io.rs:258` — `tempfile::tempdir()`,
   `conformance_c_tests.rs:179` — `std::env::temp_dir()`.
3. Формулировка кандидата «путь к ресурсу не найден» **не подтвердилась**:
   ресурс не читается, тест пишет. Класс ошибки (ФС из-за POSIX-пути) тот же.

### Факт 4. Windows в CI отсутствует

`.github/workflows/ci.yml` содержит **ровно один** job — `ubuntu`
(`runs-on: ubuntu-latest`): сборка `--all-features --all-targets --examples`,
`cargo check`, `cargo test`. Матрицы нет. Отсюда — корневая причина: оба класса
дефектов пролежали в репозитории до тех пор, пока разработчик случайно не собрал
проект на Windows при работе над 0021. **Правка шести тестов без CI лечит
симптом, а не причину.**

> **Правило 18.** Диаграмма не добавляется: ADR **не меняет** ни синтаксис, ни
> семантику языка (правится только тестовый код и конфигурация CI), а потоки
> данных между компонентами не затрагиваются. Условие «строго необходимо» не
> выполняется — таблица падающих тестов выше информативнее любой схемы.

## Decision Drivers

1. **Не менять продуктовый контракт ради теста.** `split_include_dirs`
   задокументирована, покрыта тестами и ведёт себя корректно на обеих
   платформах. Тест обязан подстроиться под продукт, а не наоборот
   (правило 11: CLI-контракт `lamc` сохранить).
2. **Устранить причину, а не симптом.** Без Windows в CI класс дефектов вернётся;
   это подтверждено историей — дисциплина `cfg` в файле **уже была**, но её не
   применили секцией ниже, и никто не заметил.
3. **Честность проверки (правило 5).** Аналитик на macOS проверить исправление
   не может — значит, механизм проверки должен быть частью самой фичи.
4. **Минимальность диффа.** Дефекты тестовые; цена правки должна быть
   соразмерна, без побочного рефакторинга продуктового кода.
5. **Собственные правила проекта.** `CLAUDE.md`: «пути — через
   `std::path::Path`»; `docs/CODE.md` — правила Rust-кода. Решение не должно
   плодить новые нарушения.

## Considered Options

### Решение 1. Как проверять разбиение путей `-I` кросс-платформенно

#### Option A. Параметризовать тесты платформенным разделителем

Ввести в `mod tests` константу разделителя и строить вход динамически:

```rust
#[cfg(windows)]
const SEP: &str = ";";
#[cfg(not(windows))]
const SEP: &str = ":";

#[test]
fn parse_include_dirs_separator() {
    let args = vec!["-I".to_string(), format!("/lib/lam{SEP}/usr/lam"), "main.lam".to_string()];
    let opts = parse_compile_args(&args).unwrap();
    assert_eq!(opts.include_dirs, vec!["/lib/lam", "/usr/lam"]);
}
```

**Pros:**
- Продуктовый код **не трогается вовсе**: CLI-контракт, документация, поведение
  для пользователя — байт-в-байт прежние (правило 11).
- **Одно** тело теста покрывает обе платформы — в отличие от дублирования под
  `#[cfg]`, тесты не разъезжаются при правках.
- Продолжает **уже принятую в этом файле** дисциплину (`split_*`-тесты
  платформо-разделены) — решение не изобретается, а доводится до конца.
- Дифф ≈ 10 строк, риск регресса ≈ 0.
- Проверяется само намерение теста: «строка режется **разделителем платформы**»,
  а не «строка режется двоеточием» — последнее и было ложным утверждением.

**Cons:**
- Тест на Windows и на Unix проверяет формально **разные** входные строки, то
  есть одна платформа не покрывает вторую — гарантия даётся только матрицей CI
  (снимается решением 3).
- Имена тестов с «colon» становятся неточными → требуется переименование
  (`parse_include_dirs_colon` → `parse_include_dirs_separator`), что задевает
  историю поиска по именам.

#### Option B. Перевести `split_include_dirs` на `std::env::split_paths`

**Pros:**
- Стандартная, отлаженная функция; **снимает** ручной `cfg` из кода.
- Обрабатывает **кавычки** на Windows (`"C:\dir with spaces";C:\other`) — сейчас
  такой вход разбирается неверно (кавычки попадут в имя каталога).
- Формально ближе к подводному камню `CLAUDE.md` (работа с путями средствами
  `std::path`), даёт `PathBuf` вместо `String`.

**Cons:**
- **Молча меняет CLI-контракт** — прямое нарушение правила 11 без обоснования:
  - `split_paths` **не обрезает пробелы**, а текущая функция обрезает (`  /x  :  /y  `
    → `["/x", "/y"]`, тест `split_trims_whitespace`, `lamc.rs:739`). Вход
    `-I " /a : /b "` начал бы давать каталоги с пробелами в имени;
  - `split_paths` **не отбрасывает пустые сегменты** (`/a::/b` → три записи,
    средняя пустая), а текущая — отбрасывает (`parse_include_filters_empty_segments`).
    Пустая запись означала бы поиск импортов в CWD.
- **Смена типа**: `split_paths` даёт `PathBuf`, а `include_dirs: Vec<String>` и
  публичный API `grammar::compile_to_c(&self, …, search_paths: &[String])`
  ожидают `String`. Обратное преобразование — `to_string_lossy()`, то есть
  **потеря** ровно тех не-UTF-8 путей, ради корректности которых `PathBuf` и
  берут. Выгода обнуляется, пока не типизирован весь тракт до `semantic/tree.rs`.
- **Не решает поставленную задачу**: пять тестов упали бы ровно так же — они
  зашивают `:`, а `split_paths` на Windows режет по `;` (тот же `cfg` внутри std).
- Дифф расползается: продуктовый код + публичный API + документация + тесты — при
  том, что чинятся **тестовые** дефекты.

#### Option C. Убрать разделитель из CLI: только повторяемый `-I`

Оставить `-I /a -I /b` (уже поддержан, `lamc.rs:190–196`) и запретить `-I /a:/b`.

**Pros:**
- Полностью снимает платформенную зависимость: `-I` становится
  кросс-платформенным по построению; `-I /a -I /b` — единственная форма,
  работающая одинаково везде (это уже рекомендовано в `lamc.rs:90–92`).
- Проще: исчезает `split_include_dirs`, `cfg` и весь класс тестов.

**Cons:**
- **Слом обратной совместимости CLI без нужды** (правило 11): вызовы вида
  `lamc compile -I /lib/lam:/home/user/lam main.lam` из скриптов, документации
  (`README`, `lamc.rs:19`, `print_usage()`) и `precheck.sh`-подобных обвязок
  перестанут работать, причём **тихо** — `/a:/b` станет одним несуществующим
  каталогом, импорты просто не найдутся, а диагностики о неверном флаге не будет.
  Тихая деградация — худший вид слома.
- Расходится с конвенцией `PATH`, привычной пользователям компиляторов
  (`gcc -I` тоже принимает список).
- Обосновать слом нечем: платформенная проблема — только в тестах.

#### Option D. `#[cfg]`-дублирование тестов (по два на каждый случай)

**Pros:**
- Точнее всех выражает намерение: «на Unix ждём вот это, на Windows — вот то».
- Не требует переименования существующих тестов (Unix-вариант остаётся как есть).

**Cons:**
- Дублирование пяти тестов → **десять**; каждая будущая правка `parse_compile_args`
  требует синхронной правки двух копий — ровно тот способ, которым тесты
  разъезжаются (и уже разъехались: `split_*`-секция `cfg`-разделена, а
  `parse_*` — нет).
- Windows-копии **невидимы на Unix** (не компилируются) → опечатка в них
  всплывёт только в CI. Умножает нагрузку на решение 3.
- Противоречит правилу о размере модуля: `lamc.rs` — 1149 строк при лимите ~1000
  (`CLAUDE.md`), +5 тестов усугубляют существующее нарушение.

### Решение 2. Как чинить POSIX-путь в тесте `viewport`

#### Option E. Удалить отладочную запись

Убрать `fs::write("/tmp/…")` и `println!` — оставить только `assert!`.

**Pros:**
- Убирает причину падения **и** побочный эффект: сейчас тест на macOS/Linux
  молча гадит файлом в общий `/tmp` при каждом прогоне — тест не должен оставлять
  артефактов и тем более гоняться за право писать в фиксированное имя (проект
  гоняет тесты `--test-threads=1` именно из-за гонок за общие файлы, `CLAUDE.md`).
- Ничего не теряется: `assert!` работает со строкой в памяти, дамп в проверке не
  участвует.
- Дифф — минус две строки; риск нулевой.

**Cons:**
- Исчезает удобство «посмотреть SVG глазами» при отладке падения. Митигация:
  сообщение `assert!` уже печатает фрагмент SVG, а при нужде дамп воспроизводится
  одной строкой локально.

#### Option F. Писать в `std::env::temp_dir()`

**Pros:**
- Кросс-платформенно; дамп сохраняется для отладки.

**Cons:**
- Оставляет тесту **побочный эффект и обращение к ФС**, которых он не требует, —
  и вместе с ним `unwrap()` на ФС-операции, то есть падение теста по причине, не
  связанной с проверяемым свойством (полный диск, права, антивирус на Windows).
- Фиксированное имя в общем каталоге сохраняет риск гонки при параллельных
  прогонах.

#### Option G. `tempfile::tempdir()` (как в `state_io.rs:258`)

**Pros:**
- Кросс-платформенно, изолированно, самоочищается; согласуется с образцом в том
  же крейте (`tempfile` уже в зависимостях `simulation`).

**Cons:**
- Каталог удаляется по выходу из теста — то есть «сохранить дамп для отладки»,
  единственный мотив записи, **не достигается вовсе**. Получаем сложность без
  выгоды.

### Решение 3. Ставить ли Windows в матрицу CI

#### Option H. Добавить job `windows` (`windows-latest`)

**Pros:**
- **Единственное, что закрывает причину.** Пока Windows не в CI, дисциплина
  `cfg`/путей держится на памяти разработчика — и уже дважды не сдержалась.
- **Единственный доступный способ проверить эту фичу** (правило 5): на macOS все
  шесть тестов зелены и до, и после правки. Без раннера критерии приёмки 0037
  непроверяемы в принципе.
- Windows — заявленная платформа: продукт содержит `#[cfg(windows)]`-ветки
  (`split_include_dirs`), а отчёт 0021 писался на Windows 11. Ветка, которую
  никто не собирает, — мёртвый код по факту.
- Дёшево: GitHub Actions даёт `windows-latest` бесплатно для публичных
  репозиториев; job копируется с `ubuntu` (~10 строк YAML).
- Защищает **все** последующие фичи, а не только 0037.

**Cons:**
- **Windows-минуты дороже** (для приватных репозиториев — множитель ×2 к
  тарификации); время прогона на Windows заметно выше (медленная ФС, линковка).
  Полное время `push`-прогона примерно удваивается.
- **Риск разовой стабилизации:** на Windows-раннере впервые окажутся тесты,
  которых там никогда не гоняли. Кроме шести известных могут всплыть новые
  (кандидаты риска: `precheck.sh`-подобные пути, `cmake/ninja`-обвязка примеров,
  системные шрифты `fontdb` для `resvg`, `/tmp/stacker_sim.log` в
  `scripts/precheck.sh:63` — в CI не вызывается, но тот же класс). Пока они не
  разобраны, CI может быть красным.
  Митигация — см. Decision (job **не блокирует** до стабилизации).
- Выбор ABI не нейтрален: `windows-latest` по умолчанию даёт **MSVC**, а отчёт
  0021 писался на **GNU/MinGW**. Полного совпадения окружений не будет.

#### Option I. Оставить CI как есть (только Ubuntu)

**Pros:**
- Ноль затрат; прогон остаётся быстрым; ни одного нового красного job.
- Основная цель проекта (правило 12) — синтез C для промышленных систем; сборка
  тулчейна под Linux покрывает типового пользователя.

**Cons:**
- **Гарантирует рецидив.** Ровно так и появились обе поломки. Формулировка
  кандидата в `FEATURES.md` («оформить фикс/фичу») лечит шесть тестов; седьмой
  прилетит на следующей фиче.
- Правки 0037 **невозможно проверить** — фича закрывается на честном слове.
- `#[cfg(windows)]`-ветки продукта остаются непроверяемыми **никогда и никем**.

#### Option J. Полная матрица (`ubuntu` + `windows` + `macos`)

**Pros:**
- Максимальное покрытие; macOS — платформа текущей разработки (аналитик работает
  на darwin), и она тоже сейчас не в CI.
- Стоимость `macos-latest` для публичных репозиториев — тоже бесплатно.

**Cons:**
- Утраивает время и площадь стабилизации **в рамках фичи, у которой другая
  цель**. macOS-раннер не имеет отношения ни к одному из шести падений.
- macOS-минуты — самые дорогие (множитель ×10 для приватных репозиториев).
- Три платформы разом — три источника нового красного; риск, что фича 0037
  надолго увязнет в чужих дефектах, максимален.

## Decision

Принимается **комбинация A + E + H**.

**Решение 1 → Option A (параметризация тестов разделителем).** Продуктовый код
корректен, поэтому чинится то, что сломано, — тесты. Вариант A даёт наименьший
дифф при нулевом риске и **не трогает CLI-контракт** (правило 11). Options B и C
отвергнуты как правки продукта ради теста: B к тому же тихо ломает обрезку
пробелов и фильтрацию пустых сегментов (и **не чинит** сами падения — они не в
`split_include_dirs`), C ломает документированную форму `-I /a:/b` тихой
деградацией. Option D отвергнут как дублирование, умножающее расхождение — тот
самый механизм, которым дефект и возник.

Отдельно: наблюдение Option B о **кавычках** на Windows — реальный, ранее не
известный пробел (`-I "C:\dir with spaces";C:\other` разбирается неверно). Он
**не относится** к падениям 0037 и выносится **в бэклог** как кандидат «типизация
путей include (`Vec<PathBuf>` + `split_paths`) со сквозной правкой публичного
API `grammar`» — вместе с осознанным решением судьбы обрезки пробелов и пустых
сегментов. Правило 2 (декомпозиция): смешивать это с починкой тестов нельзя.

**Решение 2 → Option E (удалить отладочную запись).** Запись не участвует в
проверке, нарушает подводный камень `CLAUDE.md` про пути и оставляет побочный
эффект в общем `/tmp`. Options F и G сохраняют обращение к ФС там, где оно не
нужно; G вдобавок удаляет дамп сразу после записи, обнуляя единственный мотив
его существования.

**Решение 3 → Option H (Windows в матрицу; macOS — нет).** Это ядро фичи:
без раннера критерии приёмки 0037 непроверяемы, а класс дефектов гарантированно
вернётся. Option I отвергнут: он оставляет фичу недоказуемой. Option J отвергнут
по правилу 2 — macOS не имеет отношения к падениям и утраивает площадь
стабилизации; **macOS в матрицу — отдельным кандидатом бэклога**.

Условия принятия H, снимающие риск «красного CI»:

1. Job `windows` добавляется с **`continue-on-error: true`** и остаётся таким до
   первого зелёного прогона (подзадача 0037-03). Так фича не блокируется чужими,
   ещё не разобранными дефектами Windows.
2. Снятие `continue-on-error` — **явный шаг с отдельным коммитом** после первого
   зелёного прогона. До снятия фича **не переводится в `ГОТОВО`**: иначе
   получится нескончаемо жёлтый job, который никто не читает.
3. Любые **новые** падения, вскрытые job `windows` (сверх шести известных),
   **не втягиваются** в 0037: они заводятся кандидатами в `FEATURES.md`
   (правило 7). 0037 отвечает ровно за шесть перечисленных.
4. Тулчейн job `windows` — **тот же nightly**, что в `ubuntu`, ABI по умолчанию
   для `windows-latest` (**MSVC**). Расхождение с окружением отчёта 0021
   (GNU/MinGW) принимается осознанно: MSVC — умолчание платформы и типовой выбор
   пользователя; проверка обоих ABI избыточна для целей фичи. Если сборка
   упрётся в MSVC-специфику, откат на `-gnu` — решение внутри 0037-03.

Сопутствующие наблюдения, **вынесенные в бэклог** (правило 7, не входят в 0037):

- **CI не соблюдает `--test-threads=1`.** `ci.yml` вызывает `cargo test` без
  флага, тогда как `CLAUDE.md` и `scripts/precheck.sh:22` требуют однопоточного
  прогона «иначе гонки за общие файлы». На Windows с его блокировками файлов
  цена гонки выше, чем на Linux. Правка однострочная, но это **изменение
  контракта прогона для всех платформ** — отдельный кандидат, а не довесок к 0037.
- **`actions-rs/*` не поддерживаются** (архивированы автором); `actions/checkout@v2`
  устарел. Модернизация (`dtolnay/rust-toolchain`, `checkout@v4`) — отдельный
  процессный кандидат: она задевает **весь** CI, а не Windows-часть.
- **Латентный паникёр в том же тесте:** `&svg_str[..500]` в сообщении `assert!`
  (`viewport.rs:1457`) паникует, если SVG короче 500 байт или граница попадает
  внутрь UTF-8-символа. Срабатывает только на уже провалившемся assert (маскируя
  сообщение), к Windows отношения не имеет. Правится в 0037-02 попутно **как
  часть той же строки кода**, чтобы не оставлять полуисправленный тест.

## Consequences

### Положительные

- Прогон тестов на Windows становится осмысленным: 0 известных падений вместо 6;
  правило 5 выполнимо на всех трёх платформах разработки.
- Дисциплина «платформо-зависимое поведение → платформо-зависимый тест»
  доведена до конца в `lamc.rs` и **проверяется машиной**, а не памятью.
- Тест `viewport` перестаёт оставлять артефакт в общем `/tmp` на всех
  платформах — попутно снимается источник гонки при параллельных прогонах.
- Продуктовый код и CLI-контракт `lamc` не тронуты — регресс невозможен
  по построению (правило 11).
- `#[cfg(windows)]`-ветки продукта впервые получают реальную сборку и прогон.

### Отрицательные / Action items

- **Время CI растёт** примерно вдвое (Windows-раннеры медленнее).
- **Возможен период жёлтого job `windows`** до разбора ранее не проверявшихся
  тестов. Ограничено условиями 1–3 Decision.
- **Action item:** снять `continue-on-error` отдельным коммитом после первого
  зелёного прогона; до этого 0037 не закрывать.
- **Action item:** завести кандидатов в `FEATURES.md`: (а) типизация путей
  include (`PathBuf`/`split_paths` + кавычки на Windows + судьба обрезки
  пробелов); (б) `--test-threads=1` в CI; (в) модернизация `actions-rs`/`checkout`;
  (г) macOS в матрицу CI.
- **Action item:** отразить правило «платформо-зависимое поведение проверяется
  платформо-параметризованным тестом» в `docs/CODE.md` — иначе решение снова
  не доедет до следующей секции тестов. (Правка `docs/CODE.md` — вне границ
  0037; кандидат в бэклог.)
- **Остаточный риск:** MSVC в CI против GNU/MinGW в отчёте 0021 — падения,
  специфичные для MinGW, матрицей не ловятся.

### Acceptance criteria

1. В `grammar/src/bin/lamc.rs` **ни один** безусловный `#[test]` не зашивает
   `:` как разделитель списка путей: проверяется чтением диффа и `grep` по
   `mod tests` на литералы вида `"…:/…"` вне `#[cfg(not(windows))]`.
2. Пять тестов разбора `-I` проходят на обеих платформах; на macOS/Linux
   `cargo test --bin lamc -- --test-threads=1` остаётся **44/44** (число тестов
   не уменьшается: параметризация, а не удаление).
3. `split_include_dirs`, `parse_compile_args`, `CompileOptions`, `print_usage()`
   и модульная документация `lamc.rs` **не изменены** — дифф подзадачи 0037-01
   не выходит за пределы `mod tests` (проверка: `git diff` по файлу).
4. В `simulation/src/unit/viewport.rs` отсутствуют обращения к ФС в
   `#[cfg(test)]`-коде (`grep` на `fs::write`/`"/tmp` в тестовых секциях файла →
   пусто); `test_highlight_frame_contains_orange_bg` зелёный на macOS/Linux.
5. `.github/workflows/ci.yml` содержит job `windows` на `windows-latest`, шаги —
   те же, что в `ubuntu` (build/check/test).
6. **Итоговый критерий:** job `windows` даёт **зелёный** прогон
   `cargo build --all-features --all-targets --examples`, `cargo check`,
   `cargo test`, после чего `continue-on-error` снят. Только с этого момента
   фича может перейти в `ГОТОВО`.
