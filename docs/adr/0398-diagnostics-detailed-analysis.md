# ADR 0398: Подробный разбор кодов диагностик в приложении

- **Status:** Proposed — **признак отбора выбирает заказчик**
- **Date:** 2026-08-22
- **Authors:** Архитектор + Аналитик
- **Related issues:** [Фича 0398](../features/0398-diagnostics-detailed-analysis.md);
  описания — [0311](0311-diagnostic-descriptions.md); сверка кодов —
  [0290](0290-book-diagnostics-codes-gate.md)

## Context

Приложение `book/` «Ошибки и предупреждения» состоит из двух частей: **сводная
таблица** (называет смысл каждого кода — работа 0311, сторожится гейтом
`check-diagnostic-descriptions.py`) и **подробный разбор** (пример входа + вывод
инструмента).

Замер **переснят 2026-08-22**:

| Что | Прежняя запись (0311, 2026-08-20) | Пересъём |
|---|---|---|
| кодов в реестре | 229 | **234** |
| кодов в приложении | — | **234** (сверено гейтом 0290) |
| разборов | 83 | **85** (заголовков `===` — 97, из них с кодом — 85) |

То есть разобрано **85 из 234**; за два дня реестр вырос на пять кодов, а
разборов прибавилось два. Пропорция сама по себе не дефект: разбор нужен там,
где текст диагностики без примера непонятен.

⚠️ **Машина здесь бессильна по существу:** «заслуживает ли код разбора» —
вопрос о пользе, а не о согласованности. Список «кому нужен разбор» пришлось бы
вести руками, и он разошёлся бы с документом (класс 0084/0193/0195).

## Decision Drivers

1. **«Разобрать все» — не цель:** 234 разбора превратят приложение в свалку, а
   большинство кодов понятны из описания (0311 это и обеспечила).
2. **Признак отбора должен быть проверяемым**, иначе список станет вкусовым и
   расползётся.
3. **Гейт уже сверяет состав** (0290: множества кодов тождественны) — значит
   новый разбор не может «повиснуть» на несуществующем коде.
4. **Цена одного разбора невелика** (пример + вывод инструмента), но их
   десятки — работа объёмная и должна иметь границу.

## Considered Options

### Option A. Отобрать по признаку вреда (Tier класса ошибки)

Разбирать коды, за которыми стоит **молчаливое расхождение** или **невалидный
вывод** — то есть те, что рождены фичами Tier 1–2.

**Pros:** признак объективен и уже применяется к фичам; список выводится из
карточек, а не ведётся руками.
**Cons:** привязывает документ к внутренней шкале процесса — читателю она
неизвестна (правило 24: номеров фич и процесса в документе быть не должно).
Значит признак используется **при отборе**, но в документ не попадает.

### Option B. Отобрать по частоте: коды, которые автор встречает чаще

**Pros:** прямая польза читателю.
**Cons:** частоту нечем измерить — телеметрии нет; оценка была бы вкусовой.

### Option C. Отобрать по «непонятности текста»: код, чьё сообщение не
объясняет причину без примера

**Pros:** ровно тот случай, ради которого разбор существует.
**Cons:** оценка субъективна; но её можно свести к проверяемому признаку —
**сообщение ссылается на устройство** (`представление`, `понижение`,
`раскладка`, `упакованный`) либо называет **чужой инструмент** (`iec2c`,
`verilator`, `clippy`).

### Option D. Оставить как есть

**Cons:** приложение обещает «разбор основных ошибок», не называя, что такое
«основные»; читатель не знает, почему одного кода нет.

## Decision

**Признак отбора выбирает заказчик.** Аналитик предлагает **C** (сообщение
ссылается на устройство или на чужой инструмент) как единственный
**проверяемый** признак: его можно применить грепом по реестру и получить
воспроизводимый список, а не вкусовой.

⚠️ Что бы ни было выбрано, вторая часть приложения обязана **назвать свой
признак** — сегодня она называется «Подробный разбор основных ошибок», и слово
«основных» ничем не определено.

## Consequences

### Положительные

- Читатель понимает, почему разобран один код и не разобран другой.
- Список воспроизводим: следующая фича, заводя код, сразу знает, нужен ли ему
  разбор.

### Отрицательные / Action items

- Работа объёмная: даже узкий признак даст десятки разборов.
- Каждый разбор — пример **и** вывод инструмента; вывод обязан быть снят
  прогоном, а не написан по памяти (иначе класс «проза расходится с кодом»).
- Гейт 0290 придётся дополнить: сегодня он сверяет состав кодов, но не
  проверяет, что разобранные коды удовлетворяют признаку.

### Acceptance criteria

1. Признак назван в самом приложении (в первом абзаце второй части).
2. Список разобранных кодов получается **применением признака**, а не
   перечислением: тот же признак воспроизводится скриптом.
3. Каждый новый разбор содержит вход и **снятый прогоном** вывод инструмента.
4. Гейт 0290 расширен проверкой признака (или заведён соседний).
5. `make -C book build` зелёный; `./scripts/precheck.sh` зелёный.
