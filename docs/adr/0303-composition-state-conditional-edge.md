# ADR 0303: Условное ребро состояния-композиции

- **Status:** Accepted
- **Date:** 2026-08-19
- **Authors:** Архитектор + аналитик + разработчик
- **Related issues:** [Фича 0303](../features/0303-composition-state-conditional-edge.md); найдено контрольным входом при закрытии [0267](../features/0267-state-of-model-in-targets.md); правило «переход берётся по завершении реализации» — [0181](../features/0181-sim-state-implementation-tick.md); порядок `ref` перед `next` — там же; безусловное ребро завершает цепочку — [0213](../features/0213-c-redundant-break.md)

## Context

Состояние может нести **реализацию** — композицию моделей — и при этом иметь
собственные рёбра:

```takt
start Entry = Worker | Idler {
    ref Finish: flag = 3;      // собственное ребро состояния-композиции
}

state Finish;
```

Правило языка задано фичей [0181](../features/0181-sim-state-implementation-tick.md):
реализация тикается **до** проверки переходов, и переход берётся **по её
завершении** — на том же такте. Эталон исполняет это буквально: после
завершения композиции он проверяет переходы состояния — сначала `ref`-рёбра в
порядке объявления, затем `next` (последним, «иначе безусловный `next` затенил
бы их все» — комментарий `build_transitions`).

**Замер 2026-08-19 (`scripts/probe.sh`, правило 30) показал, что цели этого не
делают: они печатают только `next`, а собственные `ref`-рёбра теряют.**

| Вход | Эталон | Все восемь целей |
|---|---|---|
| `ref Finish: flag = 3;`, условие истинно в момент завершения | → `Finish` | → `END` |
| `ref Finish: flag = 99;`, условие ложно всегда | **остаётся** в `Entry` | → `END` |
| `next Finish;` (контроль) | → `Finish` | → `Finish` |

Порождённый C на первом входе:

```c
case PLAINCOND_ENTRY: {
    PlaincondWorker_tick(&model->entry.worker0, model);
    PlaincondIdler_tick(&model->entry.idler1, model);
    if (PlaincondWorker_is_done(…) && PlaincondIdler_is_done(…)) {
        model->state = PLAINCOND_END;   // ребро `ref Finish` не напечатано
        break;
    }
    break;
}
```

Состояние `Finish` в перечислении объявлено и **недостижимо**. Вывод валиден,
`cc -Wall -Wextra -Werror` молчит, `verilator` и `yosys` молчат, `iec2c`
принимает — **автомат другой, и об этом не говорит никто**. Это `Tier 1` по
шкале `FEATURES.md`.

⚠️ **Расхождение двустороннее.** Мало того, что цели не идут в `Finish`, — они
уходят в `END` там, где эталон **ждёт** (второй вход): при ложном условии
композиция уже завершена, но переход не разрешён, и узел остаётся в состоянии.

⚠️ **Контроль отделил форму от предмета.** Замер снят дважды: с формой
`S(Модель) = Состояние` и с обычным условием (`flag = 3`) — результат один и
тот же. То есть дело не в виде условия, а в том, что рёбра состояния-композиции
не печатает никто. Третий контроль (`next`) показывает, что механизм перехода у
целей есть — не хватает именно `ref`-рёбер.

## Decision Drivers

1. **Норма уже определена и записана** — правилом 0181 и порядком
   `build_transitions` эталона. Речь не о выборе семантики, а о том, что цели её
   не исполняют.
2. **Молчание — худшая часть дефекта.** Инструменты целевых языков этот класс не
   видят: вывод валиден при любом исходе.
3. **Механизм перехода в целях есть.** `next` печатается всеми; недостаёт
   печати `ref`-рёбер в той же ветви.
4. **Отказ вместо перевода был бы регрессом:** запись законна, эталон её
   исполняет, а корпус её не содержит — то есть запрет ударил бы по чужим
   моделям ради нашего удобства.

## Considered Options

### Option A. Печатать `ref`-рёбра в ветви завершения композиции (норма эталона)

Внутри `if (композиция завершилась)` цель печатает сначала условные рёбра
состояния (в порядке объявления; безусловное завершает цепочку — правило 0213),
затем `next` либо `END`.

**Pros:**
- цели начинают исполнять уже записанное правило языка;
- механизм переиспользуется: печать рёбер у обычных состояний есть в каждой
  цели;
- расхождение снимается в **обе** стороны — и «не пошёл в `Finish`», и «ушёл в
  `END` вместо ожидания».

**Cons:**
- правка в четырёх целях; несогласованность видна только сверкой (вывод остаётся
  валидным).

### Option B. Отвергать такую запись семантикой

**Pros:** одна проверка вместо четырёх правок.

**Cons:** запрещает законную и работающую в эталоне конструкцию; правило 0181
прямо описывает её поведение. Это регресс языка ради удобства целей.

### Option C. Оставить как есть, задокументировав различие

**Pros:** ноль правок.

**Cons:** документирует расхождение вместо его устранения — прошивка ведёт себя
не так, как отлаженная в симуляторе модель. Ровно тот класс, ради которого
заведены потактовые сверки.

## Decision

Принимается **Option A**.

Цели `c`, `st`, `rust`, `sv` (а с ними `c-hal`, `st-at`, `sv-mmio`) печатают
собственные рёбра состояния-композиции внутри ветви завершения — **перед**
переходом по `next`/`END`, в порядке объявления. Порядок и приоритет берутся у
эталона: `ref` вперёд, `next` последним.

Сторож — **потактовые сверки**, а не гейты: инструменты целевых языков принимают
и прежний, и новый вывод.

## Consequences

### Положительные

- эталон и цели сходятся на записи, которую язык допускает с 0181;
- недостижимое состояние в перечислении перестаёт быть недостижимым;
- ожидание при ложном условии воспроизводится в прошивке.

### Отрицательные / Action items

- вывод целей на таких входах меняется — но в `examples/` записи нет ни одной
  (проверено), поэтому снапшоты корпуса не двигаются;
- в документ (`book/`, раздел о композиции) добавляется описание перехода из
  состояния-композиции: когда проверяются рёбра и почему `next` идёт последним.

### Acceptance criteria

1. Вход с истинным условием: эталон и цели `c`, `sv`, `rust`, `st` дают
   переход в `Finish` (потактовые сверки).
2. Вход с ложным условием: все они **остаются** в состоянии-композиции.
3. Контроль `next` — прежнее поведение сохранено.
4. Безусловное `ref`-ребро завершает цепочку (правило 0213): `next`/`END` после
   него не печатается.
5. Корпус и гейты целей не изменились; `./scripts/precheck.sh` зелёный.
