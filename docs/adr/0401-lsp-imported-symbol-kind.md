# ADR 0401: Вид импортированного символа в LSP

- **Status:** Proposed — исполнителю; **брать по решению заказчика** (цена сегодня мала)
- **Date:** 2026-08-22
- **Authors:** Архитектор + Аналитик
- **Related issues:** [Фича 0401](../features/0401-lsp-imported-symbol-kind.md);
  замер — [0256](0256-lsp-import-binding-kind.md); отвергнутый индекс —
  [0153](0153-lsp-workspace-index.md)

## Context

Имя из `import { a } from "lib.takt";` получает вид `SymbolKind::Imported`,
отвечающий **любому** пространству имён. Настоящий вид (порт, функция,
переменная, тип) записан в **чужом** файле, а слой `semantic::usages`
однофайловый по устройству: его зовут и там, где рабочей области нет вовсе —
подсветка, форматирование, плагины поверх библиотеки.

Замер 0256 (2026-08-19) подтверждён чтением 2026-08-22: вид символа читает
**одно** место — `lsp/rename.rs` (отказ на имени модели), поэтому цена
неточности мала.

⚠️ Точный вид требует чтения источника, то есть либо многофайлового слоя, либо
состояния, обязанного не устаревать, — ровно того, что ADR 0153 отверг замером
(12 мс на 347 файлов по требованию против индекса, который надо поддерживать).

## Decision Drivers

1. **Цена неточности сегодня мала** — один потребитель вида.
2. **Цена точности известна и высока** — многофайловый слой либо кэш; 0153
   отверг его замером, а 0257 (кэш по mtime) **заморожена** заказчиком.
3. **Ошибка допущения односторонняя:** `Imported` отвечает любому
   пространству, то есть даёт **лишнюю** связь внутри файла, где имя и так
   занято импортом, — а не теряет настоящую.
4. **Класс подорожает**, если вид начнёт влиять на подсветку или
   автодополнение: тогда `Imported` покажет неверную иконку.

## Considered Options

### Option A. Оставить (статус-кво)

**Pros:** ноль работы; поведение корректно для единственного потребителя.
**Cons:** запись остаётся в бэклоге и всплывает при каждой правке слоя.

### Option B. Читать источник по требованию — только в LSP-путях

Там, где рабочая область есть (а это ровно `references`/`rename`, 0153),
разрешать имя в источнике и брать настоящий вид.

**Pros:** не заводит состояния; пользуется уже имеющимся обходом области;
точность появляется там, где она нужна.
**Cons:** вид символа становится зависимым от контекста вызова — в
однофайловых путях (подсветка, форматирование) он останется `Imported`. То есть
знание раздваивается: «вид без области» и «вид с областью».

### Option C. Многофайловый слой `usages`

**Cons:** отвергнут замером 0153; воскрешать его ради вида символа
несоразмерно.

## Decision

Предлагается **Option A** (оставить) до появления **второго** потребителя вида;
если он появится — **Option B**.

Довод: сегодня вид читает одно место, и `Imported` там работает верно; Option B
раздваивает понятие «вид символа», а Option C уже отвергнут замером. Решение
брать фичу — за заказчиком.

⚠️ **Сигнал к пересмотру назван:** как только вид символа начнёт влиять на
подсветку (`semantic_tokens`) или автодополнение, `Imported` станет видимой
неточностью — иконка и группа в списке окажутся неверными.

## Consequences

### Положительные (A)

- Ноль работы; слой остаётся однофайловым, как решено 0153.

### Отрицательные / Action items

- Неточность сохраняется; при появлении второго потребителя вида фичу надо
  брать (Option B).

### Acceptance criteria (для Option B)

1. В путях с рабочей областью вид импортированного символа совпадает с видом
   объявления в источнике.
2. В однофайловых путях поведение прежнее (`Imported`), и это **названо** в
   коде — иначе разница читается как дефект.
3. `rename` по-прежнему «полнота в пределах рабочей области или отказ» (0153).
4. Тесты `lsp55`, `ws0153`, `goto56` зелены; `precheck.sh` зелёный.
