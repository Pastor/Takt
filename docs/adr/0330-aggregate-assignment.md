# ADR 0330: Присваивание агрегата печатается поэлементно

- **Статус:** Accepted
- **Дата:** 2026-08-20
- **Фича:** [../features/0330-aggregate-assignment.md](../features/0330-aggregate-assignment.md)

## Контекст

Замер 2026-08-20 на `a := {1, 2};` в теле состояния (`a: [u8; 2]`):

| Потребитель | Ответ |
|---|---|
| эталон, `c`, `c-hal`, `rust`, `plantuml` | исполняют; цель `c` печатает `model->a[0] = 1; model->a[1] = 2;` |
| **`st`, `st-at`** | **`ST-011`**, и текст обещал «часть 2 задачи 0041-04» |
| **`sv`, `sv-mmio`** | **`SV-002`** |

Текст отказа `st` обещал работу, которой нет: класс «ветвь-заглушка,
пережившая свою задачу» (урок фикса 0134-02).

## Решение

Обе цели печатают присваивание **поэлементно** — так же, как цель `c`:

```
a[0] := 1;      (* st *)
a_next[0] = 1;  // sv
```

Значение элемента печатается **по типу элемента** (`coerce`), поэтому вариант
перечисления и логический литерал восстанавливаются, как и при обычном
присваивании.

## Почему не агрегатная форма

- В IEC 61131-3 агрегатной формы значения массива **нет вовсе** — присвоить
  список нечем.
- У `sv` шаблон `'{…}` работает в ветви сброса (фича 0309), но в `always_comb`
  его пришлось бы согласовывать по ширине с каждым элементом; поэлементная
  форма выразима всегда и совпадает с той, что уже печатает цель `c`.

## Последствия

- Присваивание агрегата переводят все восемь целей.
- Сверка потактовая: значения элементов **разные** и меняются по тактам, иначе
  перепутанный порядок или потеря присваивания были бы незаметны.
