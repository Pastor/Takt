# ADR 0049: Верификация модели (Model Checking) на основе LTL

## Context

Конвейер верификации оборвался на середине. Затравка `grammar/src/verification/`
(фича 0010) даёт **два первых звена** — проверено чтением кода:

| Готово | Место | Факт |
|---|---|---|
| Тип `Ltl` (11 вариантов, `Hash`/`Ord`/`Display`) | `verification/ltl.rs:11` | пригоден как состояние автомата |
| Мост АСД→семантика | `semantic/formula.rs:57` | `ltl_ast_to_semantic` (полные имена атомов) |
| NNF / отрицание | `verification/buchi.rs:6` | `to_nnf(&Ltl) -> Rc<Ltl>` |
| Автомат Бюхи (GPVW + дегенерализация GBA→BA) | `verification/buchi.rs:327` | `build_buchi(&Ltl) -> BuchiAutomaton` |
| Сбор атомов | `semantic/ltl_check.rs:172` | `collect_atoms` |
| Граф FSM (сырьё) | `semantic/mod.rs:1023`, `:1455` | `StateNode.references()`, `ReferenceNode{name,cond,object}` |
| Обход переходов (образец) | `generator/c/c_model.rs:430` | `generate_state_transitions` |

**Отсутствует середина конвейера** (grep по `product|emptiness|kripke|nested_dfs|
scc|counterexample` — 0 совпадений; `build_buchi` **не вызывается** вне
юнит-тестов):

1. **Структура Крипке** из `ModelNode` — переиспользуемый граф «состояния + рёбра
   + разметка пропозиций». Сейчас логика графа вплавлена в C-генератор.
2. **Оценка атома в состоянии** — `Ltl::Atom(String)` семантически ни с чем не
   связан; `ltl_check` (0035) лишь сверяет имя (SE-056), предиката нет.
3. **Синхронное произведение** модели Крипке с автоматом `¬φ`.
4. **Проверка пустоты** — достижимый принимающий цикл (nested-DFS / SCC).
5. **Контрпример** — лассо (префикс + цикл).
6. **CLI `lamc verify`** — подкоманды нет (есть только `compile`, `fmt`).

Итог: `: [LTL] φ;` сегодня — терминальная аннотация. Фича 0044 сделала имя
инварианта атомом LTL, 0035 — разбор во всех позициях; но **проверить** свойство
нечем. Профильная цель проекта (правило 12 — синтез автоматных моделей
промышленных систем) требует формальной проверки свойств **до** синтеза.

### Ключевая развилка: что такое атом и какова структура Крипке

Атом LTL — голое имя. Что оно обозначает над моделью Lam и как построить конечную
структуру Крипке — **языковое решение, не техническое**; принимает заказчик.

## Decision Drivers

1. **Профильная цель (правило 12).** Формальная проверка свойств автоматной
   модели — не украшение, а прямое назначение DSL промышленных систем.
2. **Переиспользовать затравку, не переписывать.** `build_buchi` тотальна и
   протестирована; решение обязано опереться на неё, а не строить второй автомат.
3. **Конечность и разрешимость.** Структура Крипке обязана быть конечной, иначе
   проверка не завершается. Абстракция выбирается так, чтобы гарантировать
   конечность by construction.
4. **Соразмерность объёма.** Полный explicit-state (control × data) даёт взрыв
   пространства (u8 = 256 значений/переменную); символьный MC — отдельный крупный
   проект. Первый рабочий срез обязан быть цельным и завершаемым.
5. **Честная граница.** Что **не** проверяется — сообщается явно (наследие 0035:
   ни один путь LTL не молчит).

## Considered Options

Развилка — **семантика атома + структура Крипке** (вынесена заказчику).

### Option A (принимается). Управляющий граф: атом = состояние FSM

Атом `S` истинен в состоянии Крипке `k` ⟺ `k` — состояние с именем `S`. Структура
Крипке = граф переходов автомата: вершины — состояния FSM, рёбра — `ref`-переходы
(гарантии абстрагированы: любой guarded-`ref` считается **возможным**
недетерминированным переходом). Данные (`var`/порты) в разметку не входят.

**Pros:**
- **Конечна и разрешима by construction**: |Крипке| = число состояний FSM.
- Ложится на природу Lam (это и есть FSM); граф переходов уже обходится
  (`c_model.rs:430`) — образец переиспользуется.
- Проверяемы содержательные свойства управления: достижимость, порядок состояний
  (`G(Fault -> F Idle)`), живость, отсутствие тупиков.
- Затравка `build_buchi` используется как есть; атом-предикат тривиален (сравнение
  имени состояния).
- Соразмерна первому срезу; расширение на данные — отдельная фича поверх.

**Cons:**
- Свойства над **данными** (`G(temp <= 100)`) невыразимы — атом-переменная/`cond`
  не проверяется. Сообщается явно (диагностика: «атом — имя состояния; условие/
  переменная в этой абстракции не поддержаны»).
- Абстракция гарантий (guarded-`ref` → возможный) даёт **over-approximation**:
  контрпример может быть недостижим по данным (ложное срабатывание). Осознанный
  размен; фиксируется в документации и контрпримере пометкой «абстракция
  управления».

### Option B. Явное состояние (control × data) через симулятор

Атом = состояние ИЛИ `cond`/переменная, вычисляемые конкретно; Крипке = достижимые
пары (состояние × оценка данных), перечисляемые прогоном симулятора.

**Pros:**
- Точность по данным: `G(temp <= 100)` проверяемо; контрпримеры реальны.

**Cons:**
- **Взрыв пространства состояний** (256^n): без предела/оптимизации не
  завершается на реальных моделях.
- Втягивает крейт `simulation` как генератор состояний — межкрейтная зависимость и
  крупный объём, несоразмерный первому срезу (драйвер 4).
- Требует решить, как атом-`cond` вычисляется символически/конкретно.

### Option C. Bounded Model Checking (разворот на k шагов)

Развернуть модель на `k` тактов, искать контрпример длины ≤ k.

**Pros:**
- Дёшево находит короткие контрпримеры с данными.

**Cons:**
- **Не доказывает** свойство (только опровергает до глубины k) — для верификации
  «свойство держится всегда» непригодно.
- **Не использует затравку** `build_buchi` — другой алгоритм (обычно SAT), то есть
  выбросить готовое звено и построить новое.

## Decision

Принимается **Option A** — решение заказчика от 2026-07-16.

Обоснование. A — единственная опция, которая (1) конечна и разрешима без предела,
(2) переиспользует затравку `build_buchi` целиком, (3) ложится на природу Lam как
FSM и на уже существующий обход графа переходов, (4) соразмерна первому рабочему
срезу. B точнее по данным, но взрывается и втягивает симулятор; C не доказывает
свойство и игнорирует затравку. Ограничение A (данные вне охвата) **честно
сообщается** (наследие 0035) и снимается отдельной фичей-расширением (explicit-
state или символьный MC), которая строится поверх готового конвейера A.

**Конвейер (стандартный автоматный подход):** для свойства `φ` строится автомат
`A_¬φ = build_buchi(Not(φ))`; синхронное произведение `K × A_¬φ`; проверка
пустоты языка произведения (достижимый принимающий цикл). Пусто ⟹ `φ` держится;
непусто ⟹ найден контрпример-лассо, нарушающий `φ`.

## Consequences

### Положительные

- `: [LTL] φ;` впервые **проверяется**: `lamc verify` даёт вердикт держится/нарушено
  с контрпримером. Профильная возможность DSL реализована.
- Затравка `verification/` входит в продуктовый контур (сейчас — только ради
  собственных тестов).
- Класс дефекта «LTL — терминальная аннотация» закрыт для управляющих свойств;
  SE-055 (0035) для проверяемых формул снимается (появляется потребитель).
- Конечный, завершающийся, детерминированный алгоритм — воспроизводимый вердикт.

### Отрицательные / Action items

- **A1.** Явная разметка алфавита: извлечь литералы (`Atom`/`Not(Atom)`) из
  состояний `BuchiAutomaton` (сейчас неявны в `states[i].old`) для согласования в
  произведении.
- **A2.** Терминальные/тупиковые состояния FSM: добавить самопетлю (stutter),
  иначе конечные прогоны не дают бесконечных слов, которых требует семантика Бюхи.
- **A3.** Свойства над данными невыразимы — **явная диагностика** при атоме, не
  являющемся именем состояния (в выбранной абстракции), плюс раздел README.
- **A4.** Over-approximation: контрпример может быть недостижим по данным —
  пометить в выводе «абстракция управления» (правило 5 — честность результата).
- **A5.** Версия языка **не растёт**: синтаксис не меняется, `lamc verify` —
  аддитивная оснастка (прецедент `lamc fmt`, фича 0024). Атом получает
  **операционный** смысл (имя состояния), но принимаемое множество программ то же.
- **A6.** `parse_ltl` (`ltl.rs`) остаётся тестовым (паникует, атом = 1 символ) —
  продуктовый путь идёт через `ltl_ast_to_semantic`; не трогается.
- **A7.** Кандидаты-расширения (вносит координатор, правило 7): (1) верификация
  свойств над данными (explicit-state/символьный MC); (2) `X`-оператор и точная
  трактовка stutter на терминальных; (3) контрпример как трасса симулятора.

### Acceptance criteria

1. `lamc verify <file.lam>` проверяет все `: [LTL] φ;` модели: для держащегося
   свойства — «держится», для нарушенного — «нарушено» + контрпример-лассо.
2. Управляющее свойство `G(Fault -> F Idle)` на модели, где `Fault` не всегда
   ведёт к `Idle`, **опровергается** с контрпримером; на модели, где ведёт —
   **подтверждается**.
3. Достижимость: `F Done` истинно ⟺ состояние `Done` достижимо из старта.
4. Атом, не являющийся именем состояния (переменная/`cond`), даёт **явную
   диагностику** «в абстракции управления не поддержан» (не молча false).
5. Проверка **завершается** на всех примерах `examples/` (конечность Крипке).
6. Вердикт **детерминирован** (гейт 0048 — тот же вход даёт тот же вывод).
7. `build_buchi(Not(φ))` и произведение согласуются: известные теоремы
   (`F p` на модели без `p`; `G p` на модели с `!p`) дают ожидаемый вердикт
   (юнит-тесты на малых Крипке).
8. `./scripts/precheck.sh` зелёный; версия языка не изменена.
