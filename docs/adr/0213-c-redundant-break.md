# ADR 0213: Цель c печатает лишний break после безусловного перехода

- **Status:** Accepted
- **Date:** 2026-08-17
- **Authors:** Архитектор + лид разработки
- **Related issues:** [Фича 0213](../features/0213-c-redundant-break.md); родственные
  ADR — [0028](./0028-c-generator-stubs.md) (заглушки печатника цели `c`),
  [0236](./0236-c-unresolved-condition-refusal.md) (неразрешённое условие ребра)

## Context

Цель `c` печатает тело `case` состояния так: сначала `always`/`every`, затем
рёбра переходов, затем — общий `break;`, закрывающий ветвь `switch`
(`c_model.rs`, печать хвоста ветви). Ребро **условное** печатается блоком
`if (…) { … break; }` — его `break` обязателен, он выходит из `switch` изнутри
блока. Ребро **безусловное** (`ConditionNode::None`) печатается без обёртки, и
за ним следует такой же `break;` — уже в теле самой ветви. Общий `break;` в
конце `case` печатается всегда, поэтому получается пара подряд.

Замер на корпусе `examples/generated/c` (2026-08-17, 391 файл дерева, C-корпус —
8 моделей): **7 мест** с `break; break;` в шести файлах — `elevator.c`,
`elevator_mini.c`, `float_regulator.c`, `pid_regulator.c`, `regulator.c`,
`stacker.c` (×2). Проба минимальной модели воспроизводит и второй вид того же
корня: ребро, записанное **после** безусловного, печатается целиком и
недостижимо вместе со своим `if`:

```c
case PROBE_RUN: {
    model->n = model->n + 1;
    model->state = PROBE_DONE;
    break;
    if (model->n == 3) {      // недостижимо
        model->state = PROBE_LATE;
        break;
    }
    break;                    // недостижимо
}
```

Инструменты молчат: `cc -Wall -Wextra -Wunreachable-code` на корпусе даёт только
`-Wunused-parameter` (известный кандидат фичи
[0220](../features/0220-c-gate-wextra.md)) — недостижимый `break` clang не
считает достойным сообщения. То есть цена — не отказ сборки, а **шум в коде,
который читает пользователь**: порождённый C для прошивки читают глазами.

**Главный факт замера — цель `c` в этом одинока.** Три остальные цели на
безусловном ребре **прекращают** эмиссию рёбер, потому что всё дальнейшее
недостижимо:

| Цель | Поведение на безусловном ребре | Место |
|---|---|---|
| `rust` | `return Ok(true)` — эмиссия рёбер прекращается; комментарий прямо ссылается на цель `c`: «в C это молча, в Rust валит `-D warnings`» | `rust_tick.rs` |
| `st` | `return Ok(())` — «цепочка на нём заканчивается» | `st_model.rs` |
| `sv` | ветвь `begin`/`else begin`, дальше цикл не идёт | `sv_fsm.rs` |
| `c` | печатает переход, печатает `break;`, **продолжает** цикл по рёбрам | `c_model.rs` |

Эталон (симулятор) на пробе выбирает `Done` — то есть недостижимость хвоста есть
свойство языка (порядок рёбер), а не расхождение цели с эталоном. Поведение
цели `c` верно; неверна только **форма** вывода.

## Decision Drivers

1. **Читаемость порождённого кода.** Вывод цели `c` — артефакт для человека
   (его кладут в прошивку, читают на ревью, отлаживают на объекте). Два `break`
   подряд и недостижимый `if` заставляют читателя искать смысл там, где его нет.
2. **Единый контракт целей.** Три цели из четырёх уже решают этот вопрос
   одинаково; отставание одной — знакомый проекту класс (0084/0193/0195: «два
   списка одного набора расходятся», «отставала одна цель»).
3. **Поведение не меняется.** Правка обязана быть тождественной по семантике:
   удаляется только код, до которого исполнение не доходит.
4. **Детерминированность и снапшоты.** Вывод корпуса
   (`examples/generated/`) — снапшот под гейтом; изменение формы обязано пройти
   через пересборку корпуса, а не остаться расхождением.

## Considered Options

### Option A. Не печатать `break;`, когда безусловное ребро — последнее печатаемое

Печать хвоста сохраняется; `break;` подавляется только у последнего по счёту
ребра (с учётом фильтра «цель вне достижимых состояний»).

**Pros:**
- Минимальная правка, вывод в случае «безусловное ребро не последнее» остаётся
  байт-в-байт прежним.
- Недостижимый хвост остаётся **виден** автору в порождённом коде.

**Cons:**
- Лечит следствие, а не причину: недостижимый `if` и его собственный `break`
  остаются — то есть «лишнего кода» после правки по-прежнему сколько угодно.
- Цель `c` остаётся единственной, кто печатает хвост, — расхождение с тремя
  соседями сохраняется, и следующая правка целей снова обойдёт `c`.
- Заводит в печатнике новое знание («какое ребро последнее»), которого нет ни у
  одной другой цели.

### Option B. Прекращать эмиссию рёбер на первом безусловном и `break;` не печатать

Как в `rust`/`st`/`sv`: безусловное ребро завершает цепочку. Собственного
`break;` у него нет — ветвь закрывает общий `break;` в конце `case`.

**Pros:**
- Устраняет **оба** проявления одного корня: и пару `break; break;`, и
  недостижимый хвост.
- Приводит цель `c` к контракту трёх остальных целей — «безусловное ребро
  завершает цепочку», один ответ на один вопрос у четырёх бэкендов.
- Печатник становится проще: цикл выходит на первом безусловном ребре, знания «я
  последний» не требуется.

**Cons:**
- Ребро, написанное после безусловного, исчезает из вывода — автор перестаёт
  видеть в C то, что написал в `.takt`. ⚠️ Смягчается тем, что три другие цели
  ведут себя так уже сейчас, а сама запись бессмысленна (ребро недостижимо
  всегда) и заслуживает **диагностики**, а не отражения в выводе.
- Диагностики о недостижимом ребре сегодня нет — вопрос выносится кандидатом.

### Option C. Оставить как есть, объяснив комментарием в коде генератора

**Pros:**
- Ноль риска.

**Cons:**
- Шум остаётся; расхождение с тремя целями остаётся; фича закрывается ничем.

## Decision

Принимается **Option B**. Он лечит причину, а не проявление, и снимает
расхождение цели `c` с тремя остальными целями — то самое, что уже описано
комментарием в `rust_tick.rs` как известное отставание. Поведение при этом
тождественно: удаляется исключительно код, до которого исполнение не доходит
(безусловное ребро завершает ветвь `case` через общий `break;`).

Недостижимое ребро остаётся **законной записью языка** — фича его не запрещает и
диагностики не заводит: это отдельный предмет (кандидат в `FEATURES.md`,
по образцу проверки недетерминированных переходов).

## Consequences

### Положительные

- В порождённом C не остаётся ни `break; break;`, ни недостижимых блоков рёбер.
- Четыре цели отвечают на «что после безусловного ребра» одинаково.
- Печать ветви `case` короче на одну ветвь логики.

### Отрицательные / Action items

- Снапшоты `examples/generated/c` меняются — обязательна пересборка корпуса и
  проверка гейта детерминированности.
- Нужен **сторож формы**: греп-тест по порождённому C всего корпуса «нет двух
  `break;` подряд». Без него класс вернётся незамеченным (уроки 0168/0212 —
  падать сторож обязан **списком** мест).
- Нужен фикстурный сторож на случай «ребро после безусловного»: корпус его не
  содержит (проверено), значит один корпус класс не покрывает.
- Кандидат в `FEATURES.md`: диагностика «ребро недостижимо — стоит после
  безусловного перехода» (сегодня об этом молчат все пять потребителей).

### Acceptance criteria

1. В `examples/generated/c/*.c` нет ни одной пары `break;` подряд (грепом).
2. Ребро, записанное после безусловного, целью `c` не печатается; поведение
   пробы (симулятор ≡ порождённый C) совпадает с прежним.
3. Потактовые сверки `conformance_*` и гейты корпуса зелены; вывод
   детерминирован (два прогона → `diff -r` без отличий).
4. Сторож формы падает **списком** мест при возврате дефекта (проверено
   мутацией).
