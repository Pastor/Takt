# ADR 0224: Подъём Kotlin в плагине intellij-takt снимет ограничение на пусковой JDK

- **Status:** Accepted
- **Date:** 2026-08-17
- **Authors:** Архитектор + аналитик
- **Related issues:** [Фича 0224](../features/0224-intellij-kotlin-upgrade.md);
  повод находки — [ADR 0159](0159-intellij-jdk21-build.md) (преflight-проверка
  пускового JDK)

## Context

Сборка плагина `extensions/intellij-takt` ограничивает **пусковой** JDK — тот, на
котором работает демон Gradle (не путать с JDK компиляции: его задаёт
`jvmToolchain(21)` и скачивает сам Gradle). Под слишком новым пусковым JDK
сборка падает сообщением, состоящим из одной строки — номера версии:

```
* What went wrong:
26.0.2
```

Фича 0159 поставила преflight-проверку, объясняющую отказ, и записала причину:
«таблица версий Java внутри `kotlin-gradle-plugin` 2.0.21 обрывается на
`JAVA_21`». Кандидат, из которого заведена фича 0224, предложил лечение: поднять
Kotlin — «более свежий Kotlin ограничение снял бы вовсе». Не сделано было по
трём причинам: нужна сеть, нужна проверка совместимости с
`org.jetbrains.intellij.platform` 2.1.0, и **проверить исход нечем** — JDK
новее 21 на машине не было.

### Что показала проба (замеры кандидата перепроверены)

Все три препятствия сегодня сняты, и главный замер оказался **неверным**.

**1. Сеть есть.** `repo1.maven.org` и `plugins.gradle.org` отвечают `200`.

**2. Проверить исход есть чем.** На машине стоит `openjdk 26.0.2` (Homebrew,
`/opt/homebrew/opt/openjdk`), то есть пусковой JDK заведомо новее границы.
Отказ воспроизведён на нём дословно (`* What went wrong: 26.0.2`).

**3. Причина названа неверно.** Стектрейс отказа (`--stacktrace`) указывает не на
`kotlin-gradle-plugin` проекта, а на **встроенный в Gradle** компилятор
Kotlin-скриптов, которым компилируется сам `build.gradle.kts`:

```
at org.jetbrains.kotlin.com.intellij.util.lang.JavaVersion.parse(JavaVersion.java:305)
at org.jetbrains.kotlin.cli.jvm.modules.JavaVersionUtilsKt.isAtLeastJava9(javaVersionUtils.kt:11)
...
at org.gradle.kotlin.dsl.support.KotlinCompilerKt.compileKotlinScriptToDirectory(KotlinCompiler.kt:149)
```

Класс — `com.intellij.util.lang.JavaVersion` внутри **Gradle 8.10.2**, а не
`commons-lang3 JavaVersion` внутри KGP. Отсюда следствие: версия
`kotlin("jvm")`, объявленная в `plugins {}`, к этому отказу отношения не имеет —
падение происходит **до** того, как она вообще применяется.

**4. Подъём одного Kotlin ограничения не снял бы.** Независимая проверка того же
вывода: таблица `commons-lang3 JavaVersion` внутри самих KGP-jar (`javap`):

| Kotlin | таблица доходит до |
|---|---|
| 2.0.21 (текущий) | `JAVA_21` |
| 2.1.21 | `JAVA_22` |
| 2.2.21 | `JAVA_22` |
| 2.4.10 (последний стабильный) | `JAVA_24` |

Даже новейший Kotlin не покрывает JDK 26 — то есть предложенное кандидатом
лечение не сработало бы и по своей же логике.

**5. Что снимает ограничение — подъём Gradle.** Проба на копии проекта
(guard снят, чтобы увидеть настоящий отказ):

| Связка | Пусковой JDK 26.0.2 |
|---|---|
| Gradle 8.10.2 + IPP 2.1.0 + Kotlin 2.0.21 (как есть) | `IllegalArgumentException: 26.0.2` при компиляции скрипта сборки |
| Gradle 9.3.0 + IPP 2.1.0 | скрипт компилируется; падает **плагин платформы**: `Adding a provider of configurations directly to the configuration container is not allowed` |
| Gradle 9.3.0 + IPP 2.18.1 + Kotlin 2.0.21 | `compileKotlin` **успешен** |
| Gradle 9.7.0 + IPP 2.18.1 + Kotlin 2.4.10 | сборка и тесты успешны (89/90; единственный провал — корпусный тест, которому нужен корень репозитория: проба живёт вне его) |

Та же связка под пусковым **JDK 17** — тоже 89/90. Конфигурационный кэш Gradle
работает (`Configuration cache entry stored`).

**6. Kotlin поднять всё же стоит — но по другой причине.** На Gradle 9.7 KGP
2.0.21 печатает `Declaring a Usage attribute with a legacy value has been
deprecated. This will fail with an error in Gradle 10` (значения
`java-api-jars`/`java-runtime-jars`). С Kotlin 2.4.10 эти предупреждения
исчезают. То есть подъём Kotlin — не лечение пускового JDK, а условие
работоспособности на следующем мажоре Gradle.

### Побочная находка: форма списка IDE в верификаторе

В IPP 2.18.1 метода `ide("IC-2024.3")` больше нет; ближайшая замена —
`create(type, version)`. Но записи трёх версий **схлопываются**: в 2.1.0 плагин
заводил отдельную конфигурацию на каждую IDE
(`intellijPluginVerifierIdesDependency_IC_2024.3`, `…_IC_2025.1`, `…_IC_2025.2`),
а в 2.18.1 конфигурация одна, и обычный резолв Gradle сводит три версии к
старшей (`idea:ideaIC:2024.3 -> 2025.2`). README плагина ровно об этом и
предупреждал — «форма `ide(type, version)` для одного типа схлопнулась бы в одну
проверку». Проверить, теряется ли покрытие на самом деле, можно только прогоном
`verifyPlugin` (решение заказчика 2026-08-17: прогнать).

## Decision Drivers

1. **Лечение обязано соответствовать причине.** Кандидат называл Kotlin;
   измерение называет Gradle. Подъём не той зависимости оставил бы отказ на
   месте — и был бы объявлен «починкой».
2. **Исход должен быть доказан прогоном.** JDK 26 на машине есть, значит
   отговорка 0159 («проверить нечем») больше не действует.
3. **Не потерять то, что работало.** Пусковой JDK 17 обязан работать
   по-прежнему: на него настроен скрипт установки и им пользуются.
4. **Границы guard — замер, а не догадка.** Комментарий 0159 прямо требует:
   «подняли Kotlin — ПЕРЕЗАМЕРЬТЕ границы».

## Considered Options

### Option A. Поднять только `kotlin("jvm")` (буквально по кандидату)

**Pros:**
- Минимальная правка одной строки.

**Cons:**
- **Не решает задачу — доказано дважды:** отказ приходит из embedded-компилятора
  Gradle до применения KGP, а таблица версий даже у Kotlin 2.4.10 обрывается на
  `JAVA_24` при пусковом JDK 26.

### Option B. Поднять сборочную связку: Gradle + плагин платформы + Kotlin

**Pros:**
- Снимает ограничение по факту: связка Gradle 9.7.0 + IPP 2.18.1 + Kotlin 2.4.10
  собирает и прогоняет тесты под пусковым JDK 26 **и** 17.
- Снимает deprecation-предупреждения, обещающие отказ на Gradle 10.
- Плагин платформы 2.1.0 → 2.18.1 закрывает семнадцать минорных версий
  отставания.

**Cons:**
- Правка API: `ide("IC-…")` → другая форма, и её поведение требует проверки
  прогоном `verifyPlugin`.
- Подъём трёх компонентов сразу: если что-то сломается позже, виновника придётся
  искать перебором.

### Option C. Оставить как есть, ограничившись guard'ом 0159

**Pros:**
- Ноль работы; отказ объяснён преflight-проверкой.

**Cons:**
- Ограничение остаётся, а машина разработчика уже несёт JDK 26: сборка требует
  держать рядом старый JDK и помнить про `JAVA_HOME`.
- Отставание сборочной связки растёт: Gradle 10 сломает KGP 2.0.21 обещанным
  отказом.

## Decision

Принимается **Option B**: подъём **Gradle 8.10.2 → 9.7.0**,
**`org.jetbrains.intellij.platform` 2.1.0 → 2.18.1**, **Kotlin 2.0.21 → 2.4.10**;
`platformVersion` (2024.2.5) и `sinceBuild` (242) **не трогаются** — совместимость
плагина с IDE предметом фичи не является.

Границы преflight-проверки перезамеряются: измеренного «плохого» пускового JDK
больше нет (17 и 26 проверены прогоном), поэтому жёсткий `error` снимается, а
предупреждение о непроверенных версиях остаётся — ровно по логике самого 0159
(«запрещать неизмеренное — та же догадка, только с другим знаком»).

Заголовок фичи говорит о Kotlin — он остаётся как есть (номер фичи привязан к
названию), но предмет уточнён этим ADR: Kotlin входит в объём, однако
ограничение снимает **Gradle**.

## Consequences

### Положительные

- Сборка плагина идёт на любом пусковом JDK из измеренного диапазона 17…26;
  держать рядом старый JDK не нужно.
- Сборочная связка перестаёт отставать на семнадцать минорных версий плагина
  платформы и на мажор Gradle.
- Скрипт установки (`install-rustrover-plugin.sh`/`.ps1`) больше не обязан
  искать JDK 17 — правка документируется вместе со связкой.

### Отрицательные / Action items

- **Форма списка IDE верификатора меняется**, и её эквивалентность старой
  доказывается прогоном `verifyPlugin` (стадия 6). Схлопывание к одной версии —
  регресс покрытия, и если новая форма его даёт, список задаётся иначе.
- Плагин по-прежнему собирается **только локально** (`./gradlew --offline test`)
  и в `precheck.sh`/CI не входит — фича этого не меняет (правило 29: сторож
  `TaktKeywordSyncTest` существует, но машина его не запускает).
- Числа guard'а и README снова устареют при следующем подъёме — это свойство
  измеренной границы, и текст обязан говорить, **что** измерено, а не «работает».

### Acceptance criteria

1. `./gradlew test` зелёный под пусковым JDK **26** и под **17** (все тесты, в
   том числе `TaktPsiCorpusTest`, который требует корня репозитория).
2. `./gradlew buildPlugin` даёт zip; `verifyPlugin` отрабатывает и его вывод
   показывает, сколько IDE проверено (три — покрытие сохранено).
3. Deprecation-предупреждений вида «legacy Usage attribute» в сборке нет.
4. Преflight-проверка в `build.gradle.kts` перезамерена: числа соответствуют
   пробам, жёсткого отказа на неизмеренной версии нет.
5. README плагина, скрипты установки и живой контекст (`CLAUDE.md`) не обещают
   снятого ограничения.
