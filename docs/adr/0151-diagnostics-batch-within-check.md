# ADR 0151: Накопление диагностик внутри отдельной проверки `validate`

- **Status:** Accepted
- **Date:** 2026-08-05
- **Authors:** Архитектор + Заказчик (кандидат отобран заказчиком 2026-07-28, взят в работу 2026-08-05)
- **Related issues:** [Фича 0151](../features/0151-diagnostics-batch-within-check.md); граница задана [ADR 0130](0130-diagnostics-batch.md) (накопление **между** проверками) и [0152](../features/0152-semantic-recovery-element-boundary.md) (терминальность стадий построения); в фичу сложен кандидат «два неразрешённых условия дают одну диагностику»

## Context

Фича 0130 накопила диагностики **между** проверками: `validate_model_all`
собирает все, а не первую. Внутри каждой проверки остался ранний возврат — цикл
с `?`, — поэтому две неверные переменные давали **одно** сообщение, и цикл
«правка → компиляция» вернулся наполовину.

Кандидат блока 2 `FEATURES.md` описывал частный случай («два неразрешённых
условия дают одну `SE-025`») и требовал пробы: дыра обхода или ранний выход?
**Проба (2026-08-05): ранний выход.** Два условия теряются одинаково и в разных
состояниях, и в одном — то есть обход доходит, а проверка возвращается после
первой находки. Кандидат тем самым складывается в эту фичу.

### Замер потерь (2026-08-05)

| Вход | Диагностик до | Класс |
|---|---|---|
| два `ref` с неразрешённым условием | 1 | `SE-025`, `validate` |
| два `cond` с неразрешённым условием | 1 | `SE-025`, `validate` |
| две переменные `bit` с недопустимым значением | 1 | `SE-035`, `validate` |
| два массива недопустимого размера | 1 | `SE-038`, `validate` |
| два `address` на несуществующие порты | 1 | `SE-048`, `validate` |
| два обращения к ячейке в инициализаторах | 1 | `SE-099`, `validate` |
| две ссылки на несуществующее состояние | 1 | `SE-002`, **стадия построения** |
| два неизвестных имени в инициализаторах | 1 | `SE-003`, **стадия построения** |

Проверок «первой ошибки» — **одиннадцать** (массив `single` в
`validate_model_all`); остальные уже накапливали.

### Что определяет форму решения

**Не всякий ранний выход — привычка.** Внутри **одного** выражения вторая ошибка
почти всегда следствие первой: разрешив имя неверно, обход дальше сообщает о
последствиях. Тот же довод 0152 применила к стадиям построения дерева.

**Между элементами следствий нет.** Два объявления, два ребра, два оператора
`address` независимы: молчание о втором — чистая потеря.

**Граница уже проведена и не здесь.** `SE-002`/`SE-003` рождаются на стадиях
построения, терминальных по решению 0152. Их накопление — не предмет этой фичи.

## Decision Drivers

1. **Цикл «правка → компиляция» стоит времени пользователя** — ради его
   сокращения и делалась 0130.
2. **Сообщение о следствии хуже молчания:** оно уводит от причины.
3. **Порядок вывода не должен стать наблюдаемым** — накопленную пачку
   нормализует `diagnostics::normalize` (позиция + дедуп).
4. **Правило должно быть одно и называемое**, иначе следующая проверка выберет
   произвольно.

## Considered Options

### Option A. Накопление по элементам, ранний выход внутри элемента

Правило: **одна диагностика на элемент; высказываются все элементы.** Элемент —
объявление, ребро перехода, именованное условие, оператор `address`.

**Pros:**
- Убирает чистые потери и не плодит сообщения о следствиях.
- Формулируется одной фразой — новую проверку писать по образцу.
- Правка механическая: `?` → накопление в векторе, 11 функций.

**Cons:**
- Две независимые ошибки **внутри одного** выражения по-прежнему дают одну.
  Случай редкий (в одном выражении обычно одна опечатка) и не бесплатный: чтобы
  различать «независимо» и «следствие», нужен анализ выражений.

### Option B. Накопление везде, включая обход выражений

**Pros:** максимум сообщений за прогон.

**Cons:**
- Возвращает шум следствий: неразрешённое имя внутри выражения делает
  ошибочными все его узлы, и пользователь получит их списком.
- Требует различать причину и следствие внутри выражения — задача другого
  порядка сложности, чем предмет фичи.

### Option C. Оставить как есть, описать в документе

**Pros:** нулевая правка.

**Cons:** документ обещает «все независимые ошибки сразу» (раздел о
диагностиках) — пришлось бы описывать исключение вместо того, чтобы его снять.

## Decision

Принимается **Option A**.

Все одиннадцать проверок массива `single` переведены с
`Result<(), Diagnostic>` на `Vec<Diagnostic>`; внешние циклы накапливают,
внутренний обход одного выражения по-прежнему возвращает первую ошибку.
Точка сбора (`validate_model_all`) складывает векторы, нормализация не
меняется.

**Граница названа:** `SE-002`/`SE-003` и прочие ошибки **стадий построения**
остаются терминальными (решение 0152) — тесты фиксируют это как решение.

## Consequences

### Положительные

- Шесть измеренных классов теперь высказываются полностью.
- Правило накопления названо и применимо к будущим проверкам.
- Интерфейс проверок стал однородным: все отдают вектор.

### Отрицательные / Action items

- Две независимые ошибки внутри одного выражения по-прежнему дают одну —
  осознанная граница Option A.
- Тесты, стоявшие на `Result` (`is_ok`/`unwrap_err`), обновлены.

### Acceptance criteria

1. Два нарушения одного вида в разных элементах дают **два** сообщения — для
   `SE-025` (ребро и `cond`), `SE-035`, `SE-038`, `SE-048`, `SE-099`.
2. Разные проверки по-прежнему складываются (свойство 0130).
3. Ошибки стадий построения остаются терминальными.
4. Порядок сообщений — по позиции.
5. Одна диагностика на элемент (внутри выражения — первая).
6. `./scripts/precheck.sh` — код возврата 0.
