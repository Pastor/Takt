# ADR 0124: Экспорт графов верификации (Крипке/Бюхи/произведение) в Graphviz DOT

- **Status:** Accepted
- **Date:** 2026-07-25
- **Authors:** Архитектор + лид разработки
- **Related issues:** [Фича 0124](../features/0124-verify-graph-export.md); использует движок верификации [0049](../features/0049-model-checking-ltl.md)/[0068](../features/0068-verify-data-properties.md); потребитель — раздел документа «Практический пример» (фикс `0118-01`).

## Context

Движок верификации строит структуру **Крипке** (`verification/kripke.rs`), автомат
**Бюхи** для `¬φ` (`buchi.rs`) и их **произведение** (`product.rs`), но наружу
отдаёт только **текст**: вердикт, текстовый `--trace` (дампы `Kripke::trace`,
`BuchiAutomaton::dump`, `Product::trace`) и контрпример-лассо. Графического вывода
нет. Разделу документа «Практический пример» нужны **наглядные диаграммы**
построения модели Крипке и автомата Бюхи для разных спецификаций, чтобы показать,
как работает model-checking. Рисовать их вручную — значит оторвать иллюстрацию от
настоящего вывода инструмента (расхождение при любой правке движка).

Требуется: из тех же структур, что использует проверка, породить граф в формате,
который **локально рендерится в SVG** для встраивания в book (PDF собирается
`xelatex`, картинки — SVG через `rsvg-convert`).

## Decision Drivers

1. **Диаграмма = настоящий вывод движка.** Граф строится из тех же
   `Kripke`/`BuchiAutomaton`/`Product`, что и вердикт; правка движка автоматически
   отражается в диаграмме, расхождение невозможно.
2. **Локальный рендер в SVG доступной утилитой.** В окружении сборки есть
   `dot` (Graphviz, `/opt/homebrew/bin/dot`), а `plantuml` — **нет**. Формат должен
   рендериться тем, что установлено.
3. **Идиоматичность.** Автоматы и структуры Крипке в литературе рисуют графами
   переходов (кружки-состояния, двойной кружок — принимающее, стрелки-рёбра) —
   ровно модель Graphviz.
4. **Минимальная и согласованная CLI-поверхность.** Экспорт живёт в существующей
   подкоманде `verify`, а не в новой; не ломает прежние вызовы (аддитивность,
   правило 11).
5. **Единый источник истины отбора Крипке.** Экспорт обязан выбирать
   управляющую/данными Крипке (0049 vs 0068) **той же** логикой, что проверка, —
   иначе диаграмма покажет не тот граф, что проверялся.

## Considered Options

### Option A. PlantUML (state diagram)

**Pros:**
- Единый формат с ADR-диаграммами проекта и целью `plantuml` компилятора.

**Cons:**
- `plantuml` в окружении **не установлен** — нечем рендерить в SVG для book.
- State-diagram PlantUML плохо выражает автомат Бюхи (множества формул в узле,
  двойной кружок принятия) — пришлось бы бороться с нотацией.

### Option B. Graphviz DOT (`taktc verify --emit-graph <kind>`)

**Pros:**
- `dot` установлен → `dot -Tsvg` рендерит SVG для book сразу.
- Идиоматично для автоматов/Крипке; принятие рисуется `shape=doublecircle`,
  старт — точкой-источником, разметка атомов — меткой узла.
- Экспорт — аддитивный флаг существующей подкоманды `verify`.
- DOT-строку легко проверять тестом (детерминированный порядок из `BTreeMap`).

**Cons:**
- Ещё один текстовый формат в кодовой базе (но узкий, только под верификацию).

### Option C. Собственный SVG-эмиттер

**Pros:**
- Без внешних зависимостей рендера.

**Cons:**
- Раскладка графа (layout) — сложная задача; переизобретать Graphviz неоправданно.

## Decision

Принимается **Option B — Graphviz DOT**. Добавляется флаг
`taktc verify --emit-graph <kripke|buchi|product>` (при необходимости с
`--property φ`): строит запрошенную структуру тем же конвейером и печатает **DOT**
в stdout (перенаправляется в файл, рендерится `dot -Tsvg`). Эмиттеры — новый модуль
`verification/dot.rs` (`kripke_to_dot`/`buchi_to_dot`/`product_to_dot`). Отбор
Крипке (управление 0049 vs данные 0068) выносится в общий помощник
`verify::select_kripke`, которым пользуются и проверка (`run`), и экспорт, — чтобы
диаграмма показывала **ровно** проверявшийся граф.

- `kripke` — без `--property` даёт **управляющую** Крипке; с `--property` — ту, что
  реально проверялась бы (данными, если атомы φ — предикаты).
- `buchi`/`product` требуют `--property` (строятся по `¬φ`); без него — понятный
  отказ, а не молчание.

Форматом рендера в book остаётся **SVG**: `.dot` → `dot -Tsvg` при подготовке
раздела; в репозиторий кладутся и `.dot` (воспроизводимость), и порождённый `.svg`.

## Consequences

### Положительные

- Диаграммы Крипке/Бюхи/произведения — настоящий вывод движка, привязанный к его
  коду; правка верификации отражается в картинке.
- Прежние вызовы `verify` не затронуты (флаг аддитивен); текстовый `--trace`
  остаётся.
- Общий `select_kripke` убирает риск расхождения «проверили одно — нарисовали
  другое».

### Отрицательные / Action items

- Рендер в SVG — внешний шаг (`dot`), не в `precheck.sh` (как и сборка PDF). Гейт
  проверяет **порождение DOT** (юнит-тест на валидность/структуру), а не картинку.
- `verify` инструмент, а не библиотека: эмиттеры — публичные функции
  `verification::dot`, CLI лишь вызывает их и печатает.

### Acceptance criteria

1. `taktc verify --emit-graph kripke m.takt` печатает валидный DOT структуры
   Крипке (старт помечен, тотальность/самопетли видны); `dot -Tsvg` рендерит.
2. `taktc verify --emit-graph buchi --property "F S" m.takt` печатает DOT автомата
   `¬φ`: начальные и **принимающие** (`doublecircle`) состояния различимы.
3. `--emit-graph product --property φ` печатает DOT произведения с пометкой
   принимающих пар.
4. `buchi`/`product` без `--property` → понятный отказ (код ≠ 0), не молчание.
5. Отбор Крипке экспорта совпадает с проверкой (общий `select_kripke`): для
   свойства над данными экспортируется data-Крипке.
6. Юнит-тесты на DOT-вывод (захват зондом, затем ассерты); `./scripts/precheck.sh`
   зелёный; прежний вывод `verify`/`--trace` неизменен.
