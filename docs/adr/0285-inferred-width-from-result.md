# ADR 0285: Ширина выведенного типа берётся у результата

- **Status:** Accepted
- **Date:** 2026-08-19
- **Authors:** Архитектор + аналитик + разработчик
- **Related issues:** [Фича 0285](../features/0285-inferred-width-from-result.md); смежные — [0192](../features/0192-const-init-fold.md) (свёртка), [0207](../features/0207-bitwise-not-unsigned-literal.md) (нормирование вычисленного), [0208](../features/0208-const-evaluators-unification.md) (где найдено), [0287](../features/0287-wider-type-array-literal.md) (соседний класс)

## Context

Инициализатор объявления сворачивается в литерал (0192), а вычисленное значение
**нормируется по типу объявления** (0207): беззнаковое переполнение — обёртка
`mod 2ⁿ`, как в теле состояния. Оба правила верны и согласованы между девятью
потребителями.

Но тип **выводится до свёртки** (порядок 0192: разрешить → вывести типы →
свернуть), а вывод берёт тип у **операндов**. Отсюда: `const K := 1 + 255;`
получает `[bit;8]` от левого литерала, и нормирование заворачивает вычисленные
`256` в **ноль**.

**Замер 2026-08-19** (`scripts/probe.sh`, проба признана годной):

| Запись | Значение | Почему |
|---|---|---|
| `1 << 8` | **0** | ширина от `1` — 8 бит |
| `1 + 255` | **0** | то же |
| `255 + 1` | **0** | порядок операндов не спасает |
| `2 * 128` | **0** | не только сложение |
| `200 + 200` | **144** | `400 mod 256` |
| `300 - 44` | 256 ✓ | ширина от `300` — 16 бит |
| `1000 + 1` | 1001 ✓ | то же |

⚠️ **Кандидат винил сдвиг — дело в любой арифметике.** Строки `300 - 44` и
`1000 + 1` показывают причину: там ширины хватало **случайно**, потому что
левый операнд сам по себе не влезал в восемь бит.

⚠️ **Расхождения между потребителями нет:** значение сворачивается в семантике,
и все девять дают одно и то же. Это `Tier 2` по шкале проекта — «молча неверное
значение при согласии инструментов»: инструменты не противоречат друг другу,
они одинаково неправы относительно написанного.

⚠️ **Прежде это была ошибка `SE-089`.** Фича 0207 сменила отказ на нормирование
— верно для **явного** типа (там ширину выбрал автор) и неожиданно для
**выведенного** (там её выбрал операнд).

## Decision Drivers

1. **Автор не выбирал ширину.** Если тип не написан, единственное, что автор
   выразил, — это выражение; подгонять его результат под ширину случайного
   операнда значит отвечать не на то, что спросили.
2. **Явный тип трогать нельзя.** `var u: u8 := 200 + 100;` = `44` — принятое
   решение 0207, согласованное с телом состояния.
3. **Молчание хуже отказа.** До 0207 здесь была диагностика; теперь ни
   диагностики, ни верного значения.
4. **Граница правил должна быть узкой.** Соседние правила (нормирование
   0207, вывод из сигнатуры функции Ce6) верны и обязаны остаться нетронутыми.

## Considered Options

### Option A. Оставить как есть

**Pros:** ноль правок; поведение согласовано и выводимо из двух правил.

**Cons:** `const K := 1 + 255;` даёт ноль, и об этом не говорит никто.
«Выводимо из правил» — не то же, что «ожидаемо для автора».

### Option B. Предупреждение, когда нормирование меняет значение

**Pros:** не меняет поведения.

**Cons:** значение остаётся неверным. Предупреждение уместно там, где поведение
**нормировано** (`SE-090`), а здесь нормировать нечего — верный ответ известен.

### Option C. Вернуть `SE-089` для выведенного типа

**Pros:** громко.

**Cons:** отвергает запись, у которой есть очевидный верный смысл. И
противоречит 0207, снявшей этот отказ.

### Option D. Ширина выведенного типа — по результату вычисления

**Pros:**
- `const K := 1 + 255;` даёт `256` — то, что написано.
- Явный тип, вывод из сигнатуры и правило 0207 не затронуты.
- Ничего не добавляется в язык: меняется только выбор ширины там, где её никто
  не выбирал.

**Cons:** правка стоит **в свёртке**, то есть после вывода типов — приходится
запоминать, был ли тип объявлен. Требует трёх границ (см. ниже), и каждая из
них — потенциальный перебор.

## Decision

Принимается **Option D**.

1. Имена, у которых тип **не объявлен**, снимаются **до** вывода типов (после
   него `Inference` заменён, и отличить «автор выбрал ширину» от «её выбрал
   операнд» уже нечем).
2. После свёртки, если такое объявление получило литерал, **превышающий верхнюю
   границу** выведенного типа, тип переопределяется по результату
   (`infer_int_type`) — тем же носителем, каким выбирается тип литерала.
3. Границы берутся у **единственного** носителя
   (`validate::literal_range::type_range`): своя копия разошлась бы с `SE-089`.

**Три границы, и каждая поймана чужим тестом, а не чтением:**

- **явный тип не трогать** — иначе ломается правило 0207;
- **тип из сигнатуры функции не трогать** — первая редакция переопределяла тип
  **всегда**, и `fn get32() -> [bit;32]` с `var val := get32();` дал `[bit;8]`,
  потому что вычислитель сворачивает вызов в `0` (упал тест Ce6);
- **отрицательное не расширять** — вторая редакция смотрела и на нижнюю
  границу, и `var u := ~0;` перестал давать `255` (упал тест нормирования 0207).

## Consequences

### Положительные

- Объявление без типа даёт то значение, которое написано.
- Диагностики не добавилось, язык не сузился: изменился только выбор ширины.
- Правило 0207 и вывод Ce6 остались нетронутыми — доказано их же тестами.

### Отрицательные / Action items

- **Наблюдаемое поведение меняется**: `const K := 1 + 255;` было `0`, стало
  `256`. Прежнее значение было дефектом, а не контрактом.
- ⚠️ Правка живёт в свёртке и опирается на множество «имена без объявленного
  типа». Новый путь, добавляющий объявления **после** вывода типов, обойдёт её
  молча — граница названа в коде.

### Acceptance criteria

1. `1 + 255`, `255 + 1`, `2 * 128`, `1 << 8` дают `256`; `200 + 200` — `400`
   (A1).
2. `300 - 44` и `250` не изменились (A2, контроль).
3. `var u: u8 := 200 + 100;` = `44` (A3).
4. `var u := ~0;` = `255` (A4).
5. `var val := get32();` сохраняет `[bit;32]` (A5).
6. `./scripts/precheck.sh` зелён (A6).
