# ADR 0197: Стиль кода языка Takt — свод правил оформления и раздел документа

- **Status:** Accepted
- **Date:** 2026-08-04
- **Authors:** Архитектор + Заказчик (запрос 2026-08-02; решения по источнику истины, форме свода и синонимам — 2026-08-04)
- **Related issues:** [Фича 0197](../features/0197-language-code-style.md); смежные — [ADR 0024](0024-lam-formatter.md) (канонический форматтер), [фича 0101](../features/0101-language-book.md) (инфраструктура документа), [фича 0133](../features/0133-book-examples-gate.md) (гейт примеров документа)

## Context

Заказчик просит описать стиль оформления кода на Takt «по типу PEP 8», взяв за
отправную точку K&R.

**Канон уже существует — но в виде программы, а не текста.** `taktc fmt`
приводит `.takt` к канонической форме, `taktc fmt --check` сторожит её в
предкоммите по всему `examples/`. Правила действуют, но прочитать их можно
только по выводу инструмента или по коду `takt-lang/src/format/`.

### Что показала проба

Прогон `taktc fmt --stdin` на файле с нарочно сбитым оформлением:

```takt
model M {
start S { always { v := 1; } }
      var v: u8 := 0;
   const K := 3;
}
```

вернул

```takt
model M {
    start S {
        always {
            v := 1;
        }
    }
    var v: u8 := 0;
    const K := 3;
}
```

Отсюда три факта, определяющих форму работы:

1. **Предложение заказчика узаконивает существующее.** Наблюдаемый канон уже
   K&R-подобен: открывающая скобка на строке заголовка, отступ 4 пробела,
   тело блока — на своих строках, `;` завершает оператор.
2. **`fmt` разворачивает однострочные тела.** `start S { always { v := 1; } }`
   стал пятью строками — то есть «компактная» запись каноном не является.
3. **`fmt` НЕ трогает порядок элементов.** `start S` остался перед `var` и
   `const`, хотя в корпусе преобладает обратный порядок (объявления → состояния).

Факт 3 — главный: свод неизбежно содержит правила **разной силы**. Часть из них
инструмент исполняет сам и предкоммит стережёт; часть (порядок элементов,
именование, содержание комментариев, длина строки) не проверяет никто.

## Decision Drivers

1. **Двух источников истины быть не должно.** Свод, расходящийся с `taktc fmt`,
   хуже отсутствующего: он обещает то, чего инструмент не делает.
2. **Обещание должно быть исполнимым.** Проект трижды подряд закрывал дефекты
   этого класса (0201 — мёртвые слова в списках, 0202 — формат, обещанный
   документом и не выдаваемый инструментом, 0202-01 — сверка, ничего не
   сверявшая). Свод не должен стать четвёртым.
3. **Стоимость правки форматтера — дифф всего корпуса** и фикстур, завязанных
   на позиции.
4. **Правило 24:** раздел описывает язык, без номеров фич и деталей реализации;
   правило 26 требует блока типичных ошибок, правило 27 — функционального
   примера; примеры раздела проходят гейт документа.

## Considered Options

### Option A. Свод описывает форматтер

Истина — `taktc fmt`; текст излагает действующее поведение. Расхождение текста и
инструмента есть дефект **текста**.

**Pros:** код не меняется, корпус не сдвигается; свод верен по построению в день
написания; работа сводится к чтению `format/` и корпуса.
**Cons:** заказчик этой фичей стиль не меняет — для смены нужна отдельная фича;
связь «текст ↔ поведение» держится дисциплиной, машинной сверки нет.

### Option B. Свод предписывает, форматтер приводится в соответствие

**Pros:** позволяет изменить стиль там, где он не нравится.
**Cons:** каждое расхождение даёт дифф всего `examples/` и фикстур; объём
непредсказуем до выбора правил; риск, что текст уедет вперёд инструмента и
временно окажется ложным.

### Option C. Свод как отдельный документ вне `book/`

**Pros:** не трогает структуру документа.
**Cons:** нарушает правило 24 (описание языка живёт только в `book/`) и заводит
второе место, где написано про язык.

## Decision

Принимается **Option A** — решение заказчика (2026-08-04).

**Форма свода — единый сплошной список правил** (решение заказчика). Архитектор
предлагал разделить его на два блока — «исполняет `taktc fmt`» и «остаётся на
авторе», — потому что факт 3 пробы делает разницу существенной; заказчик выбрал
форму PEP 8. Риск («читатель решит, что инструмент поддерживает всё
перечисленное») снимается **внутри** формулировок: там, где правило исполняет
форматтер, это сказано в самом предложении. Отдельных блоков и пометок не
заводится — свод остаётся сплошным.

**Синонимы объясняются, выбор остаётся автору** (решение заказчика). `while`/
`loop` и `: [Guard] x;` / `: x;` свод называет равноправными, объясняет уместность
каждого и советует держаться одного в пределах файла. АСД (`ast::LoopKeyword`,
`Guard::explicit`) хранит выбор автора именно ради этого — правок не требуется.

**Место раздела:** новый `book/src/21-code-style/` в блоке «Применение», последним
пунктом. Стиль — не описание языка, а способ им пользоваться, поэтому блок
«Описание языка» (01–16) не трогается; перенумеровывать существующие разделы
ради «правильного» места не станем — цена (все ссылки и пути) несопоставима с
пользой.

## Consequences

### Положительные

- Действующий канон становится читаемым: его можно прочесть, а не выводить из
  поведения инструмента.
- Свод верен по построению: он описывает то, что уже проверяется предкоммитом.
- Примеры раздела проходят гейт документа — неверный пример не переживёт прогон.

### Отрицательные / Action items

- **Машинной сверки «текст ↔ форматтер» нет и не будет** в этой фиче. Связь
  держится примерами и дисциплиной. ⚠️ Отсюда обязанность: фича, меняющая
  поведение `taktc fmt`, обязана проверить этот раздел — записать в живой
  контекст.
- Стиль этой фичей **не меняется**; если заказчику что-то в нём не нравится,
  нужна отдельная фича с правкой форматтера (Option B).
- Правила, которые инструмент не проверяет (порядок элементов, именование,
  комментарии), остаются советами. Формулировки обязаны это показывать, иначе
  свод пообещает несуществующее.

### Acceptance criteria

1. Раздел `book/src/21-code-style/` заведён и подключён в `SUMMARY.md`.
2. Каждое правило о расстановке пробелов, отступов и скобок **проверено пробой**
   `taktc fmt` — текст не расходится с инструментом.
3. Правила, которые форматтер не исполняет, сформулированы как советы, и это
   видно из самой формулировки.
4. Синонимы `while`/`loop` и `[Guard]` объяснены, выбор оставлен автору.
5. Есть функциональный пример (правило 27) и блок типичных ошибок (правило 26).
6. Примеры раздела проходят гейт документа (компиляция целью `c` + симуляция).
7. `./scripts/precheck.sh` — код возврата 0.
