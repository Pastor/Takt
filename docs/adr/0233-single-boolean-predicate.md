# ADR 0233: Правило булевости условия — одно

- **Status:** Accepted
- **Date:** 2026-08-05
- **Authors:** Архитектор + Заказчик (требование — 2026-08-05, при закрытии [0232](../features/0232-implicit-bool-warning-delivery.md))
- **Related issues:** [Фича 0233](../features/0233-single-boolean-predicate.md); отчёт 0232 оставил сведение предикатов открытым вопросом; класс — «набор/правило, записанное дважды» (0084, 0193, 0195, 0230, 0232)

## Context

Проверка неявной булевости (`SE-037`) хранила **два** правила «что считать
булевым условием»:

- `is_boolean_semantic_condition` — по разрешённому `ConditionNode`;
- `is_boolean_ast_condition` — по «сырому» `ast::Condition`, для условия,
  оставшегося `ConditionNode::Unresolved`.

Они уже разошлись: про `after` знало АСД-правило, семантическое — нет. Цена
расхождения измерена фичей 0232: 16 ложных срабатываний на примерах документа,
из-за которых проверку нельзя было отдать пользователю.

### Замер (2026-08-05) — какой путь живой

Инструментированный прогон по `examples/`, фикстурам `takt-lang/tests/data`,
`takt-sim/tests/data` и примерам документа: **433 проверки условий, из них
`Unresolved` — ноль**. Отдельная проба на `S(Ping) = End` (единственная форма,
ради которой запасной путь и держали) показала: условие приходит **разрешённым**.

**И не может быть иначе.** Условие, которое не разрешилось, даёт ошибку
`SE-025`; предупреждения считаются только тогда, когда ошибок нет — так устроены
**оба** потребителя (`compile` прекращает работу на ошибках,
`collect_diagnostics_at` возвращается до сбора предупреждений). То есть второе
правило было недостижимо не по случайности, а по устройству конвейера.

### Что мешает «честному» сведению двух правил в общий обход

Входы разнотипны: `ast::Condition` (плюс модель — для разрешения имён) и
`ConditionNode` (имена уже разрешены). Общий обход потребовал бы слоя
абстракции — трейта «фактов об узле» с адаптером на каждый вход. Это **дороже**
самой проверки и оставляет ровно то, что расходится: **классификацию** узлов
(именно на ней и произошёл разрыв по `after`), — унифицируя лишь композицию
(`&`/`|`, скобки).

## Decision Drivers

1. **Правило, записанное дважды, расходится** — доказано этим же кодом.
2. **Мёртвая ветвь — не страховка, а обещание.** Второе правило создавало
   видимость поддержки случая, которого не бывает.
3. **Дешевизна решения соразмерна проверке.** Слой абстракции ради одной
   диагностики — цена выше пользы.
4. **Молчание безопаснее догадки.** О булевости того, чего семантика не поняла,
   судить нечем.

## Considered Options

### Option A. Удалить АСД-правило; единственное правило — по `ConditionNode`

Ветвь `Unresolved` попадает в то же правило и отвечает «булево» (то есть
молчание).

**Pros:**
- Правило существует в **одном** экземпляре: расходиться нечему **по
  построению**, а не по дисциплине.
- Минус ~150 строк кода и ~40 тестов, стоявших на недостижимом пути.
- Решение «на неразрешённом молчим» записано там же, где все прочие
  классификации.

**Cons:**
- Если конвейер когда-нибудь начнёт отдавать `Unresolved` в предупреждения,
  проверка промолчит вместо того, чтобы разобрать «сырой» АСД. Цена — молчание,
  а не ложное срабатывание.

### Option B. Общий обход через трейт «фактов об узле»

`Shape { Boolean | Numeric | Parens | AndOr }` и два адаптера.

**Pros:** оба входа сохраняются; композиция правила — одна.

**Cons:**
- Унифицирует **не то**, что разошлось: классификацию узлов адаптеры по-прежнему
  описывают порознь, а разрыв по `after` был именно в ней.
- Слой абстракции (трейт, обобщённая функция, две обёртки) на одну диагностику —
  сложность без соразмерной пользы; недостижимая ветвь при этом остаётся жить.

### Option C. Оставить два правила, добавить сверку

Тест, сравнивающий вердикты обоих правил на наборе условий.

**Pros:** ловит расхождение, не трогая устройство.

**Cons:** сверка нужна ровно потому, что правил два; проще их не иметь. И сверять
пришлось бы **разрешимые** условия — то есть входы, которых второе правило
никогда не увидит.

## Decision

Принимается **Option A**.

- `is_boolean_ast_condition` и `ast_condition_summary` удалены; запасной путь в
  `check_one_ref` удалён вместе с ветвлением.
- Единственное правило (`is_boolean_semantic_condition`) явно классифицирует
  `ConditionNode::Unresolved` как булево — то есть **молчит**; решение записано
  там же, где остальные, и объяснено недостижимостью ветви.
- Тесты, стоявшие на удалённом правиле, заменены **табличным** тестом по
  исходникам: те же случаи проверяются через вердикт `check_implicit_bool_conditions`.

## Consequences

### Положительные

- Правило одно; класс «разошлись два описания одного правила» здесь закрыт по
  построению.
- Проверка стала короче на треть, тесты — ближе к наблюдаемому: они судят по
  исходнику, а не по внутренней функции.

### Отрицательные / Action items

- Ветвь `Unresolved` **не покрыта тестом**: её невозможно получить через
  публичные входы (мутация «предупреждать на Unresolved» тестов не валит —
  честная граница, записана в отчёте).
- Удалено ~40 юнит-тестов; их предмет покрыт таблицей правил на исходниках.

### Acceptance criteria

1. В коде остаётся **одно** правило булевости.
2. Поведение не изменилось: корпус и примеры документа молчат, настоящие
   срабатывания на месте.
3. Каждое правило (сравнение, `!`, скобки, `cond`, `bit`/`bool`, `&`/`|` над
   булевыми, `after`, доступ к одному биту; и числовые случаи) покрыто тестом
   **по исходнику**.
4. Мутация правила валит таблицу.
5. `./scripts/precheck.sh` — код возврата 0.
