# ADR 0024: Канонический форматтер .lam (lamc fmt)

- **Status:** Accepted
- **Date:** 2026-07-13
- **Authors:** Архитектор + Аналитик
- **Related issues:** [Фича 0024](../features/0024-lam-formatter.md); учитывает
  [ADR 0019](0019-condition-expression-unification.md) (унификация грамматик
  Condition/Expression)

## Context

Нужен канонический автоформат исходников `.lam`: единый детерминированный стиль,
воспроизводимые диффы, проверяемость в CI (`lamc fmt --check`) и переиспользование
одним ядром тремя потребителями — CLI (`lamc fmt`), LSP (`textDocument/formatting`
в `lam-lsp`) и плагином IntelliJ («Reformat Code», фичи 0022/0023). Форматтера
сейчас нет ни в одном инструменте.

Ключевой вопрос — **из какого представления печатать** и **как не потерять
комментарии**. Исследование крейта `grammar` дало опорные факты:

- `parse(src, file_no) -> Result<(ast::Model, Vec<ast::Comment>), …>`
  (`grammar/src/lib.rs`): результат парсинга — AST-модель **и отдельный вектор
  комментариев**.
- **Каждый узел AST несёт `Location`** (байтовые смещения `start..end`) —
  `grammar/src/parser/ast.rs` («Каждый узел несёт в себе информацию о
  местоположении»).
- **Комментарии — side-channel:** лексер складывает их в `Vec<Comment>` и **не
  включает в поток токенов** (`grammar/src/parser/lexer.rs`, строка ~344). Три
  вида: `Comment::Line`, `Comment::DocLine`, `Comment::Block`, каждый с
  `Location`.
- **Генераторы C и PlantUML печатают от семантического дерева** (`ModelNode`,
  `generator/{c,plantuml}/`), которое нормализует имена (`Root`,
  snake_case) и теряет исходную раскладку — для форматтера это **непригодно**.

То есть и узлы AST, и комментарии несут байтовые позиции — их можно
переассоциировать по смещению без построения нового синтаксического дерева.

## Decision Drivers

1. **Сохранение комментариев (главный риск карточки).** Печать не должна терять
   `//`, `///`, `/* */`; они обязаны вставляться в осмысленные места.
2. **Идемпотентность.** `fmt(fmt(x)) == fmt(x)` для всех конструкций языка.
3. **Отсутствие семантического сдвига (правило 11).** Форматтер меняет только
   раскладку, не текст идентификаторов и не структуру — версия языка **не**
   растёт (правило 22).
4. **Переиспользование одним ядром** тремя потребителями (CLI/LSP/IntelliJ).
5. **Пропорциональность.** Не строить тяжёлую инфраструктуру там, где хватает
   существующих AST + `Vec<Comment>`.

## Considered Options

### Option A. Pretty-printer от AST + переассоциация комментариев по `Location`

Ядро принимает результат `parse` — `(ast::Model, Vec<Comment>)` — и печатает
канонический текст обходом позиционно-размеченного AST; комментарии из вектора
привязываются к узлам по байтовым смещениям (ведущий/висячий/хвостовой) и
печатаются в канонических местах.

**Pros:**
- Переиспользует готовую инфраструктуру: AST с `Location` и собранный
  `Vec<Comment>` — новых слоёв парсера не нужно.
- Решает проблему комментариев напрямую (у обоих есть смещения).
- Печать от AST (а не от семантики) сохраняет исходные имена и структуру.
- Идемпотентность достигается канонической печатью из нормализованной модели.

**Cons:**
- Нужна эвристика привязки комментариев (ведущий/хвостовой/висячий) — тестируемо,
  но требует аккуратности на краевых случаях.
- Пустые строки не хранятся ни в AST, ни в `Vec<Comment>` — «осмысленные»
  пустые строки надо восстанавливать из зазоров между смещениями узлов в
  исходнике (отдельный поддмеханизм).

### Option B. Lossless CST (rowan-подобное дерево, доработка парсера)

Ввести полное синтаксическое дерево с trivia (пробелы/переносы/комментарии как
узлы) и печатать из него.

**Pros:**
- Максимально устойчиво к trivia; естественная база для будущих rename/inspection.

**Cons:**
- Непропорционально объёму: переписывает слой парсинга (LALRPOP), большой риск и
  трудозатраты ради форматтера.
- Дублирует уже работающие AST + `Vec<Comment>`.

### Option C. Репринтер потока токенов с нормализацией пробелов

Пере-эмитировать поток токенов лексера с канонической расстановкой пробелов, а
переносы/отступы брать из AST.

**Cons:**
- Комментарии **не входят в поток токенов** (side-channel) — их всё равно надо
  сшивать по позиции, т.е. половина Option A без её плюсов.
- Структурные решения (переносы, вложенность блоков) всё равно требуют AST —
  два источника истины, выше риск рассинхронизации и потери идемпотентности.

## Decision

Принимается **Option A** — pretty-printer от позиционно-размеченного AST с
переассоциацией комментариев из `Vec<Comment>` по `Location`. Это единственный
вариант, который решает проблему комментариев, не строя новый слой парсера, и
опирается на уже существующие в `grammar` данные.

Ядро форматирования размещается в крейте `grammar` (например, модуль `format/`)
и экспортируется публичным API (напр. `format_source(src) -> Result<String, …>`),
поверх которого строятся `lamc fmt`, LSP `textDocument/formatting` и действие
IntelliJ. Пустые строки нормализуются по правилу «не более одной подряд»,
восстановление осмысленных пустых строк — из зазоров исходника между смещениями
узлов.

## Consequences

### Положительные

- Единое ядро для трёх потребителей; CI-проверка `lamc fmt --check`.
- Опора на готовые AST/`Vec<Comment>` — минимум новой инфраструктуры.
- Семантика не затрагивается → обратная совместимость сохраняется, версия языка
  не растёт.

### Отрицательные / Action items

- Спроектировать и покрыть тестами эвристику привязки комментариев
  (ведущий/хвостовой/висячий) — вынести в анализ и тест-план.
- Реализовать восстановление осмысленных пустых строк из зазоров исходника.
- Гарантировать идемпотентность на всех конструкциях (составные состояния, порты,
  `match`/`switch`, циклы, `enter`/`exit`/`always`) — обязательный тест-инвариант.
- Согласовать печать с [ADR 0019](0019-condition-expression-unification.md): при
  унификации грамматик меняется набор печатаемых узлов (см. «Зависит от» в
  анализе).

### Acceptance criteria

1. `format_source` идемпотентна: `fmt(fmt(x)) == fmt(x)` на всех фикстурах
   `tests/data/` и примерах `examples/*.lam`.
2. Комментарии всех трёх видов (`//`, `///`, `/* */`) сохраняются и печатаются в
   канонических местах; ни один не теряется.
3. Форматирование **не меняет семантику**: `parse(fmt(x))` даёт AST,
   эквивалентный `parse(x)` (сравнение по структуре, без учёта `Location`).
4. `lamc fmt --check` возвращает ненулевой код на неотформатированном входе и
   нулевой — на каноническом.
5. LSP `textDocument/formatting` и действие IntelliJ используют то же ядро (нет
   расхождения стилей между инструментами).
