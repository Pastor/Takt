# ADR 0190: Разделение предкоммита на компоненты и выборочный запуск

- **Status:** Accepted
- **Date:** 2026-08-01
- **Authors:** Архитектор
- **Related issues:** [Фича 0190](../features/0190-precheck-selective-gates.md); продолжает [ADR 0090](0090-ci-precheck.md) (предкоммит — единый источник истины гейтов)

## Context

`scripts/precheck.sh` — единственный вход всех проверок (909 строк, ~30 стадий) и
единственный источник истины для CI. Заказчик поставил задачу разложить его на
компоненты с выборочным запуском: цикл «правка → проверка» стал дороже самой
правки.

Карточка фичи требовала начать с **замера**: «оптимизировать без замера значит
гадать». Замер выполнен 2026-08-01 инструментированной копией скрипта (таймер на
каждой стадии; копия — вне репозитория, рабочий скрипт не трогался).

### Замер: где на самом деле время

Полный прогон на **тёплом** дереве (сборка уже выполнена), macOS arm64, 12 ядер:

| Стадия | Время | Доля |
|---|---|---|
| `cargo test --all-features -- --test-threads=1` | **218.7 с** | **84 %** |
| гейт тестбенчей `sv` (verilator `--binary`) | **23.0 с** | **8.8 %** |
| гейт воспроизводимости (2 прогона × цели) | 3.4 с | 1.3 % |
| `cargo build` (три вызова) | 2.7 с | 1.0 % |
| формат примеров (`fmt --check`) | 2.0 с | 0.8 % |
| ссылки Markdown | 1.5 с | 0.6 % |
| размер модулей | 1.5 с | 0.6 % |
| гейт `iec2c` | 1.4 с | 0.5 % |
| гейты `sv` / `rust` (линт, синтез, clippy) | 1.1 / 1.0 с | 0.8 % |
| **прочие 20 стадий** (все документные, все `check-*.sh`, генерация, `c-hal`, `sv-mmio`, `book/`) | **< 1 с каждая, ~2 с суммарно** | **~1 %** |
| **Итого** | **261 с (4.4 мин)** | |

**Две стадии — 93 % времени.** Это в точности сценарий, которого опасалась
карточка: «может оказаться, что 80 % времени съедают две стадии, и дешевле
ускорить их, чем строить механизм выбора».

### Замер: цена параллельных тестов

| Прогон (то же дерево) | Время | Итог |
|---|---|---|
| `cargo test -- --test-threads=1` (контроль) | 146 с | зелёный |
| `cargo test` (параллельно, 12 ядер, `--no-fail-fast`) | **89 с** | **1 упавший тест из ~1400** |

Падает `st_tests::test_plain_st_target_ignores_addresses_and_emits_no_configuration`
с `Os { code: 22, InvalidInput }`. Причина — не параллельность сама по себе, а
то, что каталог вывода уникален **по фикстуре, а не по тесту**:

```rust
fn target_dir(name: &str) -> PathBuf {
    Path::new(env!("CARGO_TARGET_TMPDIR")).join(format!("st_{}", name))
}
```

Несколько тестов используют фикстуру `types_all`, и каждый начинает с
`remove_dir_all` **общего** каталога: один сносит его, пока другой пишет.
Комментарий рядом это признаёт («тесты гоняются в один поток, но общий каталог
всё равно связал бы их друг с другом») — уникальность по фикстуре рассчитана
именно на однопоточность.

⚠️ **Гонок оказалось две, и вторую полный прогон не показал.** После починки
`target_dir` отдельный прогон набора `st_tests` уронил другой тест: помощник
`compile_st_source` строит каталог по **имени входного файла**, а его берут два
теста. То есть «зелёный полный прогон» тут ничего не доказывает — гонка
проявляется от расклада потоков. Отсюда протокол проверки: не один прогон, а
серия, и отдельно по наборам.

### Оговорки к замеру (без них цифры врут)

1. **Дерево тёплое.** `cargo check`/`clippy`/`build` показывают доли секунды; на
   холодном они займут минуты. Заявленные в карточке «порядка двадцати минут» —
   это, вероятно, прогон с холодной сборкой, и его отдельно **не мерили**.
2. **Разброс.** Первый однопоточный прогон дал 462 с, повтор — 146 с; аномалия
   не воспроизвелась (почти наверняка конкуренция с фоновым процессом). Прежде
   чем цифра станет основанием решения, протокол требует повторов на незанятой
   машине.
3. **`cargo test` не «чистый Rust»**: внутри сверок работают `cc`, `verilator`,
   `iec2c`, то есть часть этих 218 с — внешние инструменты.

## Decision Drivers

1. **Полный прогон остаётся умолчанием и обязателен перед коммитом.** Всякое
   сужение — громкое; молчаливо суженное покрытие неотличимо от пройденного
   (урок оси 5 фичи [0187](../features/0187-port-io-redesign.md)).
2. **В CI (`PRECHECK_STRICT=1`) — весь набор, без выбора и кэша**, иначе
   `precheck.sh` перестаёт быть единым источником истины (ADR 0090).
3. **Выигрыш соразмерен цене.** Механизм, экономящий 2 % времени, не окупает ни
   строчки сложности.
4. **Зависимости стадий реальны:** всё после сборки `taktc` требует её, всё
   после генерации — её. Выбор, игнорирующий это, даст зелёный прогон на
   устаревшем выводе.

## Considered Options

### Option A. Именованные компоненты + выборочный запуск (исходный замысел)

Разложить скрипт на компоненты (`docs`, `lint`, `test`, `targets:sv`, …), дать
`--only` / `--skip`.

**Pros:**
- прямо отвечает формулировке задачи;
- позволяет гонять один целевой гейт при правке одного бэкенда.

**Cons:**
- **экономия ≤ 7 %**, если не трогать тесты: все документные и быстрые гейты
  вместе стоят ~2 с из 261 с;
- требует явной модели зависимостей (иначе «только `sv`» проверит вчерашний
  вывод) — сложность растёт, выигрыш остаётся малым;
- заводит второй способ запускать проверки, который может разойтись с CI.

### Option B. Параллельные тесты (снять `--test-threads=1`)

Развести каталоги тестов по тесту, а не по фикстуре, и убрать принудительную
однопоточность.

**Pros:**
- **146 → 89 с на стадии тестов** (−39 %), то есть ~22 % полного прогона;
- цена входа — правка одной функции в одном файле (подтверждено: падает ровно
  один тест);
- ускоряет и локальный прогон, и CI, не меняя состава проверок — **покрытие не
  сужается вовсе**, драйвер 1 не задет.

**Cons:**
- параллельность может вскрыть другие скрытые связи через общие пути (сегодня
  она ровно одна, но новые тесты обязаны писать в свой каталог);
- порядок вывода тестов перестаёт быть детерминированным.

### Option C. Кэш по отпечатку входов

Пропускать гейт, входы которого не изменились (хеш каталога/файлов).

**Pros:**
- экономит без участия человека — нельзя «забыть включить гейт»;
- бьёт по дорогим стадиям: тестбенчи `sv` (23 с) при нетронутом `sv` — чистая
  экономия.

**Cons:**
- отпечаток обязан включать **все** входы (исходники компилятора → любой гейт
  целей), иначе кэш соврёт; ошибка здесь равна молчаливо пропущенному гейту;
- в CI кэш запрещён драйвером 2, то есть выигрыш только локальный.

### Option D. Прогон тестовых наборов параллельно (`cargo nextest`)

`cargo` параллелит тесты **внутри** набора, но наборы гоняет последовательно;
`nextest` снимает это ограничение.

**Pros:**
- потенциально больше, чем B (у проекта ~45 наборов, многие мелкие);
- заодно даёт машиночитаемый отчёт.

**Cons:**
- внешняя зависимость в обязательном пути сборки — решение заказчика;
- требует установки в CI и на машинах разработчиков.

### Option E. Ничего не делать

**Pros:** нулевая цена; 4.4 минуты на тёплом дереве терпимы.

**Cons:** не отвечает на запрос заказчика; холодный прогон не измерен и может
быть заметно хуже.

## Decision

**Решение заказчика 2026-08-01: принимается Option B** — параллельные тесты,
каталог теста уникален по тесту.

Обоснование: замер показал, что 84 % времени предкоммита — одна стадия
`cargo test`, и однопоточность держалась не на природе тестов, а на **двух
строках** в `st_tests`. Вариант даёт наибольший выигрыш на единицу сложности и
**не трогает состав проверок вовсе** — драйвер 1 (никакого молчаливого сужения)
не задет по построению.

Прочие варианты **не отвергнуты, а отложены**: A (компоненты) экономит ≤ 7 % и
после B станет ещё менее выгодным; C (кэш) и D (`nextest`) остаются кандидатами,
если после B время снова станет мешать. E (ничего не делать) снят выбором B.

## Consequences

### Положительные

- **`cargo test`: 146 с → 95–127 с** (три параллельных прогона подряд, 12 ядер),
  то есть ~30 % самой дорогой стадии и ~20 % полного предкоммита.
- **Состав проверок неизменен** — ускорение получено без единого пропуска.
- **Устранён скрытый дефект тестов**: гонок оказалось две (каталог по фикстуре и
  каталог по имени входного файла), причём вторая проявилась только при
  отдельном прогоне набора — то есть жила бы дальше незамеченной.

### Отрицательные / Action items

- Порядок вывода тестов больше не детерминирован — при разборе падения читать
  имя теста, а не позицию в выводе.
- **Новые тесты обязаны писать в свой каталог.** Правило записано в `CLAUDE.md`:
  покраснел параллельный прогон — чинить каталог теста, а не возвращать флаг.
- Холодный прогон по-прежнему не измерен; «двадцать минут» из карточки к нему и
  относятся. Отдельная работа, если заказчик сочтёт нужным.

### Что остаётся верным независимо от выбора

- **разделение на компоненты само по себе задачу не решает**: 93 % времени лежит
  в двух стадиях, и ни одна из них выбором не убирается — обе обязательны;
- **любой выбранный путь не вправе сужать покрытие молча** (драйвер 1); это
  относится и к кэшу (C), где ошибка в наборе входов равносильна пропуску гейта;
- **однопоточность тестов — не свойство тестов, а следствие одного дефекта**
  (общий каталог на фикстуру), и он подлежит устранению независимо от выбранной
  оси.

### Acceptance criteria

1. Полный прогон остаётся умолчанием; в `PRECHECK_STRICT=1` состав проверок не
   сужается ничем (ни выбором, ни кэшем).
2. Всякое сужение печатается в вывод — законный пропуск и пропуск-дефект
   различимы.
3. Заявленный выигрыш подтверждён замером **после** правки, тем же протоколом,
   что и до неё.
