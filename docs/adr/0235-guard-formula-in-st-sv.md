# ADR 0235: Цели st и sv теряют охранную формулу

- **Status:** Accepted (Option C с уточнением заказчика: `st` предупреждает, а не отказывает; 2026-08-15)
- **Date:** 2026-08-15
- **Authors:** Архитектор
- **Related issues:** [Фича 0235](../features/0235-guard-formula-in-st-sv.md); находка [фичи 0203](../features/0203-validate-formulas-traversal.md) (validate не обходил формулы); смежно с [ADR 0044](0044-sim-assert-invariant.md) (`invariant` как сахар над `cond` + `Formula::Guard`), [ADR 0041](0041-st-backend.md) (бэкенд ST), [ADR 0045](0045-sv-backend.md) (бэкенд SV)

## Context

Охранная формула — средство **безопасности**: `: [Guard] level < 3;` и
`invariant Safe = level < 3;` объявляют условие, которое обязано держаться.
Фича [0203](../features/0203-validate-formulas-traversal.md) закрыла молчание в
семантике: опечатка в имени внутри формулы стала ошибкой компиляции. Но она же
назвала границу, оставленную вне объёма: **цели `st` и `sv` не печатают
проверку вовсе — и при верном имени тоже**.

Автор, собирающий ПЛК или FPGA, получает прошивку **без** объявленного им
средства безопасности. Компилятор при этом рапортует об успехе.

### Пробой (2026-08-15)

Вход — одна модель, одна формула:

```takt
var level: u8 := 0;
invariant Safe = level < 3;
start Run { : [Guard] level < 3; always { level := level + 1; } ref Run; }
```

| Цель | Что в выводе |
|---|---|
| `c` | `assert(model->level < 3);` |
| `rust` | `assert!(self.level < 3, "нарушен инвариант 'Safe'");` |
| `st` | **ничего** |
| `sv` | **ничего** |
| симулятор | `SIM-025` при нарушении |

### Возможна ли трансляция вообще — измерено, а не предположено

**Цель `sv`.** Immediate assertion внутри `always_ff`:

| Форма | verilator `--lint-only -Wall` | yosys `synth` |
|---|---|---|
| `assert (level < 3);` | **принял** (код 0) | **принял** (код 0) |
| `assert (level < 3) else $error("…");` | принял (код 0) | **ОТВЕРГ**: `syntax error, unexpected TOK_ELSE` |

Статистика синтеза для принятой формы: 29 ячеек, из них **`$check` — одна**,
логика прежняя (8 `$_DFF_PN0_` и комбинационная обвязка). То есть проверка
попадает в вывод как **формальное свойство** и синтезируемую логику не трогает.

⚠️ Отсюда следствие: **текст сообщения (имя инварианта) в цель `sv` перенести
нельзя** — форма с `else $error(…)` валит yosys. Цель `rust` имя печатает, цель
`c` игнорирует, цель `sv` не сможет по устройству инструмента.

**Цель `st`.** В IEC 61131-3 конструкции `assert` **нет вовсе**. Проба
ближайшего аналога — булев флаг нарушения:

```st
IF NOT (level < 3) THEN guard_violated := TRUE; END_IF;
```

`iec2c` принимает (код 0). То есть техническая возможность есть, но она
**вводит в язык новую сущность**: переменную, которой никто не читает, и
семантику «нарушение зафиксировано, выполнение продолжается».

### Замер корпуса: цена отказа цели `st` — ноль правок

| Где | Файлов с `invariant` / `: [Guard]` |
|---|---|
| **`examples/`** (корпус гейтов `st`/`sv`) | **0** |
| `book/src/*/examples/` | 2 (`airlock`, `lift`) — гейт 0133 компилирует их целью **`c`** |
| `takt-sim/tests/data/` (фикстуры эталона) | 5 |
| `takt-lang/tests/data/formula0203/` | фикстуры 0203, целями не собираются |

⚠️ То есть главный минус вариантов с отказом (**«ломает корпус»**) на замере
**отсутствует**: ни один пример, который гейт транслирует целью `st`, формул не
содержит. Обратная сторона того же факта: **корпус этот класс не покрывает
вовсе** — потому потеря и дожила незамеченной, и любое решение обязано прийти
со своей фикстурой.

### Дополнительная находка: в цели `sv` инфраструктура уже заведена

`SvMap` хранит поле `guard_enable` («эмитить ли guard-проверки — флаг
`--guard-disable` наоборот») и отдаёт его геттером `guard_enable()`. **Ни один
печатник цели `sv` этот геттер не вызывает.** То есть заготовка под проверки
существует с самого бэкенда, а самих проверок нет — тот же класс, что 0194
(«механизм на месте, поле не наполнено») и 0232 («проверка считалась и
выбрасывалась»).

## Decision Drivers

1. **Молчаливая потеря средства безопасности недопустима.** Это тот же класс,
   ради которого заведена 0203: автор написал охрану, её нет, и никто не сказал.
2. **Возможности целей различны, и это не вкусовщина.** В SV средство штатное и
   принимается обоими инструментами гейта; в IEC 61131-3 его нет.
3. **Кодогенератор не вправе вводить семантику, которой нет в языке.** Флаг
   `guard_violated` в ST — новая наблюдаемая сущность: кто её читает, что
   означает её значение между сканами, попадает ли она в интерфейс
   `FUNCTION_BLOCK`. Такие решения принимает язык, а не бэкенд.
4. **Отказ — законный ответ.** У проекта есть прецедент: `SV-003` на `float`,
   `ST-011` на агрегатную инициализацию, `RS-011` на поля структур. Отказ с
   причиной честнее молчания и дешевле неверной семантики.
5. **Уже заведённый флаг `--guard-disable` обязан работать одинаково** во всех
   целях, которые проверки печатают.

## Considered Options

### Option A. Обе цели печатают проверку

`sv` → `assert (expr);`; `st` → булев флаг нарушения плюс присваивание.

**Pros:**
- Ни одна цель не теряет объявленное средство безопасности.
- Для `sv` цена нулевая: синтезируемая логика не меняется.

**Cons:**
- В ST вводится **новая сущность языка** через бэкенд: переменная-флаг, которую
  никто не читает, и молчаливое продолжение работы после нарушения. Симулятор в
  той же ситуации **останавливается** (`SIM-025`) — то есть цель `st` получила бы
  семантику, отличную от эталона, и это расхождение пришлось бы описывать.
- ⚠️ Флаг попадает в состав `FUNCTION_BLOCK`, то есть в наблюдаемый интерфейс.

### Option B. Обе цели отказывают с диагностикой

`ST-…` и `SV-…`: «охранная формула целью не транслируется».

**Pros:**
- Молчание исчезает; поведение целей единообразно.
- Не вводит семантики, которой нет в языке.

**Cons:**
- Для `sv` это **отказ там, где средство есть и работает**: обе пробы приняли
  `assert`. Отказывать при наличии штатного механизма — терять даром.
- Программы корпуса, содержащие `invariant`, перестанут собираться этими целями
  (совместимость; объём правки корпуса надо мерить).

### Option C. `sv` печатает, `st` отказывает

Разные ответы, потому что возможности целей различны: в SV — `assert (expr);`
(без `else`, по пробе); в ST — диагностика `ST-…` с названной причиной («в IEC
61131-3 конструкции assert нет; выразить проверку без введения новой сущности
невозможно»).

**Pros:**
- Каждая цель делает **максимум возможного**, и ни одна не молчит.
- Ничего не выдумывается: SV получает штатное средство, ST — честный отказ.
- Мёртвый `guard_enable` в `SvMap` оживает, флаг `--guard-disable` начинает
  работать и там.

**Cons:**
- Ответы целей различаются — это надо назвать в документе, иначе следующий
  читатель сочтёт расхождением.
- Отказ `st` ломает сборку программ с `invariant` этой целью (нужен замер
  корпуса).

### Option D. `sv` печатает; `st` печатает флаг только по явному запросу CLI

Как C, но у `st` появляется опция `--st-guard-flag`, включающая эмиссию флага.

**Pros:**
- Автор ПЛК получает выбор.

**Cons:**
- Флаг CLI, меняющий **семантику** вывода, — прямое нарушение принципа 0042
  («CLI не должен менять логику автомата»); единственное узаконенное исключение
  (0096) документировано и сверяется трассами.
- Умножает состояния: два вывода `st` вместо одного, оба надо сверять.

## Decision

Принимается **Option C с уточнением заказчика** (2026-08-15): цель `sv`
**печатает** проверку, цель `st` **предупреждает**, а не отказывает.

- **Цель `sv`:** `assert (<условие>);` внутри тактового блока. Форма
  подтверждена обеими пробами; ⚠️ **без `else $error(…)`** — эта форма валит
  yosys (`syntax error, unexpected TOK_ELSE`), то есть имя инварианта в цель
  `sv` перенести нельзя по устройству инструмента, а не по забывчивости.
  Проверка уважает `--guard-disable` через уже существующее поле
  `SvMap::guard_enable`, которое до сих пор не читал никто.
- **Цель `st`:** новый код **`ST-022`** — предупреждение «охранная формула не
  транслируется: в IEC 61131-3 конструкции `assert` нет». **Вывод остаётся**:
  модель по-прежнему собирается для ПЛК, автор лишь узнаёт, что охрана в
  прошивку не попала. Канал доставки у цели `st` уже есть (`report`,
  `emit_functions` → `warnings`).

Почему предупреждение, а не отказ (уточнение заказчика): отказ лишил бы автора
рабочей трансляции ПЛК из-за конструкции, которая для этой цели лишь
**неприменима**, а не ошибочна. Предупреждение снимает молчание — то есть
решает предмет фичи — и не отнимает возможности собрать модель.

⚠️ Почему **не** булев флаг нарушения в ST (Option A): он ввёл бы в язык
сущность, которой в нём нет, и семантику «нарушено, но работаем дальше»,
расходящуюся с эталоном (`SIM-025` останавливает прогон). Такое решение
принимает язык, а не бэкенд.

## Consequences

### Положительные

- Охранная формула перестаёт молча исчезать: в SV она попадает в вывод, в ST
  автор узнаёт о невозможности **до** прошивки ПЛК.
- Поле `guard_enable` в `SvMap` перестаёт быть мёртвым, а `--guard-disable`
  начинает работать в трёх целях из четырёх.

### Отрицательные / Action items

- **Совместимость цели `st` НЕ нарушается** (уточнение заказчика: предупреждение
  вместо отказа): программы с `invariant`/`: [Guard]` по-прежнему собираются, к
  выводу лишь добавляется `ST-022`. Замер корпуса это подтверждает избыточно —
  в `examples/` таких программ ноль.
- ⚠️ **Предупреждение печатается из библиотеки** (`eprintln!` в `report`) — общий
  дефект доставки, названный ещё ADR 0064 и заведённый фичей
  [0168](../features/0168-generator-warnings-return.md) (`СОЗДАНА`). `ST-022`
  наследует его вместе с образцом; чинить здесь нельзя — фича превратилась бы в
  рефакторинг доставки.
- **Сверка поведения:** проверка в SV не должна менять трассу
  (`conformance_sv_tests`), иначе «добавили безопасность — сломали поведение».
- **Форма без `else` фиксируется гейтом:** попытка добавить сообщение через
  `else $error(…)` уронит yosys, и об этом обязан знать следующий.
- Смежное, вне объёма: цель `c` игнорирует имя инварианта, `rust` печатает —
  расхождение существовало до фичи и остаётся.

### Acceptance criteria

1. Охранная формула не исчезает молча ни в одной цели.
2. Цель `sv` печатает проверку, и вывод принимается **обоими** инструментами
   гейта (verilator и yosys).
3. Синтезируемая логика цели `sv` не изменилась (сверка трасс зелёная).
4. Флаг `--guard-disable` подавляет проверки и в цели `sv`.
5. Цель `st` выдаёт **предупреждение `ST-022`** и **продолжает** трансляцию;
   это закреплено тестом и названо в документе.
6. Замер корпуса выполнен: известно, какие примеры задеты.
7. `./scripts/precheck.sh` зелёный.
