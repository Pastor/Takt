# ADR 0127: Единая семантика переполнения целых во всех целях

- **Status:** Accepted
- **Date:** 2026-07-27
- **Authors:** Системный аналитик, архитектор, дизайнер языка
- **Related issues:** [Фича 0127](../features/0127-int-overflow-semantics.md)

## Context

Аудит 2026-07-27 показал живой пробой: типовой счётчик
`var t: u8 := 250; always { t := t + 1; }` — конструкция, которая есть в
**каждом** примере книги (`beacon`, `traffic`, `watchdog`, `lift`) — ведёт себя
в целях по-разному. Симулятор, `c` и `sv` считают дальше (`255 → 0`), а
порождённый **Rust паникует**: `attempt to add with overflow`. Хуже того, в
release-профиле тот же код молча оборачивается — то есть поведение прошивки
зависело от **профиля сборки пользователя**.

При этом правило у проекта **уже есть**, только не названо правилом языка. Анализ
фичи [0025](0025-simulator-expression-eval.md) фиксирует принцип: «определённое в
C поведение — воспроизводим; неопределённое (UB) — не воспроизводим и не
паникуем, а диагностируем», и из него два следствия:

- **S1** — переполнение беззнакового: в C определено (обёртка mod 2ⁿ),
  симулятор её воспроизводит;
- **S2** — переполнение знакового: в C это **UB**, симулятор **диагностирует**
  (`SIM-003`).

То есть эталон определён, а расхождение целей с ним никем не проверялось: сверки
`conformance_*` переполнения не касались вовсе, поэтому дефект цели `rust` дожил
до аудита. Поведение цели `st` при переполнении не проверялось **никогда**.

## Decision Drivers

1. **Эталон уже есть** — задача не изобрести правило, а **возвести его в норму
   языка** и привести цели к нему.
2. **Прошивка не должна зависеть от профиля сборки.** Паника в debug и обёртка в
   release — это два разных изделия из одного исходника.
3. **Проверять, а не декларировать.** Урок 0045: гейт доказывает, что вывод
   компилируется, но не что он верен; нужна потактовая сверка.
4. **Не расширять объём.** Знаковое переполнение — отдельная тема (в C это UB),
   и «чинить» его в целях означало бы изобретать семантику, которой у языка нет.

## Considered Options

### Option A. Возвести S1/S2 в правило языка; цель `rust` привести к S1

Беззнаковое переполнение — нормативная обёртка `mod 2ⁿ`; цель `rust` печатает
`wrapping_add`/`wrapping_sub`/`wrapping_mul` для беззнаковых операндов.
Знаковое — ошибка программы (симулятор диагностирует, цели не обязаны совпадать).
Сверки переполнения добавляются во **все четыре** цели.

**Pros:**
- Совпадает с уже принятым эталоном (0025), ничего не переопределяет.
- Устраняет зависимость поведения от профиля сборки.
- Малый объём: печать трёх операций в одном печатнике плюс четыре сверки.
- Знаковый случай остаётся честно названным «ошибкой программы», а не
  замаскированным.

**Cons:**
- Порождённый Rust становится многословнее (`a.wrapping_add(b)` вместо `a + b`).
- Знаковое переполнение по-прежнему ведёт себя в целях по-разному (но теперь это
  **названо** и задокументировано).

### Option B. Обёртка для **всех** целых в цели `rust` (и знаковых тоже)

**Pros:**
- Единообразие внутри цели `rust`; никакой зависимости от профиля.

**Cons:**
- **Молча** расходится с эталоном: симулятор на знаковом переполнении даёт
  `SIM-003`, а прошивка тихо продолжит с другим значением. Проект такие
  расхождения считает худшим исходом («один вход — четыре ответа, и три из них
  молча»).
- Отнимает у разработчика единственный бесплатный сигнал об ошибочной программе
  (паника debug-профиля).

### Option C. Диагностировать переполнение во всех целях (проверки в рантайме)

**Pros:**
- Полное совпадение с эталоном, включая знаковый случай.

**Cons:**
- Цена в коде: проверка на каждой арифметической операции — недопустимо для
  прошивки МК и **невыразимо** в RTL (цель `sv`), где «сообщить об ошибке»
  некому.
- Меняет назначение целей: они порождают управляющую логику, а не отладочный
  рантайм.

## Decision

Принимается **Option A**.

**Правило языка (нормативно):**

1. **Переполнение беззнакового целого — обёртка по модулю `2ⁿ`.** Одинаково у
   эталона-симулятора и у всех целей генерации; проверяется потактовыми сверками.
2. **Переполнение знакового целого — ошибка программы.** Симулятор
   диагностирует (`SIM-003`) и останавливает прогон; поведение порождённого кода
   в этом случае языком **не гарантируется** (в C это UB). Программа, полагающаяся
   на переход знакового через край, некорректна.

**Реализация:** цель `rust` печатает беззнаковую арифметику `+`, `−`, `*` как
`wrapping_add`/`wrapping_sub`/`wrapping_mul` (тип операнда определяется уже
существующим `expression_type`); свёртка в составное присваивание (`x += 1`) для
таких узлов отключена — она вернула бы панику. Знаковая арифметика печатается
как прежде: паника debug-профиля — полезный сигнал об ошибочной программе, а не
дефект.

## Consequences

### Положительные

- Прошивка на Rust больше не зависит от профиля сборки в вопросе переполнения.
- Правило названо и **проверено исполнением** во всех четырёх целях
  (`conformance_{c,rust,sv,st}`), а не заявлено в документации.
- Поведение цели `st` при переполнении проверено **впервые**.
- Документация языка перестала утверждать неверное: прежняя формулировка
  «арифметика выполняется по модулю разрядности типа» распространяла обёртку и
  на знаковые типы, где её нет.

### Отрицательные / Action items

- **Знаковое переполнение остаётся разноголосым** (симулятор — диагностика,
  C — UB, Rust — паника/обёртка по профилю, SV — обёртка). Это **названо**
  правилом («программа ошибочна»), но не устранено; полное устранение — Option C,
  отвергнутый по цене.
- **Порождённый Rust многословнее.** Цена принята: читаемость уступает
  предсказуемости.
- **Сверка ST идёт с поправкой на INIT-сдвиг** цели `st` (существующий долг
  контракта 0033, к переполнению отношения не имеющий) — по той же конвенции,
  что уже принята в Q-сверке.

### Acceptance criteria

1. `wrapping_*` печатается для беззнаковой арифметики в цели `rust`; свёртка в
   `+=` для таких узлов не применяется.
2. Потактовая сверка переполнения проходит у **всех четырёх** целей.
3. Сторож взведён: откат правки генератора обязан красить сверку `rust`.
4. Правило записано в документ описания языка (раздел «Типы»), включая явное
   различие беззнакового и знакового случаев.
5. `./scripts/precheck.sh` зелёный; изменения в `examples/generated/rust`
   объяснимы (обёртка вместо `+`).

> Диаграмма по правилу 18 **не требуется**: синтаксис не меняется — нормируется
> семантика уже существующей арифметики.
