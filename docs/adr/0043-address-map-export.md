# ADR 0043: Формат и форма экспорта карты адресов портов

- **Status:** Accepted
- **Date:** 2026-07-15
- **Authors:** Архитектор + системный аналитик + дизайнер языков
- **Related issues:** [Фича 0043](../features/0043-address-map-export.md); развивает
  [ADR 0020](./0020-port-address-decl.md) (раздел «Потребители», пункт
  «SVD-подобный экспорт»); пересечения с фичами
  [0041](../features/0041-st-backend.md) и [0042](../features/0042-address-defines.md)

## Context

ADR 0020 ввёл внутренний слой `AddressMap` и назвал среди будущих потребителей
«**SVD-подобный экспорт**: `lamc address-map --emit …` выгружает карту наружу
(отдельная фича)». Эта фича — тот самый вынос. Решить надо три вопроса:
(1) **в каком формате** выгружать, (2) должен ли результат **читаться обратно**,
(3) **какая форма CLI**.

### Что реально есть в коде (проверено 2026-07-15)

Модуль карты лежит в **`grammar/src/address_map.rs`** (не в `semantic/`, как
указано в некоторых описаниях задачи):

| Сущность | Место | Содержимое |
|---|---|---|
| `AddressMapEntry` | `address_map.rs:36` | `name: String`, `addr: i64`, `bit: Option<i64>`, `loc` |
| `parse_address_map` | `address_map.rs:138` | парсер `.ld`-подобного формата, коды `AM-001…006` |
| `AddressSource` | `address_map.rs:350` | `Inline` \| `Operator` \| `External` |
| `ResolvedAddress` | `address_map.rs:361` | `addr: i64`, `bit: Option<i64>`, `source: AddressSource` |
| `AddressResolution` | `address_map.rs:372` | `map: HashMap<String, ResolvedAddress>`, `diagnostics` |
| `resolve_addresses` | `address_map.rs:409` | приоритет inline < `address` < внешняя карта; SE-050/051/052 |

CLI (`grammar/src/bin/lamc.rs`) сегодня имеет **две** подкоманды: `compile`
(строка 474) и `fmt` (строка 462); у `compile` — флаги `-t/--target` (176),
`-o/--output` (183), `-I/--include-dirs` (190), `-v/-q` (201/204),
`--guard-enable/--guard-disable` (207/210), `--address-map` (213). Цели: `c`,
`c-hal`, `plantuml` (551–655).

### Проба (2026-07-15): что выгружать вообще есть

Компиляция модели с тремя источниками адреса и внешней картой-оверлеем
(`lamc compile -t c-hal --address-map plat.map probe.lam`) даёт:

```text
Предупреждение [SE-050]: внешняя карта переопределяет адрес порта 'BTN', заданный в модели
Предупреждение [SE-051]: внешняя карта задаёт адрес для несуществующего порта 'GHOST'

static const Probe_In_BitPort__ADDR[]     = { [PROBE_SW]  = { 0x300000u,   3, 4 } };
static const Probe_Out_BitPort__ADDR[]    = { [PROBE_LED] = { 0x200004u,  -1, 4 } };
static const Probe_In_NumericPort__ADDR[] = { [PROBE_BTN] = { 0x40000000u,-1, 1 } };
```

Приоритет источников работает (`BTN`: inline `0x200000` перекрыт картой
`0x40000000`). На реальном примере `examples/elevator_mini.lam` (44 порта) без
карты — ошибка `SE-052`; с полной картой — компилируется, все 44 адреса
разрешены.

### Ключевая находка: чего в `AddressMap` нет

`ResolvedAddress` содержит **только** `addr`, `bit`, `source`. Всё остальное, что
нужно «настоящему» описанию регистра, живёт **вне карты**:

- **разрядность** — вычисляется в C-генераторе: `width_from_ctype`
  (`generator/c/c_header.rs:617`) поверх `port_ctype` (там же, 628). В карте её
  нет. Более того, для типа `Bit` она **недостоверна**: `get_c_type(Bit) → "int"`
  → `width = 4`, тогда как дефолтный HAL разыменовывает `uint8_t` (проба выше:
  `PROBE_SW`/`PROBE_LED` имеют `width 4` при однобитовом типе). Дефект известен и
  зафиксирован в `CLAUDE.md` / кандидате 0029;
- **права доступа** — выводимы из `direction: PortDirection`
  (`semantic/mod.rs:847`, `VariableNode::Port`), но в карту **не попадают**;
- **группировка в peripherals, reset-значения, `addressUnitBits`, размер
  регистра** — таких понятий в языке Lam **нет вообще**;
- **квалификация имени** — ключ карты плоский (`HashMap<String, _>`), при том
  что C-генератор индексирует таблицу **квалифицированными** enum-вариантами
  (проба: `ELEVATOR_MINI_CABIN_…` / `ELEVATOR_MINI_MOTOR_…`, тогда как ключ
  карты — голое `CabinButton_DC`).

**Вывод:** карта **стабильна и достаточна** для выгрузки того, что она и есть —
`имя → (адрес, бит, источник)`; и **недостаточна** для схемы, требующей
разрядности/прав/иерархии регистров. Это и определяет выбор формата.

## Decision Drivers

1. **Не врать потребителю.** Отладчик/`svd2rust` доверяют формату. Правдоподобный,
   но выдуманный SVD хуже отсутствия SVD: ошибка уедет в чужой тулчейн молча.
2. **Правило 12 (профиль проекта).** Lam — промышленные системы управления. SVD —
   стандарт ARM Cortex-M; целевая аудитория Lam включает ПЛК/IEC 61131-3
   (фича 0041), где SVD не применяется.
3. **Соответствие фактическим адресам.** Выгрузка обязана совпадать с тем, что
   потребляет `-t c-hal`, включая приоритет источников. Единственный корректный
   путь — общий `resolve_addresses`, а не повторный разбор источников.
4. **Проверяемость.** Формат должен иметь сильный тестовый оракул в CI без
   внешних зависимостей и сетевых схем.
5. **Переиспользование инфраструктуры** (драйвер из ADR 0020) — не плодить парсеры
   и не тащить обязательных зависимостей в `lamc`.
6. **Формат = внешний контракт.** Выпущенный формат придётся поддерживать; цена
   ошибки выше, чем у внутреннего API.

## Considered Options

### Option A. Настоящий CMSIS-SVD (XML)

**Pros:**
- Готовая экосистема потребителей: OpenOCD, pyOCD, SEGGER Ozone, `svd2rust`.
- Стандарт ARM со строгой XSD — потребителю ничего не надо адаптировать.

**Cons:**
- **Схема требует данных, которых у Lam нет.** Обязательны `<device>` c
  `addressUnitBits`, `width`, `size`, `resetValue`, и иерархия
  `peripherals → peripheral(baseAddress) → registers → register(addressOffset,
  size, access)`. У Lam нет понятий peripheral, reset-значения и достоверного
  размера регистра (см. Context: `width` для `Bit` заведомо неверна).
- **Заполнение ⇒ фабрикация.** Пришлось бы синтезировать фиктивный peripheral,
  проставить `resetValue = 0` и `size = 32` «по умолчанию». Это нарушает драйвер 1:
  отладчик покажет неверную разрядность регистра как факт.
- **Промах по профилю** (драйвер 2): ARM-специфичный формат для проекта, чей
  целевой стек включает ПЛК.
- Валидация по XSD в CI требует внешнего валидатора/схемы — вес и хрупкость.
- Нет кругового рейса: `--address-map` XML не читает.

### Option B. Собственный JSON

**Pros:**
- Описывает **ровно то, что есть**, без фабрикации: имя, адрес, бит, источник,
  тип, направление.
- Тривиально потребляется генераторами HAL и скриптами на любом языке.
- Проверяем в CI без внешних схем: `serde_json` уже **безусловная dev-зависимость**
  `grammar` (`Cargo.toml`), при том что в самом бинаре `serde_json` — **опционален**
  (за `lsp`). Значит, эмиссию можно написать руками (плоские записи из строк и
  чисел), а тесты — разбирать `serde_json`. Новых обязательных зависимостей ноль.

**Cons:**
- **Нет готовых потребителей** — каждому нужен свой адаптер (но для генератора
  HAL адаптер нужен в любом случае).
- Круговой рейс не бесплатен: `--address-map` JSON не читает.

### Option C. Повторный вывод в `.ld`-подобный формат карты

**Pros:**
- **Круговой рейс даром**: `parse_address_map` (`address_map.rs:138`) уже читает
  этот формат — export → `--address-map` замыкается, и это проверяемый инвариант.
- Ноль нового кода парсинга; формат уже документирован (EBNF в
  `address_map.rs:14–21` и в ADR 0020).
- Привычен платформенным инженерам (модель линкер-скрипта).

**Cons:**
- **Лоссовый**: несёт только `имя = адрес[:бит]`. Ни направления, ни типа, ни
  источника — то есть генератору HAL его мало.
- Отладчиками не читается.

### Option D. Несколько форматов через `--emit <fmt>`

**Pros:**
- Разные потребители получают разное: круговой рейс — из `map`, полнота — из `json`.
- Точка расширения: SVD/иное добавляется позже без слома CLI.

**Cons:**
- Больше поверхности (флаг-матрица, тесты на каждый формат).
- Риск «эмиттер ради эмиттера», если формат не имеет потребителя.

## Decision

Принимается **Option D в ограниченном составе: ровно два формата — `map` и
`json`**; **Option A (настоящий SVD) отклоняется** и выносится в кандидаты.

### 1. Формат выгрузки (главное решение)

`lamc address-map --emit map|json`, по умолчанию **`map`**.

- **`map`** (Option C) — `.ld`-подобный формат, побайтово тот же, что читает
  `--address-map`. Потребители: сам `lamc`, платформенные скрипты, `diff` карт
  между ревизиями.
- **`json`** (Option B) — полная запись: квалифицированное имя, адрес, бит,
  источник, тип, направление. Потребители: генераторы HAL, внешний тулинг.

Оба берут данные из **одного** `resolve_addresses`, поэтому по построению
совпадают с тем, что эмитит `-t c-hal` (драйвер 3).

**Почему не SVD.** Кандидат назывался «SVD-подобный экспорт», и соблазн выпустить
именно SVD велик — но по факту (Context) Lam не располагает **ни одним** из
обязательных полей схемы SVD, кроме адреса: нет peripherals, нет reset-значений,
а `width` в единственном месте, где она сегодня считается (`c_header.rs:617`), для
типа `Bit` **неверна**. SVD, собранный из адреса плюс проставленных «по
умолчанию» полей, — это не экспорт, а фабрикация, которая уедет в отладчик под
видом факта (драйвер 1). Плюс промах по профилю (драйвер 2): SVD — ARM Cortex-M,
а Lam целится и в ПЛК (0041). Поэтому SVD отложен до появления **реальных**
данных: иерархии портов, достоверных разрядностей (кандидат 0029) и понятия
периферии. Тогда он заводится отдельной фичей и добавляется как третье значение
`--emit` — CLI под это уже готов.

### 2. Круговой рейс — да, для формата `map`

Выгрузка `--emit map` **обязана** читаться обратно через
`compile --address-map`, а повторный экспорт — давать **побайтово тот же** текст
(идемпотентность). Свойство ценно втройне:

- **практически** — «сними карту с модели → отредактируй под платформу → подай
  назад» есть рабочий процесс платформенного инженера, ради которого 0020 и
  вводила оверлеи;
- **как оракул** — export → import → export = identity ловит расхождения
  эмиттера и парсера в CI без эталонных файлов (драйвер 4);
- **как страховка контракта** — формат уже зафиксирован парсером, то есть
  контракт не выдумывается заново.

Для `json` круговой рейс **не требуется** (это выход, а не вход): читать JSON
как карту адресов — отдельная фича, если появится спрос. Симметрия ради симметрии
здесь дала бы второй парсер входного формата — против драйвера 5.

Важная оговорка: круговой рейс **сохраняет адрес и бит, но не источник** — после
импорта все адреса станут `External`. Это не дефект, а семантика оверлея (карта
главнее модели); фиксируется в контракте формата и проверяется тестом.

### 3. Форма CLI — подкоманда, не флаг у `compile`

Принимается **`lamc address-map [-I …] [--address-map FILE] [--emit map|json]
[-o FILE] <input.lam>`**.

Обоснование против флага `compile --emit-address-map`:

1. **Экспорт — не компиляция.** Он не порождает целевой код; у `compile`
   вид результата уже выбирается `-t`, и ортогональный `--emit` создал бы
   бессмысленную матрицу (`-t c --emit json` — компилировать и выгружать? только
   выгружать?).
2. **Прецедент в самом проекте.** `fmt` (`lamc.rs:462`) — уже подкоманда для
   работы, не являющейся компиляцией. Решение следует сложившейся форме.
3. **Свой набор флагов.** Подкоманде нужны `-I`, `--address-map`, `-o` — и не
   нужны `-t`, `--guard-*`. Подкоманда выражает это честно.

Цена — дублирование разбора `-I`/`--address-map`; снимается вынесением общего
разбора в функции (задача 0043-03).

### О диаграмме (правило 18)

Диаграмма **не добавляется**, и это осознанно. Правило 18 требует её, когда ADR
меняет **синтаксис или семантику языка** — здесь язык не меняется вовсе (`.lam`
не затронут, версия языка остаётся 0.2.0), — либо когда она **строго необходима**
для понимания. Поток данных «источники → `AddressMap` → потребители» уже
изображён в [ADR 0020](./0020-port-address-decl.md) (раздел «Ядро: `AddressMap`»);
0043 лишь добавляет к нему одну стрелку-потребителя, ради которой схема-дубль
понимания не прибавит. Грамматика формата `map` также не нова — её EBNF
зафиксирована в ADR 0020 и в `address_map.rs:14–21`, а 0043 обязуется её
воспроизводить, а не менять.

## Consequences

### Положительные

- Адреса становятся доступны стороннему тулингу — закрывается пункт «потребители»
  из ADR 0020.
- Круговой рейс `map` даёт рабочий процесс платформенного инженера и сильный
  инвариант для CI.
- Проект не выпускает недостоверный SVD и не берёт на себя контракт, который не
  может честно исполнить.
- Новых обязательных зависимостей нет; язык не меняется (правило 22: версия
  языка **не** повышается).
- CLI готов принять SVD третьим значением `--emit`, когда данные появятся.

### Отрицательные / Action items

- **Формат `json` становится внешним контрактом.** → Обязательства: поле версии
  формата с первого выпуска; перечень `source` объявляется **открытым**
  (потребитель обязан терпеть незнакомое значение) — иначе фича 0042 (`--define`)
  сломает потребителей, добавив четвёртый источник.
- **Обогащение `ResolvedAddress`** (тип, направление, квалифицированное имя) —
  добавление полей в публичную структуру ⇒ **минорный бамп** крейта `grammar` по
  SemVer. Данные брать там, где они уже под рукой (`resolve_model`,
  `address_map.rs:447–453`), а не вторым обходом модели.
- **Плоский ключ карты** (`HashMap<String, _>`, `address_map.rs:374`) —
  одноимённые порты в разных под-моделях делят ключ, тогда как C-генератор
  индексирует квалифицированными вариантами. Латентный дефект **ядра 0020**, не
  созданный 0043, но напрямую бьющий по экспорту. → Оформить кандидатом; в 0043 —
  задокументированное ограничение и тест, фиксирующий текущее поведение.
- **Порт без адреса** (`SE-052`) — политика экспорта: недостижимый порт без
  адреса выгружается **с явной пометкой «адреса нет»** (в `json`) и
  **опускается** в `map` (запись `NAME = ;` формату неизвестна). Категорически
  **не** подставлять `0`, как это делает C-таблица (`c_header.rs:686`,
  `.unwrap_or(0)`): в выгрузке это неотличимо от настоящего адреса `0x0`.
- **Дублирование разбора CLI-флагов** между `compile` и `address-map` — вынести
  общий разбор.

### Acceptance criteria

1. `lamc address-map --emit map <input.lam>` печатает карту фактически
   разрешённых адресов; приоритет inline < `address` < `--address-map` соблюдён.
2. **Круговой рейс:** вывод `--emit map` принимается `compile --address-map` без
   диагностик формата, а повторный экспорт даёт побайтово тот же текст.
3. `lamc address-map --emit json <input.lam>` печатает валидный JSON, разбираемый
   `serde_json`, с полями: версия формата, имя, адрес, бит, источник, тип,
   направление.
4. Адреса в выгрузке **совпадают** с таблицей `__ADDR[]`, эмитируемой
   `-t c-hal` на той же модели и той же карте.
5. Порт без адреса не порождает фиктивный `0x0`: в `json` — явная пометка, в
   `map` — запись отсутствует.
6. `--emit` с неизвестным форматом → ошибка с ненулевым кодом возврата.
7. Цели `c`, `c-hal`, `plantuml` и подкоманды `compile`/`fmt` не затронуты
   (регресс = 0); версия языка остаётся 0.2.0.
