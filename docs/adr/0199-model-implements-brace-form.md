# ADR 0199: Реализация модели (`model M = A | B { … }`)

- **Status:** Accepted (Option C — решение заказчика 2026-08-03)
- **Date:** 2026-08-03
- **Authors:** Архитектор + аналитик
- **Related issues:** [Фича 0199](../features/0199-model-implements-brace-form.md);
  вскрыто при закрытии [0194](../features/0194-sim-composition-model-always.md)
  (тело `always` модели-композиции)

## Context

Грамматика принимает `model Имя ["=" Выражение] "{" элементы "}"`, то есть у
модели может быть **реализация** (`= A | B`) наравне с телом. Форма описана в
приложении-грамматике документа (`book/src/appendix-grammar/`), то есть заявлена
как часть языка.

Пробы 2026-08-03 показали **три разных поведения** одной формы:

| Форма | Эталон | Цели `c` / `rust` / `sv` / `st` |
|---|---|---|
| `model M = A \| B { always … }` — тело **без** состояний | пустая трасса `[—]`, завершение на шаге 1 | **все четыре** отказывают: `CC-005`, `RS-013`, `SV-011`, `ST-013` — «состояние ' ()' не найдено» |
| `model M = A \| B { start S … }` — тело **со** своими состояниями | исполняется **только** `S`; `= A \| B` **молча игнорируется** | компилируется, композиции нет |
| `model M = A \| B;` — без тела | — | грамматикой **не принимается** (`SY-002`): блок обязателен |

⚠️ **Поправки к записи находки.** Кандидат называл отказ только у цели `c`;
отказывают **все четыре**. И, что важнее, кандидат не знал о **второй** форме —
а она хуже первой: там не отказ, а **молчаливая потеря** половины записи.

### Причина — одна, и она точечная

`ModelNode.implements` заполняется при построении дерева как
`Extend::Unresolved(выражение)` (`semantic/tree.rs:189`) и **никогда не
разрешается**: `extend::unroll_extend_expression` вызывается **только** для
состояний (`StateNode::Implement`, `tree.rs:730`). Модельного вызова нет.

Отсюда всё наблюдаемое:

- симулятор: `build_extend(Extend::Unresolved)` → `Unit::default()` → пустая
  трасса (ветвь, которую фича 0194 правила «симметрично», но проверить значением
  не могла — ломается раньше);
- цели: `minimap.rs:489` переводит `Extend::Unresolved` → `StateExtend::None`,
  модель остаётся без состояний, и генератор ищет состояние с пустым именем.

### Смежная находка (в объём не входит)

Фикстура `takt-lang/tests/data/generator/valid/forward_decl.takt` использует эту
форму и лежит в каталоге **valid**, но сама **не разбирается**: `next` в теле
модели грамматикой не принимается (`SY-002`). Никем не гоняется — тест
`codegen_tests::test_header_has_forward_declarations` использует собственный
inline-исходник. Мёртвая фикстура в `valid` — отдельная запись, кандидат.

## Decision Drivers

1. **Молчаливая потеря хуже отказа.** Сегодня вторая форма теряет `= A | B` без
   единого слова — это худший из трёх исходов, и он существует прямо сейчас.
2. **Грамматика и документ заявляют форму частью языка.** Убирать её — сужение
   языка, а не починка; такое решение принимает заказчик, а не разработчик.
3. **Эквивалент существует и работает.** `model M { always … start Inner = A | B; }`
   исполняется эталоном и переводится всеми четырьмя целями (проверено).
4. **Причина точечная.** Не хватает одного вызова разрешения; это делает
   «доделать» дешёвым, но не делает его автоматически правильным.

## Considered Options

### Option A. Разрешать реализацию модели — форма начинает работать

Вызвать `unroll_extend_expression` для `ModelNode.implements` там же, где он
вызывается для состояний. Форма становится синонимом «композиция + тело
владельца».

**Pros:**
- грамматика, документ и поведение сходятся: то, что принято разбором,
  исполняется;
- ветвь `build_composition` (заведена 0194) наконец получает вход, который можно
  проверить **значением** — сегодня она не проверена;
- короткая запись для частого случая: композиция с телом владельца.

**Cons:**
- **не отвечает на вторую форму**: что делать, когда у модели есть и
  реализация, и свои состояния? Ответ нужен всё равно — иначе молчаливая потеря
  останется;
- расширяет поверхность языка: форму придётся описать в разделе о моделях
  (сейчас она есть только в приложении-грамматике), а значит документировать
  правило её взаимодействия с телом.

### Option B. Отвергать реализацию модели диагностикой

`model M = …` → ошибка семантики с указанием эквивалента
(`model M { start Имя = …; }`).

**Pros:**
- честно отражает факт: форма не работает ни в одной стороне и никогда не
  работала;
- убирает **обе** проблемы разом — и отказ, и молчаливую потерю;
- дёшево и проверяемо.

**Cons:**
- **сужает язык** и требует правки приложения-грамматики документа;
- отвергает запись, которую грамматика принимает, — то есть расхождение
  грамматики и семантики остаётся, просто становится громким;
- ⚠️ ломает мёртвую фикстуру `forward_decl.takt` (её всё равно надо чинить или
  удалять — она и сейчас не разбирается).

### Option C. Разрешать, но назвать конфликт (гибрид)

Реализация модели разрешается (как в A) — **и** случай «реализация + свои
состояния» отвергается диагностикой: модель не может быть одновременно
композицией и автоматом.

**Pros:**
- закрывает **все три** наблюдения: первая форма работает, вторая перестаёт
  молча терять запись, третья остаётся синтаксической ошибкой;
- правило простое и объяснимое: `=` задаёт **реализацию** модели, тело — её
  элементы; собственный `start` в теле противоречит реализации;
- ветвь 0194 получает проверяемый значением вход.

**Cons:**
- работы больше, чем в A и B: разрешение + диагностика + документирование;
- нужно решить смежный вопрос: допустима ли реализация модели с телом, где есть
  `var`/`const`/`always`, но нет `start` (по правилу — да, это и есть основной
  случай).

## Decision

**Рекомендация архитектора — Option C.**

Довод: Option A оставляет молчаливую потерю (драйвер 1) — худшее из трёх
поведений; Option B устраняет её ценой сужения языка, заявленного документом
(драйвер 2), хотя рабочий эквивалент показывает, что смысл у формы **есть**.
Option C — единственный, где все три наблюдения получают ответ, а правило
формулируется одной фразой: `=` задаёт реализацию модели, и собственного
стартового состояния у такой модели быть не может.

Решение заказчика (2026-08-03) — **Option C**, совпало с рекомендацией.
Развилка была: C **доделывает** язык (форма работает, конфликт назван),
B **сужает** его (формы нет), A **оставляет** половину дефекта.

## Consequences

### Положительные

- `Extend::Unresolved` у модели перестаёт быть состоянием, в котором дерево
  живёт до самого конца;
- ветвь `build_composition` (0194) впервые получает вход, проверяемый значением;
- исчезает форма, молча теряющая часть записи.

### Отрицательные / Action items

- **A1.** Документирование (правило 24) обязательно: раздел о моделях получает
  форму и правило её взаимодействия с телом; при Option B — наоборот, форма
  убирается из приложения-грамматики.
- **A2.** Проверить **все пять** потребителей (эталон + 4 цели) **значением**,
  а не фактом компиляции: конструкция новая для всех.
- **A3.** Проверить взаимодействие с фичей 0194: тело `always` владельца-
  композиции обязано исполняться **ровно раз за такт** и в этой форме тоже.
- **A4.** Мёртвая фикстура `forward_decl.takt` — починить или удалить; в объём
  фичи не входит, но оставлять её в `valid` нельзя (запись кандидатом).
- **A5.** Проверить `--parameters=specialize`: реализация модели с параметрами
  (`model M = Tuner(gain := 2) | Tuner(gain := 3) { … }`) — законна ли и что
  делает.

### Acceptance criteria

1. `model M = A | B { always … }` исполняется эталоном и переводится всеми
   четырьмя целями; трассы совпадают потактово.
2. Тело `always` владельца исполняется **ровно раз за такт** (инвариант 0194).
3. `model M = A | B { start S … }` отвергается диагностикой с обеими позициями
   (реализация и собственный `start`).
4. `model M = A | B;` по-прежнему синтаксическая ошибка.
5. Документ описывает форму и правило; корпус не задет, предкоммит зелёный.
