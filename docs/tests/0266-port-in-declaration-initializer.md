# Тест-план фичи 0266: Чтение порта в инициализаторе объявления

> Фича: [../features/0266-port-in-declaration-initializer.md](../features/0266-port-in-declaration-initializer.md) · ADR: [../adr/0266-port-in-declaration-initializer.md](../adr/0266-port-in-declaration-initializer.md) · анализ: [../analyze/0266-port-in-declaration-initializer.md](../analyze/0266-port-in-declaration-initializer.md)

## Область и цель

Фича **меняет язык** (принимаемое множество программ сужается), поэтому правило
16 применяется: нужны пример, контрпример и проверка компилятором.

- **Контрпример** (форма отвергается): `in sensor: bit; var mirror: u8 := sensor;`
- **Пример** (форма законна): чтение того же порта в теле —
  `var mirror: u8 := 0; start Run { always { mirror := sensor; } }`

Оба вошли в документ: приложение «Ошибки и предупреждения» (раздел `SE-113`) и
языковой раздел «Порты и адреса», где правило записано текстом рядом с
симметричным `SE-094`.

⚠️ **Сторож стоит на СЕМАНТИКЕ, а не на целях, и это не экономия.** Отказ
приходит до генерации, поэтому один тест отвечает за всех девять потребителей;
тест на каждую цель проверял бы, что до неё вход не доходит, — то есть чужое
свойство.

⚠️ **Проверки зовут `pipeline::collect_compile_diagnostics`** — общий вход CLI и
языкового сервера (правило 0130/0232). Так проверяется **доставка** диагностики
до редактора, а не только её выработка: у проекта уже был случай, когда
проверка считалась и выбрасывалась (`SE-037`, фича 0232).

## Тестовые данные и окружение

- Дерево: ветка `v2`, толчейн `rust-toolchain.toml` (стабильный `1.97.1`).
- T1–T7 автоматизированы: `takt-lang/tests/semantic/init_port_read_tests.rs`
  (тема `semantic`, подключён в `tests/semantic/main.rs`).
- T8, T9 — ручной прогон на фикстуре замера; отказ приходит из общей
  `validate`, поэтому в автотест вынесен один раз, а не по потребителю.
- Отдельного набора фикстур в `tests/data/` не заводилось: входы двухстрочные и
  читаются прямо в тесте — так проверка видна вместе с ожиданием.
