# Анализ фичи 0348: массив в параметре функции

> Фича: [../features/0348-st-array-parameter.md](../features/0348-st-array-parameter.md) · ADR: [../adr/0348-st-array-parameter.md](../adr/0348-st-array-parameter.md) · тест-план: [../tests/0348-st-array-parameter.md](../tests/0348-st-array-parameter.md)

## Цель и контекст

Кандидат заведён замером фичи 0346: там передача массива аргументом была одной
из причин, маскированных отказом семантики.

## Зависимости фичи (правило 17/19)

- **Зависит от:** 0210 (именованный тип массива для `VAR_IN_OUT`), 0346
  (индексация параметра — без неё функция не строилась). Закрыты.
- **Влияние на порядок разработки:** снимает кандидата.

## Требования и проверяемые условия

- **R1.** `iec2c` принимает вывод.
- **R2.** **C, порождённый `iec2c`, собирается** — без этого условия форма
  выбрана бы неверно.
- **R3.** Значения совпадают с эталоном.
- **R4.** Вывод корпуса не изменился.

## Разбор

### Почему проверка идёт до `cc`

`VAR_INPUT` с массивом `iec2c` **разбирает**. Дефект виден только на следующем
шаге: порождённый C не компилируется. Правило для будущих проб цели `st`:
форма, принятая разбором, не считается годной, пока не собран вывод.

### Почему имя типа по форме

Функция вызывается с разными массивами, поэтому тип обязан зависеть от формы
(размер и элемент), а не от владельца, как в 0210. Отсюда же ограничение:
именованными становятся **только** формы, встречающиеся в параметрах, — иначе
правка задела бы каждый массив вывода.

### Порядок аргументов

Параметры-массивы уходят в другую секцию, а позиционный вызов IEC следует
порядку объявления. Без перестановки `at_index(arr, 1)` печатался как
`at_index(arr, 1)` при объявлении `(i, a)` — «Data type incompatibility …
position 1».

## Риски

- **Функция, меняющая параметр-массив.** `VAR_IN_OUT` — ссылка; поведение
  разошлось бы с эталоном. Сегодня язык такой записи не даёт — граница названа.
