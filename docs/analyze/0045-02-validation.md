# Анализ 0045-02: Проверяемость порождённого SystemVerilog

> Обзор: [0045-sv-backend.md](0045-sv-backend.md) · ADR: [../adr/0045-sv-backend.md](../adr/0045-sv-backend.md) (вопрос 6) · задача: [../development/0045-02-validation.md](../development/0045-02-validation.md) · тест-план: [../tests/0045-sv-backend.md](../tests/0045-sv-backend.md)
>
> Требование **R12**; критерии **A3**, **A4**.

## Зачем это отдельный документ

Проект дважды закрывал фичи на непроверяемом выводе и дважды за это платил:

- **тихие пропуски** — фичи 0025 (восемь дефектов при зелёных тестах), 0028, 0029
  (переменная-массив исчезает из структуры **без диагностики**);
- **непроверяемое в CI** — плагин IntelliJ (0022/0023): «собрать плагин в CI-среде
  нельзя — `runIde` требует GUI».

У соседней фичи 0041 проверяемость — **заявленный главный риск** (её карточка:
«пока она не пройдена, корректность порождённого ST держится только на
снапшотах»). Поэтому для 0045 вопрос «чем валидировать» разобран **до** начала
разработки и **фактическими пробами**, а не рассуждениями.

## Исходное состояние среды (проверено)

```
$ which verilator iverilog yosys vvp sv2v
verilator not found
iverilog not found
yosys not found
vvp not found
sv2v not found
```

**В среде не было ни одного SV-инструмента.** Homebrew присутствует
(`/opt/homebrew/bin/brew`, Homebrew 6.0.10). Установлены в ходе проработки:

```
$ brew install verilator     # -> Verilator 5.050 2026-07-01
$ brew install yosys         # -> Yosys 0.67+post (git sha1 b8e7da6f40…)
```

Icarus Verilog не устанавливался: его роль (поведенческая симуляция) полностью
покрывается Verilator, который к тому же уже нужен как линтер.

## Кандидаты и что они умеют на самом деле

| Инструмент | Что это | Роль-кандидат |
|---|---|---|
| **Verilator** | линтер + компилирующий симулятор (SV → C++) | синтаксис, ширины, петли; тестбенч |
| **yosys** | **синтезатор** RTL (SV → нетлист) | фактическая синтезируемость |
| Icarus Verilog | интерпретирующий симулятор | дублирует Verilator |
| sv2v | SV → Verilog-2005 | вспомогательный, не гейт |

## Пробы (проведены фактически)

Все пробы — на модуле `stacker_lift_controller.sv`, написанном от руки в целевом
стиле по решениям ADR (модель `LiftController` из `examples/stacker.lam:355-385`,
сверена с зондом C `stacker.c:277-326`), и на двух контрпримерах.

### Проба 1. Целевой модуль проходит оба инструмента

```
$ verilator --lint-only -Wall stacker_lift_controller.sv
# чисто; код возврата 0

$ yosys -p "read_verilog -sv stacker_lift_controller.sv; \
            synth -top stacker_lift_controller; stat"
# код возврата 0; статистика: 22 cells
```

**Вывод:** выбранный стиль (two-process, `typedef enum logic [1:0]`, синхронный
сброс, `unique case`) **синтезируется** и **чист по линту**. Решения вопросов 1–4
ADR подтверждены не рассуждением, а инструментом.

### Проба 2. `real` — контрпример к вопросу 4 (`Rational`)

```systemverilog
module bad_real (input logic clk, output real y);
    always_ff @(posedge clk) y <= y + 1.5;
endmodule
```

| Инструмент | Результат | Код |
|---|---|---|
| `verilator --lint-only -Wall` | **принял молча** — ни ошибки, ни предупреждения | **0** |
| `yosys -p "read_verilog -sv …; synth"` | `bad_real.sv:1: ERROR: syntax error, unexpected TOK_REAL` | **1** |

**Это ключевая находка.** Распространённое утверждение «`verilator --lint-only`
даёт проверку синтеза» — **неверно**: Verilator — линтер и **симулятор**, для него
`real` абсолютно легален (в симуляции он и должен работать). Если бы гейтом был
только Verilator, решение «`Rational` → `SV-003`» осталось бы непроверенным, а
регресс (кто-то эмитит `real`) уехал бы в CI незамеченным.

### Проба 3. Комбинационная петля — контрпример к вопросу 3 (композиция `M1 | M2`)

```systemverilog
module loop (input logic clk, input logic a, output logic y);
    logic p, q;
    always_comb p = q | a;
    always_comb q = p & a;
    assign y = p;
endmodule
```

| Инструмент | Результат | Код |
|---|---|---|
| `verilator --lint-only -Wall` | `%Warning-UNOPTFLAT: Signal unoptimizable: Circular combinational logic: 'loop.p'` | **1** |
| `yosys -p "read_verilog -sv …; synth"` | **синтезировал молча** — ни ошибки, ни предупреждения о петле | **0** |

**Вторая ключевая находка, зеркальная первой.** Петля — **центральный риск**
отображения `M1 | M2` (ADR, вопрос 3: `stacker.lam` даёт цикл
`lift_request → lift_done → lift_request`, если отображать под-модели отдельными
модулями с комбинационными связями). Синтезатор её **не ловит**; ловит **только**
линтер.

### Проба 4. Тестбенч — механика сверки и контракт 0033

```
$ verilator --binary --timing --top-module tb_lift tb_lift.sv \
            stacker_lift_controller.sv -o simtb
$ ./obj_dir/simtb
после сброса (до 1-го такта): state=0 cmd_fork=0
такт 1: state=0 cmd_fork=0 lift_done=0
такт 2: state=0 cmd_fork=0 lift_done=0
такт 3: state=1 cmd_fork=1 lift_done=0
такт 4: state=1 cmd_fork=1 lift_done=0
такт 5: state=2 cmd_fork=0 lift_done=1
такт 6: state=2 cmd_fork=0 lift_done=1
такт 7: state=0 cmd_fork=0 lift_done=1
```

**Что доказано:** сразу после сброса, **до первого такта**, автомат уже находится
в стартовом состоянии `LIFT_IDLE` (`state=0`) с исполненным `enter`
(`cmd_fork=0`). Синтетического `INIT` нет; такт 1 уже исполняет **тело**
`LiftIdle`. **Сдвиг = 0** — контракт [ADR 0033](../adr/0033-init-tick-alignment.md)
выполняется (ср. C: тело исполняется на такте 2/3/4 при глубине 1/2/3).

**Что доказано методически:** `verilator --binary --timing` собирает и прогоняет
тестбенч с потактовой печатью — это и есть механика задачи 0045-07 (сверка с
симулятором). Работоспособность подтверждена.

> Оговорка о добросовестности: смены входов в этом тестбенче поданы после фронта,
> поэтому реакция видна через такт — артефакт **пробного** тестбенча, а не
> модуля. На доказываемое (состояние и `enter` после сброса) он не влияет.
> В задаче 0045-07 воздействия подаются по образцу
> `conformance_c_tests.rs` — от трассы симулятора.

## Вывод: гейтов должно быть два

Сводная матрица (по фактическим пробам):

| Класс дефекта | Verilator `--lint-only -Wall` | yosys `synth` |
|---|---|---|
| Синтаксис SV | ловит | ловит |
| **Несинтезируемый тип (`real`)** | **пропускает** | **ловит** |
| **Комбинационная петля** | **ловит** | **пропускает** |
| Несовпадение ширин | ловит | частично |
| Защёлка вместо регистра (`LATCH`) | ловит | не сообщает |
| Незаданный/неиспользуемый сигнал | ловит | не сообщает |
| Фактическая реализуемость в ячейках | не проверяет | **проверяет** |
| Поведение (потактовая трасса) | **`--binary`** | не умеет |

**Инструменты ловят непересекающиеся классы дефектов, причём ровно те два, что
критичны для принятых решений ADR** (`real` — вопрос 4; петля — вопрос 3). Ни один
по отдельности не достаточен.

**Операциональное определение (принято ADR, вопрос 6):**

> **«Валидный SV» для фичи 0045** = `verilator --lint-only -Wall` (код 0)
> **И** `yosys -p "read_verilog -sv …; synth"` (код 0).
> **Поведенческая корректность** = тестбенч через `verilator --binary --timing`
> сходится с трассой симулятора Lam.

Это аналог существующего C-гейта в `scripts/precheck.sh` («сгенерировали →
скомпилировали настоящим компилятором» через cmake/ninja), но **сильнее**: у C
гейт один, здесь два, и они перекрывают слепые зоны друг друга.

## Сравнение с гейтом фичи 0041 (честно)

| | **0045 (SV)** | 0041 (ST) |
|---|---|---|
| Гейт | Verilator + yosys | MatIEC `iec2c` → `cc` |
| Установка | **`brew install` — выполнено** | **не пакет Debian**; сборка из исходников (autoreconf/bison/flex) |
| Проверено в репозитории? | **да, пробы пройдены** | **нет** — заявленный главный риск фичи |
| Нужна ли обёртка вокруг вывода? | **нет** — модуль проверяется как есть | **да** — `iec2c` требует полной `CONFIGURATION`/`RESOURCE`/`PROGRAM`, а не голого FB |
| Число гейтов | **2 (взаимодополняющих)** | 1 |
| Оценка риска | **низкая** | **высокая / критично** |

Отсюда — довод правила 19.4 в обзоре: 0045 **ниже по риску**, чем 0041, при
сопоставимом объёме.

## Что делает задача 0045-02

1. Встроить оба гейта в `scripts/precheck.sh` по образцу существующего C-гейта:
   генерация `-t sv` для всех транслируемых `examples/*.lam` → `verilator
   --lint-only -Wall` → `yosys … synth`.
2. Обеспечить **мягкую деградацию**: если инструмента нет в среде — шаг
   **пропускается с явным сообщением**, а не падает (образец —
   `cc_available()` в `conformance_c_tests.rs:69`). CI-образ инструменты ставит;
   машина разработчика — как получится.
3. Добавить шаг в `.github/workflows/ci.yml` (в CI инструменты **обязательны** —
   иначе гейт бессмыслен).
4. **Проверить, что гейт ловит регресс:** намеренно испортить вывод (эмитировать
   `real`; замкнуть комбинационную петлю) и убедиться, что `precheck.sh` **краснеет**
   на каждом из двух. Гейт, который никогда не падал, — не гейт.

## Открытые вопросы (для реализации)

- **Версии инструментов в CI.** Verilator 5.x и yosys 0.6x — свежие; в
  Ubuntu-репозиториях версии старее. Возможен разрыв «работает локально —
  падает в CI». Решение — зафиксировать минимальные версии и проверить на
  CI-образе в рамках 0045-02.
- **`unique case` и yosys.** В пробе принят; при переходе на старые версии yosys
  проверить повторно (при проблеме — обычный `case` + `default`).
- **Шум `-Wall`.** Verilator строг (`UNUSEDSIGNAL` на неиспользуемый `clk` в пробе
  3). Порождённый код не должен требовать `lint_off`: если требует — это сигнал
  дефекта генератора, а не повод глушить предупреждение.
