# Анализ фичи 0020: адрес порта отдельно от объявления

> Фича: [../features/0020-port-address-decl.md](../features/0020-port-address-decl.md) · ADR: [../adr/0020-port-address-decl.md](../adr/0020-port-address-decl.md)

## Цель и контекст

Дать возможность задавать аппаратный адрес порта отдельной конструкцией
`address NAME = <expr>;`, не в объявлении. По ADR 0020 — **Option A**, аддитивно:
инлайн-форма `in NAME: T = <addr>;` сохраняется как сокращение.

## Зависимости фичи (правило 17/19)

- **Зависит от:** нет. Затрагивает `grammar` (лексер, грамматика, семантика
  портов, C-генератор). Пересечения с 0019 нет (разные части грамматики) — можно
  вести параллельно.
- **Влияние на порядок разработки:** завершение никого не разблокирует.

## Требования и проверяемые условия

- **R1. Новый оператор.** `address NAME = <expr>;` на уровне модели
  привязывает адрес к ранее/позже объявленному порту `NAME`.
- **R2. Совместимость.** Инлайн-форма `in NAME: T = <addr>;` работает без
  изменений; существующие `.lam` не ломаются (регресс = 0).
- **R3. Разрешение адреса.** Порт получает адрес из `address`-оператора, если он
  есть; иначе — из инлайн-инициализатора.
- **R4. Диагностика конфликта.** Адрес задан и инлайн, и через `address` для
  одного порта → ошибка (новый SE-код).
- **R5. Диагностика висячей привязки.** `address` для несуществующего порта →
  ошибка.
- **R6. Идентичный C-код.** Для порта с адресом через `address` генерируется тот
  же C, что и для инлайн-адреса.
- **R7. Без новых LR(1)-конфликтов.**

## Критерии приёмки и способ проверки

| # | Критерий | Способ проверки |
|---|---|---|
| A1 | `address NAME = expr;` парсится и привязывается | новые фикстуры `valid/port_address_separate.lam` + тест |
| A2 | Регресс инлайн-формы = 0 | `cargo test --features lsp -- --test-threads=1` |
| A3 | Конфликт адресов → ошибка | контрпример `invalid/port_address_conflict.lam` |
| A4 | Висячая привязка → ошибка | контрпример `invalid/port_address_dangling.lam` |
| A5 | C-код идентичен | сравнение вывода C для инлайн vs `address` |
| A6 | Нет LR(1)-конфликтов | `cargo build` без предупреждений |

## Особенности по обратной функциональности

Изменение **аддитивное**: новый синтаксис не отменяет старый. Существующие `.lam`
с инлайн-адресом валидны. Поэтому слом совместимости, которого опасалась исходная
задача (STATUS п. 11), **не требуется** — это результат выбора Option A.

Язык расширяется (новый оператор) → **версия языка повышается** (правило 22);
крейт `grammar` — минорный/патч-бамп по SemVer.

## Риски и зависимости

- **Ключевое слово `address`** может конфликтовать с идентификаторами в
  существующих `.lam`. → **Снижение:** grep по `examples/`/фикстурам на
  использование `address` как имени; при коллизии — рассмотреть контекстное
  ключевое слово или иной токен (fallback Option C `@`).
- **Семантика двойного адреса** — нужна явная проверка (R4), иначе тихое
  переопределение.
- Порядок объявления: `address` может встретиться до/после объявления порта —
  разрешение должно быть двухпроходным (сначала собрать порты, затем адреса).

## Декомпозиция разработки

- **0020-01** — грамматика + AST: оператор `address NAME = <expr>;`, ключевое
  слово в лексере, узел AST, фикстуры парсинга.
- **0020-02** — семантика: разрешение адреса (address → порт), диагностики
  конфликта (R4) и висячей привязки (R5); C-генерация из разрешённого адреса (R6).

(Декомпозиция ориентировочная; уточняется при реализации.)
