# Анализ фичи 0198: Форматтер выносит комментарий из тела блока наружу

> Фича: [../features/0198-formatter-comment-in-block.md](../features/0198-formatter-comment-in-block.md) · ADR: [../adr/0198-formatter-comment-in-block.md](../adr/0198-formatter-comment-in-block.md) · тест-план: [../tests/README.md](../tests/README.md)

## Цель и контекст

ADR принял **Option A** (рекомендация архитектора и решение заказчика совпали):
печатники операторов обязаны спрашивать комментарии, как это уже делают
печатники элементов.

⚠️ **Уточнение к ADR, найденное при разборе кода.** Формулировка «печатники не
спрашивают комментарии» верна, но причина ещё уже: в `Out` **уже есть** метод
`node_line(loc, text)`, чья док-строка гласит — «единственный путь печати
содержательных строк, так комментарий не может потеряться». Печатник операторов
им просто не пользуется: зовёт `out.line(…)` напрямую, минуя привязку.

## Зависимости фичи (правило 17/19)

**Нет.** Механизм привязки заведён фичей 0024 и работает.

## Места правки

| # | Что | Файл | Замечание |
|---|---|---|---|
| М1 | операторы с позицией печатаются через `node_line` | `format/stmt.rs` | `Expression`, `Variable`, `Continue`, `Break`, `Return`, `Match` — у всех `Location` первым полем кортежа |
| М2 | комментарий последней строкой тела | `format/stmt.rs::close_body` + `Out::comments_before` | ведущих ему никто не выдаст: следующего оператора нет |
| М3 | — | `format/expr.rs` | **правок не потребовалось**: выражения печатаются внутри строки оператора, своих строк не занимают |

## Ограничения, которые определяют форму решения

- **О1. Позиция есть у каждого оператора.** В кортежных вариантах `ast::Statement`
  `Location` стоит **первым полем**; поиск по `loc:` его не находит, отсюда
  первоначальное впечатление, что позиций нет у 13 из 16 вариантов.
- **О2. Комментарий последней строки тела — отдельный случай.** Он не «ведущий»
  ни для чего: до конца блока операторов больше нет. Без явного вызова перед
  `}` его выдаст `leading()` следующего **элемента** — то есть привяжет к чужому
  узлу. Это ровно тот случай, который остался невылеченным после М1.
- **О3. Блочные операторы (`If`, `Loop`, `For`) печатаются через
  `block_with_head`,** и их ведущие комментарии выдаются при печати **первого
  оператора тела** или заголовка вложенного блока. Отдельной привязки заголовку
  не потребовалось — проверено пробой на вложенном `if`.
- **О4. Идемпотентность — свойство, которое нельзя потерять.** До правки
  форматтер был идемпотентен (комментарий уезжал **один раз**), и после правки
  обязан остаться таким.

## Требования и проверяемые условия

| # | Требование | Проверяемое условие |
|---|---|---|
| R1 | Комментарий первой строкой тела остаётся на месте | `always { // … \n n := …; }` |
| R2 | Между операторами — тоже | комментарий в середине тела |
| R3 | Последней строкой тела — тоже | комментарий перед `}` |
| R4 | Во вложенном `if` — внутри своей вложенности | не всплывает на уровень состояния |
| R5 | В теле функции — внутри функции | не уезжает к следующему элементу файла |
| R6 | Хвостовой комментарий оператора остаётся на его строке | `n := n + 1; // счёт` |
| R7 | Идемпотентность | повторный `fmt` ничего не двигает |
| R8 | Корпус не сдвинут | `fmt` по `examples/` и `book/` даёт пустой дифф |

## Критерии приёмки и способ проверки

| # | Критерий (из ADR) | Способ проверки |
|---|---|---|
| A1 | место сохраняется во всех телах | фикстурные тесты R1–R5 |
| A2 | хвостовые комментарии удержаны | тест R6 |
| A3 | идемпотентность | тест R7 |
| A4 | сторож фикстурный, не корпусный | корпус класс не покрывает |
| A5 | дифф корпуса объяснён | R8 — дифф **пуст** |

## Особенности по обратной совместимости (правило 11)

- **Язык не меняется** — правка целиком в форматторе.
- **Вывод `taktc fmt` меняется** только там, где комментарий стоял внутри тела:
  раньше он уезжал, теперь остаётся. Это и есть предмет фичи.
- Корпус и `book/` не задеты (R8): в них комментарии внутри тел не встречаются
  в форме, дававшей переезд.

## Документирование (правило 24)

**Не требуется.** Фича не меняет ни синтаксис, ни семантику, ни поведение целей
— она чинит инструмент. Правила расстановки комментариев в `book/` не описаны и
описываться не должны: документ описывает **язык**, а не форматтер.

## Редакторский слой (правило 29)

**Правок не требуется.** Лексика, синтаксис и семантика не меняются. ⚠️ LSP
**затронут косвенно и в лучшую сторону**: `textDocument/formatting` идёт через
тот же `format_source`, поэтому редактор перестаёт переносить комментарии вместе
с `taktc fmt` — отдельной правки для этого не нужно.

## Риски

- **Риск сдвинуть форматирование корпуса.** Снижение: R8 — дифф проверен и пуст;
  тесты форматтера (15 штук) зелёные.
- **Риск потерять идемпотентность** (О4). Снижение: отдельный тест R7.
- **Риск «починили не все формы».** Снижение: семь форм в сторожах, включая
  вложенность и тело функции — те, что кандидат не называл.
