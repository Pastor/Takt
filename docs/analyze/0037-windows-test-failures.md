# Анализ фичи 0037: Сбои тестов на Windows (пути include, ресурс viewport)

> Фича: [../features/0037-windows-test-failures.md](../features/0037-windows-test-failures.md) · ADR: [../adr/0037-windows-test-failures.md](../adr/0037-windows-test-failures.md) · тест-план: [../tests/0037-windows-test-failures.md](../tests/0037-windows-test-failures.md)

## Цель и контекст

Устранить шесть падений тестов, воспроизводящихся **только на Windows**, и
закрыть причину их появления — отсутствие Windows в CI. Источник —
[отчёт 0021](../reports/0021-swap-assign-compare.md): «Обнаружены два
предсуществующих класса сбоев окружения (Windows), не связанных с 0021 (падают и
на исходном коде): 5 тестов `lamc` … и 1 тест `viewport` (путь к ресурсу не
найден). Рекомендуется завести отдельной фичей/фиксом».

Решения приняты в [ADR 0037](../adr/0037-windows-test-failures.md):
**A** (параметризация тестов платформенным разделителем) + **E** (удаление
отладочной записи в `/tmp`) + **H** (job `windows` в матрице CI, временно
`continue-on-error`). Язык не меняется → версия языка остаётся **0.2.0**
(правило 22). Продуктовый код не меняется → CLI-контракт `lamc` сохранён
(правило 11).

### Установленные факты (перепроверено чтением кода, 2026-07-15)

Кандидат в `FEATURES.md` **не называет** конкретные тесты — их поиск и есть
основная фактическая работа анализа. Ниже — результат; всё, что установлено
чтением, помечено как факт, всё остальное — как непроверенное.

**Класс 1 — пять тестов `lamc` (файл `grammar/src/bin/lamc.rs`, `mod tests`):**

| # | Тест | Строка | Вход в тесте | Ожидание | Поведение на Windows (по коду) |
|---|---|---|---|---|---|
| 1 | `parse_include_dirs_colon` | 811 | `-I` + `"/lib/lam:/usr/lam"` | `["/lib/lam", "/usr/lam"]` | `["/lib/lam:/usr/lam"]` → `assert_eq!` падает |
| 2 | `parse_include_dirs_long_flag` | 837 | `--include-dirs` + `"/lib:/usr"` | `["/lib", "/usr"]` | `["/lib:/usr"]` → падает |
| 3 | `parse_include_dir_glued_colon` | 857 | `"-I/a:/b"` (слитная форма) | `["/a", "/b"]` | `["/a:/b"]` → падает |
| 4 | `parse_full_args` | 865 | `-I "/lib/lam:/usr/lam" -I "/local/but"` | 3 элемента | 2 элемента → падает |
| 5 | `parse_include_filters_empty_segments` | 990 | `-I "/a::/b"` | `["/a", "/b"]` | `["/a::/b"]` → падает |

Ровно пять — **совпадает** с числом из отчёта 0021.

**Класс 2 — один тест `viewport` (файл `simulation/src/unit/viewport.rs`):**

- `test_highlight::test_highlight_frame_contains_orange_bg`, строка **1452**:
  `std::fs::write("/tmp/highlight_test.svg", &svg_str).unwrap();`
  (+ `println!` на 1453). Это **единственное** обращение к ФС по жёстко зашитому
  POSIX-пути в тестах `simulation` (проверено `grep` по `/tmp`, `save_to_file`,
  `tests/data` в крейте). Соответствует «`simulation` 149/150» в отчёте 0021.

**Точный механизм сбоя класса 1.** Продуктовая функция `split_include_dirs`
(`lamc.rs:105–118`) **платформо-корректна** — разделитель выбирается через
`cfg`: `;` на Windows, `:` на прочих. Именно это и снимает конфликт с буквой
диска: `C:\lib;C:\usr` режется по `;`, двоеточие после `C` разделителем не
является. **Падает не функция, а тесты**: пять тестов `parse_compile_args`
зашили `:` во вход и ожидания, оставаясь безусловными `#[test]`; на Windows
`sep = ';'`, строка не режется, `assert_eq!` не сходится.

Показательно, что **дисциплина `cfg` в этом же файле уже есть**, но применена
только к тестам самой `split_include_dirs` (`lamc.rs:713–780`:
`split_colon_unix`, `split_empty_segments_skipped`, `split_trims_whitespace`,
`split_semicolon_is_not_unix_separator` — под `#[cfg(not(windows))]`;
`split_semicolon_windows`, `split_trims_whitespace_windows` — под
`#[cfg(windows)]`). Секцией ниже, в тестах `parse_compile_args`, её не применили.
Это и есть класс дефекта: **платформо-нейтральный тест платформо-зависимого
поведения**.

**Точный механизм сбоя класса 2.** На Windows каталога `/tmp` не существует
(путь трактуется как `\tmp` на текущем диске), `fs::write` → `Err(NotFound)`,
`unwrap()` → паника **до** собственного `assert!` теста. Запись — отладочный
артефакт: проверка (`assert!(svg_str.contains("FFF3DC") || …)`) работает со
строкой в памяти и от файла не зависит.

**Уточнения к формулировке кандидата (факт не подтвердился — фиксируем честно):**

1. Кандидат: «путь к ресурсу не найден». **Не подтвердилось.** Ресурс не
   читается — тест **пишет** отладочный дамп. Класс ошибки (ФС из-за
   POSIX-пути) тот же, но починка иная: удалить строку, а не искать ресурс.
2. Кандидат: «разбиение `--include-dirs` по `:` конфликтует с Windows-путями/
   буквами дисков». **Подтвердилось как мотив, но не как механизм.** Разбиение
   по `:` на Windows не выполняется вовсе (там `;`), поэтому с `C:\path`
   конфликта нет. Продуктового бага в разбиении **не обнаружено**.
3. Кандидат: «Оформить фикс/фичу». Принято, но объём **расширен** относительно
   кандидата: добавлена подзадача 0037-03 (Windows в CI). Обоснование — правка
   шести тестов лечит симптом; причина (`.github/workflows/ci.yml` содержит
   **только** job `ubuntu`, матрицы нет — проверено чтением файла) остаётся.

**Найденное попутно (в границы 0037 не входит, кроме п. 3):**

1. `split_include_dirs` **неверно обрабатывает кавычки** на Windows:
   `-I "C:\dir with spaces";C:\other` даст каталог с кавычкой в имени
   (`std::env::split_paths` кавычки снимает, ручной `split` — нет). Реальный,
   ранее не зафиксированный пробел; **не связан** с падениями → кандидат бэклога
   (ADR, Decision).
2. `.github/workflows/ci.yml` вызывает `cargo test` **без** `--test-threads=1`,
   тогда как `CLAUDE.md` и `scripts/precheck.sh:22` требуют однопоточного
   прогона «иначе гонки за общие файлы» → кандидат бэклога.
3. `viewport.rs:1457`: `&svg_str[..500]` в сообщении `assert!` паникует, если
   SVG короче 500 байт либо граница не на границе UTF-8-символа. К Windows
   отношения не имеет, но правится **в той же строке кода** → включено в 0037-02
   (R6), чтобы не оставлять тест полуисправленным.
4. `actions-rs/*` не поддерживаются (архивированы), `actions/checkout@v2`
   устарел → кандидат бэклога (задевает весь CI, не только Windows).
5. `lamc.rs` — **1149 строк** при лимите ~1000 (`CLAUDE.md`). Решения 0037
   выбраны так, чтобы **не увеличивать** размер модуля (это довод против
   `#[cfg]`-дублирования тестов, Option D в ADR); само деление модуля — предмет
   фичи [0027](../features/0027-module-size-split.md).
6. **Doctest `parse_compile_args` мёртв** (`lamc.rs:149–161`). Он тоже зашивает
   `"/lib/lam:/usr/lam"`, но **не исполняется**: `lamc` — `[[bin]]`-таргет
   (`grammar/Cargo.toml:15–17`), а `cargo test` берёт doctest'ы только с
   lib-таргета. Проверено прогоном: `cargo test --doc -p grammar` → **31 passed,
   5 ignored** (= 36, что сходится с «doctests 36/36» отчёта 0021 — то есть все
   они из библиотеки). Решающее доказательство: doctest открывается строкой
   `# use grammar_bin::{…};`, а крейта `grammar_bin` в workspace **нет**
   (`grep` по репозиторию даёт единственное вхождение — саму эту строку); если бы
   doctest исполнялся, он не компилировался бы и на darwin, где прогон зелёный.
   Значит, шестого падения на Windows он не даёт и в объём 0037 не входит; но
   документированный пример `lamc` **никем не проверяется** → кандидат бэклога.

## Зависимости фичи (правило 17/19)

- **Зависит от:** **нет.**

  Проверка проведена по четырём осям:

  1. **По контракту языка.** Фича не трогает грамматику, AST, семантику,
     генераторы. Версия языка не меняется (правило 22) → зависимостей от фич
     языка (0019, 0020, 0021) нет. Фича 0021, при тестировании которой сбои
     выявлены, **закрыта** (`ГОТОВО`) и причиной сбоев не является: отчёт 0021
     прямо фиксирует, что они воспроизводятся и на коде до неё, а затронутые
     файлы фича 0021 не меняла.
  2. **По коду.** Правки лежат в трёх местах: `grammar/src/bin/lamc.rs`
     (`mod tests`), `simulation/src/unit/viewport.rs` (`mod test_highlight`),
     `.github/workflows/ci.yml`. Пересечений с незакрытыми фичами **не найдено**:
     - [0027](../features/0027-module-size-split.md) (деление модулей) целится в
       `validate.rs`, `lsp.rs`, `generator/c/c_expr.rs` — `lamc.rs` в её объёме
       не заявлен; даже при расширении объёма конфликт был бы текстовым, а не
       логическим;
     - [0036](../features/0036-sim-visibility.md) (видимость публичного API
       `simulation`) может задеть `viewport.rs`, но на уровне **модификаторов
       видимости** продуктовых элементов, тогда как 0037 правит только тело
       теста в `mod test_highlight`. Пересечение — максимум конфликт слияния;
       логической зависимости нет, порядок безразличен.
  3. **По инфраструктуре.** Ни одна незакрытая фича не меняет
     `.github/workflows/ci.yml`. Кандидаты бэклога, которые его тронут
     (`--test-threads=1`, модернизация `actions-rs`), **ещё не заведены как
     фичи** и потому зависимостью быть не могут; они, наоборот, выиграют от того,
     что матрица появится раньше.
  4. **По процессу.** Блокеров нет: ADR принят, анализ выполнен, подзадачи
     нарезаны. Статус `ЗАБЛОКИРОВАНА` **не ставится**.

- **Влияние на порядок разработки:**
  - Фича **никого не блокирует** (пустой список зависимых) и **никого не
    разблокирует** — на «Зависит от» других фич завершение 0037 не влияет.
  - Тем не менее аналитик пользуется **правилом 19 п.4** и предлагает **не
    откладывать** 0037 в хвост очереди кандидатов: подзадача 0037-03 создаёт
    инструмент проверки, которым пользуются **все** последующие фичи, и чем
    раньше матрица появится, тем больше фич успеет ею защититься. Это довод
    «необходимости», а не «приоритета»: по важности фича — Tier 2 (карточка,
    раздел «Приоритет»), то есть **ниже** [0026](../features/0026-c-root-typedef.md)
    (Tier 1, порождённый C не компилируется), но **выше** прочих Tier 2-фич по
    отношению «польза/затраты».
  - **Порядок подзадач внутри фичи:** `0037-01` и `0037-02` независимы и
    выполняются в любом порядке; `0037-03` **обязана идти последней** — она
    проверяет результат первых двух. Обратный порядок дал бы заведомо красный
    первый прогон Windows-job.

## Требования и проверяемые условия

- **R1. Тесты разбора `-I` не зашивают разделитель.** В `mod tests` файла
  `grammar/src/bin/lamc.rs` ни один безусловный `#[test]` не содержит списка
  путей с литеральным `:` в качестве разделителя. Вход строится из
  платформенного разделителя (`cfg`-константа в тестовом модуле). Относится к
  пяти тестам: `parse_include_dirs_colon`, `parse_include_dirs_long_flag`,
  `parse_include_dir_glued_colon`, `parse_full_args`,
  `parse_include_filters_empty_segments`.
- **R2. Продуктовый код `lamc` не меняется.** `split_include_dirs`,
  `parse_compile_args`, `CompileOptions`, `print_usage()`, модульная
  документация — байт-в-байт прежние. Дифф подзадачи 0037-01 не выходит за
  пределы `mod tests` (правило 11: CLI-контракт сохранён).
- **R3. Покрытие не уменьшается.** Число тестов в `--bin lamc` остаётся **44**:
  пять тестов **параметризуются**, а не удаляются и не отключаются под `cfg`.
  Смысл каждой проверки сохранён (разбиение списка, длинный флаг, слитная форма,
  комбинация флагов, фильтрация пустых сегментов).
- **R4. Существующая `cfg`-дисциплина не ломается.** Шесть уже корректных тестов
  `split_*` (`lamc.rs:713–780`) остаются как есть: они проверяют **конкретный
  символ** разделителя на конкретной платформе — это их предмет, и
  параметризация его бы уничтожила.
- **R5. Тест `viewport` не обращается к ФС.** В `#[cfg(test)]`-коде
  `simulation/src/unit/viewport.rs` нет ни `fs::write`, ни путей-литералов вида
  `/tmp/…`. `test_highlight_frame_contains_orange_bg` проверяет только
  содержимое строки SVG.
- **R6. Сообщение `assert!` в том же тесте не паникует.** Диагностический срез
  `&svg_str[..500]` заменён на безопасное усечение (по границам символов и с
  учётом строк короче 500 байт). Иначе провал теста маскируется паникой в
  форматировании сообщения.
- **R7. Windows в матрице CI.** `.github/workflows/ci.yml` содержит job
  `windows` на `windows-latest` с теми же шагами, что job `ubuntu`
  (`cargo build --all-features --all-targets --examples`, `cargo check`,
  `cargo test`), тулчейн — тот же nightly.
- **R8. Job `windows` не блокирует до стабилизации.** Job добавляется с
  `continue-on-error: true`; снятие флага — отдельный шаг после первого зелёного
  прогона (ADR, Decision, условия 1–2). До снятия фича не закрывается.
- **R9. Новые Windows-падения не втягиваются в 0037.** Падения сверх шести
  перечисленных оформляются кандидатами в `FEATURES.md` (правило 7), а не
  чинятся внутри фичи.
- **R10. Регресс на macOS/Linux отсутствует.** Полный прогон
  `cargo test --features lsp -- --test-threads=1` на darwin остаётся зелёным.

| **Язык Lam** (синтаксис, семантика, `.lam`-файлы) | **Нет** | Ни грамматика, ни AST, ни проходы не тронуты → версия языка **0.2.0** без изменений (правило 22) |

## Риски и зависимости

- **Р1 (главный). Проверить исправление на macOS/Linux невозможно.** Аналитик и
  разработчик работают на darwin. Все шесть тестов здесь **зелёные и до, и
  после** правки — проверено: `cargo test --bin lamc -- --test-threads=1` →
  44 passed; `cargo test -p simulation test_highlight -- --test-threads=1` →
  1 passed. Локальный прогон **не подтвердит и не опровергнет** починку:
  критерии A8/A9 в принципе непроверяемы без Windows-раннера.
  *Снижение:* подзадача 0037-03 (Windows в CI) **входит в объём фичи** и
  является её итоговым критерием (A11). Дополнительно тест-план
  ([T7–T9](../tests/0037-windows-test-failures.md)) описывает косвенные проверки
  логики `cfg` без Windows.
  *Остаток:* до первого прогона job `windows` статус починки — **гипотеза,
  основанная на чтении кода**. В отчёте о тестировании это должно быть отражено
  прямо, а не сглажено.
- **Р2. Все утверждения о поведении на Windows — из чтения кода, не из прогона.**
  Механизм (`sep = ';'` → строка не режется; `/tmp` → `NotFound`) выведен
  аналитически и **подкреплён** независимым свидетельством — отчётом 0021, где
  числа совпадают (5 тестов `lamc`; `simulation` 149/150). Совпадение чисел
  усиливает гипотезу, но прогоном не является.
  *Снижение:* A8/A9 требуют явного перечисления имён тестов в логе Windows-job.
- **Р3. Job `windows` может вскрыть новые, ещё не известные падения.** Тесты
  никогда там не гонялись. Кандидаты риска (не проверено): системные шрифты
  `fontdb`/`resvg` в `simulation/src/gif.rs:40`, `tempfile`-обвязки, длинные
  пути, блокировки файлов при параллельном прогоне (CI не использует
  `--test-threads=1`).
  *Снижение:* `continue-on-error: true` (R8) + правило «новые падения — в бэклог,
  не в 0037» (R9). Фича не берёт на себя стабилизацию всей платформы.
- **Р4. Расхождение ABI.** CI даст **MSVC** (умолчание `windows-latest`), а
  отчёт 0021 писался на **GNU/MinGW**. Падения, специфичные для MinGW, матрица
  не поймает; наоборот, MSVC может дать свои.
  *Снижение:* принято осознанно (ADR, Decision, условие 4): MSVC — типовой выбор
  пользователя. Оба ABI — избыточно для целей фичи.
- **Р5. Рост времени CI** примерно вдвое (Windows-раннеры медленнее).
  *Снижение:* принято; для публичного репозитория `windows-latest` бесплатен.
- **Р6. Решение не «прилипнет» к процессу.** Дисциплина `cfg` в `lamc.rs` уже
  существовала и всё равно не доехала до соседней секции тестов — значит, одной
  правки мало.
  *Снижение:* матрица CI делает нарушение машинно-обнаружимым. Дополнительно —
  action item ADR: зафиксировать правило в `docs/CODE.md` (вне границ 0037,
  кандидат бэклога, т.к. `docs/CODE.md` — сквозной документ).
- **Р7. Конфликт слияния с фичей 0036** (может править `viewport.rs`).
  *Снижение:* правка 0037 — две строки в `mod test_highlight`; логической
  зависимости нет (см. «Зависимости фичи»), порядок безразличен, конфликт
  разрешается тривиально.
- **Зависимости фич: нет** (обоснование — в разделе «Зависимости фичи»).
