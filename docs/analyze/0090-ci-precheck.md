# Анализ фичи 0090: CI прогоняет весь `precheck.sh` (живые гейты + check-links)

> Фича: [../features/0090-ci-precheck.md](../features/0090-ci-precheck.md) · ADR: [../adr/0090-ci-precheck.md](../adr/0090-ci-precheck.md) · тест-план: [../tests/0090-ci-precheck.md](../tests/0090-ci-precheck.md)

## Цель и контекст

CI видит один живой гейт из семи (`sv`); шесть остальных (C, c-hal, ST, rust,
sv-mmio, тестбенчи sv) плюс инфраструктурные (воспроизводимость 0048, float→q
0096, канон формата, check-links) исполняются только на машине разработчика.
ADR 0090 принял **Option A**: CI вызывает `./scripts/precheck.sh` целиком под
строгим режимом — одна реализация гейтов, дрейф исключён конструктивно.

## Зависимости фичи (правило 17/19)

- **Зависит от:** **нет.** Проверены две подозреваемые зависимости:
  - **0041 (бэкенд ST).** CLAUDE.md утверждал, что ST-гейт «пока не включён»
    (пустые `FUNCTION_BLOCK`). **Опровергнуто пробой 2026-07-20:** `iec2c` принял
    **все 8** примеров корпуса (`comprehensive`…`stacker`). Гейт активен и зелёный
    — 0041 **не блокирует**.
  - **Инструментальная готовность.** Полный `precheck.sh` прогнан локально
    2026-07-20 (все инструменты присутствуют) → **EXIT=0**, рабочее дерево не
    изменилось (идемпотентность). Живых препятствий к прогону в CI нет.
- **Влияние на порядок разработки:** фича **разблокирующая по покрытию** —
  защищает `main` от класса «дыра в покрытии» (0026/0020-01/0041-01), но формально
  ни одну фичу очереди не разблокирует (у хвоста 0070–0094 колонка «Зависит от»
  пуста). **Пересмотр (правило 19):** Option A неизбежно модернизирует `ci.yml`
  (замена архивных `actions-rs/*`, соблюдение `--test-threads=1`) — эти два
  под-пункта номинально числились за 0037. После 0090 за **0037 остаётся только
  матрица Windows** (задача 0037-03). Зависимости между 0090 и 0037 **нет** (обе
  правят `ci.yml`, но 0037 — последняя в очереди по решению заказчика; при её
  взятии базой станет уже переписанный workflow).

## Требования и проверяемые условия

- **R1. Единственная реализация гейтов.** Логика живых гейтов существует **только**
  в `precheck.sh`; `ci.yml` её не дублирует, а вызывает скрипт.
- **R2. Строгость в CI.** Под `PRECHECK_STRICT=1` отсутствие любого инструмента
  (`python3`, `cc`, `cmake`/`ninja`, `iec2c`, `verilator`, `yosys`) — **ошибка**,
  не пропуск. Обобщает существующий `SV_GATE_REQUIRED`.
- **R3. Формат под строгим режимом.** Под `PRECHECK_STRICT=1` формат проверяется
  (`cargo +nightly fmt --check`), а не применяется — неканоничный коммит валит CI.
- **R4. Мягкость сохранена локально.** Без флага `precheck.sh` ведёт себя как
  прежде: мягкие пропуски мягкие, `fmt` применяется. DX разработчика не тронут.
- **R5. Все живые гейты исполняются в CI.** C (cmake/ninja), c-hal (`cc -c`), ST
  (`iec2c`), rust (rustc + clippy-driver + исполнение), sv (verilator + yosys),
  sv-mmio, тестбенчи sv, воспроизводимость, float→q, канон формата примеров,
  check-links — каждый даёт строку успеха в логе.
- **R6. Инструменты ставятся в CI.** apt: `cmake ninja-build verilator yosys bison
  flex build-essential`; `iec2c` — сборкой из исходников (`ensure-iec2c.sh`);
  `python3` присутствует на `ubuntu-latest`; toolchain — nightly + rustfmt +
  clippy (даёт `rustc`/`clippy-driver`).
- **R7. Обратная совместимость.** Инфраструктура; язык, публичный API крейтов и
  вывод генераторов **не меняются**. Версия языка не поднимается (правило 22).

## Критерии приёмки и способ проверки

| # | Критерий | Способ проверки |
|---|---|---|
| A1 | `ci.yml` = установка инструментов + один вызов `precheck.sh`; нет собственной логики гейтов | grep по `ci.yml`: нет `verilator`/`yosys`/`cmake`/`iec2c`/`rustc`, есть `precheck.sh` |
| A2 | Под строгим режимом исполняется каждый гейт | инспекция лога CI: строка успеха каждого из R5 присутствует |
| A3 | Отсутствие инструмента в CI → красный | проба: `PRECHECK_STRICT=1` + удалить `verilator` из PATH → `precheck.sh` возвращает ≠ 0 |
| A4 | Локально без флага пропуск остаётся мягким | проба: без `verilator`, без флага → строка `[пропуск]`, EXIT=0 |
| A5 | `precheck.sh` зелёный на чистом `main` в CI | зелёный прогон workflow на push |
| A6 | Формат под флагом = `--check` (неканон → провал) | проба: испортить формат файла, `PRECHECK_STRICT=1 ./scripts/precheck.sh` → провал на fmt |
| A7 | Язык/вывод не изменены | `git diff` вывода генераторов пуст; версия языка та же |

## Особенности по обратной функциональности

Фича не касается конвейера компиляции — ни лексер/парсер/семантика, ни один из
семи генераторов не правится. Единственные изменяемые артефакты: `scripts/
precheck.sh` (обобщение строгого режима), `.github/workflows/ci.yml`
(переписывание), `CLAUDE.md` (устаревшая заметка про ST-гейт), `README.md`
(упоминание CI-строгости, если уместно). Проверка обратной функциональности
(правило 11) сводится к **A4/A7**: локальный DX и вывод генераторов неизменны.

## Риски и зависимости

- **Риск: `iec2c` не соберётся в CI** (нет bison ≥ 2.4). Снижение: `ubuntu-latest`
  несёт bison 3.x (карта фичи подтверждает); под `PRECHECK_STRICT=1` отказ сборки
  `iec2c` станет **громким** (не тихим пропуском), то есть заметен сразу, а не
  латентен.
- **Риск: рост времени CI до ~20 мин** сделает `on: push` тяжёлым. Снижение:
  кеширование (rust-cache, кеш `iec2c`/apt) — кандидат в бэклог; при
  необходимости заказчик вправе сузить триггер (`on: [push, pull_request]` в
  ветки). В объём фичи оптимизация не входит.
- **Риск: пересечение с 0037 по `ci.yml`.** Снижение: 0090 переписывает workflow
  первой (0037 — последняя в очереди), 0037 берёт за базу уже готовый; конфликта
  слияния нет, так как между ними лежат другие фичи и 0037 добавляет **матрицу**
  поверх, а не переписывает шаг заново.
- **Зависимость от внешних action’ов:** `dtolnay/rust-toolchain`,
  `actions/checkout@v4` — поддерживаемые, широко используемые; замена архивных
  `actions-rs/*` обязательна для запуска `run:`-шага.
