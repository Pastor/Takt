# Анализ фичи 0178: Приведение LSP и плагинов в соответствие языку + сторож

> Фича: [../features/0178-editor-layer-language-sync.md](../features/0178-editor-layer-language-sync.md) · ADR: [../adr/0178-editor-layer-language-sync.md](../adr/0178-editor-layer-language-sync.md) · тест-план: [../tests/README.md](../tests/README.md)

## Цель и контекст

Правило 29 свода обязывает при изменении лексики/синтаксиса/семантики проверять
редакторский слой. Правило переносит ответственность на человека — фича даёт
машину, которая поймает пропуск, и попутно догоняет уже накопленное отставание.

Решение — Option B [ADR 0178](../adr/0178-editor-layer-language-sync.md):
исчерпывающий разбор токена (компилятор вместо дисциплины) + тест на список
автодополнения + исполнение тестов LSP в предкоммите.

## Зависимости фичи (правило 17/19)

- **Зависит от:** `нет`. Все затрагиваемые слои существуют и закрыты: LSP
  (0022/0038/0056/0072/0131), приём исчерпывающего разбора (0093), гейты
  предкоммита (0090).
- **Влияние на порядок разработки:** фича **не разблокирует** другие, но
  **удешевляет** каждую последующую языковую (0143, 0144, 0155, 0156, 0157,
  0170, 0172, 0176 — восемь незакрытых фич меняют язык): после неё пропуск в
  редакторском слое ловится машиной, а не ревью. Поэтому в таблице она стоит
  первой среди Tier 2 — критерий 4 правила 19 («раньше взять фичу,
  разблокирующую много других», здесь — удешевляющую).
- ⚠️ **Не зависит** от [0159](../features/0159-intellij-jdk21-build.md) (JDK 21):
  правило 4 ADR оставляет плагин IntelliJ вне `precheck.sh` — сборка плагина в
  объём фичи не входит.

## Что именно расходится (замер 2026-07-28)

### Подсветка — 11 непокрытых токенов

Разбор `Token` в `lsp/semantic_tokens.rs` заканчивается `_ => continue`
(строка 197). Не разобраны:

| Токен | Текст | Решение (правило 1 + A-2 ADR) |
|---|---|---|
| `Invariant` | `invariant` | → `TT_KEYWORD` |
| `LtlNext`, `LtlFinally`, `LtlGlobally`, `LtlUntil`, `LtlRelease` | `X` `F` `G` `U` `R` | → `TT_KEYWORD` |
| `TypeLtl`, `TypeGuard` | `LTL`, `Guard` | → `TT_KEYWORD` |
| `Arrow` | `->` | → `TT_OPERATOR` (единообразно с `-->`) |
| `FatArrow` | `=>` | → `TT_OPERATOR` |
| `Question` | `?` | → `TT_OPERATOR` |
| `Sharp`, `Semicolon`, `Comma`, `Colon`, скобки (6) | `#` `;` `,` `:` `()` `{}` `[]` | **явная** ветка «не подсвечиваем» |

### Автодополнение — 11 непокрытых ключевых слов

`BUT_KEYWORDS` содержит 39 записей, `KEYWORDS` лексера — 47. Отсутствуют:
`invariant`, `template`, `string`, `_`, `X`, `F`, `G`, `U`, `R`, `LTL`, `Guard`.

Решение по каждому (правило 2 ADR — либо в список, либо в исключения):

- **В список (10):** `invariant`, `template`, `string`, `X`, `F`, `G`, `U`, `R`,
  `LTL`, `Guard`. Все они пишутся автором в исходнике и заслуживают описания.
- **В исключения (1):** `_` — подстановочный образец ветки `match`. Это знак
  препинания по роли, а не слово: автодополнять нечего, предложение «`_` —
  подстановочный образец» в списке имён было бы шумом.

⚠️ Обратное направление проверять **нельзя**: в `BUT_KEYWORDS` законно живут
`enter`, `exit`, `always` — имена **блоков**, ключевыми словами лексера не
являющиеся (лексер отдаёт их как `Identifier`). Тест на равенство множеств
покраснел бы на верном списке; проверяется **вложение**
`KEYWORDS ⊆ BUT_KEYWORDS ∪ исключения`.

### Гейт — тесты LSP не исполняются

`precheck.sh:91` — `cargo test -- --test-threads=1`, **без** `--features lsp`.
Зонд: `test_semantic_tokens_highlight_time_constructs` под обычным `cargo test`
не запускается («тест подсветки НЕ ИСПОЛНЕН»), под `cargo test --features lsp` —
`ok`. Компиляцию тестов обеспечивает `clippy --all-targets --all-features`
(строка 63), исполнение — ничто.

## Требования и проверяемые условия

- **R1. Исчерпывающий разбор.** `semantic_tokens.rs` разбирает **все** варианты
  `Token` без подстановочной ветки и объявляет
  `deny(clippy::wildcard_enum_match_arm)`.
- **R2. Подсветка догнала язык.** `invariant`, LTL-операторы и типы формул
  подсвечиваются как ключевые слова; `->`, `=>`, `?` — как операторы.
- **R3. Автодополнение догнало язык.** `BUT_KEYWORDS` покрывает `KEYWORDS`
  лексера с точностью до явного списка исключений.
- **R4. Сторож списка.** Rust-тест проверяет вложение и краснеет при добавлении
  ключевого слова в лексер без правки списка.
- **R5. Сторож исполняется.** `precheck.sh` гоняет тесты с `--features lsp`.
- **R6. Ядро не тронуто.** Лексер, парсер, семантика и генераторы не изменены;
  вывод генераторов байт-в-байт прежний.
- **R7. Живой контекст исправлен.** Запись `CLAUDE.md` о тестах LSP приведена в
  соответствие замеру (A-4 ADR).

## Критерии приёмки и способ проверки

| # | Критерий | Способ проверки |
|---|---|---|
| A1 | Подстановочной ветки по `Token` нет; `deny` объявлен | греп `_ =>` и `wildcard_enum_match_arm` в `semantic_tokens.rs` |
| A2 | Удаление варианта из разбора не собирается | **мутация**: убрать `Token::Invariant` → `cargo clippy --all-features` красный |
| A3 | `invariant` подсвечен наравне с `cond` | тест: число токенов `TT_KEYWORD` для двух структурно равных моделей совпадает |
| A4 | LTL-операторы и типы формул подсвечены | тест на `: [LTL] G flag;` — `TT_KEYWORD` присутствует у `LTL` и `G` |
| A5 | `->`, `=>`, `?` подсвечены как операторы | тест на объявлении функции с `-> u8` и ветке `match` с `=>` |
| A6 | `BUT_KEYWORDS` покрывает лексер | Rust-тест вложения (R4) |
| A7 | Сторож списка взведён | **мутация**: убрать `invariant` из `BUT_KEYWORDS` → тест красный |
| A8 | Тесты LSP исполняются предкоммитом | прогон `precheck.sh`; в выводе виден прогон с `--features lsp` |
| A9 | Сторож исполнения взведён | **мутация**: сломать любой тест LSP → `precheck.sh` красный (сегодня был бы зелёным) |
| A10 | Вывод генераторов не изменён | `git diff --stat examples/generated/` пуст после регенерации |
| A11 | Рост времени предкоммита измерен | замер до/после, число в отчёте (A-1 ADR) |

⚠️ **A2, A7, A9 — мутационные и обязательны.** Урок 0056: «сторож, не
проверяющий взведённость ловушки, проверяет собственную удачу». Зелёный тест сам
по себе не доказывает, что он что-то ловит, — особенно A9, где гейт до фичи был
зелёным именно потому, что ничего не исполнял.

## Особенности по обратной функциональности

- **Наблюдаемое поведение редактора меняется** (это и есть цель): токены,
  прежде не окрашенные, окрашиваются. Совместимость протокола не нарушается —
  набор `SemanticTokenType` в `capabilities.rs` не расширяется, используются
  уже объявленные `KEYWORD` и `OPERATOR`.
- **Ядро языка не затронуто:** ни лексер, ни грамматика, ни семантика. Версия
  языка **не растёт** (правило 22): язык не изменился — изменился инструмент,
  который его показывает.
- **Крейт `takt-lang`** растёт по minor (аддитивно: новые тесты, расширенные
  списки; публичный API не меняется).

## Риски и зависимости

- **Риск 1 (главный): исчерпывающий разбор вскроет варианты, о которых нет
  решения.** Снижается тем, что решение по всем непокрытым вариантам принято
  **до** правки — таблица выше; спорных три (`->`, `=>`, `?`), и по ним есть
  прецедент `-->`.
- **Риск 2: рост времени предкоммита** (A-1 ADR). Сборка с иной комбинацией
  фич — отдельная единица компиляции. Замер обязателен; если рост велик,
  обсуждать способ (например, гонять с `--features lsp` только крейт
  `takt-lang`), а не отменять правило.
- **Риск 3: список исключений станет свалкой.** Сегодня в нём одна запись (`_`)
  с обоснованием. Правило 2 ADR требует обоснования рядом с записью; ревью
  обязано смотреть на рост этого списка как на сигнал.
- **Риск 4: `Token::Pragma` — мёртвая ветка** (A-3 ADR). Исчерпывающий разбор
  её **сохранит**, а не вскроет: токен разобран, просто не порождается лексером.
  В объём не берётся; зафиксировано, чтобы не открыть в третий раз.
- **Зависимость: нет.** Плагин IntelliJ вне объёма (правило 4 ADR), плагин Zed
  правок не требует (своих списков не ведёт).
