# Анализ фичи 0021: смена операторов — `<=` присваивание, `=` сравнение

> Фича: [../features/0021-swap-assign-compare.md](../features/0021-swap-assign-compare.md) · ADR: [../adr/0021-swap-assign-compare.md](../adr/0021-swap-assign-compare.md) · тест-план: не заведён (фича остановлена на «Анализ»)

## Цель и контекст

Заказчик предлагает `<=` сделать присваиванием, а `=` — сравнением. Цель —
убрать путаницу `=`/`==` (случайное присваивание в условии) и приблизить синтаксис
к инженерам АСУ ТП. По **ADR 0021** прямой запрос (Option A) отвергнут из-за
коллизии с реляционным `<=` и расхождения с C-целью компиляции; рекомендован
**Option B** — `:=` присваивание, `=` сравнение (стиль ST/IEC 61131-3), где
реляционный `<=` сохраняется. Настоящий документ разбирает **последствия для
понятности, читаемости, многословности** и совместимости — как просил заказчик.

## Зависимости фичи (правило 17/19)

- **Зависит от:** формально — **нет** (не требует закрытия других фич для старта).
  Есть **пересечение** с фичей **0019** (унификация `Condition`/`Expression`): обе
  трогают инвариант `=`/`==`. Внедрение 0021 (Option B) **устраняет** этот
  инвариант (`=` всюду сравнение, `==` выводится), что меняет вводные 0019 —
  часть её обоснований («разделение `=`/`==` намеренно») отпадает. Это **связь по
  контексту, не блокирующая зависимость**: фичи не обязаны идти в строгом порядке,
  но при принятии 0021 к разработке 0019 должна быть пересмотрена (и наоборот).
- **Влияние на порядок разработки:** 0021 никого не разблокирует и сама не
  заблокирована. Приоритет низкий: фича — крупный слом совместимости с неясной
  окупаемостью; держится в конце последовательности до решения заказчика.
  Рекомендация — **не брать в разработку** до явного подтверждения варианта.

## Влияние на понятность, читаемость и многословность (ключевой разбор)

Сравнение по вариантам ADR (A — прямой запрос, B — рекомендуемый, C — статус-кво).

### Понятность (семантическая однозначность)

- **Статус-кво (C):** `=` двусмыслен — присваивание в выражении, равенство в
  условии (инвариант `=`/`==`). Источник ошибок и сложности парсера/диагностик.
- **Option A (`<=` присв., `=` сравн.):** `=` в выражении больше не присваивает —
  «footgun» снят. **Но** `=` остаётся **связывателем** в декларациях
  (`var x = e;`) → двусмысленность «связывание vs сравнение» не исчезает. Плюс
  `<=` теперь перегружен: присваивание против «меньше-или-равно». Понятность
  **улучшается частично, но появляется новая перегрузка `<=`**.
- **Option B (`:=` присв., `=` сравн.):** `:=` — отдельный однозначный токен
  присваивания; `=` — всегда сравнение; `<=` — всегда «меньше-или-равно».
  **Максимальная однозначность**, инвариант `=`/`==` устраняется полностью.

### Читаемость

- `:=` (B) и `<=` (A) визуально читаются как «получает значение» (стрелка) — оба
  нагляднее `=` для присваивания в глазах инженера АСУ ТП.
- **A ухудшает читаемость реляционных выражений**: `x <= 10` в старом коде читалось
  «x не больше 10», в новом — «x получает 10». Немой конфликт значений на одном
  символе — высокий риск неверного прочтения при code review и миграции.
- **B не трогает `<=`** — реляционные выражения читаются как раньше; новый смысл
  несёт только новый значок `:=`. Меньше «ложных друзей».
- Расхождение с C: сгенерированный C-код использует `=`/`==`/`<=` в классическом
  смысле. При A читатель, знающий и Lam, и C, постоянно переключает контекст
  (`<=` там и там значит разное) — когнитивная нагрузка. При B расхождение локализовано
  в `:=` (в C его нет вовсе — визуально явный «это Lam-присваивание»).

### Многословность

- Присваивание: было `=` (1 символ) → стало `:=`/`<=` (2 символа). Рост на 1
  символ на каждое присваивание — присваивания частотны, суммарно код чуть
  многословнее. Эффект одинаков для A и B.
- Равенство: было `==` (2) → стало `=` (1). Экономия 1 символа на сравнение.
  Сравнения в условиях частотны → частично компенсирует рост присваиваний.
- Итог по объёму: близко к нейтральному; знак меняется в пользу того, чего в
  коде больше (присваиваний или сравнений). Для FSM-моделей с обилием условий
  переходов экономия на `=` заметна.

### Вывод по понятности/читаемости

Цель заказчика (снять путаницу `=`/`==`) достигается. Но **`<=`-присваивание
(Option A) создаёт новую, более коварную путаницу** — совмещение присваивания и
сравнения на одном символе `<=`, плюс расхождение с C. **Option B даёт тот же
выигрыш без этих минусов** и потому рекомендован. Чистый статус-кво (C) сохраняет
двусмысленность `=`, но её можно частично закрыть диагностикой без слома языка.

## Требования и проверяемые условия (для варианта B, если будет принят)

- **R1. Однозначность присваивания.** `:=` — единственный оператор присваивания
  (в выражениях и инициализаторах деклараций); `=` в позиции выражения/условия —
  только сравнение на равенство.
- **R2. Сохранение реляционного `<=`.** `x <= y` остаётся `LessEqual` во всех
  грамматиках; коллизии с присваиванием нет.
- **R3. Устранение `==`.** Токен `==` выводится из языка (или помечается
  устаревшим с миграцией) — равенство пишется `=`.
- **R4. Миграция совместимости.** Существующие `.lam` переводятся мигратором
  (`=`-присваивание/инициализатор → `:=`; `==` → `=`); поведение после миграции
  идентично исходному (регресс = 0).
- **R5. Версия языка.** Слом синтаксиса → **мажорное** повышение версии языка
  (правило 22); README и doctests синхронизированы (правила 15, 16).
- **R6. Без LR(1)-конфликтов.** `grammar.lalrpop` собирается без новых конфликтов
  LALRPOP.

## Особенности по обратной функциональности (правило 11)

**Слом совместимости неизбежен для A и B** (для C — нет). Обоснование
необходимости слома: цель фичи — именно смена семантики базовых операторов, её
нельзя достичь аддитивно без двусмысленности. Смягчение: **скрипт-мигратор** `.lam`
(один проход, детерминированный: присваивания/инициализаторы `=`→`:=`, `==`→`=`;
реляционный `<=` не трогается в варианте B) + мажорная версия языка + запись в
README раздела о миграции. Без мигратора внедрение недопустимо.

## Риски и зависимости

- **Риск: коллизия `<=` (только Option A).** Реляционный оператор теряет знак. →
  Снятие: выбран Option B, где `<=` сохранён.
- **Риск: тотальный слом `.lam`.** → Снятие: детерминированный мигратор + мажорная
  версия + сверка регресса кодогена (A3/A4).
- **Риск: расхождение с C-целью компиляции.** `<=`-присваивание (A) читается в C
  иначе. → Снятие: Option B локализует новизну в `:=`, которого в C нет.
- **Риск: LR(1)-конфликты** при контекстной трактовке (Option A/D). → Снятие:
  свежий токен `:=` (B) конфликтов не даёт; при A — обязателен PoC.
- **Связь с 0019** (не блокирующая): принятие 0021 обнуляет часть обоснований
  0019 (инвариант `=`/`==` исчезает). При старте любой из них — пересмотреть
  вторую (правило 19).
- **Организационный риск:** высокая стоимость при неочевидной выгоде. →
  Рекомендация: **решение о внедрении за заказчиком**; по умолчанию — не брать в
  разработку, при отказе от слома рассмотреть дешёвый Option C (диагностика).

## Резюме для заказчика

1. Прямой запрос (`<=` присваивание, `=` сравнение) технически возможен, но
   **создаёт новую путаницу** (`<=` = присваивание vs «меньше-или-равно») и
   расходится с C — **не рекомендуется**.
2. Та же цель достигается чище через **`:=` присваивание, `=` сравнение**
   (стиль ST/IEC 61131-3 — стандарт АСУ ТП): сохраняется `<=`, устраняется
   инвариант `=`/`==`, минимум грамматических рисков.
3. Любой из вариантов A/B — **слом совместимости** (мажорная версия языка +
   мигратор). Если слом нежелателен — дешёвая альтернатива: оставить `=`/`==` и
   добавить диагностику на подозрительный `=` в условии (Option C).
4. **Дальнейший шаг требует решения заказчика** между B (рекомендуется), A или C.
   До решения фича остаётся в статусе «Анализ» и в разработку не берётся.
