## Краткое описание

Стенд обновляется сам, когда в `master` приезжает коммит: GitHub уведомляет
стенд, тот забирает ветку и поднимает стек. Сегодня выкатку начинает человек с
рабочей машины (`scripts/deploy-stand.sh`), и стенд отстаёт от `master` ровно
настолько, насколько занят разработчик.

Ветка выкатки — **`master`**. Рабочая ветка проекта другая (`v2`), поэтому
фича обязана назвать, что попадает в `master` и когда: без этого «стенд
показывает master» означает «стенд показывает то, что кто-то туда влил».

> Фича зарегистрирована по запросу заказчика; далее проходит жизненный цикл по
> своду.

## Постановка (что предстоит продумать)

Раздел — не решение, а перечень вопросов стадии «Архитектура». Решения
принимает ADR.

### 1. Кто кого зовёт: уведомление или опрос

- **Уведомление (webhook).** GitHub шлёт `POST` на адрес стенда при событии
  `push`. Быстро (секунды), но требует адреса, открытого наружу, и приёмника,
  который этому адресу отвечает.
- **Опрос (polling).** Стенд сам спрашивает `git ls-remote` по таймеру. Ничего
  не открывает наружу и работает за любым NAT; цена — задержка и лишние
  запросы.
- **Actions с self-hosted runner.** В проекте **Actions заблокированы** и CI не
  исполняется (это записано в живом контексте), поэтому вариант в объём не
  входит, но должен быть назван и отвергнут явно.

Вопрос ADR: уведомление, опрос или уведомление с опросом как запасным ходом.

### 2. Что нужно от GitHub

Для уведомления: настройка репозитория «Settings → Webhooks» — адрес приёмника,
`Content-Type: application/json`, событие только `push`, **секрет**. GitHub
подписывает тело HMAC-SHA256 и кладёт подпись в `X-Hub-Signature-256`.

Вопросы ADR: где хранится секрет на стенде (переменная окружения стека, файл с
правами `600`); как он попадает туда (руками, как `TAKT_WEB_JWT_SECRET`); что
делать при повороте секрета.

### 3. Что нужно на стенде

- Приёмник: своя ручка сервиса (`/hooks/github`) либо отдельный маленький
  слушатель. Вопрос ADR: класть ли выкатку в тот же сервис, который она
  перезапускает, — приёмник внутри стека умрёт вместе с ним посреди работы.
- Права: выкатка зовёт `git` и `docker compose`. От какого пользователя,
  и как он получает право на docker (группа `docker` против sudo-правила).
- Сама выкатка: `git fetch --prune`, `git reset --hard origin/master`,
  `scripts/stand.sh up` — то же, что делает `deploy-stand.sh` на удалённой
  стороне; носитель обязан быть один, иначе ручная и автоматическая выкатки
  разойдутся молча.
- Одновременность: два уведомления подряд не должны запускать две сборки —
  замок и очередь из одного места (последний коммит побеждает).
- Ответ GitHub: у него на доставку около десяти секунд, а сборка образа идёт
  минуты. Значит приёмник отвечает сразу (`202`), а работу ведёт в фоне.

### 4. Что проверять до выкатки

Предкоммит гоняется на машине разработчика, и в `master` может приехать коммит,
его не проходивший. Вопрос ADR: гонять ли на стенде проверку до подъёма стека
(и какую её часть — предкоммит целиком идёт около шести минут), либо считать
`master` доверенной веткой и проверять только сборку образа.

### 5. Отказ и видимость

Что происходит, когда сборка не удалась: стенд остаётся на прошлой версии
(образ не заменяется) — это решение или требование? Где виден отказ: журнал
стенда, отметка коммита в GitHub (`statuses` API), письмо. Вопрос ADR: нужен ли
приёмнику обратный канал в GitHub и токен для него.

### 6. Безопасность

- Подпись проверяется **всегда**: приёмник без проверки подписи означает, что
  выкатку на стенд может запустить кто угодно, знающий адрес.
- Тело запроса не исполняется: из него берётся только имя ветки и
  идентификатор коммита; ветка сверяется со списком (`refs/heads/master`).
- Адрес приёмника не должен раскрывать состав стенда (общий домен занят соседним
  сервисом — правило локейшенов из 0531).

### 7. Что попадает в `master`

Рабочая ветка — `v2`. Вопрос ADR: слияние по завершении фичи, по тегу версии
языка либо по кнопке человека. От ответа зависит, что видит читатель стенда:
последнюю закрытую фичу или последний коммит разработки.

## Критерии приёмки (черновик)

- Коммит в `master` доводит стенд до этого коммита без участия человека.
- Запрос с негодной подписью выкатки не запускает и говорит об этом в журнале.
- Событие не по `master` игнорируется.
- Два уведомления подряд дают одну выкатку, а не две.
- Отказ сборки оставляет работающей прежнюю версию.
- Ручная выкатка (`scripts/deploy-stand.sh`) продолжает работать — носитель
  шагов у них общий.
- У проверки приёмника есть контроль: негодная подпись, чужая ветка, повтор.

- **Status:** Accepted

### Context

Замер 2026-09-16, чтение дерева и истории.

- Ветки `master` в репозитории нет. Есть `origin/main`, последний коммит в ней
  от 2026-03-21, и от `v2` она отстаёт на 1334 коммита (`main` — предок `v2`).
  Карточка называла веткой выкатки ветку, которой не существует.
- Выкатка сегодня — `scripts/deploy-stand.sh` на машине разработчика: пуш
  текущей ветки, затем по `ssh` на стенде `git fetch`, `git checkout`,
  `git reset --hard origin/<ветка>`, `scripts/stand.sh up`, затем проверка
  `<адрес><префикс>/health` снаружи. Шаги удалённой стороны записаны строкой
  внутри `ssh` и второго носителя не имеют.
- `stand.sh up` зовёт `docker compose up -d --build`: образ собирается раньше
  замены контейнеров, поэтому провал сборки оставляет работать прежнюю версию.
  Провал уже после замены (сервис не ответил на `/health`) прежнюю версию не
  возвращает.
- nginx на стенде общий: Takt приносит локейшены `<префикс>/` внутрь чужого
  `server`-блока (`setup-nginx-takt.sh`). Более длинный префикс nginx выбирает
  раньше, так что локейшен `<префикс>/hooks/` отбирается у сервиса без правки
  соседа.
- GitHub Actions в проекте заблокированы: запуск с собственного исполнителя
  Actions тоже не стартует.
- Закрытие фичи по правилу проекта кончается зелёным предкоммитом, коммитом и
  пушем в `v2`; промежуточные коммиты стадий (карточка, ADR) тоже пушатся.

### Decision Drivers

- D1 — ветка выкатки `v2` (решение заказчика): стенд показывает каждый пуш
  рабочей ветки, промежуточные коммиты стадий включительно.
- D2 — уведомление GitHub и опрос как запасной ход (решение заказчика): пропущенная
  доставка не оставляет стенд позади дольше периода опроса.
- D3 — приёмник вне стека Docker (решение заказчика): python3 без зависимостей
  и служба systemd; перезапуск стека не убивает выкатку, которая его ведёт.
- D4 — проверка до подъёма — сборка образа и `/health`, исход — журнал и файл
  состояния (решение заказчика).
- D5 — носитель шагов выкатки один у ручной выкатки, уведомления и опроса.
- D6 — подпись проверяется всегда, из тела берутся только ветка и коммит.
- D7 — одна выкатка за раз на стенде: уведомление, опрос и ручная выкатка
  исключают друг друга; ожидающие коммиты схлопываются в последний.

### Considered Options

1. **Ветка `main` с перемоткой при закрытии фичи** — отвергнуто заказчиком.
2. **Ветка `master`, как в карточке** — отвергнуто: ветки нет, заводить её ради
   третьего имени незачем.
3. **Только опрос** — отвергнуто заказчиком: задержка до периода таймера.
4. **Только уведомление** — отвергнуто заказчиком: пропущенная доставка
   оставляла бы стенд позади до следующего пуша.
5. **Собственный исполнитель GitHub Actions** — отвергнуто: Actions
   заблокированы, задания не стартуют.
6. **Ручка сервиса `takt-web-server`** — отвергнуто: приёмник умер бы вместе со
   стеком, который перезапускает.
7. **Контейнер с сокетом `docker.sock`** — отвергнуто заказчиком: доступ к
   сокету равен правам root на хосте.
8. **Приёмник на python3 и systemd** — принято.
9. **Предкоммит на стенде** — отвергнуто заказчиком: около шести минут и полный
   набор чужих инструментов на стенде; ветка доверенная.
10. **Отметка коммита через `statuses` API** — отложено: токен GitHub на стенде
    ради того, что видно в журнале.

### Decision

- **Носитель шагов** — `scripts/stand-hook.py deploy`: замок стенда (`flock` на
  файле в каталоге состояния), `git fetch --prune origin`,
  `git checkout -B <ветка> origin/<ветка>` поверх `git reset --hard`,
  `scripts/stand.sh up`, запись файла состояния (коммит, начало, конец, исход).
  Ручная выкатка зовёт его же: `deploy-stand.sh` отдаёт на стенд
  `git fetch` и затем `git show origin/<ветка>:scripts/stand-hook.py | python3 -
  deploy …` — исполняется носитель той версии, которая выкатывается, и
  скрипт не правит сам себя посреди исполнения.
- **Приёмник** — `stand-hook.py serve`: слушает `127.0.0.1:8739`, отвечает на
  `POST <префикс>/hooks/github` и `GET <префикс>/hooks/status`.
  - Тело не больше 1 МиБ; подпись `X-Hub-Signature-256` сверяется
    `hmac.compare_digest` с секретом из окружения; нет секрета — отказ старта.
  - `ping` — `200`; `push` чужой ветки — `202` «пропущено»; `push` ветки
    выкатки — `202` «принято», коммит кладётся в ожидающие, ответ не ждёт
    выкатки (у GitHub на доставку десять секунд).
  - Негодная подпись — `401` и строка журнала; тело не разбирается.
  - Один рабочий поток: берёт последний ожидающий коммит, пропускает уже
    выкаченный, зовёт носитель.
  - `status` отдаёт файл состояния: коммит, время и исход, без журнала сборки.
- **Опрос** — `stand-hook.py poll`: `git ls-remote origin refs/heads/<ветка>`
  против выкаченного коммита из файла состояния; расходятся — носитель.
  Таймер systemd раз в 15 минут.
- **Установка** — `scripts/setup-stand-hook.sh`: службы `takt-hook.service` и
  `takt-hook-poll.timer` от пользователя клона (в группе `docker`), секрет —
  файл `/etc/takt/hook.env` с правами `600`, `--print` печатает всё без
  установки. Локейшены приёмника — в `setup-nginx-takt.sh`, свой апстрим.
- **Настройка GitHub** (действие заказчика): Settings → Webhooks, адрес
  `https://<стенд><префикс>/hooks/github`, `application/json`, событие `push`,
  секрет — тот же, что в `hook.env`. Поворот секрета — правка обеих сторон и
  перезапуск службы.

### Consequences

- Стенд показывает каждый пуш `v2`, в том числе коммиты стадий без кода: это
  прямое следствие выбора ветки.
- Провал сборки образа оставляет прежнюю версию работать; провал `/health`
  после замены контейнеров — нет, откат в объём не входит и назван.
- Приёмник обновляется только перезапуском службы: новый `stand-hook.py`
  приезжает с выкаткой, но слушатель остаётся прежним до `systemctl restart`.
  Носитель выкатки исполняется всегда свежим (из `git show`).
- Адрес `<префикс>/hooks/status` открыт: он показывает коммит и исход последней
  выкатки, но не журнал сборки и не состав стенда.

#### Acceptance criteria

1. Годное уведомление ветки выкатки запускает носитель с этим коммитом, ответ
   приходит до конца выкатки.
2. Негодная подпись, отсутствие подписи — `401`, носитель не запускается.
3. Чужая ветка — `202` «пропущено», носитель не запускается.
4. Повтор выкаченного коммита выкатки не запускает; коммиты, пришедшие во время
   выкатки, схлопываются в одну следующую — с последним.
5. Опрос запускает выкатку только при расхождении с выкаченным коммитом.
6. Замок: вторая выкатка ждёт первую, а не идёт параллельно.
7. Провал носителя записывается в файл состояния исходом `failure`.
8. `deploy-stand.sh` исполняет тот же носитель.
9. Установка печатается `--print` и проверяется без root и systemd.

выкатку сразу, опрос раз в 15 минут подбирает пропущенное. Замер — в ADR.

### Зависимости фичи

### Риски и зависимости

- Живая проверка на стенде требует действий заказчика: запуск установки от
  root и регистрация уведомления в настройках GitHub. Проверка в дереве идёт
  на подменённом стенде (голый репозиторий, команда вместо стека).
- `git show origin/<ветка>:scripts/stand-hook.py` в `deploy-stand.sh` требует,
  чтобы носитель уже был в выкатываемой ветке: первая выкатка после слияния
  фичи идёт им же.
- `fcntl` и `flock` — только POSIX; стенд — Linux.

## Разработка

### Задача — носитель, приёмник и опрос

- `scripts/stand-hook.py` (python3 без зависимостей): режимы `deploy`
  (`flock`, `git fetch --prune`, `checkout -B`, `reset --hard`, команда
  подъёма, файл состояния `status.json`; `--force` выкатывает и выкаченное),
  `serve` (`ThreadingHTTPServer` на петле, подпись `hmac.compare_digest`, тело
  до 1 МиБ, `ping`/`push`, один рабочий поток с одним ожидающим коммитом,
  `status` без журнала), `poll` (`git ls-remote` против файла состояния).
  Команда подъёма подменяется `TAKT_HOOK_COMMAND` — для проверки.
- `scripts/deploy-stand.sh`: удалённая сторона — `git fetch`, затем
  `git show origin/<ветка>:scripts/stand-hook.py | python3 - deploy --force`.

### Задача — установка на стенде

- `scripts/setup-stand-hook.sh`: `/etc/takt/hook.env` (секрет создаётся один раз,
  права `600`), `takt-hook.service`, `takt-hook-poll.service` и `.timer`
  (15 минут), пользователь клона обязан быть в группе `docker`, приёмник
  только на петле; `--print` печатает всё без root.
- `scripts/setup-nginx-takt.sh`: апстрим `takt_hook`, точные локейшены
  `<префикс>/hooks/github` (предел тела 1 МиБ) и `<префикс>/hooks/status`,
  строка проверки статуса в смоуке.

### Задача — проверки

- `scripts/test-stand-hook.sh` и `scripts/test-stand-hook-cases.py`: стенд
  подменён голым репозиторием и командой, пишущей коммит и отметки начала и
  конца; условия H1…H13 и контроль — приёмник с изъятой сверкой подписи обязан
  провалить набор. Шаг предкоммита.
- `scripts/test-setup-nginx-takt.sh`: условие N11.

## Тест-план

### Проверки (условие → ожидаемый результат)

1. H1 — `serve` без `TAKT_HOOK_SECRET` → ненулевой код, текст называет
   переменную (R1).
2. H2 — чужой секрет и отсутствие подписи → `401`, команда подъёма не
   исполнялась; контроль — без сверки подписи набор падает (R2).
