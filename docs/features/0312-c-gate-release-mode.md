## Краткое описание

Оба гейта цели `c` собирали порождённый код только в отладке, тогда как
прошивки собирают с `-DNDEBUG`. Добавлен релизный прогон — и первый же его
запуск нашёл отказ: харнесс `batch_cycle` проверял порядок фаз `assert`-ами,
которые в релизе исчезают.

> Фича зарегистрирована из блока кандидатов `FEATURES.md`.

## Документирование (правило 24)

**Не требуется:** правится процесс проверки, а не язык.

## Итог (что сделано)

**Класс «видно только в релизе» перестал быть невидимым.**

- **Корпус собирается в двух режимах** (отладка + `Release -DNDEBUG`), каждый
  под `-Wall -Wextra -Werror`; каталоги сборки **разные** — общий заставлял бы
  cmake перекомпилировать всё на каждом прогоне (кэш хранит флаги).
- **Харнессы `batch_cycle` и `stacker` запускаются в релизе**, а не только
  собираются: собравшийся харнесс без проверок — ровно тот случай, который
  фича и нашла.
- **`c-hal` компилируется дважды** — с `-DNDEBUG` и без.
- ⚠️ **Первый прогон нашёл дефект:** `batch_cycle_main.c` не компилировался в
  релизе (`-Wunused-but-set-variable` на счётчике `phases`), и причина глубже
  предупреждения — проверки стояли на `assert`, а под `-DNDEBUG` они исчезают.
  Харнесс, собравшийся в релизе, **не проверял бы ничего**; правило «`assert` в
  неисполненном коде молчит всегда» записала сама фича 0166, и нарушалось оно у
  неё же.
- ⚠️ **Отладочный прогон сохранён намеренно:** в релизе не исполняются `assert`,
  которые печатает **цель** (охранные формулы 0235).
- ⚠️ **Разница между режимами была измерена раньше** (0260: 53 предупреждения
  под `-DNDEBUG` против 49 без него) — и с тех пор не сторожилась ничем.
