# Исправление 0181-01: симулятор исполняет `always` композиции ДВАЖДЫ за такт

> Фича: [../features/0181-sim-state-implementation-tick.md](../features/0181-sim-state-implementation-tick.md) · анализ: [../analyze/0181-sim-state-implementation-tick.md](../analyze/0181-sim-state-implementation-tick.md) · отчёт: [../reports/0181-sim-state-implementation-tick.md](../reports/0181-sim-state-implementation-tick.md)

- **Статус:** **ЗАВЕДЁН** (2026-07-29). **Tier 2 — эталон молча неверен.**
  Симулятор — эталон поведения проекта; порождённый код (`c`/`rust`/`st`/`sv`)
  **верен** и правки не требует.
- **Обнаружено:** при разработке фичи 0181 (проба на композите `|`, поставленная
  для того, чтобы новый спуск в реализацию состояния не добавил третьего
  исполнения).
- **Класс:** «эталон А и эталон Б разошлись» — тот же, что у
  [0057-01](0057-01-sim-composition-next.md), но на **параллельной** композиции.
- **В объём фичи 0181 не входит:** дефект существует независимо от неё,
  вскрыт попутно и требует собственного решения (какое из двух исполнений
  лишнее — вопрос ADR, а не правки на месте). Смешивать два предмета под одним
  номером — урок фичи 0171.

## Проблема

Тело `always` под-модели **параллельной** композиции исполняется **дважды** за
один такт. Накапливающее присваивание (`n := n + 1`) даёт удвоенный результат.

Проба 2026-07-29 (дерево до и после правок 0181 — поведение одинаково):

```
var n: u8 := 0;
model A { start S { always { n := n + 1; } } }
model B { start T; }
start P = A | B;
```

| Эталон | Значение `n` после такта 1 |
|---|---|
| Порождённый C (`cc` + харнесс) | **1** |
| Симулятор (`takt-sim -n 3`) | **2** |

## Причина

Двойной обход в такте композита:

1. `tick_body` (`takt-sim/src/unit/tick.rs`) зовёт `self.execution("always")`;
   `Unit::execution` для `Parallel`/`Sequential` **рекурсирует в детей** и
   исполняет их блоки `always`;
2. затем `tick_parallel`/`tick_sequential` тикают тех же детей через
   `tick_mode`, и `tick_body` **каждого ребёнка** снова зовёт
   `execution("always")`.

То есть шаг «исполнить `always`» выполняется и родителем за ребёнка, и самим
ребёнком.

## Почему дожило

Корпусные композиции пишут **идемпотентные** присваивания (`x := <выражение>`),
а не накопления: `stacker` (`CR | MC | LC`) и `elevator_mini` (`Cabin | Motor`)
дают один и тот же результат при любом числе исполнений. Потактовые сверки
(`conformance_c_tests`, `conformance_sv_tests`) наблюдают именно такие
переменные, поэтому удвоение в них не проявляется.

⚠️ Значит, дефект **невидим для всего существующего покрытия** — воспроизводится
только накапливающим телом, которого в корпусе нет.

## Что делать

Оставить исполнение `always` **ровно одно**. Решение о том, какое из двух
убрать, — за ADR:

- либо `Unit::execution` перестаёт рекурсировать в детей (тогда каждый ребёнок
  исполняет свой `always` сам, в своём `tick_mode`);
- либо `tick_body` композита не зовёт `execution("always")` вовсе, ограничиваясь
  блоками **своего** уровня.

⚠️ У правки есть цена: `Unit::execution` — публичный метод, зовётся не только из
такта, и смена его рекурсии затрагивает всех вызывающих. Поэтому нужен разбор, а
не однострочник.

После починки завести **значенческий** регресс с накапливающим телом
(`n := n + 1` в ветви `|`) и сверить его с целью `c` — существующие сверки этот
класс не ловят по построению.

## Проверки

Не выполнялись: фикс **заведён**, не исправлен.
