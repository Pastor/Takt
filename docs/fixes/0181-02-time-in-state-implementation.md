# Исправление 0181-02: выдержка after и every не срабатывают в модели, реализующей состояние

> Фича: [симулятор исполняет реализацию состояния с переходом next](../features/0181-sim-state-implementation-tick.md)

Состояние: **исправлено** (2026-09-13). Эталон раздаёт модельное время и в
реализации состояний; трассы эталона и цели `c` совпадают такт в такт.

## Проблема

Заказчик 2026-09-12: «в симуляции не работают функции времени, конструкции
`after` не обрабатываются». Прогон показал, что время ломается не везде, а
ровно в одном месте: **внутри модели, которая реализует состояние**
(`state Work = Heater { next Done; }`). Там выдержка по времени не истекает
никогда, а периодический блок не исполняется ни разу. Автомат стоит во
внутреннем состоянии до конца прогона, диагностики нет.

Страница онлайн-редактора прогоняет модель тем же `SimulationRunner::step`,
поэтому дефект одинаков у `takt-sim` и в браузере.

### Замер (2026-09-12, эталон `takt-sim`, `-n 12`)

| Проба | Что проверяет | Итог |
|---|---|---|
| p1 | `after 5ms`, `clock 1kHz`, корневая модель | срабатывает на такте 6 (5 мс) — верно |
| p2 | то же без `clock` (период по умолчанию 1 мс) | верно |
| p3 | `after 3t` | верно |
| p4 | `every 2ms` | исполняется на 2, 4, 6, 8 мс — верно |
| p5 | `after` в двух ветвях `A \| B` (4 мс и 7 мс) | верно, ветви независимы |
| p6 | `after K` (константа) и `after (hold)` (переменная `duration`) | верно |
| **p7** | `after 5ms` в модели, реализующей состояние | **не срабатывает**: `[Work, W]` все 12 тактов при часах 11 мс |
| **p8** | `every 2ms` в модели, реализующей состояние | **не исполняется ни разу**: `n = 0` все 12 тактов |
| p9 | `after 3t` в модели, реализующей состояние (контроль) | срабатывает на такте 5 — верно |
| p10 | стенд `extern` в модели, реализующей состояние (контроль) | доезжает — верно |

Проба p7:

```takt
model Heater {
    clock 1kHz;
    out h: u8;
    start W {
        enter { h := 1; }
        ref D: after 5ms;
    }
    state D {
        enter { h := 2; }
    }
}
model Host {
    clock 1kHz;
    out o: u8;
    start Idle {
        enter { o := 1; }
        ref Work: true;
    }
    state Work = Heater {
        next Done;
    }
    state Done {
        enter { o := 3; }
    }
}
start Main = Host;
```

Контрольные пробы разводят причины. Счётчик тактов внутри реализации идёт
(p9), значит, дело не во вложении как таковом. Стенд `extern` доезжает (p10),
значит, дело не в контексте. Сломаны именно **модельные часы** внутри
реализации.

### Замер целей (2026-09-13, `scripts/probe.sh -n 14`)

Пробы потребовали трёх поправок, чтобы цели вообще можно было измерить, и
каждая — про пробу, а не про цель: `ref Work: true` заменён безусловным
`ref Work` (константное условие даёт общий отказ `SE-047`), `clock 1kHz` снят
(без `--tick-hz` — `SE-069`), выходным портам даны адреса (`c-hal` и `st-at` —
`SE-052`). Эталон на изменённых пробах ломается так же.

Все семь целей вывод печатают, и арбитры его принимают (`cc`, `iec2c`,
`rustc` с `clippy`, `verilator` с `yosys`). Поведение цели `c` снято харнессом
«1 мс на такт»: `after 5ms` — `h = 2` на такте 7, `o = 3` на такте 8; `every 2ms` —
`t` = 1, 2, 3, 4 на тактах 4, 6, 8, 10, `o = 3` на такте 11. Цель считала верно, а
эталон — нет, молча и вопреки документу (раздел «Время»): **Tier 1** подтверждён.

## Причина

Модельное время эталон хранит в поле узла `UnitKind::Node::time_ns`, а не в
контексте модели. Перед каждым тактом `SimulationRunner` раздаёт его
рекурсивным `Unit::set_time_ns` (`takt-sim/src/unit/clock.rs`). Обход
спускается в детей `Parallel` и `Sequential`, а в ветви `Node` ставит время
только самому узлу и **не спускается в реализации состояний**
(`UnitKind::Node::state_impls`).

Реализация состояния — дочерний юнит со своими узлами (`build_extend` в
`unit/builder.rs`). Её часы навсегда остаются на нуле, поэтому
`since_state_entry_ns()` внутри неё всегда `0 − 0 = 0`:

- `after <длительность>` (`predicate.rs`, ветви `After` и `AfterExpr`) никогда
  не истинно;
- `every` (`unit/every.rs`) считает прошедшее от входа тем же вызовом и не
  исполняется ни разу.

Выдержка в тактах (`after 3t`) идёт другим счётчиком — `ticks_in_state`. Его
растит собственный `tick_mode` реализации, и потому она работает.

Класс виден по коду. Все обходы `Unit` в `unit/mod.rs` (чтение и запись
значений, наблюдение, трасса, активные состояния) спускаются в
`state_impls`, а в `unit/clock.rs` не спускается ни один. Дожило потому, что
потактовые сверки времени (`conformance_c_time_tests`, `conformance_after*`)
держат выдержку только в корневой модели.

## Решение

Реализовано по плану:

1. `Unit::set_time_ns`, ветвь `Node`: кроме своего `time_ns` ставить время
   **всем** реализациям из `state_impls`. Всем, а не только активной: время у
   дерева одно (так сказано в документации метода), и реализация, в которую
   автомат войдёт на следующем такте, обязана войти с верными часами —
   `enter_initial_state` отмечает вход её же `time_ns`.
2. Остальные обходы `unit/clock.rs` пройти тем же вопросом:
   - `advance_state_ticks` — не трогать: реализацию тикает её собственный
     `tick_mode`, и спуск дал бы двойной счёт (тот же класс, что
     [симулятор исполняет `always` композиции дважды за такт](0181-01-sim-parallel-always-twice.md));
   - `set_extern_stubs` — стенд доезжает через цепочку `parent` контекста
     (p10), правка не нужна; в тест войдёт как контроль;
   - `since_state_entry_ns` и `ticks_in_state` ветви `Node` читают своё поле
     и верны.
3. Комментарий модуля `clock.rs` описывает время «во все узлы дерева», и после
   правки он станет верен. Отдельной правки текста не требуется.

Язык не меняется: эталон начинает делать то, что документ уже обещает.
Раздел «Время» `book/` не затронут; «Документирование» — не требуется.
Редакторский слой не затронут.

## Проверки

План, по свежему замеру:

1. **Значенческий тест эталона** (`takt-sim/tests/sim/`, набор времени):
   пробы p7 и p8 фикстурами.
   - p7: вход во внутреннее `W` на такте 2 (1 мс), `after 5ms` истекает при
     6 мс — ожидается `[Work, D]` и `h = 2` на такте 7, `[Done]` на такте 8.
   - p8: `n` растёт на 2 мс от входа во внутреннее состояние.

   Ожидаемые такты подтверждаются потактовой сверкой, а не рассуждением.
2. **Контроль** в том же наборе: `after 3t` и `extern` внутри реализации — p9
   и p10, срабатывали и до правки.
3. **Потактовая сверка с целью `c`** на фикстуре «выдержка в модели,
   реализующей состояние» (`conformance_c_time_tests`), затем `st`, `rust` и
   `sv` — по имеющимся сверкам времени. Правка без сверки доказала бы только,
   что эталон стал считать как-то, а не так же, как цели.
4. **Мутация**: снять спуск — тесты p7 и p8 обязаны покраснеть.
5. `./scripts/precheck.sh` зелёный (правка задевает крейт `takt-sim` — полный
   прогон по правилу соразмерности).

## Что осталось

- **Сверки времени в реализации у `st`, `rust` и `sv` не заведены.** Готовые
  сверки времени этих целей завязаны на корневые фикстуры, а поведение на
  реализации снято только у `c`; `probe.sh` подтвердил лишь валидность вывода.
  Генераторы правка не трогала. Кандидат в `FEATURES.md`.
- **Соседний класс**: восстановление из снимка (`state_io.rs`, `publish_tree`)
  тоже не спускается в `state_impls` — по чтению кода состояние внутри
  реализации после `--load-state` в реестр не публикуется. Замера нет,
  кандидат в `FEATURES.md`.
