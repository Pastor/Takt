# Инструментарий

С моделями на Takt работают три инструмента командной строки:

| Инструмент | Назначение |
|------------|-----------|
| `taktc` | компилятор: генерация кода, форматирование, верификация, экспорт карты адресов |
| `takt-sim` | симулятор: прогон модели по тактам и визуализация (GIF/SVG) |
| `takt-lsp` | сервер языка (LSP) для редакторов: диагностики, переход к объявлению, форматирование |

## Компилятор `taktc`

У `taktc` несколько подкоманд:

```
taktc compile [флаги] <input.takt> [-o <output>]
taktc fmt [--check] [--stdin] <файлы/каталоги>
taktc verify [--property "φ"] [--scope file|all] [--trace] <input.takt>
taktc address-map [--emit map|json] [--address-map <файл>] <input.takt>
```

### Генерация кода — `compile`

Подкоманда `compile` порождает из модели код выбранной цели. Цель задаётся флагом
`-t` (`--target`); по умолчанию — `c`.

| Цель | Что порождает |
|------|---------------|
| `c` | переносимый C (заголовочный файл) |
| `c-hal` | C с таблицей адресов портов и доступом к ним через HAL |
| `st` | Structured Text (IEC 61131-3) для ПЛК |
| `st-at` | ST с размещением портов по адресам (`AT %…`) |
| `rust` | `no_std` Rust для микроконтроллеров |
| `sv` | синтезируемый SystemVerilog (FPGA/ASIC) |
| `sv-mmio` | SystemVerilog с регистровым файлом портов по адресам |
| `plantuml` | диаграмма состояний PlantUML |

Пример — сгенерировать C:

```bash
taktc compile -t c traffic.takt -o out/
```

Вывод при успехе:

```text
Скомпилировано: traffic.takt → out/ (путей поиска: 0)
```

Та же модель в диаграмму состояний:

```bash
taktc compile -t plantuml traffic.takt -o out/
```

Полезные флаги: `-I <dirs>` — пути поиска импортируемых файлов; `-v` —
подробный вывод (все предупреждения, полные пути); `-q` — только ошибки.

**Способ сборки параметризованных моделей** — `--parameters=assign|specialize`
(по умолчанию `assign`), общий для всех целей:

```bash
taktc compile --parameters=specialize line.takt -o out/
```

- `assign` — модель в порождённом коде одна, значение параметра становится
  значением поля экземпляра;
- `specialize` — на каждую различную настройку порождается своя копия модели, и
  неизменяемый параметр становится константой (это единственный способ употребить
  параметр там, где значение нужно уже при сборке — выдержка `after`, адрес порта).

Поведение программы от способа не зависит — только форма порождённого кода. См.
«Параметризация моделей» в разделе о моделях и состояниях.

### Форматирование — `fmt`

`fmt` приводит исходный текст к каноническому виду. Без флагов форматирует файлы
на месте; с `--check` — ничего не меняет, а лишь сообщает о расхождениях (и
возвращает ненулевой код — удобно для CI):

```bash
taktc fmt --check traffic.takt
```

```text
требуется форматирование: traffic.takt

Не отформатировано файлов: 1 из 1
```

Если файл не разбирается, форматировать нечего: `fmt` сообщает об ошибке в том
же виде, что и остальные инструменты, — с позицией и кодом:

```text
traffic.takt:2:11: Ошибка компиляции [SY-002]: нераспознанный токен 'u8', ожидалось ";", ":", ":="
```

Ошибок может быть несколько — тогда каждая печатается своей строкой. При чтении
из `--stdin` пути нет, поэтому позиция не показывается: остаются код и текст.

### Верификация свойств — `verify`

`verify` проверяет темпоральные свойства (LTL) над управляющим графом модели.
Свойство задаётся флагом `--property`:

```bash
taktc verify --property "F Start" model.takt
```

Если свойство выполняется:

```text
СВОЙСТВО ДЕРЖИТСЯ: F Start

Проверено свойств: 1; все держатся
```

Если нарушено — печатается контрпример (путь по состояниям):

```bash
taktc verify --property "F Finish" model.takt
```

```text
СВОЙСТВО НАРУШЕНО: F Finish
  контрпример: [ Start ]*
  (абстракция управления: условия переходов не учитываются — контрпример может быть недостижим по данным)

Проверено свойств: 1; не держится/не проверено: 1
```

Подробнее о языке свойств и абстракции — в разделе «Верификация свойств».

### Карта адресов — `address-map`

`address-map` выгружает фактически разрешённую карту адресов портов — в
`.ld`-подобном формате (`--emit map`) или как JSON-контракт (`--emit json`):

```bash
taktc address-map --emit json model.takt -o ports.json
```

## Симулятор `takt-sim`

`takt-sim` прогоняет модель по тактам — для отладки поведения и наглядной
визуализации. Базовый вызов:

```bash
takt-sim model.takt -n 20
```

Флаг `-n` задаёт число шагов (без него симуляция идёт до терминального
состояния). Входные воздействия и проверки описываются JSON-файлом сценария
(`-s`), а состояние можно сохранять и загружать (`--save-state`/`--load-state`):

```bash
takt-sim model.takt -s scenario.json -n 50
```

**Файл сценария.** Это массив шагов; шаг задаёт значения входных портов и, при
желании, проверку (`guard`) после такта. Порты называются по имени:

```json
[
  {
    "in_ports": {"kick": 1},
    "guard": {"out": {"alarm": 0}, "vars": {"idle": 0}}
  },
  {
    "guard": {"vars": {"idle": 1}}
  }
]
```

Перечислять нужно только те порты, значение которых **меняется**: значения
сохраняются между тактами, как удерживается уровень на реальном входе. Шаг без
`in_ports` не трогает входы вовсе — во втором шаге примера `kick` остаётся
равным `1`.

Если одно и то же имя объявлено в нескольких моделях композиции, его уточняют
именем модели — `"Cabin::sensor"`. Имя, которого в модели нет (в том числе порт
не того направления), — **ошибка**, а не молчаливый пропуск: сценарий, отставший
от модели, обязан о себе сообщить.

Значения портов можно задавать и **позиционным массивом** — по алфавитному
порядку имён:

```json
[{ "in_ports": [1, 0], "guard": { "out": [0] } }]
```

> **Осторожно.** Эта форма опасна: добавление или переименование порта сдвигает
> весь массив, и шаг начинает описывать другое событие — молча. Она
> поддерживается для старых файлов; для новых сценариев пользуйтесь именами.

**Визуализация.** С флагом `-o` симулятор рисует ход работы автомата — по
умолчанию анимированный GIF (режим настраивается через `--graphics-config`):

```bash
takt-sim model.takt -o out/ -n 30
```

Развёрнутый пример с генерацией, симуляцией и визуализацией, LTL-проверками и
guard'ами собран в разделе «Развёрнутый пример».

## Языковой сервер `takt-lsp`

`takt-lsp` — сервер протокола LSP: он подключается к редактору (VS Code,
IntelliJ, Zed и др.) и даёт диагностики по мере набора, переход к объявлению
(модели, состояния, импортируемого файла) и форматирование. Пути поиска
импортов передаются редактором через параметры инициализации. Сервер работает
поверх того же ядра, что и `taktc`, поэтому диагностика в редакторе совпадает с
диагностикой компилятора.
