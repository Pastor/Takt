# Модели и состояния

**Модель** — это конечный автомат: набор **состояний** и **переходов** между
ними. В каждый момент времени модель находится ровно в одном состоянии. Работа
идёт по тактам: на каждом такте проверяются условия переходов из текущего
состояния (подробно — в разделе «Модель исполнения»).

## Модель

Модель объявляется словом `model` и содержит состояния, а также — при
необходимости — переменные, порты ввода-вывода и функции:

```takt
model Motor {
    var speed: u8 := 0;
    // состояния…
}
```

Если модель в файле одна, обёртку `model` можно опустить — состояния и объявления
пишутся прямо на верхнем уровне файла, образуя **корневую** модель:

```takt
out led: bit;
start Off { ref On: true; }
state On { ref Off: true; }
```

## Состояния

Состояние объявляется словом `state`, а **стартовое** — словом `start`. Стартовое
состояние в модели ровно одно: с него начинается работа автомата.

```takt
start Idle { … }     // стартовое состояние
state Running { … }  // обычное состояние
state Done;          // состояние без тела (например, конечное)
```

Тело состояния в фигурных скобках содержит переходы и **именованные блоки**
(`enter`, `exit`, `always`) — их подробно описывает раздел «Именованные условия и
блоки»:

- `enter` — исполняется при входе в состояние;
- `exit` — при выходе из него;
- `always` — на каждом такте, пока автомат в этом состоянии.

## Переходы

Переход задаёт, в какое состояние перейти. Есть две формы.

**Условный переход** `ref` срабатывает, когда его условие истинно:

```takt
ref Running: start_btn = 1;
```

**Безусловный переход** `next` выполняется всегда (по завершении текущего шага):

```takt
next Done;
```

В теле состояния может быть несколько переходов `ref` — они проверяются в порядке
записи. Если условия двух переходов истинны одновременно, выбор недетерминирован;
компилятор предупреждает о таких состояниях (см. раздел «Диагностики»).

## Композиция моделей

Модели **композируются**: сложное поведение собирается из более простых моделей.
Точка сборки — `start` (или составное состояние), где через `=` указывается
композиция под-моделей.

**Параллельная композиция** `|` — под-модели работают **одновременно**, каждая на
своём такте:

```takt
model Cabin { … }
model Motor { … }
start Main = Cabin | Motor;
```

**Последовательная композиция** `+` — под-модели работают **по очереди**: когда
одна завершается, управление переходит к следующей, а после последней —
безусловным переходом `next` — к указанному состоянию:

```takt
model A { … }
model B { … }
start Main = A + B {
    next Done;
}
state Done;
```

Композиции можно **группировать** скобками и вкладывать, комбинируя `+` и `|`:

```takt
start Main = A + B + (C | D) + E {
    next Next;
}
```

Составным может быть не только стартовое, но и любое **состояние**:

```takt
state Middle = Engine + (Engine | Engine) {
    next End;
}
```

Общие для под-моделей данные объявляются в охватывающей (корневой) модели и видны
всем участникам композиции — так под-модели обмениваются значениями.

## Параметризация моделей

Одна и та же модель часто нужна в нескольких экземплярах с **разной настройкой**:
две подачи с разной дозой, два таймера с разной выдержкой, два регулятора с
разными коэффициентами. Настройка объявляется словом `parameter` — третьей формой
объявления наряду с `var` и `const`:

```takt
model Feeder {
    parameter portion: u8 := 1;   // значение по умолчанию — 1
    var count: u16 := 0;
}
```

Инициализатор у параметра **обязателен**: это его значение по умолчанию. Задать
другое можно в **месте инстанцирования** — там, где модель подставляется в
композицию или в реализацию состояния:

```takt
start Line = Feeder(portion := 3) | Feeder(portion := 7);   // композиция
state Dose = Feeder(portion := 5) { next Done; }            // реализация состояния
start One  = Feeder;                                        // настройка по умолчанию
```

Внутри модели параметр ведёт себя как обычное объявление: его читают, а при
необходимости и меняют. Значение — **локальная копия экземпляра**: изменение
внутри одного экземпляра не видно ни соседнему, ни объявлению.

### Значение параметра известно при сборке

Аргумент — **константное выражение**, вычисляемое компилятором: литерал (включая
литерал длительности), имя константы, арифметика над ними и вызов функции,
вычислимой при сборке (её тело опирается только на аргументы и константы):

```takt
const BASE: u8 := 10;

fn doubled(x: u8) -> u8 { return x * 2; }

start Line = Feeder(portion := BASE + 2) | Feeder(portion := doubled(BASE));
```

Ссылка на величину, известную лишь в работе (переменную, порт, результат чтения
датчика), — ошибка: настройка выбирается при сборке, а не в такте. Это и есть
граница смысла: **настройка** — свойство экземпляра, заданное сборкой; **уставка**,
измерение, задание — величины такта, и они остаются переменными.

### Два способа сборки

Форму порождаемого кода выбирает ключ компилятора:

```bash
taktc compile --parameters=assign     model.takt   # по умолчанию
taktc compile --parameters=specialize model.takt
```

- **`assign` (по умолчанию)** — модель в порождённом коде **одна**, а значение
  становится значением поля конкретного экземпляра. Проще и компактнее; параметр
  здесь — обычное поле, то есть величина работы.
- **`specialize`** — на каждую различную настройку порождается **своя копия
  модели** (одинаковые настройки дают одну копию). Тогда параметр, которому в теле
  модели ни разу не присваивают, становится **константой**, и его можно
  употреблять там, где значение требуется уже при сборке: выдержка `after`, адрес
  порта.

Поведение от способа сборки **не зависит**: одна и та же программа, собранная
любым из них, работает одинаково — отличается только форма кода. А вот
**множество принимаемых программ** отличается: параметр в позиции, требующей
значения при сборке, законен лишь во втором способе, и в первом компилятор
скажет об этом прямо, назвав нужный ключ.

```takt
model Timer {
    parameter dwell: duration := 100ms;
    start Wait { ref Done: after dwell; }   // требует --parameters=specialize
    state Done;
}
```

> **Цель `sv` и разные настройки.** Синтезируемый SystemVerilog уплощает
> композицию, поэтому два экземпляра одной модели делят одни регистры: **разные**
> настройки в способе `assign` для этой цели невыразимы, и компилятор откажет.
> Способ `specialize` ограничение снимает — у каждой копии свои регистры.

## Пример

Рассмотрим модель **светофора**. Работа его известна: горит красный — идёт
выдержка времени, затем зелёный — снова выдержка, затем короткий жёлтый — и цикл
повторяется. Каждый свет держится, пока не истечёт своё время.

```takt
{{#include examples/traffic.takt}}
```

Три света — это три состояния автомата. Работа начинается со стартового состояния
`Red` (1), объявленного словом `start`; `Green` (5) и `Yellow` (6) — обычные
состояния (`state`). Переменная `timer` считает такты, проведённые в текущем свете
— это **отрезок времени**: единственное, что в автомате законно мерить тактами.
Выходы `red`/`yellow`/`green` управляют лампами. У каждого состояния есть блок
`enter` (2): при входе он зажигает свою лампу, гасит остальные и обнуляет `timer`.
Блок `always` (3) исполняется каждый такт и наращивает `timer`. Смену света задают
переходы `ref` (4) по условию на таймере: из `Red` в `Green` при `timer >=
RED_TICKS`, затем `Green → Yellow` и `Yellow → Red` при `timer >= YELLOW_TICKS` —
короткий жёлтый. Длительности фаз вынесены в **именованные константы** и заданы **в
тактах**: такт — шаг логики, а не секунда, поэтому число подстраивается под частоту
устройства (в комментарии указана и длительность, и заложенная частота).

## Частые ошибки

Типичные ошибки при описании моделей и состояний:

- `SE-011` — в модели нет стартового состояния `start` (или их несколько);
- `SE-002` — переход `ref`/`next` указывает на несуществующее состояние;
- `SE-001` — композиция ссылается на необъявленную модель;
- `SE-046` — состояние недостижимо из стартового;
- `SE-042` — два перехода из состояния с одинаковым условием (недетерминизм);
- `SE-012` — более одного `next` в одном состоянии;
- `SE-100` — состояние названо так же, как **вложенная** модель, которую оно
  реализует (`model Pid { … } start Pid = Pid;`);
- `SE-101` — модель объявлена с реализацией (`= …`) и одновременно содержит
  собственное состояние;
- `SE-106` — в реализации стоит модель без состояний: исполнять в ней нечего.

### Модель как композиция

Модель можно объявить **реализацией** — композицией других моделей:

```takt
model Pump { … }
model Valve { … }

model Station = Pump | Valve {
    var cycles: u8 := 0;

    always { cycles := cycles + 1; }
}
```

Такая запись равнозначна объявлению композиции состоянием:

```takt
model Station {
    var cycles: u8 := 0;

    always { cycles := cycles + 1; }
    start Work = Pump | Valve;
}
```

Тело модели-реализации содержит её переменные, константы и блоки; они работают
как у обычной модели — в частности, `always` исполняется каждый такт.

> **Важно.** Модель не может быть одновременно композицией и автоматом: если у
> неё есть реализация, собственного стартового состояния быть не должно.
> Нарушение — ошибка `SE-101`.

```takt
model Station = Pump | Valve {
    start Work { … }      // ошибка SE-101
}
```

### Имя состояния и имя вложенной модели

Состояние, реализующее модель, **не может носить её имя**, если эта модель
объявлена рядом — на том же уровне вложенности:

```takt
model Pid { … }

start Pid = Pid;      // ошибка SE-100
start Loop = Pid;     // так — верно
```

Причина в том, что имя состояния и имя модели попадают в одно пространство имён
порождаемого кода, и ни одна из целей такую запись не переводит. Компилятор
сообщает об этом сразу и называет оба места.

> **Важно.** Ограничение касается только **вложенной** модели. Тёзка модели,
> объявленной уровнем выше, законна и работает:

```takt
model Ping { … }

model Toggle {
    start Ping = Ping { next Done; }   // верно: Ping объявлена не в Toggle
    state Done;
}
```
