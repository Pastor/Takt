## 2. Кандидаты в фичи

Идеи, ещё не оформленные в карточку `docs/features/XXXX-*.md`.

- **Баг генератора C: нет `typedef struct {Root} {Root};` для одиночной модели**
  (выявлено при 0020-05). Для модели **без под-моделей** заголовок `c` не эмитит
  typedef корня → прототипы `{Root}_init({Root} *)` невалидны как отдельный C
  (нужен тег `struct`). В `c-hal` исправлено локально; для цели `c` — оформить
  фикс (эмитить typedef всегда). Внимание: правка меняет вывод `c` → сверить
  codegen-снапшоты.

- **`validate.rs` — 3648 строк** при лимите ~1000 (`CLAUDE.md`, `docs/CODE.md`).
  Самое явное нарушение собственного правила о размере модуля; напрашивается
  деление по логике проверок. Следом — `lsp.rs` (2134) и `generator/c/c_expr.rs`
  (1736). Оформить как фичу-рефакторинг по образцу 0018.

- **Заглушки в генераторе C эмитятся в выходной код** (выявлено при обзоре
  2026-07-14). `generator/c/c_model.rs:769` печатает `//FIXME: Пока не
  реализовано` прямо в генерируемый C, `c_model.rs:316` — `//TODO: условный
  переход в {} не поддерживается`. Нужно выяснить достижимость этих веток: если
  достижимы — компилятор молча выдаёт заведомо неполный C **без диагностики**
  (тот же класс «тихого пропуска», что и фича 0025).

- **Генератор C: отображение типов `Array`/`Bit`/`Rational` дефектно** (выявлено
  при анализе 0025 — проверке пригодности эталона C). `get_c_type`
  (`generator/c/mod.rs:150`): (1) `Array(size, elem)` → `uint{size}_t`, где `size` —
  **число элементов**, а не разрядность → `[u8; 4]` даёт невалидный `uint4_t`, а
  размерность массива теряется; при этом переменная-массив **молча исчезает** из
  структуры (проба: `var data: [u8; 4];` → в `arr.h` только `int flag;`, без
  диагностики — тот же класс «тихого пропуска», что и фича 0025); (2) `Bit` → `int`
  (32-битный знаковый) вместо 1-битной семантики; (3) `Rational` → `float` (f32),
  тогда как симулятор считает в f64 → расхождение точности. Блокирует расширение
  сверки симулятора с C (критерий A8 фичи 0025 сужен до `Integer`/`Enum`/`Bool`).

- **`examples/comprehensive.lam` заявляет недостижимый сценарий** (выявлено при
  реализации 0025-02b-1, подтверждено прогоном). Комментарий примера обещает
  `Idle → Heating → Cooling → Done`, но `Heating` — **тупик по логике самого
  примера**: `ref Cooling: temperature > MAX_TEMP` (100), а в `Heating`
  температура не меняется (только `enter` даёт +5 → 16); `ref Idle: count >=
  MAX_COUNT` (10), а `while count < 3` упирает счётчик в 3. Ни одна ветка не
  может сработать никогда. Пример — часть документации по языку (правила 15, 16),
  поэтому обязан быть корректным: либо починить логику (например, нагрев в
  `always` состояния `Heating`), либо привести комментарий в соответствие.
  Из-за этого дефекта был **ошибочно сформулирован критерий приёмки A6** фичи
  0025 (исправлен).

- **Функции не могут вызывать функции** (выявлено при реализации 0025-02b-2,
  подтверждено пробами). Семантика отвергает вызов одной функции из тела другой:
  `fn g(n) { return n; } fn f(n) { return g(n); }` → `Ошибка: Неизвестная функция
  'g'`; прямая рекурсия `fn f(n) { return f(n); }` → `Неизвестная функция 'f'`.
  При этом из блоков состояний и условий вызовы работают. Похоже на пробел
  семантического прохода 5 («Тела функций»), а не на осознанное ограничение:
  композиция функций — базовая возможность, и генератор C её, судя по всему,
  поддержал бы. Следствие: **рекурсия в языке невозможна**, поэтому предел
  глубины `MAX_CALL_DEPTH` в симуляторе — защита от недостижимого сегодня
  сценария (оставлена намеренно). Если это ограничение осознанное — стоит
  зафиксировать его диагностикой и в документации по языку.

- **`--save-state`/`--load-state` не сохраняют переменные модели** (фича
  [0014](docs/features/0014-state-io.md); выявлено при реализации 0025-04,
  дефект **предсуществующий**). `state_io::snapshot` читает `Unit::Node {
  variables }` — собственную карту юнита, тогда как присваивания идут в
  `write_ctx` (кэш `ModelNodeContext`) — **другое хранилище**. `Unit::get_value`
  читает оба, поэтому трасса показывает верные значения, а файл состояния
  содержит `"variables": {}`. Проба: модель с `n=1, t=2` в трассе → в файле
  пусто; после `--load-state` → `n=0`. Дефект не внесён фичей 0025 (исходный код
  писал туда же), но раньше был незаметен: присваивания не исполнялись вовсе, и
  save/load «сохранял пустоту» из пустоты. Чинится согласованием хранилищ — либо
  `snapshot` должен читать через `Context`, либо запись идти в `Unit::variables`
  (второе затронет видимость между параллельными моделями — см.
  `docs/development/0025-02b-1-statement-interpreter.md`).

- **Сдвиг на два такта между симулятором и порождённым C** (выявлено
  автосверкой в 0025-07). Генератор C заводит **синтетическое состояние `INIT`
  на каждый уровень вложенности**: такт 1 — корень `INIT→ENTRY`, такт 2 —
  `Conf INIT→IDLE`, и только на такте 3 исполняется тело. Симулятор исполняет
  тело на **первом** такте. **Значения совпадают, расходится моментность** —
  трассы симулятора и прошивки смещены. Существенно для профиля проекта
  (правило 12): симуляция служит проверкой модели **до** синтеза. Пока симулятор
  не моделирует `INIT`-такты, потактовая сверка трасс невозможна — автосверка
  0025-07 вынужденно сравнивает **установившиеся** значения. Решить: моделировать
  ли `INIT` в симуляторе, или убрать лишний такт из генератора C.

- **Симулятор не поддерживает структурные типы** (выявлено при анализе 0025).
  `TypeNode::Struct(имя)` (NI3) существует, а `Value` (`simulation/src/value.rs`)
  имеет только `Number`/`Real`/`Boolean`/`Array`. В рамках 0025 фиксируется как
  явная диагностика; полноценная поддержка — отдельная фича.

- **LTL в блоках кода молча теряется** — `semantic/statement.rs:266`
  (`ast::InlineFormulaDefine::Ltl` → `Ok(StatementNode::InlineFormula(Vec::new()))`,
  с `TODO`). Формулы отбрасываются без диагностики; пересекается с фичей
  [0010](docs/features/0010-verification-ltl.md) и с кандидатом «юнит-конструкции
  языка для симуляции (assert/invariant)».

- **Предупреждения `private_interfaces` в `simulation`** — `Context`, `Value`,
  `Predicate`, `Flow` остаются `pub(crate)` при публичных полях `Unit`. Шумит при
  сборке крейта; чинится согласованием видимости. `TickResult` **исправлен**
  попутно задачей 0025-05 (стал `pub`).

- **Пред­существующие сбои тестов на Windows** (выявлены при 0021, не связаны с
  ней; падают и на исходном коде): 5 тестов `lamc` — разбиение `--include-dirs`

- **Семантическая подсветка Lam в IntelliJ через `lam-lsp`** (задел из фичи 0022,
  Option C ADR) — надстройка над лексической подсветкой плагина
  `extensions/intellij-lam` (semantic tokens `lam-lsp`; LSP4IJ/LSP API).
- **Полноценный PSI-парсер плагина IntelliJ** (поверх лексера 0022; надстройка
  над фичей [0023](docs/features/0023-intellij-navigation-include.md)) — то, что

- **Бэкенд генерации в Structured Text (IEC 61131-3 ST)** — третий целевой язык
  наряду с C и PlantUML (`generator::Language` сейчас = `C` | `PlantUML`).
  Прямо на профиль проекта («промышленные системы управления»): ST — стандартный

- **Правило в `docs/CODE.md`: запрет подстановочных веток (`_ =>`) при разборе
  семантических узлов** (`ExpressionNode`/`ConditionNode`/`StatementNode`) —
  вытекает из [ADR 0025](docs/adr/0025-simulator-expression-eval.md). Именно
  `_ => None` позволил двум вычислителям симулятора разойтись молча: добавление
  варианта не ломало сборку. Правило + линт
  `clippy::wildcard_enum_match_arm` переносят инвариант «все узлы обработаны» с
  дисциплины на компилятор. Сейчас такого правила в `docs/CODE.md` нет.
  **Реализовано точечно** в `simulation/src/eval/` задачей 0025-01 (проверено
  негативным тестом: линт валит сборку) — осталось обобщить как правило.

- **Конфликт правил: `#[non_exhaustive]` против запрета `_ =>`** (выявлен при
  реализации 0025-01). `docs/CODE.md` **предписывает** помечать публичные
  перечисления `#[non_exhaustive]`, а этот атрибут существует **ровно для того**,
  чтобы добавление варианта **не** ломало сборку зависимых крейтов — то есть
  прямо отключает механизм [ADR 0025](docs/adr/0025-simulator-expression-eval.md).
  Сейчас конфликт узкий и безвредный: помечен только `TypeNode`
  (`grammar/src/semantic/type_node.rs:495`), из-за чего `eval::coerce_to_type`
  вынужден иметь одну ветку `_` (возвращает **ошибку**, не тихий `None`), а
  ключевые `ExpressionNode`/`ConditionNode`/`StatementNode` **не** помечены —
  гарантия для адаптеров цела. **Риск:** если кто-то применит правило CODE.md к
  `ExpressionNode`, механизм 0025 **тихо умрёт** (сборка пройдёт, адаптеры
  вернутся к «молча не обработано»). Нужно решение: либо явное исключение в
  `docs/CODE.md` для семантических узлов, либо нестабильный линт
  `non_exhaustive_omitted_patterns` (проект на nightly), либо отказ от
  `#[non_exhaustive]` для этих типов.
- **Дефект `scripts/new-feature.sh`: с `--register` новый ADR получает статус
  `Accepted`** ещё до того, как ADR написан (выявлено при заведении 0025 —
  правилось вручную). Скрипт должен проставлять `Draft`/`Proposed`, а `Accepted` —
  по факту принятия решения на стадии 2.
- **`scripts/new-feature.sh` не умеет добавлять артефакт **одной** поздней стадии**
  (выявлено при заведении тест-плана 0025). Стадии наступают по очереди, а
  генератор работает «всё сразу при заведении фичи»: `--with-dev` создаёт
  development **и** tests вместе, а повторный `--register` **дублирует** строки в
  реестрах уже заведённых стадий (`insert_row` вызывается безусловно). Тест-план
  0025 пришлось рендерить вручную (правило 17 допускает как запасной путь). Нужны
  флаги вида `--stage tests|dev|report` и идемпотентный `--register` (не вставлять
  строку, если она уже есть).
